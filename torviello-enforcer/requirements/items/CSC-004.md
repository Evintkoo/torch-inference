## 1. Normative requirement

Each directory shall have a clear responsibility and avoid unrelated code, assets, and documentation.

## 2. Why this requirement exists

This requirement is part of **Common standards requirements** in [README.md](../README.md). It is traced to 6 rule control(s): CQ-07, DIR-01, DIR-02, DIR-03, DIR-04, GOV-03. Those controls state the following purpose:

- **CQ-07 — Module boundaries, cohesion, and dependency direction:** Modules must make responsibility, ownership, allowed dependencies, state, and change impact visible. The right boundary minimizes accidental coupling while keeping behavior that must change together cohesive.
- **DIR-01 — Purpose, ownership, and boundaries:** These controls govern **purpose, ownership, and boundaries**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.
- **DIR-02 — Directory documentation and adoption:** These controls govern **directory documentation and adoption**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.
- **DIR-03 — Layout, naming, and ownership contracts:** This control defines the intended outcome for **layout, naming, and ownership contracts** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.
- **DIR-04 — Test data, generated assets, and boundary migrations:** This control defines the intended outcome for **test data, generated assets, and boundary migrations** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.
- **GOV-03 — Coverage, risk analysis, and rule evolution:** Coverage must be assessed from system context and change scenarios, not inferred from file counts. The rule set must evolve as product boundaries, failure modes, threat conditions, dependencies, and operational evidence change.

Acceptance is not satisfied by citing these controls. The implementation must demonstrate the observable result in section 6, and the mapped rule clauses in section 5 define what must hold at the enforcement boundary.

## 3. Priority and interpretation

This requirement has **MUST** priority under the repository's requirement conventions. A MUST requirement is needed for the stated product direction or a safe release. A SHOULD requirement is expected unless a documented tradeoff justifies deferral. A COULD requirement is a candidate capability that requires product or technical validation. Acceptance describes observable evidence; it does not mandate a specific implementation unless the requirement says so.

### CQ-07 — Module boundaries, cohesion, and dependency direction

*Domain:* [code-quality](../../../torviello-enforcer/code-quality/README.md) · *Rule:* [07-module-boundaries-cohesion-and-dependency-direction.md](../../../torviello-enforcer/code-quality/rules/07-module-boundaries-cohesion-and-dependency-direction.md)

**Control objective.** Modules must make responsibility, ownership, allowed dependencies, state, and change impact visible. The right boundary minimizes accidental coupling while keeping behavior that must change together cohesive.

#### CQ-07.01 — A module MUST own a coherent capability, policy…

**Requirement:** A module MUST own a coherent capability, policy, or lifecycle and expose a small interface suited to its callers. Group code by behavior and reasons to change rather than only by technical layer, file type, or current convenience.

#### CQ-07.02 — Document or encode permitted module dependencies…

**Requirement:** Document or encode which modules are permitted to depend on which others. Dependencies MUST point toward stable policy or explicit interfaces; shared foundational code MUST NOT depend upward on feature or transport implementations. Cycles and hidden reach-through MUST be removed or recorded as bounded migration debt.

#### CQ-07.03 — Place behavior together when it shares invariants, transaction…

**Requirement:** Place behavior together when it shares invariants, transaction boundaries, lifecycle, security authority, or release cadence. Separate behavior when it has distinct owners, trust levels, deployment needs, resource lifetimes, or independent change pressure. Do not split based only on file size or theoretical reuse.

#### CQ-07.04 — Export only types and operations required by legitimate consumers…

**Requirement:** Export only types and operations required by legitimate consumers. Internal details, mutable storage representations, backend-specific errors, and implementation-specific synchronization MUST remain private unless a documented contract requires exposure.

#### CQ-07.05 — At important module boundaries, use validated domain types…

**Requirement:** At important module boundaries, use validated domain types, enums for finite states, explicit units, and constructors that preserve invariants. Prefer compile-time guarantees when they improve clarity without creating disproportionate type complexity; validate dynamic input at the boundary.

#### CQ-07.06 — For each shared mutable state object, define its…

**Requirement:** For each shared mutable state object, define its owner, synchronization model, consistency guarantees, initialization and shutdown behavior, and failure handling. Avoid globals and shared mutable caches unless their lifetime, invalidation, concurrency, and test isolation are explicit.

#### CQ-07.07 — A module MUST expose errors that let callers choose…

**Requirement:** A module MUST expose errors that let callers choose a safe action without depending on private implementation details. Preserve causal context for diagnosis, classify retryability and user correction where relevant, and prevent secrets or internal topology from leaking across public boundaries.

#### CQ-07.08 — Test public behavior and invariants at the module boundary…

**Requirement:** Test public behavior and invariants at the module boundary. Add architecture or build checks for forbidden dependencies when regressions are likely; mocks MUST not encode a contract different from the real implementation.

#### CQ-07.09 — A temporary cross-boundary dependency MUST identify the owner…

**Requirement:** A temporary cross-boundary dependency MUST identify the owner, reason, affected callers, containment, removal condition, and expiry/review trigger. A compatibility adapter MAY preserve an older interface, but its lifecycle and removal criteria MUST be explicit.

### DIR-01 — Purpose, ownership, and boundaries

*Domain:* [directory](../../../torviello-enforcer/directory/README.md) · *Rule:* [01-purpose-ownership-and-boundaries.md](../../../torviello-enforcer/directory/rules/01-purpose-ownership-and-boundaries.md)

**Control objective.** These controls govern **purpose, ownership, and boundaries**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### DIR-01.01 — Every maintained directory MUST have one clear purpose

Every maintained directory MUST have one clear purpose and an owning subsystem. Its local documentation MUST state what belongs there, public entry points, dependency boundaries, build/run/validation steps, and generated/runtime content.

#### DIR-01.02 — Place code and assets with the component that owns

The project MUST place code and assets with the component that owns their lifecycle. Shared code belongs in an explicit shared module with documented consumers and stable interface.

#### DIR-01.03 — Create a directory only when it establishes a useful

The project MUST create a directory only when it establishes a useful responsibility, build, test, deployment, or distribution boundary. The project MUST also separate unrelated concerns instead of turning an existing directory into a catch-all.

#### DIR-01.04 — Keep production application code under source directories, automated tests

The project MUST keep production application code under source directories, automated tests under their named test categories, and benchmarks under /benchmarks. The project MUST NOT place performance harnesses or non-unit tests in production source.

#### DIR-01.05 — Keep Dockerfiles and Compose files under /containers, package/release automation

The project MUST keep Dockerfiles and Compose files under /containers, package/release automation under /packaging, and design tokens/assets under a dedicated design area.

### DIR-03 — Layout, naming, and ownership contracts

*Domain:* [directory](../../../torviello-enforcer/directory/README.md) · *Rule:* [03-layout-naming-and-ownership-contracts.md](../../../torviello-enforcer/directory/rules/03-layout-naming-and-ownership-contracts.md)

**Control objective.** This control defines the intended outcome for **layout, naming, and ownership contracts** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### DIR-03.01 — Every maintained directory MUST have one primary responsibility…

**Requirement:** Every maintained directory MUST have one primary responsibility and an accountable owning subsystem. The owner MUST define allowed contents, public entry points, dependencies, generated content, and lifecycle.

#### DIR-03.02 — Directory and file names MUST be stable, searchable…

**Requirement:** Directory and file names MUST be stable, searchable, language-appropriate, and consistent with the repository convention. Names MUST NOT encode temporary status, personal ownership, or implementation details likely to change independently of the content.

#### DIR-03.03 — Each boundary MUST correspond to a real ownership…

**Requirement:** Each boundary MUST correspond to a real ownership, build, test, deployment, or distribution concern. Create a new module when it reduces coupling or provides independent selection; do not create levels of nesting that merely repeat product names.

#### DIR-03.04 — Public interfaces and shared assets MUST have one authoritative…

**Requirement:** Public interfaces and shared assets MUST have one authoritative location. Compatibility aliases or duplicate copies MUST identify their source of truth, synchronization mechanism, and planned removal condition.

#### DIR-03.05 — Directory-level docs MUST distinguish source, generated output…

**Requirement:** Directory-level docs MUST distinguish source, generated output, runtime data, fixtures, vendored code, and user-owned data. Build and cleanup tools MUST not delete user-owned or checked-in source data.

#### DIR-03.06 — Cross-cutting implementation MUST remain with the owning domain…

**Requirement:** Cross-cutting implementation MUST remain with the owning domain or a clearly owned shared interface; do not create a generic “optimization”, “misc”, or “common” directory without explicit scope and consumers.

### DIR-04 — Test data, generated assets, and boundary migrations

*Domain:* [directory](../../../torviello-enforcer/directory/README.md) · *Rule:* [04-test-data-generated-assets-and-boundary-migrations.md](../../../torviello-enforcer/directory/rules/04-test-data-generated-assets-and-boundary-migrations.md)

**Control objective.** This control defines the intended outcome for **test data, generated assets, and boundary migrations** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### DIR-04.01 — Production source, unit tests, integration tests…

**Requirement:** Production source, unit tests, integration tests, end-to-end tests, benchmarks, fixtures, model assets, docs source, design assets, containers, and generated outputs MUST have distinct discoverable homes consistent with their lifecycle and execution needs.

#### DIR-04.02 — Fixtures MUST be deterministic, licensed for the intended…

**Requirement:** Fixtures MUST be deterministic, licensed for the intended use, free of production secrets and personal data, and small enough for routine checks unless an explicit large-data test is separately gated.

#### DIR-04.03 — Generated files MUST identify their generator and regeneration command…

**Requirement:** Generated files MUST identify their generator and regeneration command. Hand edits to generated files MUST either be prohibited or reconciled to the source generator before merge.

#### DIR-04.04 — Large models, datasets, videos, and benchmark…

**Requirement:** Large models, datasets, videos, and benchmark corpora MUST use an approved external artifact or local cache strategy with immutable identifiers, size, license, and checksum recorded; Git history MUST not become an unbounded binary store.

#### DIR-04.05 — Boundary migrations MUST update imports, build scripts…

**Requirement:** Boundary migrations MUST update imports, build scripts, CI, package manifests, documentation links, and release automation in the same planned change. Compatibility shims MUST have an owner and removal condition.

#### DIR-04.06 — Cleanup, formatting, and code-generation commands MUST be…

**Requirement:** Cleanup, formatting, and code-generation commands MUST be scoped so they cannot recursively delete or rewrite user data, unrelated products, vendored sources, or manually maintained artifacts.

#### DIR-04.07 — New directories MUST receive purpose and agent guidance required…

**Requirement:** New directories MUST receive purpose and agent guidance required by CSC-001/002 unless the directory is a documented rules-domain exception; do not create empty files without useful local content.

### GOV-03 — Coverage, risk analysis, and rule evolution

*Domain:* [governance](../../../torviello-enforcer/governance/README.md) · *Rule:* [03-coverage-risk-analysis-and-rule-evolution.md](../../../torviello-enforcer/governance/rules/03-coverage-risk-analysis-and-rule-evolution.md)

**Control objective.** Coverage must be assessed from system context and change scenarios, not inferred from file counts. The rule set must evolve as product boundaries, failure modes, threat conditions, dependencies, and operational evidence change.

#### GOV-03.01 — A domain coverage review MUST identify relevant users…

**Requirement:** A domain coverage review MUST identify relevant users and operators, assets and data, trust boundaries, components and dependencies, deployment profiles, and intended outcomes before deciding which controls apply.

#### GOV-03.02 — A coverage review MUST consider governance, recruitment…

**Requirement:** A coverage review MUST consider governance, recruitment and role assignment, work intake, requirements, architecture, implementation, collaboration, procurement, verification, release, installation, operation, customer support, incident response, knowledge transfer, separation, migration, and retirement. Mark each area applicable, not applicable with rationale, or unresolved with owner and next review trigger.

#### GOV-03.03 — For each material boundary, consider misuse, invalid…

**Requirement:** For each material boundary, consider misuse, invalid input, resource exhaustion, concurrency, dependency failure, partial completion, restart, upgrade/downgrade, rollback, data loss, compromised credentials/artifacts, and operator error where relevant. Add controls when a credible scenario has no owner, prevention/detection behavior, recovery path, or evidence.

#### GOV-03.04 — The review MUST consider likelihood, impact, exposure…

**Requirement:** The review MUST consider likelihood, impact, exposure, reversibility, affected users, data sensitivity, blast radius, detectability, recovery time, and uncertainty. Higher-risk or irreversible outcomes MUST receive stronger prevention, independent review, and direct verification; low-risk choices MAY use proportionate checks with rationale.

#### GOV-03.05 — A change MUST be checked against adjacent domains when…

**Requirement:** A change MUST be checked against adjacent domains when it crosses their boundaries—for example API/security, model/persistence, build/release, configuration/operations, or UI/accessibility. Assign one authoritative control owner for shared obligations and cross-reference other documents instead of duplicating conflicting normative text.

#### GOV-03.06 — A gap MUST state the affected lifecycle area…

**Requirement:** A gap MUST state the affected lifecycle area, risk/scenario, impacted requirements, owner, interim mitigation, disposition, and review trigger or target. A gap MUST NOT be described as covered merely because a related document exists.

#### GOV-03.07 — After a defect, incident, security finding…

**Requirement:** After a defect, incident, security finding, near miss, production rollback, or repeated agent/user confusion, determine whether the root cause was missing, ambiguous, unenforced, or poorly assessed guidance. Update the control, tests, training/agent instructions, or ownership model as appropriate and link the corrective action.

#### GOV-03.08 — At least once per major release and when requirements…

**Requirement:** At least once per major release and when requirements or supported profiles change, reassess source versions, assumptions, controls, exceptions, owners, assessment evidence, and applicability. A new version of an external standard triggers impact analysis; it does not automatically change project policy.

#### GOV-03.09 — When a rule is obsolete, identify its replacement…

**Requirement:** When a rule is obsolete, identify its replacement or why it no longer applies, check dependent controls and open exceptions, preserve a change record, and remove stale index links. Do not leave abandoned controls appearing current.

#### GOV-03.10 — A material domain coverage review MUST dry-run its procedures…

**Requirement:** A material domain coverage review MUST dry-run its procedures against at least one ordinary case and relevant boundary/failure or lifecycle-transition cases. Record the actor, starting inputs, decision points, expected artifacts, observed ambiguities, and pass/fail outcome. A rule document’s existence or a generic “Examine/Interview/Test” section MUST NOT count as proof that a contributor can perform the work. Gaps MUST become owned rule-maintenance or training work with a review trigger.

#### GOV-03.11 — Each applicable, not-applicable, or unresolved lifecycle-area disposition…

**Requirement:** Each applicable, not-applicable, or unresolved lifecycle-area disposition in a domain trail MUST link to a dated coverage review record identifying reviewer, scope/profile, rationale, evidence, and next review trigger. Each dry-run MUST identify the procedure revision, participant, starting conditions, expected and actual outputs, result, gaps, owner, and remediation/retest evidence. An unlinked status label or an empty template MUST NOT be represented as completed coverage.

- [CQ-07] Do not create catch-all common, utils, helpers, or shared modules without a cohesive owner and stable consumers.
- [CQ-07] Do not duplicate security, authorization, or validation policy in wrappers while leaving the authoritative module unprotected.
- [CQ-07] Do not expose internal concrete types merely to avoid defining a useful contract.
- [DIR-01] The project MUST NOT add root-level files merely because a tool defaults to the repository root
- [DIR-01] The project MUST NOT mix build outputs, downloaded models, runtime data, or user configuration into source ownership directories
- [DIR-01] The project MUST NOT introduce a directory hierarchy that only mirrors concepts without clarifying ownership
- [DIR-02] The project MUST NOT treat a README or AGENTS file as the normative rule content of a rules domain
- [DIR-02] The project MUST NOT leave stale README instructions that contradict actual config, scripts, endpoints, or directory layout
- [DIR-02] The project MUST NOT create empty guidance files solely to satisfy a count
- [DIR-03] Do not place credentials, local state, caches, or generated artifacts in source-owned directories without a defined reason and cleanup policy.
- [DIR-03] Do not create an empty placeholder directory merely to satisfy a naming template.
- [DIR-04] Do not put integration or performance tests under production source to simplify discovery.
