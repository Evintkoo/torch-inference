# ENG-019 — Make runtime, hardware, and performance inspectable

**Requirement ID:** ENG-019  
**Priority:** SHOULD  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-25](../../../torviello-engine/specifications/checks/AC-ENG-25.md)  
**Rule controls:** OBS-02, PERF-01, SEC-05

## 1. Normative requirement

The engine MUST expose effective runtime, hardware, GPU, and performance information with stated measurement windows, cache expensive sampling, redact secrets, and bound profiling to an explicit request or interval.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

Operators cannot tune what they cannot see, but introspection endpoints are also a common source of secret leakage and latency amplification. The reference implementation exposes system information, effective configuration, GPU statistics, performance metrics, a profiling endpoint, optimization suggestions, and history, with a short-lived system-information cache.

Torviello requires those surfaces to be truthful and bounded: no fabricated GPU data, no secret fields, stated windows for percentiles, and profiling that does not silently remain enabled. This supports evidence-based tuning and the performance claims governed elsewhere.

## 3. Priority and interpretation

This requirement is **SHOULD**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to system information, effective configuration, GPU statistics, performance metrics, profiling, optimization suggestions, and history endpoints. It covers data accuracy, redaction, sampling cost, and measurement windows. It does not define benchmark methodology.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Report OS, architecture, CPU, memory, runtime version, feature flags, and uptime from live or cached observations.
- Report GPU devices only when a provider is usable and distinguish unavailable from zero devices.
- Report effective configuration with secrets redacted and sources identified.
- State the time window, sample count, and unit for throughput and latency percentiles.
- Cache expensive hardware sampling within a documented TTL and coalesce concurrent refreshes.
- Bound profiling to an explicit request or configured interval and restore the prior state afterward.
- Avoid returning hostnames, absolute paths, or environment dumps unless explicitly authorized.

#### OBS-02.01 — Expose bounded metrics for request volume, failures, latency distributions

The project MUST expose bounded metrics for request volume, failures, latency distributions, saturation, active work, queue depth, model load/readiness, resource use, and upstream failures.

#### OBS-02.02 — Give each metric one meaning and unit

The project MUST give each metric one meaning and unit. The project MUST also use standard base units and type suffixes where appropriate. The project MUST also use labels for bounded dimensions only; review multiplicative cardinality before adding labels.

#### OBS-02.03 — Distinguish process liveness from readiness to serve the selected

The project MUST distinguish process liveness from readiness to serve the selected product profile. A live process with required models unavailable is not ready.

#### OBS-02.04 — Restrict metrics endpoints to trusted monitoring networks or protect

The project MUST restrict metrics endpoints to trusted monitoring networks or protect them using deployment-supported authentication and TLS. The project MUST NOT expose Prometheus admin/lifecycle endpoints publicly.

#### OBS-02.05 — Monitoring profiles MUST document scrape intervals/timeouts, target discovery, authentication/TLS

Monitoring profiles MUST document scrape intervals/timeouts, target discovery, authentication/TLS, storage retention, dashboards, alert thresholds, ownership, and runbooks. Scrape timeout MUST NOT exceed scrape interval.

#### OBS-02.06 — Validate Prometheus configuration and alert/recording rules with official tooling

The project MUST validate Prometheus configuration and alert/recording rules with official tooling before deployment. Configuration changes are reviewed and rolled back on failed validation.

#### OBS-02.07 — Alerts MUST focus on user-visible symptoms, saturation, and recovery

Alerts MUST focus on user-visible symptoms, saturation, and recovery failure. Each production alert MUST have severity, owner, action, and a test path.

#### PERF-01.01 — Define the workload and target before optimizing: model, input

The project MUST define the workload and target before optimizing: model, input size, concurrency, latency percentile, throughput, peak memory, CPU/GPU utilization, energy/idle draw, and binary/build cost as applicable.

#### PERF-01.02 — Record hardware, OS, compiler, runtime/provider, driver, model digest, input

The project MUST record hardware, OS, compiler, runtime/provider, driver, model digest, input corpus, warmup, repetitions, concurrency, and measurement method. The project MUST report distributions and percentiles where latency matters.

#### PERF-01.03 — Keep benchmark code, harnesses, datasets, and reports under /benchmarks

The project MUST keep benchmark code, harnesses, datasets, and reports under /benchmarks. The project MUST also keep benchmarks out of production source and normal app startup.

#### PERF-01.04 — Compare results to a versioned baseline on the same

The project MUST compare results to a versioned baseline on the same reference environment. The project MUST also define regression thresholds and investigate material regressions before release.

#### PERF-01.05 — Profile to locate a bottleneck before changing algorithms

The project MUST profile to locate a bottleneck before changing algorithms or adding concurrency. The project MUST report both the achieved improvement and any resource/correctness tradeoff.

#### SEC-05.01 — Use maintained cryptographic libraries and standard algorithms

The project MUST use maintained cryptographic libraries and standard algorithms. The project MUST NOT implement cryptographic primitives or protocols directly.

#### SEC-05.02 — Store secrets in an appropriate OS/orchestrator secret store

Each supported deployment profile MUST name an approved secret store and enforce least-privilege read access. Prefer an OS or orchestrator secret manager; when one is unavailable, use a protected file readable only by the owning service identity on encrypted storage. The profile MUST define rotation and revocation steps and MUST fail closed if required secret material cannot be loaded or its access protections cannot be verified.

#### SEC-05.03 — Protect sensitive data in transit and at rest according

The project MUST protect sensitive data in transit and at rest according to classification and deployment threat model. Minimize retention and define deletion behavior.

#### SEC-05.04 — Keep secrets out of source control, logs, telemetry, crash

The project MUST keep secrets out of source control, logs, telemetry, crash reports, screenshots, URLs, and support bundles. Redact at system boundaries and test redaction.

#### SEC-05.05 — Use constant-time comparison for secret-derived authenticators where relevant

Every comparison of a secret-derived authenticator, including a password verifier, MAC, or token, MUST use a constant-time comparison. The project MUST generate secrets with cryptographically secure randomness and MUST fail closed if required entropy or key material is unavailable.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** ISO/IEC 25010:2023, OpenTelemetry 1.44.0, OWASP ASVS 5.0.0 Level 3 (data protection), IETF BCP 14.

- Reported configuration MUST be derived from the active immutable snapshot and MUST include source and precedence for each value.
- Performance and hardware information MUST state its sampling window, sample count, and measurement basis.
- Secrets, tokens, absolute host paths, model inputs, and personal data MUST be redacted or omitted; sampling and profiling MUST be bounded in CPU and memory cost.
- Introspection MUST be truthful under partial initialization, degradation, and failed components.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- System information matches observed OS, CPU, memory, and runtime version.
- A CPU-only host reports an empty GPU list with a reason and no fabricated values.
- Effective configuration redacts credentials and matches running values.
- Performance output states its window and reports coherent percentiles.
- Concurrent introspection requests do not trigger unbounded hardware sampling.
- Profiling reports stage timings and stops after the requested scope.

Acceptance checks: [AC-ENG-25](../../../torviello-engine/specifications/checks/AC-ENG-25.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- A diff MUST prove that reported effective configuration equals the active snapshot for every setting.
- A seeded redaction corpus MUST produce zero findings across introspection responses and exports.
- Sampling and profiling MUST be measured under load and MUST stay within the declared cost bound.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Centralize hardware sampling behind a TTL cache. Build system and configuration views from typed allowlists. Record latency histograms with explicit boundaries and compute percentiles over a stated rolling window. Profiling should be a scoped guard that restores state on drop.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not fabricate GPU utilization, memory, or temperature.
- Do not expose secrets, tokens, or full environment dumps.
- Do not report percentiles without a stated window and sample basis.
- Do not leave profiling enabled globally after a single-request profile.
- Do not perform an uncached full system probe on every scrape.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Request system information on hosts with and without accelerators.
- 2. Compare effective configuration with the running configuration and inspect redaction.
- 3. Generate known latencies and inspect reported percentiles and window.
- 4. Issue concurrent introspection requests and measure sampling behavior.
- 5. Profile one inference and verify profiling state afterward.
- 6. Record outputs, timing, and redaction checks.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Diff the introspection output against the active configuration and build manifest.
- 10. Run the redaction corpus and measure sampling overhead.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- System information from each host profile.
- GPU output for available and unavailable cases.
- Redacted effective configuration.
- Performance output with window and percentile basis.
- Sampling and profiling state evidence.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The configuration diff report.
- The redaction report and sampling-cost measurements.
- The runtime/version/hardware reconciliation record.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- Hardware values are fabricated or stale beyond the stated TTL.
- Secrets or environment dumps appear in output.
- Percentiles lack a window or are internally inconsistent.
- Profiling remains active after the request.
- Introspection dominates request latency under scrape load.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- Reported configuration differs from the active snapshot.
- A secret, path, or payload appears in introspection.
- Sampling is unbounded or materially changes latency without disclosure.
