# ENG-020 — Correlate requests through structured, redacted logs

**Requirement ID:** ENG-020  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-26](../../../torviello-engine/specifications/checks/AC-ENG-26.md)  
**Rule controls:** OBS-01, OBS-03, SEC-05, OBS-05

## 1. Normative requirement

The engine MUST assign or validate a correlation identifier at ingress, propagate it through logs and optional upstream calls, emit structured records for accepted and rejected requests, and exclude secrets, prompts, audio, images, and full payloads from logs and diagnostic access.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

Correlation is the difference between an incident report that can be reconstructed and a pile of timestamps. Rejected requests are especially important: authentication and rate-limit failures are invisible if logging sits behind those middleware. The reference implementation orders correlation and request logging outside authentication and rate limiting, propagates correlation IDs, and exposes log inspection endpoints.

Torviello requires safe structured logging and controlled diagnostic access. Logs must carry bounded metadata, not user content, and log file access must be confined to a declared root. This requirement also connects local logs to optional trace propagation without making tracing mandatory.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to every request path, middleware decision, background job, model lifecycle event, and optional upstream call. It covers correlation assignment, structured fields, redaction, log retention, diagnostic endpoints, and trace propagation. It does not define an external log aggregation product.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Assign a unique request ID when none is supplied and validate or replace unsafe supplied values.
- Place correlation assignment and request logging outside authentication and rate limiting so rejected traffic is recorded.
- Emit structured records with method, path, status, latency, request ID, and bounded model or capability identifiers.
- Exclude credentials, tokens, prompts, transcripts, audio, images, and raw payload bodies from logs and support bundles.
- Propagate trace context to configured optional upstreams using the documented header.
- Confine log inspection and deletion to declared files inside the log root and reject traversal.
- Apply retention and access rules to logs and diagnostic exports and record who accessed them where the deployment supports it.

#### OBS-01.01 — Emit structured runtime logs through the shared logging system

The project MUST emit structured runtime logs through the shared logging system. The project MUST also include timestamp, severity, service identity, event name, and correlation/trace context where available.

#### OBS-01.02 — Record operational and security events consistently: startup/shutdown, authentication

The project MUST record operational and security events consistently: startup/shutdown, authentication and authorization outcomes, configuration changes, model installation/promotion, dependency failures, and request outcomes.

#### OBS-01.03 — Log passwords, tokens, API keys, private keys, database credentials

The project MUST NOT log passwords, tokens, API keys, private keys, database credentials, full prompts, raw uploads, or unnecessary personal data. It MUST redact secrets at boundaries and sanitize untrusted values against log injection.

#### OBS-01.04 — Bound log volume and retention

The project MUST bound log volume and retention. The project MUST also use rotation or external collection without allowing disk exhaustion to interfere with application state.

#### OBS-01.05 — Use OpenTelemetry semantic conventions for HTTP, service identity, exceptions

The project MUST use OpenTelemetry semantic conventions for HTTP, service identity, exceptions, and resources. Propagate trace context across trusted service boundaries; never treat correlation identifiers as identity or authorization.

#### OBS-01.06 — Make telemetry export explicitly configurable and off by default

The project SHOULD make telemetry export explicitly configurable and off by default in local/offline profiles. The project MUST also document all exported fields and endpoints.

#### OBS-03.01 — Trace context MUST propagate across API handling, queues…

**Requirement:** Trace context MUST propagate across API handling, queues, model loading, inference, persistence, and external calls where causal relationships exist, using supported W3C trace context or an explicitly documented equivalent.

#### OBS-03.02 — Incoming trace context MUST be validated and treated as…

**Requirement:** Incoming trace context MUST be validated and treated as untrusted. It MUST NOT authorize access, select an arbitrary exporter, or cause unbounded trace state or baggage growth.

#### OBS-03.03 — Spans MUST represent operations with meaningful duration or cross-boundary…

**Requirement:** Spans MUST represent operations with meaningful duration or cross-boundary causality. Attributes MUST use stable semantic names, bounded values, documented units, and approved redaction rules.

#### OBS-03.04 — Telemetry sampling MUST define head/tail behavior, error…

**Requirement:** Telemetry sampling MUST define head/tail behavior, error and latency retention, per-profile defaults, and operator controls. Sampling MUST NOT create an unbounded memory buffer or delay request completion.

#### OBS-03.05 — Export MUST be optional for local/offline deployments. Exporter…

**Requirement:** Export MUST be optional for local/offline deployments. Exporter destination, TLS/authentication, data categories, sampling, retry buffer, and shutdown flush timeout MUST be configurable.

#### OBS-03.06 — Telemetry failures MUST not fail inference or block readiness…

**Requirement:** Telemetry failures MUST not fail inference or block readiness unless telemetry is explicitly a required product dependency. Export queues MUST have bounded size and drop behavior with a metric.

#### OBS-03.07 — Changes to semantic conventions MUST document migration and compatibility…

**Requirement:** Changes to semantic conventions MUST document migration and compatibility because dashboards and alert rules can consume the emitted names.

#### SEC-05.01 — Use maintained cryptographic libraries and standard algorithms

The project MUST use maintained cryptographic libraries and standard algorithms. The project MUST NOT implement cryptographic primitives or protocols directly.

#### SEC-05.02 — Store secrets in an appropriate OS/orchestrator secret store

Each supported deployment profile MUST name an approved secret store and enforce least-privilege read access. Prefer an OS or orchestrator secret manager; when one is unavailable, use a protected file readable only by the owning service identity on encrypted storage. The profile MUST define rotation and revocation steps and MUST fail closed if required secret material cannot be loaded or its access protections cannot be verified.

#### SEC-05.03 — Protect sensitive data in transit and at rest according

The project MUST protect sensitive data in transit and at rest according to classification and deployment threat model. Minimize retention and define deletion behavior.

#### SEC-05.04 — Keep secrets out of source control, logs, telemetry, crash

The project MUST keep secrets out of source control, logs, telemetry, crash reports, screenshots, URLs, and support bundles. Redact at system boundaries and test redaction.

#### SEC-05.05 — Use constant-time comparison for secret-derived authenticators where relevant

Every comparison of a secret-derived authenticator, including a password verifier, MAC, or token, MUST use a constant-time comparison. The project MUST generate secrets with cryptographically secure randomness and MUST fail closed if required entropy or key material is unavailable.

#### OBS-05.01 — Logs, traces, metrics, crash reports…

**Requirement:** Logs, traces, metrics, crash reports, and support bundles MUST each have a stated purpose, data classification, retention period, storage location, access policy, and deletion mechanism.

#### OBS-05.02 — Inference prompts, completions, uploaded files, model…

**Requirement:** Inference prompts, completions, uploaded files, model outputs, credentials, and direct identifiers MUST not be collected by default for diagnostics. Any opt-in collection MUST disclose fields, purpose, destination, retention, and how to disable/delete it.

#### OBS-05.03 — Structured fields MUST use an allowlist or explicit classification…

**Requirement:** Structured fields MUST use an allowlist or explicit classification policy. Redaction MUST occur before persistence or export, and tests MUST cover nested fields, exception strings, URLs, query parameters, and malformed input.

#### OBS-05.04 — Diagnostic access MUST be least-privilege and audited when it…

**Requirement:** Diagnostic access MUST be least-privilege and audited when it permits viewing security events, user identifiers, or sensitive inference content.

#### OBS-05.05 — Log rotation and storage limits MUST prevent disk exhaustion…

**Requirement:** Log rotation and storage limits MUST prevent disk exhaustion; behavior when storage is full MUST preserve service safety and surface a bounded alert.

#### OBS-05.06 — Telemetry pseudonyms and correlation identifiers MUST have bounded lifetime…

**Requirement:** Telemetry pseudonyms and correlation identifiers MUST have bounded lifetime and MUST NOT be reused as authentication credentials or stable cross-service user profiles.

#### OBS-05.07 — Support bundles MUST be previewable or field-selectable before export…

**Requirement:** Support bundles MUST be previewable or field-selectable before export and MUST exclude secrets and user payloads unless explicitly selected under an approved support workflow.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** OpenTelemetry Logs 1.44.0, W3C Trace Context, OWASP Logging Cheat Sheet, ISO/IEC 25010:2023, IETF BCP 14.

- Every request log MUST carry request ID, trace ID, span ID, route group, status, latency, model ID, and engine version in stable fields.
- Log messages MUST be structured, use stable levels, and neutralize CRLF, ANSI, and control-character injection from untrusted values.
- Secrets, credentials, prompts, transcripts, audio, images, and raw payloads MUST be redacted at emission.
- Diagnostic access and retention MUST be authorized, bounded, and auditable; clearing or exporting logs MUST emit an audit event.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- A request without a correlation header receives a generated ID visible in the response and logs.
- A malformed or oversized correlation header is replaced or rejected without log injection.
- Authentication and rate-limit rejections produce structured records.
- Prompt, audio, image, and token content is absent from logs.
- An upstream call carries the documented trace header.
- Log inspection rejects paths outside the log root.

Acceptance checks: [AC-ENG-26](../../../torviello-engine/specifications/checks/AC-ENG-26.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- An injection corpus MUST prove that CRLF, ANSI, Unicode control, and oversized fields cannot forge log records.
- W3C trace-context propagation MUST be verified across HTTP, WebSocket, and upstream calls.
- The redaction corpus MUST produce zero findings across logs, traces, and exports.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Use a request-scoped context object that carries the correlation ID and trace context. Install ingress middleware before security gates. Serialize logs through typed field structs rather than string concatenation. Keep diagnostic endpoints behind authorization and a canonical log-root check.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not log credentials, tokens, prompt text, transcripts, audio, or image bytes.
- Do not allow arbitrary text from a header to become an unescaped log field.
- Do not place request logging behind authentication or rate limiting only.
- Do not expose log files outside the declared root.
- Do not claim trace propagation while sending no context.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Send requests with and without correlation headers, including malformed values.
- 2. Trigger authentication and rate-limit failures and inspect records.
- 3. Send representative prompt, audio, and image requests and inspect logs.
- 4. Call a configured upstream and inspect propagated headers.
- 5. Attempt log file access outside the root.
- 6. Record log samples and redaction results.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Replay the log-injection and redaction corpora.
- 10. Trace one request across HTTP, execution, upstream, and response and compare identifiers.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Log records for accepted and rejected requests with correlation IDs.
- Safe handling of malformed correlation headers.
- Redaction inspection for each payload type.
- Upstream trace-header evidence.
- Path-confinement evidence for log access.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- Injection and redaction reports with zero findings.
- The trace-propagation record.
- The retention, access, and audit evidence.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- Rejected requests produce no request record.
- Correlation IDs differ between response and logs.
- Payloads or credentials appear in logs.
- Header content enables log injection.
- Log endpoints read arbitrary files.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- A log record can be forged or its fields injected.
- A request cannot be correlated across logs, traces, and response.
- A secret or payload appears in any log or export.
