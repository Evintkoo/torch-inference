# ENG-003 — Detect execution backends and report capabilities truthfully

**Requirement ID:** ENG-003  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-09](../../../torviello-engine/specifications/checks/AC-ENG-09.md)  
**Rule controls:** PERF-04, ARC-02, PERF-02

## 1. Normative requirement

The engine MUST select an execution backend from the providers the running build can actually execute, make an explicit selection observable, fail an explicit unavailable request instead of silently changing provider, and report capabilities that distinguish available, configured, compiled, and active providers.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

Inference performance and memory behavior depend entirely on the selected provider. A response that reports CUDA while executing on CPU, or a build that advertises TensorRT because a feature flag exists, misleads operators and invalidates benchmark claims.

The reference implementation maintains a device configuration (`auto`, `cuda`, `cpu`, `metal`, `mps`), a GPU manager that detects CUDA and Metal, optional torch and ORT backends, and runtime feature flags in system information. The specification turns those pieces into a strict selection and reporting contract, including fallback rules and precision flags.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to every capability that executes tensors or model graphs, including classification, detection, speech models, TTS engines, and the generic neural-network registry. It covers selection at startup and per-request observation. It does not require support for every provider on every platform.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Enumerate available providers from runtime probes, not from compile-time flags alone.
- Apply one documented selection policy for `auto`: prefer a usable accelerator in declared order, otherwise CPU, and record the reason.
- Reject an explicit device request that cannot be satisfied unless the configuration explicitly permits fallback.
- Expose the active backend, device index, precision, and selection reason through health or runtime introspection.
- Report optional providers that are compiled but unusable as unavailable with a reason, never as active.
- Validate per-request device or precision overrides against the capability set and reject unsupported combinations before model execution.
- Keep backend-specific types out of the transport contract and domain interfaces.

**Requirement:** Each accelerator backend MUST publish a tested compatibility tuple covering hardware generation, OS/kernel, driver, runtime/provider, compiler/toolchain, model format, build feature, and precision modes.

**Requirement:** Capability discovery MUST report device identity, available memory, supported operations/precision, driver/runtime version, and rejection reason without requiring model execution or exposing unstable device secrets.

**Requirement:** Provider selection MUST be deterministic for a configured policy. Auto-selection MUST document priority, tie-breaking, and behavior when multiple devices or providers are present.

**Requirement:** Fallback to CPU or another provider MUST be explicit, observable, and validated for output correctness, numerical tolerance, performance expectations, and resource impact. Unsupported forced-provider requests MUST fail clearly.

**Requirement:** Backend initialization and runtime errors MUST identify whether the failure is transient, device-specific, model-specific, or unsupported; recovery MUST release partially initialized handles and not poison unrelated providers.

**Requirement:** Build profiles MUST exclude disabled accelerator dependencies and runtime libraries. Binary packaging MUST include only legally redistributable libraries and state external driver/runtime prerequisites.

#### PERF-04.07 — Provider-specific optimizations MUST be gated by capability detection…

**Requirement:** Provider-specific optimizations MUST be gated by capability detection and have a correct baseline path; an optimization MUST not silently depend on undocumented hardware behavior.

The project MUST make hardware backends and large optional runtimes selectable capabilities. Disabled capabilities MUST NOT pull their runtime dependencies into a minimal profile.

#### ARC-02.02 — Use additive Cargo features named after user-visible capabilities

The project MUST use additive Cargo features named after user-visible capabilities and document their dependency effects. It MUST NOT use features that silently change unrelated behavior.

#### ARC-02.03 — Publish build profiles for minimal CPU, supported CPU features

The project MUST publish build profiles for minimal CPU, supported CPU features, and each supported accelerator family. The matrix states exact OS, architecture, runtime, driver, and toolchain requirements.

#### ARC-02.04 — Each adapter MUST implement the same model lifecycle contract

Each adapter MUST implement the same model lifecycle contract: capability discovery, load, readiness, inference, cancellation, shutdown, and typed failure

#### ARC-02.05 — Record architecture decisions for module boundaries, backend interfaces, serialization

The project MUST record architecture decisions for module boundaries, backend interfaces, serialization, persistence, or compatibility, including alternatives and migration cost.

#### PERF-02.01 — Bound request concurrency, queue depth, batch size, model count

The project MUST bound request concurrency, queue depth, batch size, model count, model memory, download size, temporary disk, and request execution time. Defaults MUST be safe on the minimum supported machine.

#### PERF-02.02 — Make tradeoffs between throughput, tail latency, memory, CPU load

The project MUST make tradeoffs between throughput, tail latency, memory, CPU load, GPU utilization, energy use, and idle power explicit in profiles or configuration.

#### PERF-02.03 — Maintain a backend matrix for CPU, CUDA, Metal, Vulkan

The project MUST maintain a backend matrix for CPU, CUDA, Metal, Vulkan, and AMD paths. Each claimed combination lists provider/runtime/driver versions, hardware, build flags, support level, and known limits.

#### PERF-02.04 — Backend selection MUST be observable and deterministic

Backend selection MUST be observable and deterministic. Fallback MUST be allowed only when configured and MUST report why the requested provider was unavailable.

#### PERF-02.05 — Use load shedding and backpressure rather than allowing unbounded

The project MUST use load shedding and backpressure rather than allowing unbounded queues. Overload has a documented client response, metric, and recovery condition.

#### PERF-02.06 — Preserve a CPU-only baseline and validate inference correctness on

The project MUST preserve a CPU-only baseline and validate inference correctness on every advertised backend before performance tuning.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** ISO/IEC 25010:2023 (compatibility, performance efficiency), NIST SP 800-160 Vol. 1 Rev. 1, OpenTelemetry 1.44.0, IETF BCP 14.

- Capability MUST be established by an execution probe on the actual host, not by a compiled feature flag, package presence, or configuration value.
- Selection MUST be deterministic for a given configuration, host, and probe result; every fallback MUST emit a reason and remain visible in diagnostics.
- Device, precision, provider version, and probe failure MUST be attributable in the result envelope and system information.
- A provider that cannot execute the declared operation MUST be reported unavailable, not available with a warning.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- An auto start with a usable accelerator selects it and records the reason.
- An auto start without accelerators selects CPU and does not claim accelerator support.
- An explicit CUDA request on a build without CUDA fails with backend.unavailable.
- A compiled but unloadable provider is reported unavailable with a reason.
- A response names the backend and precision used for that inference.
- An unsupported precision override is rejected before backend dispatch.

Acceptance checks: [AC-ENG-09](../../../torviello-engine/specifications/checks/AC-ENG-09.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- Every declared backend MUST be exercised on its supported target matrix, including unavailable, partially available, and probe-failure cases.
- Property tests MUST verify that auto-selection matches the documented preference order for randomized capability sets.
- Fault injection MUST remove devices, deny permissions, exhaust memory, and corrupt provider initialization without producing a false capability claim.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Create a capability registry populated at startup from provider probes. Backend selection consumes that registry and returns a structured selection result with provider, device, precision, source, and reason. Handlers read the selected result rather than re-detecting the device. Keep provider initialization behind traits so optional builds compile without accelerator dependencies.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not infer capability from a build flag without a runtime probe.
- Do not silently fall back from an explicitly requested accelerator.
- Do not report a provider as active when it is only installed or configured.
- Do not expose provider-specific types in the public API.
- Do not change precision silently to make a request succeed.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Run on a host with a usable accelerator and on a CPU-only host with the same build where possible.
- 2. Start with device_type auto and inspect the selected backend, device, precision, and reason.
- 3. Start with an explicit unavailable backend and confirm startup or request failure without fallback.
- 4. Load an optional provider that is compiled but whose runtime library is absent and inspect capability output.
- 5. Submit an unsupported precision override and confirm rejection before dispatch.
- 6. Record hosts, provider versions, configuration, and observed output.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Execute a minimal inference probe for each declared backend and record provider, device, precision, and failure mode.
- 10. Compare the reported capability set with the probe results and the build profile manifest.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Runtime capability output for each host and build.
- Selection reason and active backend from health or introspection.
- Failure envelope for an explicit unavailable backend.
- Evidence that a compiled-but-unusable provider is marked unavailable.
- The per-inference backend metadata from a successful request.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The backend-by-target matrix with probe transcripts and driver versions.
- Selection and fallback event records with reasons.
- A negative matrix showing unavailable providers are never reported as available.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- A provider is reported active without a runtime probe.
- An explicit accelerator request silently executes on CPU.
- Capabilities include a provider the build cannot load.
- Backend metadata is missing or contradicts the executed provider.
- Precision changes without an explicit response field.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- A compiled but unusable provider is reported as available.
- A silent fallback occurs without an event, diagnostic reason, or result attribution.
