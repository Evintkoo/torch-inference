# ENG-025 — Administer the registry with authorization and audit

**Requirement ID:** ENG-025  
**Priority:** SHOULD  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-31](../../torviello-engine/specifications/checks/AC-ENG-31.md)  
**Rule controls:** MOD-03, SEC-03, SEC-06

## 1. Normative requirement

Registry mutation MUST require administrative authority, validate descriptors and paths, confine scans to the configured root, record actor, action, target, and result for every mutation, and expose an export that preserves stable identity without secrets or host paths.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

The registry is the authority for what the engine can execute. Allowing inference clients to register arbitrary paths or delete models turns a serving process into a filesystem and supply-chain interface. The reference implementation exposes registration, directory scan, metadata, load, inference, statistics, and export routes under `/registry`.

Torviello requires those routes to be administrative, validated, and auditable. This is also where model provenance and local import meet: the registry must not accept a descriptor that bypasses the same path and identity rules used by acquisition and loading.

## 3. Priority and interpretation

This requirement is **SHOULD**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to registry registration, scanning, metadata lookup, loading, export, and deletion where present. It covers authorization, descriptor validation, path confinement, scan bounds, audit records, and export content. It does not define a hosted multi-tenant registry service.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Require administrative scope for every registry mutation and deny inference-scoped callers.
- Validate descriptors for stable ID, task, format, backend requirements, and asset path before registration.
- Confine registration and scan paths to the configured model root, including canonicalized symlink targets.
- Bound directory scans by depth, file count, and supported extensions.
- Record one audit entry per mutation with actor, action, target, outcome, and timestamp.
- Make audit records append-only through the public API.
- Export registered models with stable IDs and metadata while excluding secrets and absolute host paths.

#### MOD-03.01 — Registry mutations MUST require authenticated identity and least-privilege authorization

Registry mutations MUST require authenticated identity and least-privilege authorization. The project MUST also separate view, add, promote, rollback, and delete permissions where the product requires distinct roles.

#### MOD-03.02 — Validate edits through one schema and policy layer whether

The project MUST validate edits through one schema and policy layer whether they arrive through an admin API or a controlled manual file change.

#### MOD-03.03 — Audit actor, time, action, target model/version, outcome, and change

The project MUST audit actor, time, action, target model/version, outcome, and change identifier. The project MUST NOT log tokens or secret configuration values.

#### MOD-03.04 — Make changes transactional: validate a candidate, persist it safely

The project MUST make changes transactional: validate a candidate, persist it safely, then publish the new version. The project MUST provide a rollback to the last known-good registry state.

#### MOD-03.05 — The standalone engine MUST operate with a local registry/cache

The standalone engine MUST operate with a local registry/cache and MUST NOT require a hosted control plane for local inference

#### SEC-03.01 — Apply deny-by-default authorization to every operation and resource

The project MUST apply deny-by-default authorization to every operation and resource. The project MUST also define roles/scopes for inference, model administration, registry changes, user management, billing/licensing, and system configuration.

#### SEC-03.02 — Enforce authorization at the service/domain boundary, not only in

The project MUST enforce authorization at the service/domain boundary, not only in UI controls or route naming. The project MUST also check ownership for object-level access and tenant isolation for hosted deployments.

#### SEC-03.03 — Separate read, create, update, promote, revoke, and delete permissions

The project MUST separate read, create, update, promote, revoke, and delete permissions where impact differs. The project MUST also require stronger controls for high-impact administration when specified by the threat model.

#### SEC-03.04 — Audit privileged actions with actor, target, time, outcome

The project MUST audit privileged actions with actor, target, time, outcome, and correlation context. The project MUST also ensure logs cannot be edited through the same ordinary admin permission.

#### SEC-03.05 — Keep health and metrics routes minimally informative and explicitly

The project MUST keep health and metrics routes minimally informative and explicitly categorized as public, internal, or privileged.

#### SEC-06.01 — Pin and review build dependencies and release inputs

The project MUST pin and review build dependencies and release inputs. The project MUST also generate an SBOM and preserve provenance for every release.

#### SEC-06.02 — Scan dependencies, source, secrets, containers, and model artifacts

The project MUST scan dependencies, source, secrets, containers, and model artifacts. Triage findings using exploitability and deployment context; block unsafe releases under the documented severity gate.

#### SEC-06.03 — Download models only from configured trusted sources

The project MUST download models only from configured trusted sources. The project MUST also verify digest/signature and license/source metadata before installation or activation.

#### SEC-06.04 — Preserve model and software version identity

The project MUST preserve model and software version identity. Updates are atomic and have a rollback path; failed verification never replaces a known-good artifact.

#### SEC-06.05 — Review build workflows and credentials as production security boundaries

The project MUST review build workflows and credentials as production security boundaries. The project MUST also use least privilege and short-lived credentials for release automation.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** OWASP ASVS 5.0.0 Level 3 (access control, audit), OWASP API Security Top 10 2023, ISO/IEC 25010:2023, IETF BCP 14.

- Every administrative mutation MUST require a validated administrative scope and MUST be denied before handler logic otherwise.
- Audit records MUST be append-only, tamper-evident, and complete: actor, action, target, outcome, timestamp, request ID, and source policy.
- Registration and removal MUST be atomic and idempotent, with stable conflict semantics and no partially applied state.
- Names, destinations, and assets MUST be validated and confined; export MUST be stable, versioned, and redacted.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- An authorized registration returns the model ID and metadata.
- An unauthorized mutation returns 403 and records the denial.
- A path escaping the root through traversal or a symlink returns model.path_outside_root.
- A scan registers only supported files and respects declared bounds.
- Export contains every registered model with stable IDs and no secrets or host paths.
- No API call can update or delete an audit record.

Acceptance checks: [AC-ENG-31](../../torviello-engine/specifications/checks/AC-ENG-31.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- An authorization matrix MUST cover every administrative route, scope, and denied case.
- An audit-chain check MUST detect deletion, reordering, or modification of records.
- Concurrency and crash injection MUST prove atomic registration and removal.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Declare registry routes in an administrative route group with an explicit scope check. Validate descriptors through the same model descriptor type used by loading. Use a scan walker with depth and count limits. Write audit entries before returning success and expose no mutation route for them.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not allow inference clients to register or delete models.
- Do not trust a client-supplied absolute path.
- Do not scan an unbounded directory tree.
- Do not omit the actor or target from a mutation record.
- Do not leak credentials or host paths in an export.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Register a valid descriptor with an administrative token.
- 2. Attempt the same mutation with a non-admin token and inspect the audit record.
- 3. Attempt traversal and symlink escape paths.
- 4. Scan a prepared directory with supported and unsupported files.
- 5. Export the registry and inspect identity, redaction, and completeness.
- 6. Attempt to modify an audit record through the API.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Execute the authorization matrix and the audit-chain tamper tests.
- 10. Interrupt mutations at every boundary and inspect the visible catalog and audit state.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Registration response and audit entry.
- 403 response and denial record.
- Path-escape rejection evidence.
- Scan inventory and bounds behavior.
- Export content and redaction inspection.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The authorization matrix and denied-case records.
- The audit-chain integrity report.
- Crash-consistency and idempotency results.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- An inference token can mutate the registry.
- A path outside the root is registered.
- A scan traverses without bounds.
- Mutations have no audit record.
- Export exposes secrets or absolute paths.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- An unauthorized caller can mutate the registry.
- A mutation succeeds without an audit record, or the audit chain can be altered.
- A failed mutation leaves partial catalog or asset state.
