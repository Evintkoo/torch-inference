### CFG-03 — Configuration lifecycle and safe reload

*Domain:* [configuration](../../../torviello-enforcer/configuration/README.md) · *Rule:* [03-configuration-lifecycle-and-safe-reload.md](../../../torviello-enforcer/configuration/rules/03-configuration-lifecycle-and-safe-reload.md)

**Control objective.** This control defines the intended outcome for **configuration lifecycle and safe reload** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### CFG-03.01 — Configuration MUST be parsed into one typed candidate…

**Requirement:** Configuration MUST be parsed into one typed candidate and validated completely before the application binds public listeners, activates models, or mutates persistent state.

#### CFG-03.02 — Validation MUST report the setting name and a safe…

**Requirement:** Validation MUST report the setting name and a safe corrective action without echoing secret values or exposing internal paths. Multiple errors SHOULD be reported together when doing so does not expose sensitive material.

#### CFG-03.03 — Configuration reload MUST be atomic: build and validate…

**Requirement:** Configuration reload MUST be atomic: build and validate a complete candidate, verify its dependencies, then switch active state at a defined boundary. If any step fails, the running system MUST retain the last known-good configuration and report the reload failure.

#### CFG-03.04 — Each setting MUST declare whether it is startup-only…

**Requirement:** Each setting MUST declare whether it is startup-only, reloadable, or dynamically sampled. A reload MUST NOT leave components using incompatible snapshots unless the consistency model is explicitly designed and tested.

#### CFG-03.05 — Configuration watchers MUST debounce partial file writes, handle…

**Requirement:** Configuration watchers MUST debounce partial file writes, handle rename-based replacement, permission changes, deletion, and invalid intermediate files, and MUST avoid unbounded reload loops.

#### CFG-03.06 — Configuration schema evolution MUST define defaulting, deprecation…

**Requirement:** Configuration schema evolution MUST define defaulting, deprecation, migration, unknown-field, and downgrade behavior. A newer binary MUST NOT silently rewrite a file such that the prior supported version cannot start unless that migration is explicit and backed up.

#### CFG-03.07 — Operator-facing effective-configuration output MUST redact credentials, identify source…

**Requirement:** Operator-facing effective-configuration output MUST redact credentials, identify source and precedence for each value, and distinguish explicit values from defaults without exposing secret contents.

### CFG-05 — Secret configuration and operator controls

*Domain:* [configuration](../../../torviello-enforcer/configuration/README.md) · *Rule:* [05-secret-configuration-and-operator-controls.md](../../../torviello-enforcer/configuration/rules/05-secret-configuration-and-operator-controls.md)

**Control objective.** This control defines the intended outcome for **secret configuration and operator controls** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### CFG-05.01 — Secrets MUST use an approved source for the deployment…

**Requirement:** Secrets MUST use an approved source for the deployment profile: OS credential store, orchestrator secret, protected file, or explicitly configured environment input. Documentation MUST state the storage threat model and required file permissions.

#### CFG-05.02 — Production secrets MUST be validated for presence, format…

**Requirement:** Production secrets MUST be validated for presence, format, purpose, and minimum strength at startup. Missing or invalid required credentials MUST fail closed before the service accepts traffic.

#### CFG-05.03 — Secret rotation MUST support overlap or coordinated replacement where…

**Requirement:** Secret rotation MUST support overlap or coordinated replacement where clients require it, identify active key version, define rollback, and revoke compromised material without restoring the compromised value.

#### CFG-05.04 — Configuration inspection, diagnostic endpoints, support bundles…

**Requirement:** Configuration inspection, diagnostic endpoints, support bundles, crash reports, and debug logging MUST redact secret-bearing fields recursively, including nested structures and secret references.

#### CFG-05.05 — Operator controls MUST distinguish read-only inspection from mutating actions…

**Requirement:** Operator controls MUST distinguish read-only inspection from mutating actions, authenticate and authorize remote changes, audit actor/target/outcome, and prevent lost-update races with version checks or equivalent concurrency control.

#### CFG-05.06 — Configuration files and generated state MUST have explicit ownership…

**Requirement:** Configuration files and generated state MUST have explicit ownership and permissions. The service MUST detect unexpected symlinks, world-readable credentials, or writable-by-untrusted-user files where those conditions weaken the deployment threat model.

#### CFG-05.07 — Each setting with security or availability impact MUST document…

**Requirement:** Each setting with security or availability impact MUST document its default, valid range, effect, reloadability, and operational recovery path.

### OBS-04 — Alerts, SLOs, dashboards, and operator actions

*Domain:* [observability](../../../torviello-enforcer/observability/README.md) · *Rule:* [04-alerts-slos-dashboards-and-operator-actions.md](../../../torviello-enforcer/observability/rules/04-alerts-slos-dashboards-and-operator-actions.md)

#### OBS-04.01 — Each production service profile MUST define service indicators…

**Requirement:** Each production service profile MUST define service indicators and objectives for user-visible availability, latency, and correctness or error rate where measurable; state measurement population, window, exclusions, and objective owner.

#### OBS-04.03 — Alerts MUST distinguish symptoms requiring immediate intervention from diagnostic…

**Requirement:** Alerts MUST distinguish symptoms requiring immediate intervention from diagnostic conditions suitable for dashboards or tickets. Avoid paging on a single noisy host or raw dependency metric when service behavior remains healthy.

#### OBS-04.04 — Dashboards MUST show request traffic, successful and failed…

**Requirement:** Dashboards MUST show request traffic, successful and failed latency distributions, error rate, saturation, queueing, model/backend state, resource utilization, and dependency health for the selected service profile.

#### OBS-04.05 — Alert and dashboard queries MUST use bounded labels…

**Requirement:** Alert and dashboard queries MUST use bounded labels and preserve distinctions between failed and successful request latency. Missing telemetry MUST be visible rather than rendered as healthy zero.

#### OBS-04.06 — Prometheus scrape and alert configuration MUST be syntax-validated…

**Requirement:** Prometheus scrape and alert configuration MUST be syntax-validated and rule-tested before deployment; scrape timeout MUST not exceed interval and scrape/authentication settings MUST match the exposed target.

#### OBS-04.07 — Runbooks MUST explain detection, impact, first safe…

**Requirement:** Runbooks MUST explain detection, impact, first safe action, escalation, rollback/recovery, verification of recovery, and evidence to retain.

### OPS-01 — Service lifecycle and readiness

*Domain:* [operations](../../../torviello-enforcer/operations/README.md) · *Rule:* [01-service-lifecycle-and-readiness.md](../../../torviello-enforcer/operations/rules/01-service-lifecycle-and-readiness.md)

**Control objective.** These controls govern **service lifecycle and readiness**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### OPS-01.01 — Document and support installation, start, stop, restart, readiness, liveness

The project MUST document and support installation, start, stop, restart, readiness, liveness, logs, configuration, upgrade, rollback, and uninstall for each declared deployment profile.

#### OPS-01.02 — Startup MUST validate configuration and required runtime prerequisites before

Startup MUST validate configuration and required runtime prerequisites before readiness becomes true. Readiness MUST reflect whether configured capabilities can serve; liveness MUST reflect whether the process can continue operating.

#### OPS-01.03 — Shutdown MUST stop accepting work, drain or cancel requests

Shutdown MUST stop accepting work, drain or cancel requests within a defined deadline, flush required state, and release model/runtime resources. Repeated signals and abrupt termination MUST have bounded behavior.

#### OPS-01.04 — Configure process supervision or container restart behavior with bounded

The project MUST configure process supervision or container restart behavior with bounded retry/backoff and visible failure state. Endless restart loops MUST NOT hide invalid configuration or unavailable required models.

#### OPS-01.05 — Keep the local engine usable without a hosted account

The project MUST keep the local engine usable without a hosted account, hosted registry, or telemetry endpoint unless the selected profile explicitly requires that service.

#### OPS-03.01 — Every supported deployment profile MUST state target OS/architecture…

**Requirement:** Every supported deployment profile MUST state target OS/architecture, prerequisites, filesystem paths, service identity, required ports, data directories, model storage, configuration source, and network dependencies.

#### OPS-03.02 — Install and upgrade procedures MUST be repeatable from…

**Requirement:** Install and upgrade procedures MUST be repeatable from a clean machine and MUST distinguish administrator actions from service-user actions. The service MUST run with least privilege and writable paths limited to documented state/cache locations.

#### OPS-03.03 — Service definitions MUST set restart policy, startup ordering…

**Requirement:** Service definitions MUST set restart policy, startup ordering, graceful stop timeout, environment/config source, resource limits, and log routing appropriate to the target service manager.

#### OPS-03.04 — Container images MUST pin base image identity, use…

**Requirement:** Container images MUST pin base image identity, use non-root execution where feasible, include only runtime artifacts, define health checks, and avoid embedding secrets or mutable model downloads in image layers.

#### OPS-03.05 — Network listeners MUST bind to the intended interface by…

**Requirement:** Network listeners MUST bind to the intended interface by default. Remote exposure MUST require an explicit deployment choice and documented authentication, TLS termination, firewall, and proxy trust policy.

#### OPS-03.06 — First startup MUST distinguish missing prerequisites from corrupt state…

**Requirement:** First startup MUST distinguish missing prerequisites from corrupt state and transient dependency failures; automated restart MUST use backoff and MUST not create a restart loop that hides permanent configuration errors.

#### OPS-03.07 — Installation MUST preserve user data and configuration on upgrade…

**Requirement:** Installation MUST preserve user data and configuration on upgrade; uninstall MUST explain which state is retained or removed and require explicit confirmation before destructive deletion.

### OPS-06 — Operational Roles Coverage Handover and Human Continuity

*Domain:* [operations](../../../torviello-enforcer/operations/README.md) · *Rule:* [06-operational-roles-coverage-handover-and-human-continuity.md](../../../torviello-enforcer/operations/rules/06-operational-roles-coverage-handover-and-human-continuity.md)

**Control objective.** Operational resilience depends on people knowing who is on duty, what they may do, how to hand work over, and how the service remains safe when a key person or supplier is unavailable. Coverage must match the service commitment without inventing unsupported staffing promises.

#### OPS-06.01 — Each production profile MUST identify service owner, incident…

**Requirement:** Each production profile MUST identify service owner, incident lead, deploy/release authority, security escalation, data/persistence owner, customer communication owner, and backup/delegate as applicable. State whether each function is staffed continuously, during defined hours, or on best-effort basis.

#### OPS-06.02 — For supported operational channels, state hours, severity…

**Requirement:** For supported operational channels, state hours, severity classes, response targets, escalation contacts, and fallback when the primary owner is unreachable. Public service promises MUST match actual staffing, monitoring, and recovery capability.

#### OPS-06.03 — An operational handover MUST include current service health…

**Requirement:** An operational handover MUST include current service health, open incidents/changes, customer impact, risks, pending actions, access used, deadlines, and next decision. The receiving owner MUST acknowledge material risk and understand their authority.

#### OPS-06.04 — Coverage MUST use named identities and pre-authorized delegates…

**Requirement:** Coverage MUST use named identities and pre-authorized delegates with time-bounded access. Never share accounts or keys to cover an absent operator; emergency access uses the security break-glass process and post-use review.

#### OPS-06.05 — For critical operations, identify single-person and supplier dependencies…

**Requirement:** For critical operations, identify single-person and supplier dependencies, recovery documentation, alternate contacts, and minimum competent coverage. Exercise absence, simultaneous incident, and unavailability of a key vendor at a frequency proportional to impact.

#### OPS-06.06 — Operational processes MUST allow responders to escalate unsafe workload…

**Requirement:** Operational processes MUST allow responders to escalate unsafe workload, conflicting incident tasks, or insufficient authority. Rotate or hand off duties as needed under approved work policies; do not use undocumented availability expectations as a service guarantee.

#### OPS-06.07 — Changes to service hours, product scope, team…

**Requirement:** Changes to service hours, product scope, team structure, vendor, incident severity, or recovery process MUST trigger review of roles, contacts, runbooks, training, and support commitments.

**Control objective.** This control defines the intended outcome for **install, upgrade, migration, and rollback** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### REL-05.01 — Installers MUST verify package identity and integrity before executing…

**Requirement:** Installers MUST verify package identity and integrity before executing privileged operations and MUST explain requested privileges and network access.

#### REL-05.02 — Upgrade MUST stage new binaries and configuration, validate…

**Requirement:** Upgrade MUST stage new binaries and configuration, validate prerequisites and migrations, switch active versions atomically where feasible, and retain the previous known-good state until health verification passes.

#### REL-05.03 — Configuration and database migrations MUST be versioned, backed…

**Requirement:** Configuration and database migrations MUST be versioned, backed up when destructive, observable, and compatible with the rollback policy. If downgrade is unsupported, the installer MUST block it before modifying state and explain forward recovery.

#### REL-05.04 — Model assets MUST be versioned independently from binaries when…

**Requirement:** Model assets MUST be versioned independently from binaries when their size or lifecycle warrants it; model rollback MUST verify compatibility with the target runtime version.
