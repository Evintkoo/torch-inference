### API-04 — API inventory, evolution, and deprecation

*Domain:* [api](../../torviello-enforcer/api/README.md) · *Rule:* [04-api-inventory-evolution-and-deprecation.md](../../torviello-enforcer/api/rules/04-api-inventory-evolution-and-deprecation.md)

**Control objective.** This control defines the intended outcome for **api inventory, evolution, and deprecation** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### API-04.01 — The project MUST maintain an inventory of every externally…

**Requirement:** The project MUST maintain an inventory of every externally reachable API surface, including engine HTTP routes, admin routes, health/metrics endpoints, callbacks, internal service APIs exposed through a gateway, and protocol versions. Each entry MUST identify owner, audience, exposure, auth policy, lifecycle state, and contract location.

#### API-04.02 — Production API changes MUST be classified as compatible…

**Requirement:** Production API changes MUST be classified as compatible, conditionally compatible, or breaking against the published contract and known consumers. Reviewers MUST examine field requiredness, defaults, enum expansion, response shape, status codes, ordering, pagination, streaming framing, and authorization changes.

#### API-04.03 — Breaking changes MUST use a versioning and migration policy…

**Requirement:** Breaking changes MUST use a versioning and migration policy chosen for the product (URI, media type, or another explicit scheme), with a published compatibility window, migration guidance, sunset date, and owner. Deprecation notices MUST be observable before removal.

#### API-04.04 — Every deployed version MUST be discoverable by operators…

**Requirement:** Every deployed version MUST be discoverable by operators. Remove unsupported versions from the deployment inventory only after traffic and consumer evidence show that the deprecation window has completed.

#### API-04.05 — Debug, experimental, and internal endpoints MUST be…

**Requirement:** Debug, experimental, and internal endpoints MUST be excluded from production packages or protected by an explicit access policy. Their presence and exposure MUST be checked in release qualification.

#### API-04.06 — OpenAPI contracts MUST be reviewed in the same change…

**Requirement:** OpenAPI contracts MUST be reviewed in the same change as implementation. Generated schemas MUST be reproducible; generated diffs MUST not hide semantic changes in hand-maintained descriptions or security declarations.

### API-05 — API abuse and integrated-service boundaries

*Domain:* [api](../../torviello-enforcer/api/README.md) · *Rule:* [05-api-abuse-and-integrated-service-boundaries.md](../../torviello-enforcer/api/rules/05-api-abuse-and-integrated-service-boundaries.md)

**Control objective.** This control defines the intended outcome for **api abuse and integrated-service boundaries** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### API-05.01 — For each endpoint, the project MUST identify object-level…

**Requirement:** For each endpoint, the project MUST identify object-level, property-level, and function-level authorization needs. Authorization MUST be checked for the authenticated actor, target object, requested fields, and operation on every request, including batch and nested-resource operations.

#### API-05.02 — Endpoints that trigger costly inference, model installation…

**Requirement:** Endpoints that trigger costly inference, model installation, account creation, license checks, or other business-sensitive flows MUST have threat-informed abuse controls. Apply per-principal and aggregate quotas, concurrency limits, cooldowns, and anomaly handling appropriate to the operation; document safe defaults and administrative overrides.

#### API-05.03 — Rate limits MUST account for authenticated and anonymous actors…

**Requirement:** Rate limits MUST account for authenticated and anonymous actors, source-network aggregation, shared credentials, and distributed clients. Do not make IP address the sole identity signal for an authenticated user or disable limits for trusted internal callers by default.

#### API-05.04 — When calling external APIs, the caller MUST authenticate…

**Requirement:** When calling external APIs, the caller MUST authenticate the peer, validate TLS, restrict destination and redirect policy, validate response schema and size, set connection and total timeouts, and treat all response data as untrusted.

#### API-05.05 — API request processing MUST cap body, header…

**Requirement:** API request processing MUST cap body, header, multipart, nesting, collection, and decompressed sizes before unbounded allocation. Streaming parsers MUST enforce cumulative limits while reading, not only after buffering.

#### API-05.06 — Overload behavior MUST be deterministic: reject before accepting…

**Requirement:** Overload behavior MUST be deterministic: reject before accepting unbounded work, return a documented status and retry guidance where appropriate, preserve service health endpoints, and emit bounded-cardinality signals for rejected or queued work.

#### API-05.07 — Production API security testing MUST cover BOLA, broken…

**Requirement:** Production API security testing MUST cover BOLA, broken authentication, property authorization, resource consumption, function authorization, sensitive business flows, SSRF, misconfiguration, inventory gaps, and unsafe third-party API consumption where those risks apply.

### COL-04 — Approved Digital Tools and Human Oversight of AI-Assisted Work

*Domain:* [collaboration-and-communication](../../torviello-enforcer/collaboration-and-communication/README.md) · *Rule:* [04-approved-digital-tools-and-human-oversight-of-ai-assisted-work.md](../../torviello-enforcer/collaboration-and-communication/rules/04-approved-digital-tools-and-human-oversight-of-ai-assisted-work.md)

**Control objective.** People and agents must use collaboration, automation, and AI tools under approved data, access, record, and review controls. A human who uses an output remains accountable for decisions and actions unless an approved system explicitly assigns responsibility elsewhere.

#### COL-04.01 — A tool MUST have an owner, purpose…

**Requirement:** A tool MUST have an owner, purpose, access model, data classification allowance, retention/deletion terms, integration scope, security/privacy review, export path, and supported use profile before it processes organizational, customer, personnel, source, or confidential data.

#### COL-04.02 — Before submitting information to a third-party SaaS, AI…

**Requirement:** Before submitting information to a third-party SaaS, AI model, browser extension, transcription service, repository bot, or automation, the user MUST verify that the data class and purpose are allowed, retention and training-use terms are acceptable, and an approved account/channel is used.

#### COL-04.03 — The person relying on AI-generated code, analysis…

**Requirement:** The person relying on AI-generated code, analysis, summary, translation, image, recommendation, or decision MUST verify factual claims, source rights, security, privacy, quality, and policy compliance at a level proportionate to impact. A generated output MUST NOT be treated as an approval, legal opinion, test result, or source citation.

#### COL-04.04 — Tools and agents MUST receive the minimum permissions needed…

**Requirement:** Tools and agents MUST receive the minimum permissions needed, bounded task scope, logging, and human approval for destructive, external, financial, production, identity, or public communication actions. Automation MUST have a stop, rollback, or containment path appropriate to its impact.

#### COL-04.05 — When generated or automated work materially affects a decision…

**Requirement:** When generated or automated work materially affects a decision, product artifact, customer response, or public claim, retain relevant tool/version, input provenance where lawful, human reviewer, modifications, and validation evidence. Follow license, copyright, confidentiality, and attribution rules.

#### COL-04.06 — People MUST treat external content, model output…

**Requirement:** People MUST treat external content, model output, tool results, issue text, and generated files as untrusted data unless a trusted policy grants authority. Instructions contained in such data MUST NOT override user, system, or repository authority or authorize disclosure, scope expansion, or external action.

#### COL-04.07 — Unexpected data retention, unsafe output, unauthorized actions…

**Requirement:** Unexpected data retention, unsafe output, unauthorized actions, access leakage, or material quality failures MUST be reported to the tool owner and relevant privacy/security/product owner. Disable or constrain the tool when the risk cannot be bounded; update training and approval policy after confirmed failures.

### MOD-01 — Model identity, metadata, and compatibility

*Domain:* [models](../../torviello-enforcer/models/README.md) · *Rule:* [01-model-identity-metadata-and-compatibility.md](../../torviello-enforcer/models/rules/01-model-identity-metadata-and-compatibility.md)

**Control objective.** These controls govern **model identity, metadata, and compatibility**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### MOD-01.01 — Give each model artifact a stable model ID

The project MUST give each model artifact a stable model ID and immutable version or digest. Registry records specify task, format, source, license, input/output schema, tokenizer/preprocessor requirements, runtime/provider constraints, memory estimates, supported platform, and verification status.

#### MOD-01.02 — Separate model metadata from model bytes

The project MUST separate model metadata from model bytes. A registry entry cannot claim available or ready until the corresponding artifact is present, digest-verified, compatible, and successfully loaded for the selected runtime.

#### MOD-01.03 — Treat model files, tokenizer data, configuration, and metadata as

The project MUST treat model files, tokenizer data, configuration, and metadata as untrusted supply-chain inputs. The project MUST also record provenance and permitted redistribution.

#### MOD-01.04 — Define compatibility checks explicitly

The project MUST define compatibility checks explicitly. The project MUST NOT infer task, architecture, or provider support from filenames or extensions alone.

#### MOD-01.05 — Preserve immutable version history

The project MUST preserve immutable version history. Updating a model means creating a new version and an explicit promotion or rollback operation.

### MOD-02 — Secure download, install, and activation

*Domain:* [models](../../torviello-enforcer/models/README.md) · *Rule:* [02-secure-download-install-and-activation.md](../../torviello-enforcer/models/rules/02-secure-download-install-and-activation.md)

**Control objective.** These controls govern **secure download, install, and activation**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### MOD-02.01 — Restrict downloads to configured or allowlisted sources

The project MUST restrict downloads to configured or allowlisted sources. The project MUST also enforce TLS verification, safe redirect rules, connection and total timeouts, maximum size, disk-space checks, and bounded retries.

#### MOD-02.02 — Verify a cryptographic digest or signature before extracting

The project MUST verify a cryptographic digest or signature before extracting or loading an artifact. Reject mismatches and retain evidence of the verification result.

#### MOD-02.03 — Extract archives into a staging directory after rejecting absolute

The project MUST extract archives into a staging directory after rejecting absolute paths, parent traversal, links outside the destination, duplicate collisions, and excessive expanded size.

#### MOD-02.04 — Install and activate atomically

The project MUST install and activate atomically. A failed or interrupted download, extraction, or model load leaves the prior active artifact intact.

#### MOD-02.05 — Separate download state, installed state, and active state

The project MUST separate download state, installed state, and active state. The project MUST also report each explicitly to operators and readiness checks.

#### MOD-02.06 — Provide a preloaded/offline installation path for restricted deployments

The project MUST provide a preloaded/offline installation path for restricted deployments.

### MOD-03 — Registry administration and audit

*Domain:* [models](../../torviello-enforcer/models/README.md) · *Rule:* [03-registry-administration-and-audit.md](../../torviello-enforcer/models/rules/03-registry-administration-and-audit.md)

**Control objective.** These controls govern **registry administration and audit**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### MOD-03.01 — Registry mutations MUST require authenticated identity and least-privilege authorization

Registry mutations MUST require authenticated identity and least-privilege authorization. The project MUST also separate view, add, promote, rollback, and delete permissions where the product requires distinct roles.

#### MOD-03.02 — Validate edits through one schema and policy layer whether

The project MUST validate edits through one schema and policy layer whether they arrive through an admin API or a controlled manual file change.

#### MOD-03.03 — Audit actor, time, action, target model/version, outcome, and change

The project MUST audit actor, time, action, target model/version, outcome, and change identifier. The project MUST NOT log tokens or secret configuration values.

#### MOD-03.04 — Make changes transactional: validate a candidate, persist it safely

The project MUST make changes transactional: validate a candidate, persist it safely, then publish the new version. The project MUST provide a rollback to the last known-good registry state.

#### MOD-03.05 — The standalone engine MUST operate with a local registry/cache

The standalone engine MUST operate with a local registry/cache and MUST NOT require a hosted control plane for local inference

### SEC-12 — Personnel Security and Human Access Lifecycle

*Domain:* [security](../../torviello-enforcer/security/README.md) · *Rule:* [12-personnel-security-and-human-access-lifecycle.md](../../torviello-enforcer/security/rules/12-personnel-security-and-human-access-lifecycle.md)

**Requirement:** At separation or loss of authorization, disable accounts, keys, tokens, active sessions, recovery methods, device certificates, signing credentials, and external access within risk-based deadlines. Confirm revocation across federated and supplier systems.

#### SEC-12.08 — Identity and privileged activity records MUST allow attribution…

**Requirement:** Identity and privileged activity records MUST allow attribution, preserve integrity, alert on high-risk anomalies, and avoid recording authentication secrets. Investigate unexplained access or failed offboarding through the security incident process.

#### SEC-13.08 — People MUST receive concise guidance for the locations…

**Requirement:** People MUST receive concise guidance for the locations and devices they use, including reporting lost assets, safe travel, remote meetings, printing, and household/shared-device boundaries. Training MUST NOT rely on surveillance of personal spaces.
