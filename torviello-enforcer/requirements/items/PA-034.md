# PA-034 — Atomic design shall be applied as a vocabulary for reusable UI composition and shall not override cohesion, accessibility, ownership, or maintainability

**Requirement ID:** PA-034  
**Priority:** MUST  
**Source:** [product-and-architecture.md](../product-and-architecture.md) — User-facing surfaces  
**Status:** Active requirement; no implementation or evaluation evidence is recorded in this repository.  
**Rule controls:** DOC-07, MEDIA-04  
**Acceptance checks:** None recorded  
**Open decisions:** None recorded

## 1. Normative requirement

Atomic design shall be applied as a vocabulary for reusable UI composition and shall not override cohesion, accessibility, ownership, or maintainability.

## 2. Why this requirement exists

This requirement is part of **User-facing surfaces** in [product-and-architecture.md](../product-and-architecture.md). It is traced to 2 rule control(s): DOC-07, MEDIA-04. Those controls state the following purpose:

- **DOC-07 — Atomic component conventions:** Give teams a shared, practical component vocabulary and extraction method that supports reuse, consistency, accessibility, and independent maintenance without turning the atomic metaphor into arbitrary foldering or over-fragmentation.
- **MEDIA-04 — Production code, assets, and website integration:** Treat video creation automation, large assets, and website playback as maintained product work with clear boundaries, reproducible outputs, quality gates, accessibility, privacy, and operational ownership.

Acceptance is not satisfied by citing these controls. The implementation must demonstrate the observable result in section 6, and the mapped rule clauses in section 5 define what must hold at the enforcement boundary.

## 3. Priority and interpretation

This requirement has **MUST** priority under the repository's requirement conventions. A MUST requirement is needed for the stated product direction or a safe release. A SHOULD requirement is expected unless a documented tradeoff justifies deferral. A COULD requirement is a candidate capability that requires product or technical validation. Acceptance describes observable evidence; it does not mandate a specific implementation unless the requirement says so.

## 4. Scope and applicability

This requirement belongs to **User-facing surfaces** in [product-and-architecture.md](../product-and-architecture.md). It applies to the product area named by that source section and to every implementation, interface, release artifact, document, or operation that claims to satisfy it.

The mapped controls add the following applicability boundaries:

- **DOC-07:** Applies to visual components in web/application UI and design-system packages. Domain modules and services follow architecture controls; the word “atomic” does not require every code concept to be a UI atom or a separate file/package.
- **MEDIA-04:** Applies when video production uses scripts, source code, render frameworks, command-line tools, plugins, templates, CI, asset storage, a website player/embed, or automated publication. Also applies to manual workflows where asset and export consistency require controlled configuration.

The source requirement table remains authoritative if this view and the source disagree.

### DOC-07 — Atomic component conventions

*Domain:* [documentation-and-design](../../torviello-enforcer/documentation-and-design/README.md) · *Rule:* [07-atomic-component-conventions.md](../../torviello-enforcer/documentation-and-design/rules/07-atomic-component-conventions.md)

**Control objective.** Give teams a shared, practical component vocabulary and extraction method that supports reuse, consistency, accessibility, and independent maintenance without turning the atomic metaphor into arbitrary foldering or over-fragmentation.

#### DOC-07.01 — Classify by responsibility and composition, not size alone

Use atomic-design terms as descriptive levels: **tokens/primitives** are design values and native/basic elements; **atoms** are small styled controls with one UI responsibility; **molecules** combine a few primitives into a coherent reusable interaction; **organisms** form a substantial region with a clear user purpose; **templates** arrange regions/content slots into a page structure; **pages** bind a template to real route data, permissions, and states. Teams MAY adapt names, but MUST document equivalent levels consistently. A small component is not automatically an atom, and a large component is not automatically an organism.

#### DOC-07.02 — Extract a shared component only for a demonstrated boundary

Create a shared component when repeated use, a stable semantic interaction, a design-system invariant, or independent ownership makes reuse valuable. Before extraction, identify callers, common behavior, variation points, accessibility contract, and owner. Keep one-off domain logic local until a second real use or a stable cross-feature contract justifies sharing. Do not create “generic” components with many flags for unrelated use cases; split when callers require conflicting semantics or state models.

#### DOC-07.03 — Give every reusable component a narrow contract

Document purpose, semantic element/role, public props/slots/events, controlled versus internal state, defaults, valid combinations, keyboard behavior, accessible name/value/state, loading/error/disabled behavior, styling/token extension points, and unsupported use. Props MUST express domain meaning rather than leak implementation details. Use composition and typed variants for intentional differences; avoid boolean-prop combinations that create invalid or unexplained states.

#### DOC-07.04 — Keep state and business rules at the correct level

Place transient presentation state at the smallest owner that MUST coordinate it. Place workflow or domain state in the feature/page/controller layer with explicit transitions and data ownership. Reusable primitives MUST NOT secretly fetch feature-specific data, own global session state, or make authorization decisions. Do not duplicate authoritative validation in UI as a substitute for server/domain enforcement.

#### DOC-07.05 — Preserve semantic/accessibility behavior through composition

Components MUST compose into valid document semantics and retain keyboard/focus order, labels, descriptions, error associations, announcements, contrast, and target behavior. Components that render interactive content MUST not nest interactive controls or hide focus. Provide slots/composition where callers need meaningful headings or actions rather than accepting opaque markup that defeats semantics. Accessibility is tested on the composed page, not only the isolated component.

#### DOC-07.06 — Co-locate implementation evidence and examples

For each reusable component family, keep implementation, tests, usage examples/stories, and design documentation in the established owning location. Demonstrate default, variant, responsive, empty, loading, disabled, invalid, permission-limited, and failure states as applicable. Examples MUST be realistic and accessible, and MUST NOT rely on production secrets or private data.

#### DOC-07.07 — Use explicit promotion, change, and deprecation rules

Promote a feature-local component into the shared system only after review of reuse, API stability, owner, accessibility, and migration cost. Changes to shared props, tokens, semantics, or visuals require impact analysis across consumers and version/release coordination. Deprecate with replacement guidance and removal timing; avoid silent breaking changes. Remove unused components after checking dynamic references and documented consumers.

#### DOC-07.08 — Organize files around ownership and discoverability

Use the repository’s established naming and directory conventions. Group components by product/domain or stable design-system ownership, not by atomic level alone when that fragments feature context. A dedicated `atoms/`, `molecules/`, `organisms/` hierarchy MAY be used only when it improves discovery and ownership; it MUST NOT become a required taxonomy that forces awkward placement. Keep public exports intentional and prevent cross-feature imports of private implementation files.

### MEDIA-04 — Production code, assets, and website integration

*Domain:* [media-production](../../torviello-enforcer/media-production/README.md) · *Rule:* [04-production-code-and-web-integration.md](../../torviello-enforcer/media-production/rules/04-production-code-and-web-integration.md)

**Control objective.** Treat video creation automation, large assets, and website playback as maintained product work with clear boundaries, reproducible outputs, quality gates, accessibility, privacy, and operational ownership.

#### MEDIA-04.01 — Select tools by production needs and lifecycle cost

Before choosing an editor/render framework or automation, compare the actual work: manual editing versus data-driven/programmatic scenes; number of repeated variants/locales; timeline/audio requirements; collaboration/review; preview speed; deterministic rendering; format/codec support; accessibility sidecars; platform availability; licenses; security/update posture; hardware/GPU needs; offline use; CI duration/cost; and skill/maintenance burden. Keep creative editing tools where they provide needed timing and judgment; use code-driven rendering when reusable data/templates and reproducible variants justify it. Do not adopt a framework or AI media tool solely because it is available or popular. Record decision owner, tested prototype, alternatives, limitations, and reconsideration triggers.

#### MEDIA-04.02 — Give media production a separate monorepo boundary

When production workflows are maintained in this repository, use a dedicated `media/` product area with its own `README.md` and `AGENTS.md`, toolchain/lockfiles, scripts, tests, asset policy, build instructions, and ownership. It MUST NOT be a dependency of the inference engine’s build, runtime, install, or release profiles. Define explicit interfaces to shared brand assets or website packages; avoid cross-area private imports and toolchain coupling. The `media/` owner MUST maintain a supported build/render entry point and document required licenses, hardware, and external inputs.

#### MEDIA-04.03 — Organize work products for discoverability and safe revision

Use a documented layout equivalent to: `brand/` for approved style guide/tokens; `templates/` for content-type templates and reusable scene components; `projects/<video-id>/` for brief, script, storyboard, claims, rights manifest, and edit/render config; `assets/` for approved shared source media; `automation/` for render, QC, and packaging code; and `releases/<video-id>/<version>/` or an approved artifact store for release manifests and outputs. Large binaries MUST use an approved large-file or artifact store with stable IDs/checksums and access controls rather than silently bloating ordinary source history. Keep project-specific raw footage segregated and access-limited.

#### MEDIA-04.04 — Represent automated scenes as typed, validated inputs

For programmatic video, model scenes, durations, assets, narration, captions, transitions, and output profiles in a validated schema. Give each scene a stable identifier and explicit required/optional assets, timing, locale, and accessibility text. Fail early with actionable diagnostics for missing media, unsupported dimensions, unresolved fonts, invalid time ranges, unlicensed inputs, missing captions, or contradictory project settings. Avoid arbitrary code evaluation or unchecked paths in user-editable project manifests; treat asset paths and project input as untrusted data. Keep rendering deterministic where the toolchain permits and disclose nondeterministic codecs/metadata.

#### MEDIA-04.05 — Pin and inventory production dependencies

Record editor/render-tool versions, plugins, fonts, codecs, templates, scripts, model/AI services if used, and licenses. Pin automated build dependencies and verify downloaded tools/assets; store required binaries in the approved cache/mirror for offline production when offline repeatability is a project requirement. Identify end-of-life/deprecated formats and test migration. Do not promise bit-identical output when codecs, hardware encoders, timestamps, or external services prevent it; define the reproducibility level and verify content/metadata checksums appropriately.

#### MEDIA-04.06 — Build a layered validation pipeline

A production pipeline MUST support separate fast checks and full render/QC. At minimum, validate: project manifest/schema; required sources and rights metadata; broken/missing media and font dependencies; safe paths and secrets; script/claims references; caption and transcript existence and timing; render dimensions/duration/frame rate/codec/color/audio profile; audio/video synchronization; loudness/peak limits for chosen target; black/silent/frozen frames where relevant; output integrity; and playback. Add visual snapshot or representative frame review only as supporting evidence; it cannot replace watching the complete final video. Store machine-readable QC report linked to source revision and render artifact.

#### MEDIA-04.07 — Make builds and renders resource-bounded and resumable

Specify expected render time/storage/GPU/CPU and maximum source dimensions/duration per profile. Provide progress, cancellation, safe temporary-file cleanup, disk-space checks, retry behavior, and recovery from interrupted render without corrupting approved outputs. Bound parallel encodes to available resources. A release render MUST be distinguishable from a preview and MUST NOT overwrite an approved artifact without a new version and review.

#### MEDIA-04.08 — Define explicit delivery profiles and manifests

Maintain versioned profiles for intended destinations rather than one universal export. Each profile defines container, video/audio codecs, dimensions/aspect ratio, frame rate, color space/HDR policy, bitrate or quality mode, audio layout/loudness target, captions, thumbnail, metadata, and validation commands. Record profile version, source revision, toolchain versions, output checksum, and destination requirements in a release manifest. Recheck external destination specifications at release time; keep archived master settings separate from delivery transcodes.

#### MEDIA-04.09 — Integrate video into websites as an accessible, privacy-aware component

A website video component MUST include a poster/thumbnail, descriptive title, playback controls, caption tracks, transcript or equivalent text path, accessible keyboard/focus behavior, responsive sizing, fallback/error behavior, and no autoplay with sound. Provide a local/first-party player or click-to-load consent pattern when third-party embeds would set cookies, load trackers, or contact external domains before user interaction. Lazy-load noncritical media, reserve layout space to prevent layout shift, and do not make video the sole means to understand the page or complete a task. Record supported formats, caption languages, privacy behavior, and fallback.

#### MEDIA-04.10 — Release and operate the production system safely

Deploy production tooling and website changes through their owning release controls. Restrict credentials, signing keys, publication tokens, and private raw media to least privilege; use secret stores rather than project config. Publish only approved release manifests. Monitor render failures, storage saturation, artifact integrity, player failures, accessibility reports, and broken links at a level proportionate to use. Define rollback for website/player releases, disable/revoke publication credentials on compromise, and provide a manual fallback procedure if the render or hosting pipeline is unavailable.

#### MEDIA-04.11 — Test behavior at unit, integration, and release seams

Test scene/schema parsing and timeline calculations as unit tests; test asset resolution, caption association, and render invocation as integration tests; and test representative full renders and playback as release checks. Include malformed manifests, missing assets/fonts, unsupported profile, cancellation, disk exhaustion, encoder/tool failure, caption mismatch, and privacy/embed behavior as applicable. Use tiny synthetic fixtures in CI; reserve full-quality renders for scheduled or release workflows. Document hardware and resource prerequisites; report skipped GPU or platform checks honestly.


### 5.1 Implementation guidance

- **DOC-07:** 
- **MEDIA-04:** Use the production-code path only when the expected repeatability, volume, localization, validation, or maintenance benefit exceeds toolchain and CI cost. Keep the human-editable source, content/claims, reusable visual components, and output settings independently reviewable. The approved rendered video remains the deliverable; code and successful rendering alone do not prove that the content is accurate, accessible, or fit to publish.

### 5.2 Assessment determination

- **DOC-07:** Pass when component boundaries are cohesive, contracts and states are explicit, reuse is justified, and composed usage remains accessible and maintainable. Fail when categories dictate placement regardless of responsibility, generic APIs hide incompatible use, or the component breaks page-level semantics. Not applicable requires scope and rationale.
- **MEDIA-04:** Pass when production tools and assets are isolated, understandable, validated, reproducible to the stated level, resource-bounded, and integrated accessibly and privately. Fail when source/tool provenance is missing, release output cannot be traced, engine builds depend on media tooling, critical failures go undetected, or website playback excludes users or violates privacy expectations. Not applicable requires that no code/tool/site integration is used and an owner documents the manual control path.

### 5.3 Exceptions and nonconformance

- **DOC-07:** A MUST exception requires the design-system owner and affected product-area owner. Record scope, reason, accessibility/maintenance impact, migration or revisit trigger, and expiry where temporary.
- **MEDIA-04:** A MUST exception requires the media engineering owner plus affected website, security/privacy, release, accessibility, or licensing authority. Record scope, tool/profile, residual risk, mitigation, owner, and expiry. An exception cannot permit publication of unlicensed content or undisclosed sensitive data.

## 8. Prohibited conditions

The following conditions are explicitly prohibited by the mapped controls. Any one of them is sufficient to fail the requirement.

- [DOC-07] One-file-per-element or one-package-per-control fragmentation without a real independent boundary.
- [DOC-07] Shared components that conceal network calls, authorization, business workflows, or hidden global state.
- [DOC-07] A component API whose combinations permit invalid states or whose generic styling bypasses design tokens.
- [DOC-07] Atomic category labels used as a substitute for clear responsibility, ownership, tests, or accessibility.
- [MEDIA-04] Coupling video rendering or marketing site dependencies into the inference engine’s build/runtime by convenience.
- [MEDIA-04] Publishing artifacts with no source revision, delivery profile, checksum, rights record, or QC outcome.
- [MEDIA-04] Passing an automated QC report as a substitute for human review of narrative, accuracy, accessibility, and complete playback.
- [MEDIA-04] Loading third-party players or trackers before required consent/privacy behavior is implemented.
- [MEDIA-04] Embedding secrets or publication credentials in source, project files, URLs, or logs.
