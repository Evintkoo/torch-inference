# ENG-012 — Proxy assistant traffic without inventing compatibility

**Requirement ID:** ENG-012  
**Priority:** SHOULD  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-18](../../../torviello-engine/specifications/checks/AC-ENG-18.md)  
**Rule controls:** API-05, API-03, SEC-08

## 1. Normative requirement

The optional assistant surface MUST forward declared OpenAI-compatible requests to a configured upstream with bounded bodies and deadlines, preserve streaming framing, distinguish upstream failure from local inference failure, and remain absent or explicitly unconfigured when no upstream exists.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

LLM chat is a different product boundary from the local inference engine. The reference implementation forwards `/llm/*` to a loopback microservice, exposes an OpenAI-compatible model list, and supports SSE streaming for chat completions. Treating that proxy as part of the engine's own inference contract would conflate two availability and security domains.

Torviello specifies the proxy as an optional adapter: it must not fabricate OpenAI behavior, must not require the upstream for local inference, and must report upstream absence and failure with distinct codes. This keeps local mode honest and makes hosted composition a configuration choice.

## 3. Priority and interpretation

This requirement is **SHOULD**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to `/llm/{tail}`, `/v1/models`, any versioned assistant aliases, and the optional upstream configuration. It covers request and response forwarding, streaming, timeout, body limits, and error translation. It does not define LLM model quality or prompt policy.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Require an explicit upstream configuration before exposing assistant behavior; otherwise return upstream.not_configured without an outbound call.
- Forward the declared method, path, query, body, and relevant headers without rewriting semantics.
- Bound proxied request and response bodies and apply a configured upstream deadline.
- Preserve server-sent event framing and stream without buffering the complete upstream response.
- Translate connection, timeout, and upstream 5xx failures into distinct stable errors without masking the upstream status when it is meaningful.
- Propagate a correlation identifier to the upstream and include it in local logs.
- Keep assistant availability independent from local classification, speech, and detection capabilities.

#### API-05.01 — For each endpoint, the project MUST identify object-level…

**Requirement:** For each endpoint, the project MUST identify object-level, property-level, and function-level authorization needs. Authorization MUST be checked for the authenticated actor, target object, requested fields, and operation on every request, including batch and nested-resource operations.

#### API-05.02 — Endpoints that trigger costly inference, model installation…

**Requirement:** Endpoints that trigger costly inference, model installation, account creation, license checks, or other business-sensitive flows MUST have threat-informed abuse controls. Apply per-principal and aggregate quotas, concurrency limits, cooldowns, and anomaly handling appropriate to the operation; document safe defaults and administrative overrides.

#### API-05.03 — Rate limits MUST account for authenticated and anonymous actors…

**Requirement:** Rate limits MUST account for authenticated and anonymous actors, source-network aggregation, shared credentials, and distributed clients. Do not make IP address the sole identity signal for an authenticated user or disable limits for trusted internal callers by default.

#### API-05.04 — When calling external APIs, the caller MUST authenticate…

**Requirement:** When calling external APIs, the caller MUST authenticate the peer, validate TLS, restrict destination and redirect policy, validate response schema and size, set connection and total timeouts, and treat all response data as untrusted.

#### API-05.05 — API request processing MUST cap body, header…

**Requirement:** API request processing MUST cap body, header, multipart, nesting, collection, and decompressed sizes before unbounded allocation. Streaming parsers MUST enforce cumulative limits while reading, not only after buffering.

#### API-05.06 — Overload behavior MUST be deterministic: reject before accepting…

**Requirement:** Overload behavior MUST be deterministic: reject before accepting unbounded work, return a documented status and retry guidance where appropriate, preserve service health endpoints, and emit bounded-cardinality signals for rejected or queued work.

#### API-05.07 — Production API security testing MUST cover BOLA, broken…

**Requirement:** Production API security testing MUST cover BOLA, broken authentication, property authorization, resource consumption, function authorization, sensitive business flows, SSRF, misconfiguration, inventory gaps, and unsafe third-party API consumption where those risks apply.

#### API-03.01 — The API MUST use HTTP methods and status codes…

**Requirement:** The API MUST use HTTP methods and status codes according to their defined semantics; a response status MUST accurately report whether the requested operation completed, was accepted for asynchronous processing, failed validation, lacked authorization, or failed in the service.

#### API-03.02 — An operation that can be retried MUST define idempotency…

**Requirement:** An operation that can be retried MUST define idempotency behavior. For non-idempotent writes, the API MUST accept a caller-supplied idempotency key or provide another documented deduplication mechanism, scope the key to the authenticated principal and operation, retain it for a documented period, and return the original outcome for a duplicate request.

#### API-03.03 — Retries MUST be safe under the endpoint contract…

**Requirement:** Retries MUST be safe under the endpoint contract. Clients MUST NOT blindly retry non-idempotent requests; servers MUST bound retryable work and expose Retry-After only when the service can honor the stated delay.

#### API-03.04 — Pagination MUST use stable ordering and bounded page size…

**Requirement:** Pagination MUST use stable ordering and bounded page size. Cursor-based pagination SHOULD be used when concurrent inserts or deletes can make offset pagination skip or repeat records; cursors MUST be opaque, integrity-protected when they encode state, and scoped to the caller and query.

#### API-03.05 — Long-running inference and model-management operations MUST define synchronous versus…

**Requirement:** Long-running inference and model-management operations MUST define synchronous versus asynchronous behavior, request identity, status transitions, result expiry, cancellation, and duplicate-submission handling.

#### API-03.06 — HTTP caching MUST be explicit for authenticated, user-specific…

**Requirement:** HTTP caching MUST be explicit for authenticated, user-specific, model, and administrative responses. Responses containing secrets or sensitive inference data MUST use no-store or an approved stricter policy; shared caches MUST NOT reuse them across principals.

#### API-03.07 — Content negotiation and compression MUST have explicit supported media…

**Requirement:** Content negotiation and compression MUST have explicit supported media types and size limits. The service MUST reject unsupported request and response encodings safely and MUST NOT allow compressed-size limits to be bypassed by decompression expansion.

#### SEC-08.01 — Every listener MUST declare intended interface, audience…

**Requirement:** Every listener MUST declare intended interface, audience, authentication policy, TLS termination point, proxy trust, allowed origins, and firewall assumptions for each deployment profile.

#### SEC-08.02 — Loopback-only local mode MUST bind to loopback and MUST…

**Requirement:** Loopback-only local mode MUST bind to loopback and MUST reject or clearly warn when configuration exposes it to a non-loopback interface without an explicit network-exposure policy.

#### SEC-08.03 — Production network traffic carrying credentials, user data…

**Requirement:** Production network traffic carrying credentials, user data, model metadata with access impact, or administrative changes MUST use authenticated TLS with validated peer identity and supported protocol/cipher policy.

#### SEC-08.04 — Proxy-derived identity and forwarding headers MUST be trusted only…

**Requirement:** Proxy-derived identity and forwarding headers MUST be trusted only from configured proxy hops. The service MUST ignore spoofed forwarded headers from direct clients.

#### SEC-08.05 — CORS MUST use explicit origins, methods, headers…

**Requirement:** CORS MUST use explicit origins, methods, headers, and credential policy. Wildcard origins MUST NOT be combined with credentials; browser security headers and cache policy MUST match the UI/API threat model.

#### SEC-08.06 — Outbound connections MUST use destination allowlists where feasible…

**Requirement:** Outbound connections MUST use destination allowlists where feasible, validate DNS results and redirects, block prohibited address ranges, and revalidate after redirect or DNS change to resist SSRF and rebinding.

#### SEC-08.07 — DNS, proxy, TLS, certificate-expiry…

**Requirement:** DNS, proxy, TLS, certificate-expiry, and upstream timeout failures MUST be observable and fail safely without falling back to plaintext or an untrusted endpoint.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** OWASP API Security Top 10 2023 (API7 SSRF), OWASP ASVS 5.0.0 Level 3, RFC 9110, OpenTelemetry 1.44.0, IETF BCP 14.

- The upstream base URL MUST come from validated operator configuration; no client field may select an arbitrary scheme, host, port, or redirect target.
- Upstream credentials MUST remain server-side and MUST NOT appear in client responses, logs, metrics, events, or traces.
- Connect, header, first-byte, inter-chunk, and total deadlines MUST be enforced; retries MUST be bounded and limited to idempotent, retryable failures.
- Streaming framing and backpressure MUST be preserved, and upstream unavailability MUST NOT change local readiness.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- A healthy upstream chat completion passes through with its status and JSON body.
- A streaming request forwards events incrementally and ends when the upstream closes.
- An unreachable upstream returns 503 upstream.unavailable while local inference remains healthy.
- An unconfigured assistant surface returns 404 upstream.not_configured without network activity.
- An oversized proxied body returns 413 before forwarding.
- Local logs include the upstream request ID and never include prompt content.

Acceptance checks: [AC-ENG-18](../../../torviello-engine/specifications/checks/AC-ENG-18.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- An SSRF corpus MUST cover arbitrary hosts, private and link-local addresses, redirects, DNS rebinding, userinfo, encoded hosts, and unsupported schemes.
- Upstream chaos MUST cover delay, reset, malformed response, partial stream, 4xx, 5xx, and credential rejection.
- Egress capture MUST show no connection except to the configured upstream and no credential in any emitted artifact.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Implement the proxy as an explicit outbound adapter with a configured base URL and deadline. Validate and size-gate the request before opening a connection. Stream response bytes through a bounded channel. Keep upstream error mapping in one module and keep the assistant router disabled when configuration is absent.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not claim OpenAI compatibility for routes the proxy cannot forward.
- Do not require the assistant upstream for engine readiness.
- Do not buffer an unbounded upstream stream in memory.
- Do not expose upstream credentials or internal hostnames in responses.
- Do not log prompt or completion content.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Start a stub upstream and send a non-streaming and a streaming completion.
- 2. Stop the upstream and repeat, then run a local inference request.
- 3. Remove the upstream configuration and call the assistant route.
- 4. Send an oversized body and inspect the upstream request log.
- 5. Inspect correlation and redaction in local logs.
- 6. Record configuration, requests, responses, and upstream observations.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Replay the SSRF and redirect corpus and record every attempted destination.
- 10. Run the upstream chaos matrix and inspect stream termination and local readiness.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Pass-through status and body for non-streaming and streaming requests.
- Upstream failure response and local inference health during the failure.
- Unconfigured response with no outbound connection.
- Body-limit rejection before forwarding.
- Redacted log records with correlation identifiers.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The SSRF and redirect test report with blocked destinations.
- The upstream chaos matrix and local readiness timeline.
- Header and artifact inspection showing no credential disclosure.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- The proxy rewrites or fabricates response semantics.
- Streaming is fully buffered or framing changes.
- Upstream failure makes the engine unhealthy or blocks local inference.
- Unconfigured routes attempt an outbound connection.
- Prompt content or credentials appear in logs.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- A client can influence the upstream destination or follow an unapproved redirect.
- An upstream credential appears in any response or telemetry.
- Upstream failure changes local inference readiness.
