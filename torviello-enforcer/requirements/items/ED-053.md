## 1. Normative requirement

Implementation shall be driven by failing tests for approved behaviors and edge cases (TDD), with unit, contract, and integration tests kept in their categories.

## 2. Why this requirement exists

This requirement is part of **Development workflow (DDD → SDD → CDD → TDD → EDD)** in [engineering-and-delivery.md](../engineering-and-delivery.md). It is traced to 1 rule control(s): GOV-09. Those controls state the following purpose:

- **GOV-09 — Test-Driven Development (TDD):** Test-Driven Development verifies correctness while implementation proceeds. Approved behaviors and edge cases MUST be driven by failing tests through the RED → GREEN → REFACTOR cycle, with unit, contract, and integration tests kept in their categories. For interface changes, contract-first ordering MUST hold: the contract is approved before tests, and failing tests exist before implementation. A passing run on a weakened, skipped, or deleted test MUST NOT count as verification.

Acceptance is not satisfied by citing these controls. The implementation must demonstrate the observable result in section 6, and the mapped rule clauses in section 5 define what must hold at the enforcement boundary.

## 3. Priority and interpretation

This requirement has **MUST** priority under the repository's requirement conventions. A MUST requirement is needed for the stated product direction or a safe release. A SHOULD requirement is expected unless a documented tradeoff justifies deferral. A COULD requirement is a candidate capability that requires product or technical validation. Acceptance describes observable evidence; it does not mandate a specific implementation unless the requirement says so.

## 5. Detailed obligations

Each subsection below is the complete normative content of a mapped control. A requirement is not satisfied by selecting one convenient clause; every applicable clause must hold, including its negative and boundary behavior.

### GOV-09 — Test-Driven Development (TDD)

*Domain:* [governance](../../torviello-enforcer/governance/README.md) · *Rule:* [09-test-driven-development.md](../../torviello-enforcer/governance/rules/09-test-driven-development.md)

**Control objective.** Test-Driven Development verifies correctness while implementation proceeds. Approved behaviors and edge cases MUST be driven by failing tests through the RED → GREEN → REFACTOR cycle, with unit, contract, and integration tests kept in their categories. A passing run on a weakened, skipped, or deleted test MUST NOT count as verification.

#### GOV-09.01 — Each approved behavior and edge case MUST be driven by a test…

**Requirement:** Each approved behavior and edge case MUST be driven by a test that fails for the right reason before the implementation exists (RED), then passes after the minimal implementation (GREEN), and remains passing through refactoring (REFACTOR). The cycle MAY repeat per behavior, but the failing-first evidence MUST exist.

#### GOV-09.02 — Unit, contract, integration, and end-to-end tests MUST be kept…

**Requirement:** Unit, contract, integration, and end-to-end tests MUST be kept in their dedicated categories and MUST be independently selectable with documented prerequisites. A monolith test command that cannot isolate a category is insufficient.

#### GOV-09.03 — Tests MUST be deterministic and MUST NOT depend on…

**Requirement:** Tests MUST be deterministic and MUST NOT depend on unbounded sleeps, external networks, shared mutable state, or ordering between tests. Flaky, skipped, or quarantined tests MUST be reported and MUST NOT be counted as passing evidence.

#### GOV-09.04 — Contract and integration behavior MUST be verified by…

**Requirement:** Contract and integration behavior MUST be verified by tests that exercise the approved contract and its error paths, not only the happy path. Model, hardware, or environment-dependent tests MUST state their prerequisites and MUST NOT silently skip on unsupported environments.

#### GOV-09.05 — Tests MUST NOT be weakened, skipped, deleted, or made…

**Requirement:** Tests MUST NOT be weakened, skipped, deleted, or made non-asserting to make a change pass. Such a change REQUIRES human authority and MUST be recorded with the affected requirement and the reason; a green run on a weakened test MUST NOT be reported as verification.

#### GOV-09.06 — Every test MUST be traceable to a requirement, specification, or…

**Requirement:** Every test MUST be traceable to a requirement, specification, or contract, and the repository MUST record the command and result used to produce the passing evidence. Coverage claims MUST name the tests and the scope they cover.

#### GOV-09.07 — Contract-first ordering MUST precede failing-first implementation…

**Requirement:** For interface changes, failing-first tests MUST be written against the approved contract before implementation begins. Tests MUST NOT be used to discover or retroactively define the contract; a test whose expectations are absent from the contract MUST be rejected until the contract is updated and approved. The mandatory order is contract → failing test → implementation.


### 5.1 Implementation guidance

- **GOV-09:** Commit the failing test before the implementation when practical. Keep test names carrying the requirement identifier and the behavior, so coverage and traceability are mechanical.

### 5.2 Assessment determination

- **GOV-09:** The control passes only when approved behaviors have failing-first tests, required categories are independently selectable, tests are deterministic and traceable, and the recorded commands and results show them passing without weakening. Missing failing-first evidence, non-deterministic tests, or weakened tests are failures.

### 5.3 Exceptions and nonconformance

- **GOV-09:** An exception MUST identify the affected clauses, reason, risk, compensating controls, accountable approver, remediation owner, and expiry/review date, and MUST be recorded in the assurance register before it is effective. A change that passes only because a test was weakened is nonconforming and MUST NOT be reported as passing.

## 8. Prohibited conditions

The following conditions are explicitly prohibited by the mapped controls. Any one of them is sufficient to fail the requirement.

- [GOV-09] Writing implementation first and adding tests that cannot fail afterward.
- [GOV-09] Deleting, skipping, or narrowing assertions to obtain a green run.
- [GOV-09] Counting a flaky test, a quarantined test, or a skipped test as verification.
- [GOV-09] Running a single undifferentiated test command that cannot select the required category.
- [GOV-09] Claiming verification without recording the command and result that produced it.
