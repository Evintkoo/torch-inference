### CHG-04 — Emergency changes and risk acceptance

*Domain:* [change-management](../../torviello-enforcer/change-management/README.md) · *Rule:* [04-emergency-changes-and-risk-acceptance.md](../../torviello-enforcer/change-management/rules/04-emergency-changes-and-risk-acceptance.md)

**Control objective.** This control defines the intended outcome for **emergency changes and risk acceptance** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### CHG-04.01 — Emergency changes MUST be limited to restoring service…

**Requirement:** Emergency changes MUST be limited to restoring service, containing an active security risk, or preventing imminent data loss. The incident or risk identifier, affected scope, owner, and reason MUST be recorded before or during the change.

#### CHG-04.02 — An emergency change MUST use the smallest viable patch…

**Requirement:** An emergency change MUST use the smallest viable patch, retain required independent review where practicable, run focused regression and security checks, and record any check that could not run before deployment.

#### CHG-04.03 — Every emergency change MUST receive a retrospective review within…

**Requirement:** Every emergency change MUST receive a retrospective review within the project-defined response window. The review MUST assess why normal planning was bypassed, validate the deployed diff, add missing tests/documentation, and close or assign follow-up risks.

#### CHG-04.04 — Risk acceptance MUST name an accountable owner with authority…

**Requirement:** Risk acceptance MUST name an accountable owner with authority over the affected product or system, describe threat/scenario and impact, define compensating controls, name a remediation owner, set an expiry, and specify what event triggers earlier re-review.

#### CHG-04.05 — Exceptions MUST be scoped to exact controls, services…

**Requirement:** Exceptions MUST be scoped to exact controls, services, packages, versions, and environments. A general waiver MUST NOT silently cover future changes or newly discovered risks.

#### CHG-04.06 — Expired or materially invalidated exceptions MUST be treated as…

**Requirement:** Expired or materially invalidated exceptions MUST be treated as nonconformances. CI or release review MUST surface them before the affected artifact is promoted.

#### CHG-04.07 — High-severity security defects MUST follow the private reporting…

**Requirement:** High-severity security defects MUST follow the private reporting, triage, patch, coordinated disclosure, and supported-version processes defined by the security policy.

### MOD-01 — Model identity, metadata, and compatibility

*Domain:* [models](../../torviello-enforcer/models/README.md) · *Rule:* [01-model-identity-metadata-and-compatibility.md](../../torviello-enforcer/models/rules/01-model-identity-metadata-and-compatibility.md)

**Control objective.** These controls govern **model identity, metadata, and compatibility**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### MOD-01.01 — Give each model artifact a stable model ID

The project MUST give each model artifact a stable model ID and immutable version or digest. Registry records specify task, format, source, license, input/output schema, tokenizer/preprocessor requirements, runtime/provider constraints, memory estimates, supported platform, and verification status.

#### MOD-01.02 — Separate model metadata from model bytes

The project MUST separate model metadata from model bytes. A registry entry cannot claim available or ready until the corresponding artifact is present, digest-verified, compatible, and successfully loaded for the selected runtime.

#### MOD-01.03 — Treat model files, tokenizer data, configuration, and metadata as

The project MUST treat model files, tokenizer data, configuration, and metadata as untrusted supply-chain inputs. The project MUST also record provenance and permitted redistribution.

#### MOD-01.04 — Define compatibility checks explicitly

The project MUST define compatibility checks explicitly. The project MUST NOT infer task, architecture, or provider support from filenames or extensions alone.

#### MOD-01.05 — Preserve immutable version history

The project MUST preserve immutable version history. Updating a model means creating a new version and an explicit promotion or rollback operation.

### MOD-02 — Secure download, install, and activation

*Domain:* [models](../../torviello-enforcer/models/README.md) · *Rule:* [02-secure-download-install-and-activation.md](../../torviello-enforcer/models/rules/02-secure-download-install-and-activation.md)

**Control objective.** These controls govern **secure download, install, and activation**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### MOD-02.01 — Restrict downloads to configured or allowlisted sources

The project MUST restrict downloads to configured or allowlisted sources. The project MUST also enforce TLS verification, safe redirect rules, connection and total timeouts, maximum size, disk-space checks, and bounded retries.

#### MOD-02.02 — Verify a cryptographic digest or signature before extracting

The project MUST verify a cryptographic digest or signature before extracting or loading an artifact. Reject mismatches and retain evidence of the verification result.

#### MOD-02.03 — Extract archives into a staging directory after rejecting absolute

The project MUST extract archives into a staging directory after rejecting absolute paths, parent traversal, links outside the destination, duplicate collisions, and excessive expanded size.

#### MOD-02.04 — Install and activate atomically

The project MUST install and activate atomically. A failed or interrupted download, extraction, or model load leaves the prior active artifact intact.

#### MOD-02.05 — Separate download state, installed state, and active state

The project MUST separate download state, installed state, and active state. The project MUST also report each explicitly to operators and readiness checks.

#### MOD-02.06 — Provide a preloaded/offline installation path for restricted deployments

The project MUST provide a preloaded/offline installation path for restricted deployments.

### OBS-01 — Secure structured logging and traces

*Domain:* [observability](../../torviello-enforcer/observability/README.md) · *Rule:* [01-secure-structured-logging-and-traces.md](../../torviello-enforcer/observability/rules/01-secure-structured-logging-and-traces.md)

**Control objective.** These controls govern **secure structured logging and traces**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### OBS-01.01 — Emit structured runtime logs through the shared logging system

The project MUST emit structured runtime logs through the shared logging system. The project MUST also include timestamp, severity, service identity, event name, and correlation/trace context where available.

#### OBS-01.02 — Record operational and security events consistently: startup/shutdown, authentication

The project MUST record operational and security events consistently: startup/shutdown, authentication and authorization outcomes, configuration changes, model installation/promotion, dependency failures, and request outcomes.

#### OBS-01.03 — Log passwords, tokens, API keys, private keys, database credentials

The project MUST NOT log passwords, tokens, API keys, private keys, database credentials, full prompts, raw uploads, or unnecessary personal data. It MUST redact secrets at boundaries and sanitize untrusted values against log injection.

#### OBS-01.04 — Bound log volume and retention

The project MUST bound log volume and retention. The project MUST also use rotation or external collection without allowing disk exhaustion to interfere with application state.

#### OBS-01.05 — Use OpenTelemetry semantic conventions for HTTP, service identity, exceptions

The project MUST use OpenTelemetry semantic conventions for HTTP, service identity, exceptions, and resources. Propagate trace context across trusted service boundaries; never treat correlation identifiers as identity or authorization.

#### OBS-01.06 — Make telemetry export explicitly configurable and off by default

The project SHOULD make telemetry export explicitly configurable and off by default in local/offline profiles. The project MUST also document all exported fields and endpoints.

### OBS-02 — Metrics, health, and Prometheus operations

*Domain:* [observability](../../torviello-enforcer/observability/README.md) · *Rule:* [02-metrics-health-and-prometheus-operations.md](../../torviello-enforcer/observability/rules/02-metrics-health-and-prometheus-operations.md)

**Control objective.** These controls govern **metrics, health, and prometheus operations**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### OBS-02.01 — Expose bounded metrics for request volume, failures, latency distributions

The project MUST expose bounded metrics for request volume, failures, latency distributions, saturation, active work, queue depth, model load/readiness, resource use, and upstream failures.

#### OBS-02.02 — Give each metric one meaning and unit

The project MUST give each metric one meaning and unit. The project MUST also use standard base units and type suffixes where appropriate. The project MUST also use labels for bounded dimensions only; review multiplicative cardinality before adding labels.

#### OBS-02.03 — Distinguish process liveness from readiness to serve the selected

The project MUST distinguish process liveness from readiness to serve the selected product profile. A live process with required models unavailable is not ready.

#### OBS-02.04 — Restrict metrics endpoints to trusted monitoring networks or protect

The project MUST restrict metrics endpoints to trusted monitoring networks or protect them using deployment-supported authentication and TLS. The project MUST NOT expose Prometheus admin/lifecycle endpoints publicly.

#### OBS-02.05 — Monitoring profiles MUST document scrape intervals/timeouts, target discovery, authentication/TLS

Monitoring profiles MUST document scrape intervals/timeouts, target discovery, authentication/TLS, storage retention, dashboards, alert thresholds, ownership, and runbooks. Scrape timeout MUST NOT exceed scrape interval.

#### OBS-02.06 — Validate Prometheus configuration and alert/recording rules with official tooling

The project MUST validate Prometheus configuration and alert/recording rules with official tooling before deployment. Configuration changes are reviewed and rolled back on failed validation.

#### OBS-02.07 — Alerts MUST focus on user-visible symptoms, saturation, and recovery

Alerts MUST focus on user-visible symptoms, saturation, and recovery failure. Each production alert MUST have severity, owner, action, and a test path.

**Control objective.** These controls govern **service lifecycle and readiness**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### OPS-01.01 — Document and support installation, start, stop, restart, readiness, liveness

The project MUST document and support installation, start, stop, restart, readiness, liveness, logs, configuration, upgrade, rollback, and uninstall for each declared deployment profile.

#### OPS-01.02 — Startup MUST validate configuration and required runtime prerequisites before

Startup MUST validate configuration and required runtime prerequisites before readiness becomes true. Readiness MUST reflect whether configured capabilities can serve; liveness MUST reflect whether the process can continue operating.

The project MUST keep the local engine usable without a hosted account, hosted registry, or telemetry endpoint unless the selected profile explicitly requires that service.

### EXT-01 — Customer User and Community Support Operations

*Domain:* [stakeholder-relations](../../torviello-enforcer/stakeholder-relations/README.md) · *Rule:* [01-customer-user-and-community-support-operations.md](../../torviello-enforcer/stakeholder-relations/rules/01-customer-user-and-community-support-operations.md)

**Control objective.** Every user-facing request must reach an authorized and competent responder, receive an accurate acknowledgment, and be resolved, escalated, or explicitly bounded. Support must protect user privacy and feed product, security, accessibility, and reliability learning back to owners.

#### EXT-01.01 — For each supported product profile, state supported audiences…

**Requirement:** For each supported product profile, state supported audiences, support channel, hours/response expectations, languages/accessibility options as applicable, supported versions, escalation boundaries, and what the channel cannot provide. Do not imply 24/7 or guaranteed response absent an approved staffed commitment.

#### EXT-01.02 — A support owner MUST capture a case identifier…

**Requirement:** A support owner MUST capture a case identifier, minimal contact/context, product/version/profile, impact, urgency, category, consent/data handling where relevant, owner, status, and next update. Classify security, privacy, safety, accessibility, billing, data-loss, outage, and ordinary usage cases distinctly.

#### EXT-01.03 — The responder MUST confirm receipt, explain next steps…

**Requirement:** The responder MUST confirm receipt, explain next steps and realistic response timing, and avoid promises beyond authority. If the issue is urgent or outside support competence, route it to the designated incident, privacy, security, legal, or product owner.

#### EXT-01.04 — Request only the diagnostic information needed; prefer synthetic…

**Requirement:** Request only the diagnostic information needed; prefer synthetic or redacted data. Provide a secure transfer path for necessary sensitive files, restrict case access, set retention, and never ask users to send passwords, private keys, or unnecessary inference content.

#### EXT-01.05 — Support responses MUST distinguish verified facts, hypotheses…

**Requirement:** Support responses MUST distinguish verified facts, hypotheses, workarounds, and commitments; explain limitations plainly; preserve user dignity; and provide accessible alternatives where a product barrier blocks use.

#### EXT-01.06 — The case owner MUST record diagnosis, workaround/fix…

**Requirement:** The case owner MUST record diagnosis, workaround/fix, affected versions, user communication, residual risk, escalation, and closure. For unresolved issues, state owner, next update, and safe workaround; closure MUST NOT mean merely that a ticket was transferred.

#### EXT-01.07 — Repeated complaints, confusing behavior, support workarounds…

**Requirement:** Repeated complaints, confusing behavior, support workarounds, accessibility barriers, unsafe use, and common failures MUST be summarized for accountable product and engineering owners. Convert recurring risks into requirements, defects, documentation, controls, or product decisions with traceable follow-up.

#### EXT-01.08 — Support measures MAY include response and resolution times…

**Requirement:** Support measures MAY include response and resolution times, backlog age, reopen rate, user impact, and satisfaction, but MUST be interpreted with case complexity, safety, fairness, and quality. Do not reward fast closure at the expense of accurate diagnosis or user outcome.

### VER-04 — Security, robustness, and failure-injection testing

**Control objective.** This control defines the intended outcome for **security, robustness, and failure-injection testing** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### VER-04.01 — Every trust boundary MUST have negative tests for malformed…

**Requirement:** Every trust boundary MUST have negative tests for malformed, unauthorized, oversized, replayed, stale, concurrent, and unavailable inputs relevant to that boundary.

#### VER-04.02 — Parsers for HTTP bodies, TOML, model metadata…

**Requirement:** Parsers for HTTP bodies, TOML, model metadata, archives, image/audio formats, and update manifests MUST be tested for malformed structures, truncation, extreme nesting, integer overflow, decompression expansion, path escape, and resource exhaustion as applicable.

#### VER-04.03 — Failure injection MUST cover network timeout/reset, DNS/TLS failure…

**Requirement:** Failure injection MUST cover network timeout/reset, DNS/TLS failure, disk full, database unavailable, partial write, process restart, accelerator loss, model load failure, and cancellation for profiles that depend on those components.

#### VER-04.04 — Confirmed security defects MUST produce minimized regression fixtures…

**Requirement:** Confirmed security defects MUST produce minimized regression fixtures and tests that fail on the vulnerable behavior and pass on the fix.

#### VER-04.05 — Fuzz and property-based tests MUST enforce execution and memory…

**Requirement:** Fuzz and property-based tests MUST enforce execution and memory budgets, preserve seed/corpus provenance, and avoid access to production credentials or network targets.

#### VER-04.06 — Dynamic security testing MUST use an isolated environment…

**Requirement:** Dynamic security testing MUST use an isolated environment, synthetic accounts/data, explicit target authorization, and controlled cleanup; test findings MUST be triaged before release.

#### VER-04.07 — Fault tests MUST verify recovery and cleanup as well…

**Requirement:** Fault tests MUST verify recovery and cleanup as well as detection: no leaked work, stale readiness, partially published state, corrupted registry, or silent data loss.
