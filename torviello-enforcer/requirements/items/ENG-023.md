# ENG-023 — Sanitize inputs and postprocess outputs deterministically

**Requirement ID:** ENG-023  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-29](../../torviello-engine/specifications/checks/AC-ENG-29.md)  
**Rule controls:** API-01, SEC-04, MOD-05

## 1. Normative requirement

The engine MUST bound text and image inputs before inference, apply documented postprocessing to outputs, report every applied step and warning, preserve raw output when postprocessing is skipped, and keep results deterministic for identical inputs and configuration.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

Postprocessing is where probabilities become presentable, bounding boxes become image coordinates, and audio is normalized. It is also where silent policy changes hide: rounding can reorder classes, null removal can delete a required field, and image resizing can accept an input larger than the model can handle. The reference implementation has sanitizer settings for text length, image dimensions, rounding, and null removal, plus audio, classification, and detection postprocessors and a skip flag.

Torviello requires postprocessing to be explicit and reproducible. Sanitization must reject unsafe input at the boundary rather than truncating it into a different request, and every applied step must be visible in response metadata.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to text, image, and audio input sanitization and to classification, detection, and audio output postprocessing. It covers limits, rounding, confidence filtering, coordinate conversion, null removal, step reporting, and the skip behavior.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Reject text exceeding the configured maximum length or apply a documented, reported truncation policy; never execute a silently altered request.
- Reject images exceeding configured width, height, or decoded size before full pixel decoding.
- Apply postprocessing steps in a documented order and make the order stable across releases.
- Round probabilities only when configured and preserve confidence ordering.
- Remove null output fields only when configured and never remove required contract fields.
- Report each applied step and any warning in the response envelope.
- When postprocessing is skipped, return raw backend output while still enforcing input sanitization.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** ISO/IEC 25010:2023 (security, functional correctness), OWASP ASVS 5.0.0 Level 3, OWASP API Security Top 10 2023, IETF BCP 14.

- Validation and sanitization MUST complete before inference; rejected input MUST NOT consume model work or leave state.
- Postprocessing steps MUST be declared, ordered, observable, and idempotent where the capability permits.
- Identical inputs, parameters, model, and backend MUST produce identical outputs except for documented non-determinism.
- Output MUST be encoded for its declared content type and MUST NOT reflect executable or control content from the input.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- Oversized text is rejected with input.text_too_long and no model execution.
- Oversized image dimensions are rejected before full decode.
- Probability rounding produces the configured decimal count and preserves ordering.
- Null removal omits optional null fields only.
- meta.postprocess_steps lists applied steps in order and marks postprocessing applied.
- skip_postprocess returns raw values while input limits still apply.

Acceptance checks: [AC-ENG-29](../../torviello-engine/specifications/checks/AC-ENG-29.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- Property tests MUST prove validate-before-infer and determinism over randomized adversarial inputs.
- An adversarial corpus MUST cover oversized text, control characters, polyglot payloads, NaN/Inf parameters, and encoding tricks.
- Mutation testing MUST kill mutants that reorder postprocessing, skip validation, or change determinism.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Separate input sanitization from output postprocessing in the pipeline. Sanitization returns a typed accepted or rejected result. Postprocessing returns a new value plus an ordered step list and warnings. Both should be pure functions of configuration and input so identical requests produce identical output.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not silently truncate text or resize an oversized image into an accepted request.
- Do not apply postprocessing without reporting it.
- Do not change confidence ordering through rounding.
- Do not remove required fields when null removal is enabled.
- Do not bypass input sanitization when postprocessing is skipped.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Submit text and images just below and above each configured limit.
- 2. Run classification with rounding enabled and inspect decimals and ordering.
- 3. Run with null removal on and off and compare fields.
- 4. Run with postprocessing enabled, warning-producing, and skipped.
- 5. Repeat identical requests and compare outputs for determinism.
- 6. Record configuration, inputs, outputs, and metadata.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Replay the adversarial corpus and confirm rejection before dispatch.
- 10. Repeat deterministic cases and compare byte or value equality, recording tolerated non-determinism.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Limit rejection responses for text and images.
- Rounded probability output and preserved ordering.
- Null-field comparison.
- Postprocess step and warning metadata.
- Determinism comparison for repeated requests.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The adversarial corpus and validate-before-infer evidence.
- The determinism report with tolerances.
- The postprocessing order and schema validation.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- An oversized input is silently altered and executed.
- Postprocessing changes are not reported.
- Rounding reorders classes.
- Required fields disappear under null removal.
- Skipping postprocessing also skips input limits.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- Sanitization occurs after model execution.
- Postprocessing order or skip behavior is undocumented or non-deterministic.
- Identical inputs produce different outputs without a documented cause.
