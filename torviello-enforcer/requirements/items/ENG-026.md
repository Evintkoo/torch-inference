# ENG-026 — Declare and enforce supported build and platform profiles

**Requirement ID:** ENG-026  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-32](../../../torviello-engine/specifications/checks/AC-ENG-32.md)  
**Rule controls:** PORT-01, PORT-02, ARC-02

## 1. Normative requirement

The engine MUST publish a supported platform matrix, provide minimal, CPU, and accelerator build profiles with explicit contents, keep optional providers out of the minimal profile, and fail unsupported targets or unavailable providers with a documented reason.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability. At HPA-4, release artifacts MUST meet SLSA v1.2 Build Level 3 with signed provenance and SBOM, and the declared platform matrix MUST be verified with reproducible builds.

## 2. Why this requirement exists

A claim that the engine runs on a platform is a packaging and dependency claim as much as a source-code claim. Optional CUDA, Metal, ONNX Runtime, jemalloc, profiling, or microservice components can leak into the default build and make the lightest profile neither light nor portable.

Torviello requires explicit profiles and a support matrix so operators can choose an artifact and know what it contains. The matrix also prevents a partially functional installation on an unsupported target and gives CI a concrete set of builds and smoke tests.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to build features, dependency selection, release artifacts, service packaging, and platform support statements. It covers minimal and optional profiles, target matrix, provider availability, artifact metadata, and unsupported-target behavior. It does not define the benchmark competitor set.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Publish a support matrix naming OS, architecture, toolchain, runtime prerequisites, and support status.
- Define minimal, CPU, and accelerator profiles with the dependencies and capabilities each includes.
- Keep optional accelerator and service dependencies out of the minimal profile.
- Build and smoke-test every declared target in CI or record a specific approved exception.
- Fail build or startup with a clear reason when a target or required provider is unavailable.
- Include profile, version, commit, and backend contents in artifact metadata and the SBOM.
- Avoid installing a partially functional binary on an unsupported target.

#### PORT-01.01 — Publish a support matrix for each release: OS/version, architecture

The project MUST publish a support matrix for each release: OS/version, architecture, minimum CPU/instruction set, memory/storage floor, compiler/toolchain, runtime libraries, GPU provider, driver, and model format.

#### PORT-01.02 — Support the CPU-only profile as the portable baseline

The project MUST support the CPU-only profile as the portable baseline. Specialized CPU instructions are runtime-detected or excluded from targets that do not guarantee them.

#### PORT-01.03 — Claim Windows, macOS, Linux, CUDA, Metal, Vulkan, or AMD

The project MUST claim Windows, macOS, Linux, CUDA, Metal, Vulkan, or AMD support only after building and running a profile-specific smoke test on a representative target.

#### PORT-01.04 — State unsupported combinations and degraded behavior clearly

The project MUST state unsupported combinations and degraded behavior clearly. A compiled artifact alone does not establish a supported platform.

#### PORT-01.05 — Test both the oldest supported environment and a current

The project MUST test both the oldest supported environment and a current environment on each declared architecture family.

#### PORT-02.01 — Keep optional runtime dependencies behind explicit Cargo features

The project MUST keep optional runtime dependencies behind explicit Cargo features or target-specific dependencies. Default profiles include only intended capabilities.

#### PORT-02.02 — Use additive features with documented dependencies and user-visible effects

The project MUST use additive features with documented dependencies and user-visible effects. The project MUST also avoid relying on default feature behavior of transitive dependencies.

#### PORT-02.03 — Declare the minimum supported Rust and frontend toolchain

The project MUST declare the minimum supported Rust and frontend toolchain and use it in at least one CI job. The project MUST also pin release toolchains and record build flags.

#### PORT-02.04 — Test no-default-features, minimal CPU, production, and each important backend

The project MUST test no-default-features, minimal CPU, production, and each important backend combination. The project MUST also avoid an unbounded exhaustive matrix; select profiles by support commitments and risk.

#### PORT-02.05 — Keep build caches and generated artifacts target-specific

The project MUST keep build caches and generated artifacts target-specific. The project MUST NOT reuse incompatible outputs across OS, architecture, feature, or toolchain changes.

#### ARC-02.01 — Make hardware backends and large optional runtimes selectable capabilities

The project MUST make hardware backends and large optional runtimes selectable capabilities. Disabled capabilities MUST NOT pull their runtime dependencies into a minimal profile.

#### ARC-02.02 — Use additive Cargo features named after user-visible capabilities

The project MUST use additive Cargo features named after user-visible capabilities and document their dependency effects. It MUST NOT use features that silently change unrelated behavior.

#### ARC-02.03 — Publish build profiles for minimal CPU, supported CPU features

The project MUST publish build profiles for minimal CPU, supported CPU features, and each supported accelerator family. The matrix states exact OS, architecture, runtime, driver, and toolchain requirements.

#### ARC-02.04 — Each adapter MUST implement the same model lifecycle contract

Each adapter MUST implement the same model lifecycle contract: capability discovery, load, readiness, inference, cancellation, shutdown, and typed failure

#### ARC-02.05 — Record architecture decisions for module boundaries, backend interfaces, serialization

The project MUST record architecture decisions for module boundaries, backend interfaces, serialization, persistence, or compatibility, including alternatives and migration cost.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** SLSA v1.2 Build Level 3, CycloneDX 1.7, Sigstore, reproducible-builds practice, Rust target support, ISO/IEC 25010:2023, IETF BCP 14.

- Every build profile MUST declare its providers, optional dependencies, and supported targets, and the minimal profile MUST NOT contain undeclared code.
- Every release artifact MUST have verified SLSA v1.2 Build Level 3 provenance, a signed SBOM, and a bit-for-bit reproducible rebuild.
- Unsupported targets and absent providers MUST fail clearly at build or startup; they MUST NOT degrade silently.
- Claimed platform support MUST be backed by a passing target matrix and a published support lifecycle.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- The minimal artifact contains no accelerator or optional service dependencies.
- The CPU profile builds and serves supported capabilities on a host without accelerators.
- Every target in the declared matrix passes build and smoke test or has an approved exception.
- An accelerator profile without its runtime fails startup with backend.unavailable.
- Artifact metadata names profile, version, commit, and included backends.
- An unsupported target fails with a message naming the target.

Acceptance checks: [AC-ENG-32](../../../torviello-engine/specifications/checks/AC-ENG-32.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- A from-scratch rebuild MUST reproduce the released artifact bit for bit, or the non-reproducible inputs MUST be eliminated.
- Provenance and SBOM signatures MUST verify against the published identity for every artifact.
- The target and feature matrix MUST build, start, and execute a probe on every claimed profile.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Declare features in the build manifest and map each product profile to an explicit feature set. Keep optional provider code behind feature gates and runtime probes. Generate artifact metadata from the same manifest. CI should build the matrix and run a minimal smoke request for each artifact.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not claim support for a target that is not built and smoke-tested.
- Do not let optional providers leak into the minimal profile.
- Do not install a binary that cannot start on the target.
- Do not omit backend contents from artifact metadata.
- Do not silently change the meaning of a profile between releases.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Build each declared profile from a clean checkout.
- 2. Inspect dependency and artifact contents for optional components.
- 3. Run the profile smoke test on each declared target or review the approved exception.
- 4. Attempt an accelerator profile without its runtime.
- 5. Inspect artifact metadata and SBOM.
- 6. Record commands, artifact inventories, and results.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Rebuild from the recorded inputs and compare artifact digests.
- 10. Verify provenance and SBOM signatures and run the target/feature matrix.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Profile build logs and dependency inventories.
- Smoke-test results per target.
- Startup failure for a missing required provider.
- Artifact metadata and SBOM entries.
- Unsupported-target failure output.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- SLSA v1.2 provenance attestations and signature-verification logs.
- The signed CycloneDX SBOM and dependency inventory.
- The reproducible rebuild digests and target-matrix results.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- The minimal profile includes optional backends or services.
- A declared target is never built or tested.
- An unavailable provider is silently skipped.
- Artifact metadata does not identify contents.
- An unsupported target installs a broken binary.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- An artifact ships without verified provenance or a signed SBOM.
- The minimal profile contains an undeclared optional dependency.
- A claimed target or provider has no passing verification.
