# ENG-016 — Authenticate and harden the serving edge

**Requirement ID:** ENG-016  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-22](../../../torviello-engine/specifications/checks/AC-ENG-22.md)  
**Rule controls:** SEC-02, SEC-03, SEC-08, SEC-10

## 1. Normative requirement

The engine MUST default to a safe local edge, require valid credentials on protected routes when authentication is enabled, separate administrative authority from inference access, emit security headers, and apply rate limiting with a non-spoofable client identity policy.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability. At HPA-4, remote authentication MUST use asymmetric JWT algorithms with issuer, audience, expiry, and revocation checks under RFC 8725, and every non-loopback listener MUST use TLS 1.3.

## 2. Why this requirement exists

A local inference engine can be run on a laptop or exposed to a network, and the same binary must not be unsafe by accident. The reference implementation binds loopback by default, disables authentication by default for local use, supports HS256/384/512 JWT verification, installs security headers, and applies per-IP rate limiting with health and metrics exemptions.

Torviello requires the edge contract to be explicit: which routes are protected, how administrative mutation differs from inference, how identity is derived behind a proxy, and what remains available when authentication is off. It also requires that credentials and token contents never reach logs.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to all HTTP and WebSocket ingress, authentication configuration, route protection, authorization for registry and model management, security headers, and rate-limit identity. It does not define a hosted account lifecycle.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Bind loopback by default and make any public bind an explicit operator action.
- When authentication is enabled, require a valid bearer token on every protected route and return a challenge on failure.
- Define which routes are public for probes and which require inference or administrative scope.
- Enforce administrative scope on registry, model, configuration, and log mutation routes.
- Validate token signature, algorithm, and expiry and reject unsupported algorithms without fallback ambiguity.
- Emit CSP, X-Content-Type-Options, X-Frame-Options, and related headers on all responses.
- Derive rate-limit identity under a documented trusted-proxy policy and never trust arbitrary forwarding headers from untrusted peers.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** OWASP ASVS 5.0.0 Level 3, OWASP API Security Top 10 2023, RFC 8725 JWT BCP, TLS 1.3, NIST SSDF SP 800-218 v1.1, IETF BCP 14.

- The default listener MUST bind loopback; every non-loopback listener MUST use TLS 1.3 with a valid certificate and MUST NOT expose unauthenticated mutation.
- Remote authentication MUST use asymmetric JWT algorithms from an explicit allowlist with issuer, audience, expiry, not-before, and key-identifier validation; shared-secret HS algorithms are permitted only for loopback-only profiles.
- Signing keys MUST support rotation and revocation without accepting tokens signed by a retired or untrusted key; algorithm confusion, `none`, and key-substitution attacks MUST be rejected.
- Administrative mutation MUST require an administrative scope from a validated principal; rate-limit identity MUST come from the transport peer unless a trusted-proxy policy explicitly says otherwise.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- A default local start binds 127.0.0.1 and does not expose unauthenticated mutation routes remotely.
- A missing token on a protected route returns 401 with a challenge and no handler execution.
- An invalid or expired token returns 401 auth.invalid_token.
- A valid non-admin token mutating the registry returns 403 auth.forbidden.
- Every response carries the required security headers.
- A forged forwarding header does not reset the rate-limit budget.

Acceptance checks: [AC-ENG-22](../../../torviello-engine/specifications/checks/AC-ENG-22.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- The ASVS Level 3 applicable-control checklist MUST be complete, with evidence for every pass and an approved exception for every exclusion.
- The token attack corpus MUST cover `none`, algorithm confusion, kid injection, expired, not-yet-valid, wrong issuer, wrong audience, replay, and retired keys.
- A TLS scan MUST confirm protocol and cipher policy, and an authorization matrix MUST cover every protected route and scope.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Use one middleware for authentication and one for authorization decisions declared per route group. Parse tokens with an explicit algorithm allowlist and no fallback. Derive the client identity from the transport peer unless a trusted-proxy configuration names the header and trusted ranges. Install security headers outside compression and error handling so they apply to all responses.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not bind all interfaces with authentication disabled by default.
- Do not accept unsigned, expired, or algorithm-confused tokens.
- Do not treat inference authorization as administrative authorization.
- Do not trust arbitrary client-supplied forwarding headers for identity.
- Do not log tokens, secrets, or credential-bearing headers.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Start with default local configuration and inspect the bind address and protected routes.
- 2. Enable authentication and exercise missing, invalid, expired, and valid tokens.
- 3. Call an administrative mutation with a non-admin token.
- 4. Inspect headers on success, client-error, and server-error responses.
- 5. Send forged forwarding headers from an untrusted peer and observe rate-limit identity.
- 6. Record configuration, requests, responses, and log redaction.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Execute the ASVS L3 checklist and the token attack corpus.
- 10. Scan the non-loopback listener and compare the authorization matrix with the route inventory.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Bind address and route-protection evidence.
- 401 and 403 responses for the token and scope cases.
- Header inspection across response classes.
- Rate-limit behavior under forged headers.
- Log inspection showing no credential leakage.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The ASVS Level 3 control record with evidence links.
- The token attack corpus results and key-rotation/revocation records.
- The TLS scan and route-by-scope authorization matrix.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- A public bind is reachable without authentication by default.
- Invalid tokens reach a handler.
- Inference tokens can mutate administration state.
- Security headers are missing on some responses.
- Client-controlled headers bypass rate limits.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- A non-loopback listener serves plaintext or unauthenticated mutation.
- A remote profile relies on a shared secret or accepts an unapproved algorithm.
- A protected route executes before authentication or accepts a missing issuer or audience.
