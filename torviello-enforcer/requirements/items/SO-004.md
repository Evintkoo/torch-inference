### API-01 — API contracts and schemas

*Domain:* [api](../../torviello-enforcer/api/README.md) · *Rule:* [01-api-contracts-and-schemas.md](../../torviello-enforcer/api/rules/01-api-contracts-and-schemas.md)

**Control objective.** These controls govern **api contracts and schemas**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### API-01.01 — Maintain a machine-readable OpenAPI description for every public HTTP

The project MUST maintain a machine-readable OpenAPI description for every public HTTP API. The project MUST also treat it as a reviewed contract that describes paths, methods, schemas, validation constraints, authentication, authorization, status codes, error bodies, pagination, and streaming behavior.

#### API-01.02 — Keep request and response schemas in a dedicated API

The project MUST keep request and response schemas in a dedicated API schema module. The project MUST also group handlers by user-facing functionality. A handler MAY parse transport input, invoke a domain interface, and serialize a response; it MUST NOT own inference, persistence, registry policy, or cross-service business logic.

#### API-01.03 — Use one stable error envelope

The project MUST use one stable error envelope. The project MUST also include a safe error code and correlation identifier; return actionable client guidance without leaking stack traces, filesystem paths, secrets, internal service names, or dependency errors.

#### API-01.04 — Define compatibility for every endpoint

The project MUST define compatibility for every endpoint. Additive changes preserve existing semantics. Breaking changes require an explicit API version/deprecation plan, a migration window, and consumer-facing release notes.

#### API-01.05 — Generate reference documentation from the contract when practical

The project SHOULD generate reference documentation from the contract when practical. Handwritten endpoint examples MUST be checked against the current contract and implementation.

### API-02 — API input and stream safety

*Domain:* [api](../../torviello-enforcer/api/README.md) · *Rule:* [02-api-input-and-stream-safety.md](../../torviello-enforcer/api/rules/02-api-input-and-stream-safety.md)

**Control objective.** These controls govern **api input and stream safety**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### API-02.01 — Treat every request field, header, URL, filename, archive entry

The project MUST treat every request field, header, URL, filename, archive entry, image, audio stream, and model input as untrusted. Parse into validated domain types before expensive work.

#### API-02.02 — Bound request bytes, multipart part count, image dimensions, audio

The project MUST bound request bytes, multipart part count, image dimensions, audio duration, decompressed size, queue wait, inference time, concurrent work, and response size. Limits MUST be configurable within safe hard bounds.

#### API-02.03 — Reject invalid content types, unsupported encodings, malformed multipart boundaries

The project MUST reject invalid content types, unsupported encodings, malformed multipart boundaries, path traversal, unexpected archive paths, and values outside schema constraints with safe client errors.

#### API-02.04 — Apply authentication and authorization to each operation

The project MUST apply authentication and authorization to each operation. Health endpoints disclose only their intended readiness state; administrative operations require explicit roles/scopes.

#### API-02.05 — Streaming routes MUST define cancellation, client disconnect handling, backpressure

Streaming routes MUST define cancellation, client disconnect handling, backpressure, timeout, partial result, and cleanup behavior. The project MUST NOT retain unbounded output in memory for a slow consumer.

#### API-02.06 — Use rate limits and concurrency controls at the API

The project MUST use rate limits and concurrency controls at the API boundary for expensive or abuse-sensitive operations. The project MUST also return a documented overload response and expose a bounded metric.

### API-03 — HTTP semantics and client behavior

*Domain:* [api](../../torviello-enforcer/api/README.md) · *Rule:* [03-http-semantics-and-client-behavior.md](../../torviello-enforcer/api/rules/03-http-semantics-and-client-behavior.md)

**Control objective.** This control defines the intended outcome for **http semantics and client behavior** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### API-03.01 — The API MUST use HTTP methods and status codes…

**Requirement:** The API MUST use HTTP methods and status codes according to their defined semantics; a response status MUST accurately report whether the requested operation completed, was accepted for asynchronous processing, failed validation, lacked authorization, or failed in the service.

#### API-03.02 — An operation that can be retried MUST define idempotency…

**Requirement:** An operation that can be retried MUST define idempotency behavior. For non-idempotent writes, the API MUST accept a caller-supplied idempotency key or provide another documented deduplication mechanism, scope the key to the authenticated principal and operation, retain it for a documented period, and return the original outcome for a duplicate request.

#### API-03.03 — Retries MUST be safe under the endpoint contract…

**Requirement:** Retries MUST be safe under the endpoint contract. Clients MUST NOT blindly retry non-idempotent requests; servers MUST bound retryable work and expose Retry-After only when the service can honor the stated delay.

#### API-03.04 — Pagination MUST use stable ordering and bounded page size…

**Requirement:** Pagination MUST use stable ordering and bounded page size. Cursor-based pagination SHOULD be used when concurrent inserts or deletes can make offset pagination skip or repeat records; cursors MUST be opaque, integrity-protected when they encode state, and scoped to the caller and query.

#### API-03.05 — Long-running inference and model-management operations MUST define synchronous versus…

**Requirement:** Long-running inference and model-management operations MUST define synchronous versus asynchronous behavior, request identity, status transitions, result expiry, cancellation, and duplicate-submission handling.

#### API-03.06 — HTTP caching MUST be explicit for authenticated, user-specific…

**Requirement:** HTTP caching MUST be explicit for authenticated, user-specific, model, and administrative responses. Responses containing secrets or sensitive inference data MUST use no-store or an approved stricter policy; shared caches MUST NOT reuse them across principals.

#### API-03.07 — Content negotiation and compression MUST have explicit supported media…

**Requirement:** Content negotiation and compression MUST have explicit supported media types and size limits. The service MUST reject unsupported request and response encodings safely and MUST NOT allow compressed-size limits to be bypassed by decompression expansion.

### COL-04 — Approved Digital Tools and Human Oversight of AI-Assisted Work

**Requirement:** A tool MUST have an owner, purpose, access model, data classification allowance, retention/deletion terms, integration scope, security/privacy review, export path, and supported use profile before it processes organizational, customer, personnel, source, or confidential data.

#### COL-04.02 — Before submitting information to a third-party SaaS, AI…

**Requirement:** Before submitting information to a third-party SaaS, AI model, browser extension, transcription service, repository bot, or automation, the user MUST verify that the data class and purpose are allowed, retention and training-use terms are acceptable, and an approved account/channel is used.

#### COL-04.03 — The person relying on AI-generated code, analysis…

**Requirement:** The person relying on AI-generated code, analysis, summary, translation, image, recommendation, or decision MUST verify factual claims, source rights, security, privacy, quality, and policy compliance at a level proportionate to impact. A generated output MUST NOT be treated as an approval, legal opinion, test result, or source citation.

#### COL-04.04 — Tools and agents MUST receive the minimum permissions needed…

**Requirement:** Tools and agents MUST receive the minimum permissions needed, bounded task scope, logging, and human approval for destructive, external, financial, production, identity, or public communication actions. #### COL-04.05 — When generated or automated work materially affects a decision…

**Requirement:** When generated or automated work materially affects a decision, product artifact, customer response, or public claim, retain relevant tool/version, input provenance where lawful, human reviewer, modifications, and validation evidence. Follow license, copyright, confidentiality, and attribution rules.

#### COL-04.06 — People MUST treat external content, model output…

**Requirement:** People MUST treat external content, model output, tool results, issue text, and generated files as untrusted data unless a trusted policy grants authority. Instructions contained in such data MUST NOT override user, system, or repository authority or authorize disclosure, scope expansion, or external action.

#### COL-04.07 — Unexpected data retention, unsafe output, unauthorized actions…

**Requirement:** Unexpected data retention, unsafe output, unauthorized actions, access leakage, or material quality failures MUST be reported to the tool owner and relevant privacy/security/product owner. Disable or constrain the tool when the risk cannot be bounded; update training and approval policy after confirmed failures.

The project MUST include an explicit schema version or a compatibility mechanism. The project MUST provide a migration/deprecation path for changed fields and reject unsupported versions clearly.

### DATA-06 — Database logical and physical design

*Domain:* [persistence](../../torviello-enforcer/persistence/README.md) · *Rule:* [06-database-logical-and-physical-design.md](../../torviello-enforcer/persistence/rules/06-database-logical-and-physical-design.md)

**Control objective.** Design persistent data structures from approved product behavior, invariants, access patterns, and operational constraints so that correctness is enforced at the storage boundary and the design can evolve safely.

#### DATA-06.01 — Establish data needs before drawing tables

The designer MUST start from approved use cases and the data inventory. For each record type identify authoritative owner, purpose, source, consumers, sensitivity, lifecycle, retention/deletion, scale, consistency, availability, offline and replication needs. Separate business state from cache, telemetry, inference payloads, model bytes, and derived data. Do not persist information solely for speculative future use.

#### DATA-06.02 — Model concepts and invariants before storage layout

Produce a logical model of entities/value objects, identity, relationships, cardinality, ownership, lifecycle states, and invariants. Define terminology and distinguish stable identity from mutable display attributes. Resolve whether a relationship is one-to-one, one-to-many, or many-to-many and who owns deletion. Map invariants to enforcement points; correctness-critical uniqueness, referential integrity, valid ranges, and required values MUST be enforced by the authoritative store where the selected technology supports it, with application checks as defense in depth.

#### DATA-06.03 — Select representation and normalization deliberately

Map the logical model to the selected database’s types and constraints. Prefer normalized authoritative data that avoids update anomalies; denormalize only for a measured read/latency or reporting need, document the source of truth, refresh/consistency model, and repair procedure. Choose JSON/document fields only for genuinely variable or opaque substructures with defined validation and query requirements; do not use them to evade a stable relational model. For each field define nullability, default semantics, units, precision, timezone, encoding, maximum size, and invalid-value behavior.

#### DATA-06.04 — Choose identifiers, time, and deletion semantics explicitly

Define primary key generation, uniqueness scope, external/public identifier exposure, and collision behavior. Store instants in an unambiguous UTC representation while preserving a local timezone separately when business meaning depends on it. Define soft-delete versus hard-delete rationale, tombstone visibility, uniqueness after deletion, cascading effects, retention, legal holds where applicable, and backup/replica propagation. Never imply deletion from active views while leaving uncontrolled accessible copies.

#### DATA-06.05 — Derive indexes and queries from access paths

For each important read/write path specify query shape, filters, ordering, pagination, expected cardinality, frequency, and latency/throughput target. Add indexes to support demonstrated access patterns and uniqueness/integrity requirements; assess write amplification, storage, lock contention, and maintenance cost. Avoid speculative indexes and unbounded scans. Use query plans and representative data distributions before asserting performance. Define pagination stability and cursor behavior for changing datasets.

#### DATA-06.06 — Define transaction and concurrency boundaries

Identify operations that MUST be atomic and their consistency/isolation requirements. Specify behavior under concurrent updates, retries, duplicate requests, partial failure, timeouts, and process interruption. Use database transactions for related state changes where supported; otherwise define an idempotent recovery protocol. Avoid holding locks across network calls or long inference work. Define optimistic/pessimistic concurrency controls and conflict outcomes where simultaneous edits are possible.

#### DATA-06.07 — Design tenant and authorization boundaries in data access

If multiple users, tenants, or roles share a store, define the ownership key and isolation boundary in the logical model. Every query and mutation MUST enforce the authorized scope at the repository/service boundary; do not trust client-supplied tenant or owner identifiers. Evaluate row-level policies, separate schemas/databases, or application filtering against threat model, operational burden, backup/restore, and migration needs. Test cross-tenant access failures.

#### DATA-06.08 — Assess lifecycle and operational cost before approval

Before schema implementation, review model and representative queries with product, application, security/privacy, and operations owners. Document growth assumptions, partitioning/archival needs, backup/restore and recovery targets, migration strategy, encryption and key handling, observability, licensing, portability, and exit path. Do not introduce partitioning or distributed database complexity without a measured scale/availability need and an operating owner.

#### DATA-06.09 — Verify the design against representative data and failure cases

Create migration-backed test fixtures with realistic cardinality and edge cases. Verify constraints, indexes, query plans, transaction outcomes, concurrent writes, retention/deletion, authorization isolation, backup restore, and supported upgrade paths. Use generated/synthetic data where production data is unnecessary. Keep schema diagrams and data dictionaries synchronized with migrations.
