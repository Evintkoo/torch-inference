## 1. Normative requirement

The service shall recover from expected process restarts and transient upstream/model failures without manual repair.

### OBS-01 — Secure structured logging and traces

*Domain:* [observability](../../../torviello-enforcer/observability/README.md) · *Rule:* [01-secure-structured-logging-and-traces.md](../../../torviello-enforcer/observability/rules/01-secure-structured-logging-and-traces.md)

**Control objective.** These controls govern **secure structured logging and traces**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### OBS-01.01 — Emit structured runtime logs through the shared logging system

The project MUST emit structured runtime logs through the shared logging system. The project MUST also include timestamp, severity, service identity, event name, and correlation/trace context where available.

#### OBS-01.02 — Record operational and security events consistently: startup/shutdown, authentication

The project MUST record operational and security events consistently: startup/shutdown, authentication and authorization outcomes, configuration changes, model installation/promotion, dependency failures, and request outcomes.

#### OBS-01.03 — Log passwords, tokens, API keys, private keys, database credentials

The project MUST NOT log passwords, tokens, API keys, private keys, database credentials, full prompts, raw uploads, or unnecessary personal data. It MUST redact secrets at boundaries and sanitize untrusted values against log injection.

#### OBS-01.04 — Bound log volume and retention

The project MUST bound log volume and retention. The project MUST also use rotation or external collection without allowing disk exhaustion to interfere with application state.

#### OBS-01.05 — Use OpenTelemetry semantic conventions for HTTP, service identity, exceptions

The project MUST use OpenTelemetry semantic conventions for HTTP, service identity, exceptions, and resources. Propagate trace context across trusted service boundaries; never treat correlation identifiers as identity or authorization.

#### OBS-01.06 — Make telemetry export explicitly configurable and off by default

The project SHOULD make telemetry export explicitly configurable and off by default in local/offline profiles. The project MUST also document all exported fields and endpoints.

### OBS-02 — Metrics, health, and Prometheus operations

*Domain:* [observability](../../../torviello-enforcer/observability/README.md) · *Rule:* [02-metrics-health-and-prometheus-operations.md](../../../torviello-enforcer/observability/rules/02-metrics-health-and-prometheus-operations.md)

**Control objective.** These controls govern **metrics, health, and prometheus operations**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### OBS-02.01 — Expose bounded metrics for request volume, failures, latency distributions

The project MUST expose bounded metrics for request volume, failures, latency distributions, saturation, active work, queue depth, model load/readiness, resource use, and upstream failures.

#### OBS-02.02 — Give each metric one meaning and unit

The project MUST give each metric one meaning and unit. The project MUST also use standard base units and type suffixes where appropriate. The project MUST also use labels for bounded dimensions only; review multiplicative cardinality before adding labels.

#### OBS-02.03 — Distinguish process liveness from readiness to serve the selected

The project MUST distinguish process liveness from readiness to serve the selected product profile. A live process with required models unavailable is not ready.

#### OBS-02.04 — Restrict metrics endpoints to trusted monitoring networks or protect

The project MUST restrict metrics endpoints to trusted monitoring networks or protect them using deployment-supported authentication and TLS. The project MUST NOT expose Prometheus admin/lifecycle endpoints publicly.

#### OBS-02.05 — Monitoring profiles MUST document scrape intervals/timeouts, target discovery, authentication/TLS

Monitoring profiles MUST document scrape intervals/timeouts, target discovery, authentication/TLS, storage retention, dashboards, alert thresholds, ownership, and runbooks. Scrape timeout MUST NOT exceed scrape interval.

#### OBS-02.06 — Validate Prometheus configuration and alert/recording rules with official tooling

The project MUST validate Prometheus configuration and alert/recording rules with official tooling before deployment. Configuration changes are reviewed and rolled back on failed validation.

#### OBS-02.07 — Alerts MUST focus on user-visible symptoms, saturation, and recovery

Alerts MUST focus on user-visible symptoms, saturation, and recovery failure. Each production alert MUST have severity, owner, action, and a test path.

### OPS-01 — Service lifecycle and readiness

*Domain:* [operations](../../../torviello-enforcer/operations/README.md) · *Rule:* [01-service-lifecycle-and-readiness.md](../../../torviello-enforcer/operations/rules/01-service-lifecycle-and-readiness.md)

**Control objective.** These controls govern **service lifecycle and readiness**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### OPS-01.01 — Document and support installation, start, stop, restart, readiness, liveness

The project MUST document and support installation, start, stop, restart, readiness, liveness, logs, configuration, upgrade, rollback, and uninstall for each declared deployment profile.

#### OPS-01.02 — Startup MUST validate configuration and required runtime prerequisites before

Startup MUST validate configuration and required runtime prerequisites before readiness becomes true. Readiness MUST reflect whether configured capabilities can serve; liveness MUST reflect whether the process can continue operating.

#### OPS-01.03 — Shutdown MUST stop accepting work, drain or cancel requests

Shutdown MUST stop accepting work, drain or cancel requests within a defined deadline, flush required state, and release model/runtime resources. Repeated signals and abrupt termination MUST have bounded behavior.

#### OPS-01.04 — Configure process supervision or container restart behavior with bounded

The project MUST configure process supervision or container restart behavior with bounded retry/backoff and visible failure state. Endless restart loops MUST NOT hide invalid configuration or unavailable required models.

#### OPS-01.05 — Keep the local engine usable without a hosted account

The project MUST keep the local engine usable without a hosted account, hosted registry, or telemetry endpoint unless the selected profile explicitly requires that service.

### OPS-02 — Reliability objectives and recovery

*Domain:* [operations](../../../torviello-enforcer/operations/README.md) · *Rule:* [02-reliability-slos-and-recovery.md](../../../torviello-enforcer/operations/rules/02-reliability-slos-and-recovery.md)

**Control objective.** These controls govern **reliability objectives and recovery**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### OPS-02.01 — Define service-level objectives for availability, latency, and error rate

The project MUST define service-level objectives for availability, latency, and error rate for each production deployment profile. State measurement windows, exclusions, and alert thresholds.

#### OPS-02.02 — Bound request concurrency, queues, model downloads, memory, disk

The project MUST bound request concurrency, queues, model downloads, memory, disk, and timeouts. The project MUST also define backpressure and overload responses before exposure to production traffic.

#### OPS-02.03 — Changes to configuration, models, and registry state MUST validate

Changes to configuration, models, and registry state MUST validate a candidate before activation and retain a known-good rollback point.

#### OPS-02.04 — The project MUST define backup scope, frequency, retention, encryption

For persistent deployments, the project MUST define backup scope, frequency, retention, encryption, access, recovery point objective, and recovery time objective.

#### OPS-02.05 — Provide runbooks for the highest-impact failure modes, including model

The project MUST provide runbooks for the highest-impact failure modes, including model unavailable/corrupt, disk full, GPU lost, database unavailable, credentials expired, and upstream outage.

#### OPS-02.06 — Verify backup restore and release rollback periodically

The project MUST verify backup restore and release rollback periodically; a backup that has never been restored is unverified.

### OPS-04 — Incident response and operational recovery

*Domain:* [operations](../../../torviello-enforcer/operations/README.md) · *Rule:* [04-incident-response-and-operational-recovery.md](../../../torviello-enforcer/operations/rules/04-incident-response-and-operational-recovery.md)

**Control objective.** This control defines the intended outcome for **incident response and operational recovery** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### OPS-04.01 — Operational incidents MUST have severity levels based on user…

**Requirement:** Operational incidents MUST have severity levels based on user impact, data/security impact, service degradation, and recovery urgency, with an incident lead and escalation path.

#### OPS-04.02 — Runbooks MUST cover model corruption/unavailability, accelerator loss…

**Requirement:** Runbooks MUST cover model corruption/unavailability, accelerator loss, resource exhaustion, disk full, persistence failure, credential/key expiry, unsafe update, telemetry outage, and upstream outage for profiles where each dependency exists.

#### OPS-04.03 — Incident procedures MUST preserve evidence, protect user data…

**Requirement:** Incident procedures MUST preserve evidence, protect user data, bound destructive remediation, and distinguish containment from full recovery. Security incidents MUST follow private evidence handling and coordinated disclosure policy.

#### OPS-04.04 — Recovery procedures MUST state safe ordering for service…

**Requirement:** Recovery procedures MUST state safe ordering for service, database, registry, model artifacts, credentials, and dependent services; include integrity checks before restoring traffic.

#### OPS-04.05 — Backups and rollback artifacts MUST be isolated from…

**Requirement:** Backups and rollback artifacts MUST be isolated from the failure mode they mitigate, access-controlled, integrity-checked, and available for the required recovery objective.

#### OPS-04.06 — Each production release MUST provide a tested rollback path…

**Requirement:** Each production release MUST provide a tested rollback path for binaries, configuration/schema, model registry, and compatible model assets, or document why rollback is unsafe and define forward recovery.

#### OPS-04.07 — After a material incident, the owner MUST record…

**Requirement:** After a material incident, the owner MUST record timeline, impact, detection, contributing conditions, recovery actions, and corrective items without blame; corrective actions MUST have owners and verification.

### OPS-05 — Capacity, readiness, and operator change management

*Domain:* [operations](../../../torviello-enforcer/operations/README.md) · *Rule:* [05-capacity-readiness-and-operator-change-management.md](../../../torviello-enforcer/operations/rules/05-capacity-readiness-and-operator-change-management.md)

**Control objective.** This control defines the intended outcome for **capacity, readiness, and operator change management** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### OPS-05.01 — Each production profile MUST state capacity assumptions for concurrent…

**Requirement:** Each production profile MUST state capacity assumptions for concurrent requests, model count, model sizes, queue depth, memory, CPU, accelerator memory, disk, network, and startup time.

#### OPS-05.02 — Admission control MUST reject or defer work before resource…

**Requirement:** Admission control MUST reject or defer work before resource exhaustion. Queue capacity, fairness, request deadline, cancellation, overload response, and recovery behavior MUST be explicit and observable.

#### OPS-05.03 — Readiness MUST reflect ability to serve the configured profile…

**Requirement:** Readiness MUST reflect ability to serve the configured profile, including required models and data stores. Liveness MUST remain independent from optional providers so transient optional failure does not trigger restart storms.

#### OPS-05.04 — Operator changes to configuration, models, registry…

**Requirement:** Operator changes to configuration, models, registry, credentials, or deployment topology MUST be attributable, validated before activation, auditable, and reversible where possible.

#### OPS-05.05 — Capacity alerts MUST warn before service objectives are breached…

**Requirement:** Capacity alerts MUST warn before service objectives are breached and identify the constrained resource and safe mitigation; capacity plans MUST consider burst load, cold starts, fragmentation, and model replacement overlap.

#### OPS-05.06 — Operational toil MUST be measured where repeated manual repair…

**Requirement:** Operational toil MUST be measured where repeated manual repair occurs; recurring recovery actions SHOULD be automated only after failure modes and guardrails are understood.

#### OPS-05.07 — Profile changes that alter network exposure, persistence…

**Requirement:** Profile changes that alter network exposure, persistence, auth, telemetry, or resource ceilings MUST undergo a risk review and restart/reload qualification.

### OPS-06 — Operational Roles Coverage Handover and Human Continuity

*Domain:* [operations](../../../torviello-enforcer/operations/README.md) · *Rule:* [06-operational-roles-coverage-handover-and-human-continuity.md](../../../torviello-enforcer/operations/rules/06-operational-roles-coverage-handover-and-human-continuity.md)

**Control objective.** Operational resilience depends on people knowing who is on duty, what they may do, how to hand work over, and how the service remains safe when a key person or supplier is unavailable. Coverage must match the service commitment without inventing unsupported staffing promises.

#### OPS-06.01 — Each production profile MUST identify service owner, incident…

**Requirement:** Each production profile MUST identify service owner, incident lead, deploy/release authority, security escalation, data/persistence owner, customer communication owner, and backup/delegate as applicable. State whether each function is staffed continuously, during defined hours, or on best-effort basis.

#### OPS-06.02 — For supported operational channels, state hours, severity…

**Requirement:** For supported operational channels, state hours, severity classes, response targets, escalation contacts, and fallback when the primary owner is unreachable. Public service promises MUST match actual staffing, monitoring, and recovery capability.

#### OPS-06.03 — An operational handover MUST include current service health…

**Requirement:** An operational handover MUST include current service health, open incidents/changes, customer impact, risks, pending actions, access used, deadlines, and next decision. The receiving owner MUST acknowledge material risk and understand their authority.

#### OPS-06.04 — Coverage MUST use named identities and pre-authorized delegates…

**Requirement:** Coverage MUST use named identities and pre-authorized delegates with time-bounded access. Never share accounts or keys to cover an absent operator; emergency access uses the security break-glass process and post-use review.

#### OPS-06.05 — For critical operations, identify single-person and supplier dependencies…

**Requirement:** For critical operations, identify single-person and supplier dependencies, recovery documentation, alternate contacts, and minimum competent coverage. Exercise absence, simultaneous incident, and unavailability of a key vendor at a frequency proportional to impact.

#### OPS-06.06 — Operational processes MUST allow responders to escalate unsafe workload…

**Requirement:** Operational processes MUST allow responders to escalate unsafe workload, conflicting incident tasks, or insufficient authority. Rotate or hand off duties as needed under approved work policies; do not use undocumented availability expectations as a service guarantee.

#### OPS-06.07 — Changes to service hours, product scope, team…

**Requirement:** Changes to service hours, product scope, team structure, vendor, incident severity, or recovery process MUST trigger review of roles, contacts, runbooks, training, and support commitments.

### SEC-10 — Secure defaults and abuse resilience

*Domain:* [security](../../../torviello-enforcer/security/README.md) · *Rule:* [10-secure-defaults-and-abuse-resilience.md](../../../torviello-enforcer/security/rules/10-secure-defaults-and-abuse-resilience.md)

#### SEC-10.01 — Every security-relevant setting MUST have a safe default…

**Requirement:** Every security-relevant setting MUST have a safe default for its deployment profile and a validation rule preventing known-dangerous combinations.

#### SEC-10.02 — Authentication MUST be required for remote administrative and persistent…

**Requirement:** Authentication MUST be required for remote administrative and persistent user-data operations. Local account-free operation MUST be restricted to a clearly defined local exposure boundary.

#### SEC-10.03 — Authentication and authorization failures MUST not disclose credential validity…

**Requirement:** Authentication and authorization failures MUST not disclose credential validity, protected object existence, tenant membership, or internal policy details beyond what the caller needs to remediate.

#### SEC-10.04 — Expensive operations MUST enforce per-actor and global resource budgets…

**Requirement:** Expensive operations MUST enforce per-actor and global resource budgets, deadline, queue admission, cancellation, and retry ceilings; budgets MUST apply to preprocessing, model download, inference, and response serialization.

#### SEC-10.05 — Resource exhaustion MUST degrade predictably: reject new work…

**Requirement:** Resource exhaustion MUST degrade predictably: reject new work, protect existing work according to policy, preserve essential health/administrative recovery, and avoid process-wide failure from one request.

#### SEC-10.06 — Abuse detection MUST correlate repeated authentication failures, model-download…

**Requirement:** Abuse detection MUST correlate repeated authentication failures, model-download abuse, sensitive business flow automation, and unusual resource consumption with bounded signals and privacy-safe retention.

#### SEC-10.07 — Security controls MUST fail closed when their required key…

**Requirement:** Security controls MUST fail closed when their required key, policy, validator, or authorization dependency is unavailable; availability exceptions require a named decision and a bounded degraded mode.

### EXT-01 — Customer User and Community Support Operations

*Domain:* [stakeholder-relations](../../../torviello-enforcer/stakeholder-relations/README.md) · *Rule:* [01-customer-user-and-community-support-operations.md](../../../torviello-enforcer/stakeholder-relations/rules/01-customer-user-and-community-support-operations.md)

**Control objective.** Every user-facing request must reach an authorized and competent responder, receive an accurate acknowledgment, and be resolved, escalated, or explicitly bounded. Support must protect user privacy and feed product, security, accessibility, and reliability learning back to owners.

#### EXT-01.01 — For each supported product profile, state supported audiences…

**Requirement:** For each supported product profile, state supported audiences, support channel, hours/response expectations, languages/accessibility options as applicable, supported versions, escalation boundaries, and what the channel cannot provide. Do not imply 24/7 or guaranteed response absent an approved staffed commitment.

#### EXT-01.02 — A support owner MUST capture a case identifier…

**Requirement:** A support owner MUST capture a case identifier, minimal contact/context, product/version/profile, impact, urgency, category, consent/data handling where relevant, owner, status, and next update. Classify security, privacy, safety, accessibility, billing, data-loss, outage, and ordinary usage cases distinctly.

#### EXT-01.03 — The responder MUST confirm receipt, explain next steps…

**Requirement:** The responder MUST confirm receipt, explain next steps and realistic response timing, and avoid promises beyond authority. If the issue is urgent or outside support competence, route it to the designated incident, privacy, security, legal, or product owner.

#### EXT-01.04 — Request only the diagnostic information needed; prefer synthetic…

**Requirement:** Request only the diagnostic information needed; prefer synthetic or redacted data. Provide a secure transfer path for necessary sensitive files, restrict case access, set retention, and never ask users to send passwords, private keys, or unnecessary inference content.

#### EXT-01.05 — Support responses MUST distinguish verified facts, hypotheses…

**Requirement:** Support responses MUST distinguish verified facts, hypotheses, workarounds, and commitments; explain limitations plainly; preserve user dignity; and provide accessible alternatives where a product barrier blocks use.

#### EXT-01.06 — The case owner MUST record diagnosis, workaround/fix…

**Requirement:** The case owner MUST record diagnosis, workaround/fix, affected versions, user communication, residual risk, escalation, and closure. For unresolved issues, state owner, next update, and safe workaround; closure MUST NOT mean merely that a ticket was transferred.

#### EXT-01.07 — Repeated complaints, confusing behavior, support workarounds…

**Requirement:** Repeated complaints, confusing behavior, support workarounds, accessibility barriers, unsafe use, and common failures MUST be summarized for accountable product and engineering owners. Convert recurring risks into requirements, defects, documentation, controls, or product decisions with traceable follow-up.

#### EXT-01.08 — Support measures MAY include response and resolution times…

**Requirement:** Support measures MAY include response and resolution times, backlog age, reopen rate, user impact, and satisfaction, but MUST be interpreted with case complexity, safety, fairness, and quality. Do not reward fast closure at the expense of accurate diagnosis or user outcome.

Technical investigation, customer service, legal review, and public communication must have distinct responsibilities that coordinate under one incident authority.

#### EXT-04.01 — Each supported service profile MUST identify who declares…

**Requirement:** Each supported service profile MUST identify who declares an incident, approves customer notices, handles media/regulator contact, prepares technical facts, and tracks affected users. #### EXT-04.02 — For suspected security, privacy, safety, data…

**Requirement:** For suspected security, privacy, safety, data loss, or widespread availability incidents, the incident lead MUST identify affected products, users, data, jurisdictions, contracts, evidence, and potential notification deadlines. Route to qualified counsel/privacy/security owners immediately; do not wait for full root-cause certainty to begin obligation assessment.

#### EXT-04.03 — Every update MUST distinguish confirmed facts, active investigation…

**Requirement:** Every update MUST distinguish confirmed facts, active investigation, unknowns, user actions, containment, support path, next update, and timestamp. Do not speculate about cause, scope, attribution, or resolution; correct earlier statements when evidence changes.

#### EXT-04.04 — Notices MUST avoid exposing credentials, exploit detail that…

**Requirement:** Notices MUST avoid exposing credentials, exploit detail that increases harm, personal data of other people, confidential customer information, or evidence that would compromise response. Provide specific mitigations users can safely follow and an accessible contact route.

#### EXT-04.05 — Use approved channels to reach directly affected customers…

**Requirement:** Use approved channels to reach directly affected customers, public users, partners, regulators, and internal responders as applicable. Maintain a canonical notice; ensure support, status page, account contacts, and public statements do not contradict it.

#### EXT-04.06 — The incident lead MUST set the next update time…

**Requirement:** The incident lead MUST set the next update time based on impact and obligations even if investigation is ongoing. Closure communication MUST state resolved status, remaining risk, user action, remediation/support path, and where a later post-incident report will appear.

#### EXT-04.07 — After incident closure, assess timeliness, accuracy…

### VER-04 — Security, robustness, and failure-injection testing

*Domain:* [verification](../../../torviello-enforcer/verification/README.md) · *Rule:* [04-security-robustness-and-failure-injection.md](../../../torviello-enforcer/verification/rules/04-security-robustness-and-failure-injection.md)

**Control objective.** This control defines the intended outcome for **security, robustness, and failure-injection testing** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### VER-04.01 — Every trust boundary MUST have negative tests for malformed…

**Requirement:** Every trust boundary MUST have negative tests for malformed, unauthorized, oversized, replayed, stale, concurrent, and unavailable inputs relevant to that boundary.

#### VER-04.02 — Parsers for HTTP bodies, TOML, model metadata…

**Requirement:** Parsers for HTTP bodies, TOML, model metadata, archives, image/audio formats, and update manifests MUST be tested for malformed structures, truncation, extreme nesting, integer overflow, decompression expansion, path escape, and resource exhaustion as applicable.

#### VER-04.03 — Failure injection MUST cover network timeout/reset, DNS/TLS failure…

**Requirement:** Failure injection MUST cover network timeout/reset, DNS/TLS failure, disk full, database unavailable, partial write, process restart, accelerator loss, model load failure, and cancellation for profiles that depend on those components.

#### VER-04.04 — Confirmed security defects MUST produce minimized regression fixtures…

**Requirement:** Confirmed security defects MUST produce minimized regression fixtures and tests that fail on the vulnerable behavior and pass on the fix.

#### VER-04.05 — Fuzz and property-based tests MUST enforce execution and memory…

**Requirement:** Fuzz and property-based tests MUST enforce execution and memory budgets, preserve seed/corpus provenance, and avoid access to production credentials or network targets.

#### VER-04.06 — Dynamic security testing MUST use an isolated environment…

**Requirement:** Dynamic security testing MUST use an isolated environment, synthetic accounts/data, explicit target authorization, and controlled cleanup; test findings MUST be triaged before release.

#### VER-04.07 — Fault tests MUST verify recovery and cleanup as well…

**Requirement:** Fault tests MUST verify recovery and cleanup as well as detection: no leaked work, stale readiness, partially published state, corrupted registry, or silent data loss.
