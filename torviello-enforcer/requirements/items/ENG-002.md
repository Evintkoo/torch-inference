# ENG-002 — Start, signal readiness, and stop in bounded stages

**Requirement ID:** ENG-002  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-08](../../torviello-engine/specifications/checks/AC-ENG-08.md)  
**Rule controls:** OPS-01, ARC-04, OBS-02

## 1. Normative requirement

The engine MUST separate process start, dependency initialization, readiness, and shutdown; readiness MUST reflect the ability to serve the configured workload, and shutdown MUST stop admission, drain or cancel in-flight work within a deadline, and report a terminal status.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

A process that accepts traffic before its models, providers, or configuration are usable produces failures that look like bad requests. A process that never becomes ready produces outages that look like slow inference. The reference implementation already exposes `/health/live` and `/health/ready`, initializes shared state before binding, and drains requests on termination with a configured shutdown window.

What remains underspecified is the contract between those stages: which components gate readiness, how optional model failures are represented, what happens to work that outlives the drain window, and how operators can tell startup failure from runtime failure. This requirement fixes that contract so probes, packages, and operators agree.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to the shipping server process and any service wrapper that starts it. It covers startup validation, listener binding, state and model initialization, readiness and liveness semantics, signal handling, drain, and forced termination. It does not prescribe a supervisor or container runtime.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Validate configuration and required paths before binding a listener; binding MUST NOT be used as a readiness signal.
- Maintain an explicit startup state that names pending components and exposes it through readiness.
- Keep liveness independent of model availability so a failed optional model does not trigger a restart loop.
- Represent optional model failure as a degraded capability with model ID and stable error code, while preserving availability of unrelated capabilities.
- On termination, stop accepting new connections, allow in-flight requests to finish within the configured deadline, then cancel and exit with a recorded status.
- Release model, worker, and telemetry resources in a defined order; a stuck dependency MUST NOT block exit beyond the grace window.
- Emit one structured startup record and one shutdown record that name version, profile, selected backend, listeners, and terminal reason.

The project MUST distinguish process liveness from readiness to serve the selected product profile. A live process with required models unavailable is not ready.

Alerts MUST focus on user-visible symptoms, saturation, and recovery failure. Each production alert MUST have severity, owner, action, and a test path.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** ISO/IEC/IEEE 29148:2018, ISO/IEC 25010:2023 (reliability, recoverability), NIST SP 800-160 Vol. 1 Rev. 1, TLA+, IETF BCP 14.

- Every lifecycle transition MUST have an explicit guard, and no listener, worker, or model activation may occur before its guard holds.
- Readiness MUST be derived from required component state, never from a bound socket, a started task, or a successful configuration parse alone.
- Drain MUST stop admission atomically, preserve in-flight work within the grace window, and record every forced cancellation with a reason.
- Startup and shutdown MUST be idempotent under repeated signals and concurrent control requests.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- A valid engine reports liveness before readiness and readiness only after required initialization.
- Readiness names each pending component while not ready and returns 503.
- A failed optional model leaves the process alive and reports degraded capability with its ID.
- Termination stops admission immediately and completes work inside the drain window.
- A request that exceeds the drain window is cancelled and the forced exit is recorded.
- Invalid configuration exits non-zero without creating a listener.

Acceptance checks: [AC-ENG-08](../../torviello-engine/specifications/checks/AC-ENG-08.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- A TLA+ model MUST cover Created, Validating, Initializing, Ready, Degraded, Draining, Stopped, and Forced, and model checking MUST find no violation of the lifecycle invariants.
- Signal fuzzing and kill injection MUST cover initialization, readiness, active drain, repeated SIGTERM, and expiry of the grace window.
- Readiness and liveness MUST remain responsive while initialization, drain, and model loading are blocked.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Model startup as an ordered set of named stages. Each stage records pending, ready, or failed. Readiness is a projection over required stages; health aggregates optional stages without turning them into readiness failures. Signal handling should trigger a shutdown state machine with an admission gate, a drain timer, and a forced-exit path.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not report ready solely because the HTTP listener bound.
- Do not use liveness to restart the process because an optional model is absent.
- Do not wait indefinitely for a stuck model or device operation during shutdown.
- Do not drop in-flight work without recording it as cancelled or forced.
- Do not start model downloads or initialization before configuration validation.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Start with a valid configuration and poll liveness and readiness through each startup stage.
- 2. Introduce an optional model failure and repeat the probes; inspect health and the process state.
- 3. Start a long request, send a termination signal, and measure admission stop, drain completion, and exit time.
- 4. Force a request beyond the drain window and inspect the terminal record.
- 5. Start with invalid configuration and confirm the process exits before binding.
- 6. Record revision, commands, timings, and observed statuses.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Run the TLA+ model checker and retain the configuration, state count, and invariant report.
- 10. Inject termination signals at every lifecycle stage and record the transition timeline and exit status.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Probe transcripts for liveness and readiness at each stage.
- Health output for the failed optional model showing degraded status and model ID.
- Timing record for admission stop, drain, and exit.
- The structured startup and shutdown records.
- Exit status for invalid configuration and a listener check.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The TLA+ specification, model-checking log, and invariant-to-requirement map.
- The signal-injection matrix with observed transitions, exit codes, and forced-exit records.
- A shutdown timeline showing admission stop, drain duration, and resource release.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- Readiness returns 200 before required components are initialized.
- The process exits during startup because an optional model is missing.
- Shutdown hangs indefinitely or loses in-flight work without a record.
- Invalid configuration binds a listener or exits zero.
- Startup or shutdown state cannot be reconstructed from logs.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- A listener accepts traffic after validation fails or before required initialization completes.
- Readiness reports true while a required component is pending or failed.
- Shutdown exceeds the grace window without recording a forced exit and the cancelled work.
