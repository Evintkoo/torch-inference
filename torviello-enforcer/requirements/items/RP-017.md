# RP-017 — The default installation and idle runtime shall be the lightest configuration that preserves supported behavior, with enforced footprint budgets

**Priority:** MUST

## 1. Normative requirement

The default installation and idle runtime shall be the lightest configuration that preserves supported behavior, with enforced footprint budgets.

## 2. Why this requirement exists

This requirement is part of **Inference and hardware** in [runtime-and-platform.md](../runtime-and-platform.md). It is traced to 1 rule control(s): PERF-06. Those controls state the following purpose:

- **PERF-06 — Competitive performance and footprint:** These controls govern competitive performance and footprint claims. The intended outcome is that Torviello earns "fastest and lightest" only inside a declared, reproducible envelope, and that release artifacts carry enforced budgets rather than aspirational marketing language.

Acceptance is not satisfied by citing these controls. The implementation must demonstrate the observable result in section 6, and the mapped rule clauses in section 5 define what must hold at the enforcement boundary.

## 3. Priority and interpretation

This requirement has **MUST** priority under the repository's requirement conventions. A MUST requirement is needed for the stated product direction or a safe release. A SHOULD requirement is expected unless a documented tradeoff justifies deferral. A COULD requirement is a candidate capability that requires product or technical validation. Acceptance describes observable evidence; it does not mandate a specific implementation unless the requirement says so.

## 4. Scope and applicability

This requirement belongs to **Inference and hardware** in [runtime-and-platform.md](../runtime-and-platform.md). It applies to the product area named by that source section and to every implementation, interface, release artifact, document, or operation that claims to satisfy it.

The mapped controls add the following applicability boundaries:

- **PERF-06:** This control applies to every benchmark, performance or footprint claim, release artifact, dependency and feature selection, default configuration, and optimization that affects latency, throughput, memory, startup, idle cost, or artifact size. It applies to engine, serving, packaging, and evaluation work.

The source requirement table remains authoritative if this view and the source disagree.

## 5. Detailed obligations

Each subsection below is the complete normative content of a mapped control. A requirement is not satisfied by selecting one convenient clause; every applicable clause must hold, including its negative and boundary behavior.

### PERF-06 — Competitive performance and footprint

*Domain:* [performance](../../../torviello-enforcer/performance/README.md) · *Rule:* [06-competitive-performance-and-footprint.md](../../../torviello-enforcer/performance/rules/06-competitive-performance-and-footprint.md)

**Control objective.** These controls govern competitive performance and footprint claims. The intended outcome is that Torviello earns "fastest and lightest" only inside a declared, reproducible envelope, and that release artifacts carry enforced budgets rather than aspirational marketing language.

#### PERF-06.01 — Declare the competitor set and claim envelope before measuring

The project MUST name the competitors and pinned versions, hardware, operating system, runtime and driver, model digests, input distributions, batch and sequence lengths, precision, concurrency, and metric definitions before running a comparison. The project MUST state whether the claim is fastest, lightest, or parity and the allowed statistical margin. The project MUST NOT claim a universal ranking across all hardware, models, or workloads.

#### PERF-06.02 — Measure every contender through one harness and environment

The project MUST use one versioned harness, identical warmup, repetitions, percentiles, telemetry, and isolation for every contender. The project MUST record failures, exclusions, and configuration differences. The project MUST NOT treat vendor-published numbers and locally measured numbers as equivalent without a documented reconciliation.

#### PERF-06.03 — Measure the full latency, throughput, and footprint vector

The project MUST report p50, p95, and p99 latency; throughput at defined concurrency; peak RSS and VRAM; cold-start time; idle CPU and GPU cost; artifact size; and dependency count. The project MUST also verify output quality on the same workload so that speed cannot be purchased with incorrect or degraded results.

#### PERF-06.04 — Enforce footprint and performance budgets in CI

The project MUST define numeric budgets for minimal-profile artifact size, cold start, idle RSS and CPU, peak memory at the reference workload, and regression tolerance. The project MUST fail the release gate when a budget or threshold is exceeded, and MUST keep the budgets in versioned configuration with an owner and review date.

#### PERF-06.05 — Publish reproducible evidence and requalify stale claims

The project MUST publish the harness revision, commands, environment manifest, raw results, and analysis for every competitive claim. The project MUST re-run the comparison for each release and whenever a competitor, runtime, driver, or reference model changes. The project MUST retract or requalify a claim when its evidence is stale or no longer reproducible.

#### PERF-06.06 — Keep marketing and documentation aligned with evidence

The project MUST link every public "fastest" or "lightest" statement to its evidence record and scope. The project MUST state conditions, caveats, and measurement date. The project MUST NOT imply superiority outside the tested envelope or omit losing results and material regressions.


### 5.1 Implementation guidance

- **PERF-06:** Implementation MUST satisfy the applicable requirements at the boundary where the claim is made and the budget is enforced. A marketing page, a single best-case run, or a benchmark that bypasses the shipping configuration does not satisfy this control. Keep the harness, environment manifest, budgets, and published analysis in `torviello-bench/`; keep product defaults and feature gates in the owning unit.

### 5.2 Assessment determination

- **PERF-06:** A control document passes only when every applicable MUST requirement is implemented and supported by current evidence, each applicable SHOULD deviation has a documented rationale, and no unapproved or expired exception remains. A requirement fails when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the assessment cannot reproduce the claimed result. Record **pass**, **fail**, or **not applicable** per control ID; "not applicable" requires a stated condition and reviewer rationale.

### 5.3 Exceptions and nonconformance

- **PERF-06:** A deviation from a MUST requirement requires explicit approval from the accountable product or engineering owner before release. The exception record MUST identify affected controls, scope, risk, compensating measures, remediation owner, and expiry or review date. A SHOULD deviation MUST include a rationale and impact in the change record. Unapproved or expired deviations are nonconformances and MUST block the affected release when the requirement is release-critical. A competitive claim without current evidence is a nonconformance and MUST be removed or qualified.

## 7. Feature scenarios

#### Claim only inside the tested envelope

```gherkin
Given every contender runs through the same harness and environment
    When the reference workload completes at the declared concurrency
    Then results report p50, p95, and p99 latency, throughput, peak memory, cold start, idle cost, and artifact size
    And any "fastest" or "lightest" claim states the tested models, hardware, precision, batch, and date
```

#### Fail the release when a footprint budget regresses

```gherkin
Given a budget for minimal-profile artifact size, cold start, idle RSS, and peak memory
    When a release exceeds a budget or its regression tolerance
    Then the release gate fails
    And the regression is reported with the measured and budgeted values
```

#### Reject a speedup that degrades output quality

```gherkin
Given a configuration that improves latency by reducing output quality or correctness
    When the benchmark quality check runs on the same workload
    Then the result is rejected as non-comparable
    And it is not published as a performance win
```

#### Retract a stale competitive claim

```gherkin
Given a published claim whose evidence predates the current competitor or runtime version
    When the claim is reviewed for release
    Then the claim is retracted or requalified with a new measured result
    And the evidence record states the reason for the change
```

#### Compare vendor numbers only with a documented reconciliation

```gherkin
Given a competitor publishes vendor benchmark numbers
    When those numbers are cited alongside local measurements
    Then the evidence records the environment and methodology differences
    And no equivalence is asserted without a reconciliation run
```


## 8. Prohibited conditions

The following conditions are explicitly prohibited by the mapped controls. Any one of them is sufficient to fail the requirement.

- [PERF-06] The project MUST NOT claim "fastest" or "lightest" without a current, reproducible evidence record
- [PERF-06] The project MUST NOT compare results across different hardware, precision, batch size, sequence length, or concurrency as equivalent
- [PERF-06] The project MUST NOT include optional backends, models, datasets, telemetry, or hosted dependencies in the minimal CPU baseline
- [PERF-06] The project MUST NOT weaken correctness, output quality, safety, or security to improve a benchmark result
- [PERF-06] The project MUST NOT hide losing results, exclusions, regressions, or stale evidence

## 9. Verification procedure

### 9.1 Automated or observable checks

- **AC-BENCH-04 (Automated)** — CI fails when the minimal-profile artifact size, cold start, idle RSS/CPU, or peak memory exceeds its versioned budget or regression tolerance.
- **AC-BENCH-05 (Automated)** — The minimal CPU profile excludes optional backends, models, datasets, telemetry, and hosted dependencies.

### 9.2 Examination

- [PERF-06] Inspect the harness, environment manifest, competitor versions, reference workloads, budget configuration, CI gate, release notes, and public claims.
- [PERF-06] Confirm every claim maps to a dated evidence record and every budget has an owner, threshold, and regression policy.

### 9.3 Interview

- [PERF-06] When a claim depends on an external competitor or vendor configuration, interview the accountable benchmark owner and confirm the contender was configured fairly and the evidence is reproducible.
- [PERF-06] An interview alone does not establish a performance or footprint result.

### 9.4 Test

- [PERF-06] Re-run the reference comparison from the recorded commands and environment; confirm the reported percentiles, throughput, memory, startup, idle cost, and artifact size within the stated tolerance.
- [PERF-06] Confirm that exceeding a budget fails the release gate, and that a degraded-quality configuration is rejected rather than counted as a win.
- [PERF-06] Record the command or procedure, tested revision and environment, result, and any limitation. A skipped check is not passing evidence.

### 9.5 Minimum procedure

1. Identify the artifact, behavior, interface, release artifact, or operating record named by the requirement and the source acceptance criterion.
2. Confirm that every mapped control clause in section 5 is addressed at the boundary where the risk is introduced, not only in documentation or a downstream wrapper.
3. Exercise the required behavior and at least one applicable negative, boundary, or failure case.
4. Record the revision, environment, exact command or procedure, observed result, limitations, and every skipped check.
5. Link the evidence from the change, evaluation, or assurance record. Reproducibility is required; a skipped or unrecorded check is not evidence.

- [PERF-06] A recorded exception with owner, rationale, compensating measures, approval, and expiry when a budget or claim cannot be met.

- A reviewable artifact or change that identifies **RP-017**.
