### DATA-06 — Database logical and physical design

*Domain:* [persistence](../../../torviello-enforcer/persistence/README.md) · *Rule:* [06-database-logical-and-physical-design.md](../../../torviello-enforcer/persistence/rules/06-database-logical-and-physical-design.md)

**Control objective.** Design persistent data structures from approved product behavior, invariants, access patterns, and operational constraints so that correctness is enforced at the storage boundary and the design can evolve safely.

#### DATA-06.01 — Establish data needs before drawing tables

The designer MUST start from approved use cases and the data inventory. For each record type identify authoritative owner, purpose, source, consumers, sensitivity, lifecycle, retention/deletion, scale, consistency, availability, offline and replication needs. Separate business state from cache, telemetry, inference payloads, model bytes, and derived data. Do not persist information solely for speculative future use.

#### DATA-06.02 — Model concepts and invariants before storage layout

Produce a logical model of entities/value objects, identity, relationships, cardinality, ownership, lifecycle states, and invariants. Define terminology and distinguish stable identity from mutable display attributes. Resolve whether a relationship is one-to-one, one-to-many, or many-to-many and who owns deletion. Map invariants to enforcement points; correctness-critical uniqueness, referential integrity, valid ranges, and required values MUST be enforced by the authoritative store where the selected technology supports it, with application checks as defense in depth.

#### DATA-06.03 — Select representation and normalization deliberately

Map the logical model to the selected database’s types and constraints. Prefer normalized authoritative data that avoids update anomalies; denormalize only for a measured read/latency or reporting need, document the source of truth, refresh/consistency model, and repair procedure. Choose JSON/document fields only for genuinely variable or opaque substructures with defined validation and query requirements; do not use them to evade a stable relational model. For each field define nullability, default semantics, units, precision, timezone, encoding, maximum size, and invalid-value behavior.

#### DATA-06.04 — Choose identifiers, time, and deletion semantics explicitly

Define primary key generation, uniqueness scope, external/public identifier exposure, and collision behavior. Store instants in an unambiguous UTC representation while preserving a local timezone separately when business meaning depends on it. Define soft-delete versus hard-delete rationale, tombstone visibility, uniqueness after deletion, cascading effects, retention, legal holds where applicable, and backup/replica propagation. Never imply deletion from active views while leaving uncontrolled accessible copies.

#### DATA-06.05 — Derive indexes and queries from access paths

For each important read/write path specify query shape, filters, ordering, pagination, expected cardinality, frequency, and latency/throughput target. Add indexes to support demonstrated access patterns and uniqueness/integrity requirements; assess write amplification, storage, lock contention, and maintenance cost. Avoid speculative indexes and unbounded scans. Use query plans and representative data distributions before asserting performance. Define pagination stability and cursor behavior for changing datasets.

#### DATA-06.06 — Define transaction and concurrency boundaries

Identify operations that MUST be atomic and their consistency/isolation requirements. Specify behavior under concurrent updates, retries, duplicate requests, partial failure, timeouts, and process interruption. Use database transactions for related state changes where supported; otherwise define an idempotent recovery protocol. Avoid holding locks across network calls or long inference work. Define optimistic/pessimistic concurrency controls and conflict outcomes where simultaneous edits are possible.

#### DATA-06.07 — Design tenant and authorization boundaries in data access

If multiple users, tenants, or roles share a store, define the ownership key and isolation boundary in the logical model. Every query and mutation MUST enforce the authorized scope at the repository/service boundary; do not trust client-supplied tenant or owner identifiers. Evaluate row-level policies, separate schemas/databases, or application filtering against threat model, operational burden, backup/restore, and migration needs. Test cross-tenant access failures.

#### DATA-06.08 — Assess lifecycle and operational cost before approval

Before schema implementation, review model and representative queries with product, application, security/privacy, and operations owners. Document growth assumptions, partitioning/archival needs, backup/restore and recovery targets, migration strategy, encryption and key handling, observability, licensing, portability, and exit path. Do not introduce partitioning or distributed database complexity without a measured scale/availability need and an operating owner.

#### DATA-06.09 — Verify the design against representative data and failure cases

Create migration-backed test fixtures with realistic cardinality and edge cases. Verify constraints, indexes, query plans, transaction outcomes, concurrent writes, retention/deletion, authorization isolation, backup restore, and supported upgrade paths. Use generated/synthetic data where production data is unnecessary. Keep schema diagrams and data dictionaries synchronized with migrations.

*Domain:* [stakeholder-relations](../../../torviello-enforcer/stakeholder-relations/README.md) · *Rule:* [01-customer-user-and-community-support-operations.md](../../../torviello-enforcer/stakeholder-relations/rules/01-customer-user-and-community-support-operations.md)

**Control objective.** Every user-facing request must reach an authorized and competent responder, receive an accurate acknowledgment, and be resolved, escalated, or explicitly bounded. Support must protect user privacy and feed product, security, accessibility, and reliability learning back to owners.

#### EXT-01.01 — For each supported product profile, state supported audiences…

**Requirement:** For each supported product profile, state supported audiences, support channel, hours/response expectations, languages/accessibility options as applicable, supported versions, escalation boundaries, and what the channel cannot provide. Do not imply 24/7 or guaranteed response absent an approved staffed commitment.

#### EXT-01.02 — A support owner MUST capture a case identifier…

**Requirement:** A support owner MUST capture a case identifier, minimal contact/context, product/version/profile, impact, urgency, category, consent/data handling where relevant, owner, status, and next update. Classify security, privacy, safety, accessibility, billing, data-loss, outage, and ordinary usage cases distinctly.

#### EXT-01.03 — The responder MUST confirm receipt, explain next steps…

**Requirement:** The responder MUST confirm receipt, explain next steps and realistic response timing, and avoid promises beyond authority. If the issue is urgent or outside support competence, route it to the designated incident, privacy, security, legal, or product owner.

#### EXT-01.04 — Request only the diagnostic information needed; prefer synthetic…

**Requirement:** Request only the diagnostic information needed; prefer synthetic or redacted data. Provide a secure transfer path for necessary sensitive files, restrict case access, set retention, and never ask users to send passwords, private keys, or unnecessary inference content.

#### EXT-01.05 — Support responses MUST distinguish verified facts, hypotheses…

**Requirement:** Support responses MUST distinguish verified facts, hypotheses, workarounds, and commitments; explain limitations plainly; preserve user dignity; and provide accessible alternatives where a product barrier blocks use.

#### EXT-01.06 — The case owner MUST record diagnosis, workaround/fix…

**Requirement:** The case owner MUST record diagnosis, workaround/fix, affected versions, user communication, residual risk, escalation, and closure. For unresolved issues, state owner, next update, and safe workaround; closure MUST NOT mean merely that a ticket was transferred.

#### EXT-01.07 — Repeated complaints, confusing behavior, support workarounds…

**Requirement:** Repeated complaints, confusing behavior, support workarounds, accessibility barriers, unsafe use, and common failures MUST be summarized for accountable product and engineering owners. Convert recurring risks into requirements, defects, documentation, controls, or product decisions with traceable follow-up.

#### EXT-01.08 — Support measures MAY include response and resolution times…

**Requirement:** Support measures MAY include response and resolution times, backlog age, reopen rate, user impact, and satisfaction, but MUST be interpreted with case complexity, safety, fairness, and quality. Do not reward fast closure at the expense of accurate diagnosis or user outcome.

### EXT-04 — External Incident and Stakeholder Communications

*Domain:* [stakeholder-relations](../../../torviello-enforcer/stakeholder-relations/README.md) · *Rule:* [04-external-incident-and-stakeholder-communications.md](../../../torviello-enforcer/stakeholder-relations/rules/04-external-incident-and-stakeholder-communications.md)

**Control objective.** External incident communications must be coordinated, truthful, timely, privacy-preserving, and consistent with legal, contractual, and user-safety obligations. Technical investigation, customer service, legal review, and public communication must have distinct responsibilities that coordinate under one incident authority.

#### EXT-04.01 — Each supported service profile MUST identify who declares…

**Requirement:** Each supported service profile MUST identify who declares an incident, approves customer notices, handles media/regulator contact, prepares technical facts, and tracks affected users. Include deputies and a channel to reach them outside ordinary work hours where the service promise requires it.

#### EXT-04.02 — For suspected security, privacy, safety, data…

**Requirement:** For suspected security, privacy, safety, data loss, or widespread availability incidents, the incident lead MUST identify affected products, users, data, jurisdictions, contracts, evidence, and potential notification deadlines. Route to qualified counsel/privacy/security owners immediately; do not wait for full root-cause certainty to begin obligation assessment.

#### EXT-04.03 — Every update MUST distinguish confirmed facts, active investigation…

**Requirement:** Every update MUST distinguish confirmed facts, active investigation, unknowns, user actions, containment, support path, next update, and timestamp. Do not speculate about cause, scope, attribution, or resolution; correct earlier statements when evidence changes.

#### EXT-04.04 — Notices MUST avoid exposing credentials, exploit detail that…

**Requirement:** Notices MUST avoid exposing credentials, exploit detail that increases harm, personal data of other people, confidential customer information, or evidence that would compromise response. Provide specific mitigations users can safely follow and an accessible contact route.

#### EXT-04.05 — Use approved channels to reach directly affected customers…

**Requirement:** Use approved channels to reach directly affected customers, public users, partners, regulators, and internal responders as applicable. Maintain a canonical notice; ensure support, status page, account contacts, and public statements do not contradict it.

#### EXT-04.06 — The incident lead MUST set the next update time…

**Requirement:** The incident lead MUST set the next update time based on impact and obligations even if investigation is ongoing. Closure communication MUST state resolved status, remaining risk, user action, remediation/support path, and where a later post-incident report will appear.

#### EXT-04.07 — After incident closure, assess timeliness, accuracy…

**Requirement:** After incident closure, assess timeliness, accuracy, audience reach, accessibility, privacy, support readiness, and approval bottlenecks. Correct any affected claim and update contact lists, playbooks, training, controls, and contracts.

## 8. Prohibited conditions

The following conditions are explicitly prohibited by the mapped controls. Any one of them is sufficient to fail the requirement.

- [OPS-01] The project MUST NOT report ready before required models and listeners are usable
- [OPS-01] The project MUST NOT require an operator to manually repair transient failures that the service can recover from safely
- [OPS-01] The project MUST NOT make a hosted control plane a hidden startup dependency for local inference
- [OPS-02] The project MUST NOT define success only as process uptime while users cannot complete inference
- [OPS-02] The project MUST NOT retry non-idempotent operations indefinitely
- [OPS-02] The project MUST NOT claim self-maintaining service behavior without recovery evidence and alerting for unrecoverable failures
- [OPS-04] Do not declare recovery complete until readiness and representative user transactions have been verified.
- [OPS-04] Do not restore untrusted backups or model artifacts without integrity and version checks.
- [OPS-06] Do not promise continuous support based on monitoring alone.
- [OPS-06] Do not make one person the only holder of critical recovery knowledge or credentials.
- [OPS-06] Do not leave an incident active without a named lead and next update/decision owner.
- [DATA-01] The project MUST NOT add a database because a feature might need one later
- [DATA-01] The project MUST NOT store raw prompts, uploaded media, or credentials by default
- [DATA-01] The project MUST NOT assume a database choice fits both offline single-node use and hosted scale without evidence
- [DATA-02] The project MUST NOT run destructive migrations without a backup and recovery plan
- [DATA-02] The project MUST NOT claim backup readiness based solely on successful backup creation
- [DATA-02] The project MUST NOT log SQL parameters or row contents when they can contain secrets or personal data
- [DATA-03] Do not retain sensitive payloads because they are convenient for reproducing bugs.
- [DATA-03] Do not claim deletion until derived copies and backup lifecycle have been considered.
- [DATA-04] Do not hold transactions open across long model inference or unbounded network operations.
- [DATA-04] Do not treat successful in-memory mutation as durable commit when the contract promises persistence.
- [DATA-05] Do not delete the only compatible backup before confirming the migrated system is healthy.
- [DATA-05] Do not assume copying a live database file produces a consistent backup.
- [DATA-06] Choosing a database or schema before defining data ownership, access, and lifecycle needs.
- [DATA-06] Relying exclusively on application code for an invariant that the storage engine can enforce.
- [DATA-06] Storing secrets, raw prompts, or personal data without a requirement, classification, and access/retention design.
- [DATA-06] Adding indexes or denormalized copies without a query or operational rationale.
- [DATA-06] Making a migration design without a recovery strategy for real data.
- [EXT-01] Do not close a case solely because ownership was transferred.

- [EXT-01] Do not make a support promise or product roadmap commitment without the authorized owner.
