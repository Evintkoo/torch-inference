## 1. Normative requirement

The product shall be usable by non-developers, configurable by operations staff, and extensible by developers.

## 3. Priority and interpretation

This requirement has **MUST** priority under the repository's requirement conventions. A MUST requirement is needed for the stated product direction or a safe release. #### DOC-05.02 — High-impact workflows MUST be validated with representative users…

**Requirement:** High-impact workflows MUST be validated with representative users or documented usability review before broad release. Evidence MUST identify the scenario, observed friction, and resulting design decision without exposing participant personal data.

#### DOC-05.03 — User-facing error content MUST state what happened, what…

**Requirement:** User-facing error content MUST state what happened, what the user can safely do next, whether work was saved, and how to obtain support when recovery is not self-service.

#### DOC-05.04 — Product copy MUST distinguish local from hosted behavior…

**Requirement:** Product copy MUST distinguish local from hosted behavior, required from optional network access, and free/personal from licensed/commercial use according to approved legal terms.

### DOC-06 — Website design and delivery lifecycle

*Domain:* [documentation-and-design](../../../torviello-enforcer/documentation-and-design/README.md) · *Rule:* [06-website-design-and-delivery-lifecycle.md](../../../torviello-enforcer/documentation-and-design/rules/06-website-design-and-delivery-lifecycle.md)

**Control objective.** Guide a website from audience and content discovery to information architecture, interaction design, implementation, publication, operation, and retirement, with quality measured at user journeys and page boundaries.

#### DOC-06.01 — Establish audience, purpose, and success before choosing layout

For each site/surface, identify primary and secondary audiences, user goals, tasks, context, language, device/network assumptions, content owner, business or service outcome, and measurable success/failure signals. Validate consequential assumptions using user/operator evidence. Do not begin with a framework, visual style, or reference website as the problem statement.

#### DOC-06.02 — Define information architecture and route contracts

Create a page/route inventory and navigation model before implementation. For each route specify purpose, intended audience, content source and owner, access level, canonical URL/redirect behavior, metadata needs, and links to adjacent journeys. Group content by user mental model and task rather than internal org chart. Define search and findability needs for substantial content sets.

#### DOC-06.03 — Design complete user journeys and state transitions

For each critical journey, document entry points, prerequisites, user actions, decisions, success, validation, loading, empty, permission-denied, partial, offline/timeout, service-error, retry, and recovery states. Define confirmation for destructive or irreversible actions, preservation of user input after correctable errors, and navigation/back behavior. Every state MUST have an accessible message and a clear next action where one exists.

#### DOC-06.04 — Specify content and interaction before visual polish

Write or structure representative content and labels before final layout. Use semantic headings, links, buttons, forms, tables, and landmarks according to purpose. Make labels describe outcomes, validation errors identify how to recover, and help text available at the decision point. Separate content from presentation where localization, reuse, or editorial ownership requires it. Public claims MUST map to approved evidence and licensing.

#### DOC-06.05 — Design responsive, resilient behavior from content constraints

Define layout behavior across viewport sizes, zoom/reflow, pointer and keyboard input, orientation, reduced motion, and constrained network/device capability. Content MUST remain readable and task-completable without relying on a specific screen size or hover. Prefer progressive enhancement and platform semantics where they reduce failure modes. Specify supported browser/device profiles and fallbacks for unavailable scripts, APIs, fonts, or media according to the product support matrix.

#### DOC-06.06 — Apply accessibility and privacy requirements in design

Design to the project's WCAG 2.2 AA target and relevant legal/product requirements. Include keyboard path and visible focus, semantic structure, accessible names/descriptions, contrast, text resizing/reflow, error identification, non-color cues, captions/transcripts for meaningful media, and reduced-motion behavior. Define whether analytics, cookies, or telemetry are necessary; minimize collection, document consent/notice and retention where applicable, and do not collect sensitive fields through analytics or URL parameters.

#### DOC-06.07 — Define user-centered performance and reliability budgets

Specify measurable budgets for critical routes and tasks, including transfer and resource size, loading, interaction responsiveness, layout stability, API latency, failure states, and supported network/device conditions. Choose current field or lab measures suited to the surface and explain sampling limits. Optimize the journey bottleneck using measurements; do not trade away accessibility, security, or correctness for a synthetic score. Define behavior when the server or essential API is unavailable.

#### DOC-06.08 — Design routes and content for security and search/publication needs

For public content define indexability, canonicalization, metadata, robots/sitemap policy, redirects, and link lifecycle as appropriate; never expose private routes or secrets through indexing configuration. For authenticated surfaces, specify session/authentication transitions, authorization-denied behavior, CSRF/XSS/input risks, content security policy, safe external links, and cache behavior in coordination with security rules. Treat all user and CMS content as untrusted input and encode it for its output context.

#### DOC-06.09 — Keep site ownership and runtime boundary explicit

Each site MUST have a product-area owner, build/test/deploy path, runtime dependencies, environment/configuration contract, content/design ownership, support route, and rollback/decommission procedure. Landing, docs, marketing/media, admin, and inference-engine UIs MUST NOT acquire hidden runtime/build dependencies on one another. Reuse MAY occur through versioned design packages with owners and compatibility policy.

#### DOC-06.10 — Verify journeys on rendered pages and maintain after publication

Before release, test representative routes at supported viewports and input modes, keyboard-only and assistive technology paths, accessibility, browser console/network failures, links/forms, content correctness, performance budgets, security headers, and build/deployment rollback. Record route/profile coverage and known gaps. After publication monitor availability, errors, broken links, accessibility feedback, performance, search/indexing behavior where relevant, and content freshness; review ownership and retire stale routes safely.

#### DOC-06.11 — Integrate video as accessible, privacy-aware page content

When a page uses video, the page MUST provide a descriptive title, poster, keyboard-accessible controls, captions in the supported language(s), transcript or equivalent content path, responsive dimensions, layout-space reservation, and a clear fallback. It MUST NOT rely on video alone to communicate essential product information or autoplay with sound. Before loading third-party player code, assess cookies, tracking, external requests, consent, availability, accessibility, and provider exit; use click-to-load or an approved first-party player when needed. Coordinate export profiles and source ownership with the media production controls.

### DOC-07 — Atomic component conventions

*Domain:* [documentation-and-design](../../../torviello-enforcer/documentation-and-design/README.md) · *Rule:* [07-atomic-component-conventions.md](../../../torviello-enforcer/documentation-and-design/rules/07-atomic-component-conventions.md)

**Control objective.** Give teams a shared, practical component vocabulary and extraction method that supports reuse, consistency, accessibility, and independent maintenance without turning the atomic metaphor into arbitrary foldering or over-fragmentation.

#### DOC-07.01 — Classify by responsibility and composition, not size alone

Use atomic-design terms as descriptive levels: **tokens/primitives** are design values and native/basic elements; **atoms** are small styled controls with one UI responsibility; **molecules** combine a few primitives into a coherent reusable interaction; **organisms** form a substantial region with a clear user purpose; **templates** arrange regions/content slots into a page structure; **pages** bind a template to real route data, permissions, and states. Teams MAY adapt names, but MUST document equivalent levels consistently. A small component is not automatically an atom, and a large component is not automatically an organism.

#### DOC-07.02 — Extract a shared component only for a demonstrated boundary

Create a shared component when repeated use, a stable semantic interaction, a design-system invariant, or independent ownership makes reuse valuable. Before extraction, identify callers, common behavior, variation points, accessibility contract, and owner. Keep one-off domain logic local until a second real use or a stable cross-feature contract justifies sharing. Do not create “generic” components with many flags for unrelated use cases; split when callers require conflicting semantics or state models.

#### DOC-07.03 — Give every reusable component a narrow contract

Document purpose, semantic element/role, public props/slots/events, controlled versus internal state, defaults, valid combinations, keyboard behavior, accessible name/value/state, loading/error/disabled behavior, styling/token extension points, and unsupported use. Props MUST express domain meaning rather than leak implementation details. Use composition and typed variants for intentional differences; avoid boolean-prop combinations that create invalid or unexplained states.

#### DOC-07.04 — Keep state and business rules at the correct level

Place transient presentation state at the smallest owner that MUST coordinate it. Place workflow or domain state in the feature/page/controller layer with explicit transitions and data ownership. Reusable primitives MUST NOT secretly fetch feature-specific data, own global session state, or make authorization decisions. Do not duplicate authoritative validation in UI as a substitute for server/domain enforcement.

#### DOC-07.05 — Preserve semantic/accessibility behavior through composition

Components MUST compose into valid document semantics and retain keyboard/focus order, labels, descriptions, error associations, announcements, contrast, and target behavior. Components that render interactive content MUST not nest interactive controls or hide focus. Provide slots/composition where callers need meaningful headings or actions rather than accepting opaque markup that defeats semantics. Accessibility is tested on the composed page, not only the isolated component.

#### DOC-07.06 — Co-locate implementation evidence and examples

For each reusable component family, keep implementation, tests, usage examples/stories, and design documentation in the established owning location. Demonstrate default, variant, responsive, empty, loading, disabled, invalid, permission-limited, and failure states as applicable. Examples MUST be realistic and accessible, and MUST NOT rely on production secrets or private data.

#### DOC-07.07 — Use explicit promotion, change, and deprecation rules

Promote a feature-local component into the shared system only after review of reuse, API stability, owner, accessibility, and migration cost. Changes to shared props, tokens, semantics, or visuals require impact analysis across consumers and version/release coordination. Deprecate with replacement guidance and removal timing; avoid silent breaking changes. Remove unused components after checking dynamic references and documented consumers.

#### DOC-07.08 — Organize files around ownership and discoverability

Use the repository’s established naming and directory conventions. Group components by product/domain or stable design-system ownership, not by atomic level alone when that fragments feature context. A dedicated `atoms/`, `molecules/`, `organisms/` hierarchy MAY be used only when it improves discovery and ownership; it MUST NOT become a required taxonomy that forces awkward placement. Keep public exports intentional and prevent cross-feature imports of private implementation files.

### ORG-04 — Spending Procurement and Organizational Commitments

*Domain:* [organization](../../../torviello-enforcer/organization/README.md) · *Rule:* [04-spending-procurement-and-organizational-commitments.md](../../../torviello-enforcer/organization/rules/04-spending-procurement-and-organizational-commitments.md)

**Control objective.** People must not create financial, contractual, data, service, or operational commitments without an authorized sponsor and a review proportionate to lifecycle cost and risk. Procurement and commitments include subscriptions, infrastructure, software, datasets, models, contractors, marketing, public promises, and renewals.

#### ORG-04.01 — The accountable business owner MUST define spending and commitment…

**Requirement:** The accountable business owner MUST define spending and commitment classes, approval limits, budget authority, required finance/legal/security/privacy/procurement review, evidence, and renewal authority. Thresholds MUST consider total lifecycle cost, data access, lock-in, user impact, and exit cost rather than initial price alone.

#### ORG-04.02 — Before a material purchase or external commitment…

**Requirement:** Before a material purchase or external commitment, the sponsor MUST state the business/user need, expected outcome, constraints, alternatives including no purchase, evaluation criteria, full cost, risks, and measurable acceptance conditions. Selection rationale MUST be retained.

#### ORG-04.03 — Before granting a supplier or contractor sensitive information…

**Requirement:** Before granting a supplier or contractor sensitive information, production access, code contribution, model/data access, or operational responsibility, review capability, security/privacy controls, licensing, subcontractors, continuity, incident duties, data return/deletion, and termination rights as applicable.

#### ORG-04.04 — Only designated roles MAY sign agreements, accept terms…

**Requirement:** Only designated roles MAY sign agreements, accept terms, quote prices, promise features or service levels, or represent a roadmap as committed. Review obligations, implied warranties, data rights, support burden, accessibility, export/retention, indemnity, renewal, and termination before acceptance.

#### ORG-04.05 — A service or commitment owner MUST track usage…

**Requirement:** A service or commitment owner MUST track usage, total spend, renewals, budget thresholds, owner, business value, and cost anomalies. Unused or over-provisioned resources MUST be removed or justified; cost-saving actions MUST be checked for security, reliability, and user impact.

#### ORG-04.06 — Material scope, price, data, access…

**Requirement:** Material scope, price, data, access, subprocessor, support, jurisdiction, or contract changes MUST trigger reassessment and approval before taking effect. Renewal decisions MUST compare current value and alternatives and include a tested exit or export path when lock-in risk is material.

#### ORG-04.07 — At contract or project end, revoke access…

**Requirement:** At contract or project end, revoke access, return or delete information, recover assets, stop recurring charges, retain required records, transfer ownership, and verify closure. Record any retained data or continuing duty and its owner.

### EXT-01 — Customer User and Community Support Operations

*Domain:* [stakeholder-relations](../../../torviello-enforcer/stakeholder-relations/README.md) · *Rule:* [01-customer-user-and-community-support-operations.md](../../../torviello-enforcer/stakeholder-relations/rules/01-customer-user-and-community-support-operations.md)

**Control objective.** Every user-facing request must reach an authorized and competent responder, receive an accurate acknowledgment, and be resolved, escalated, or explicitly bounded. Support must protect user privacy and feed product, security, accessibility, and reliability learning back to owners.

#### EXT-01.01 — For each supported product profile, state supported audiences…

**Requirement:** For each supported product profile, state supported audiences, support channel, hours/response expectations, languages/accessibility options as applicable, supported versions, escalation boundaries, and what the channel cannot provide. Do not imply 24/7 or guaranteed response absent an approved staffed commitment.

#### EXT-01.02 — A support owner MUST capture a case identifier…

**Requirement:** A support owner MUST capture a case identifier, minimal contact/context, product/version/profile, impact, urgency, category, consent/data handling where relevant, owner, status, and next update. Classify security, privacy, safety, accessibility, billing, data-loss, outage, and ordinary usage cases distinctly.

#### EXT-01.03 — The responder MUST confirm receipt, explain next steps…

**Requirement:** The responder MUST confirm receipt, explain next steps and realistic response timing, and avoid promises beyond authority. If the issue is urgent or outside support competence, route it to the designated incident, privacy, security, legal, or product owner.

#### EXT-01.04 — Request only the diagnostic information needed; prefer synthetic…

**Requirement:** Request only the diagnostic information needed; prefer synthetic or redacted data. Provide a secure transfer path for necessary sensitive files, restrict case access, set retention, and never ask users to send passwords, private keys, or unnecessary inference content.

#### EXT-01.05 — Support responses MUST distinguish verified facts, hypotheses…

**Requirement:** Support responses MUST distinguish verified facts, hypotheses, workarounds, and commitments; explain limitations plainly; preserve user dignity; and provide accessible alternatives where a product barrier blocks use.

#### EXT-01.06 — The case owner MUST record diagnosis, workaround/fix…

**Requirement:** The case owner MUST record diagnosis, workaround/fix, affected versions, user communication, residual risk, escalation, and closure. For unresolved issues, state owner, next update, and safe workaround; closure MUST NOT mean merely that a ticket was transferred.

#### EXT-01.07 — Repeated complaints, confusing behavior, support workarounds…

**Requirement:** Repeated complaints, confusing behavior, support workarounds, accessibility barriers, unsafe use, and common failures MUST be summarized for accountable product and engineering owners. Convert recurring risks into requirements, defects, documentation, controls, or product decisions with traceable follow-up.

#### EXT-01.08 — Support measures MAY include response and resolution times…

**Requirement:** Support measures MAY include response and resolution times, backlog age, reopen rate, user impact, and satisfaction, but MUST be interpreted with case complexity, safety, fairness, and quality. Do not reward fast closure at the expense of accurate diagnosis or user outcome.
