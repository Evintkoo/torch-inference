### API-01 — API contracts and schemas

*Domain:* [api](../../../torviello-enforcer/api/README.md) · *Rule:* [01-api-contracts-and-schemas.md](../../../torviello-enforcer/api/rules/01-api-contracts-and-schemas.md)

**Control objective.** These controls govern **api contracts and schemas**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### API-01.01 — Maintain a machine-readable OpenAPI description for every public HTTP

The project MUST maintain a machine-readable OpenAPI description for every public HTTP API. The project MUST also treat it as a reviewed contract that describes paths, methods, schemas, validation constraints, authentication, authorization, status codes, error bodies, pagination, and streaming behavior.

#### API-01.02 — Keep request and response schemas in a dedicated API

The project MUST keep request and response schemas in a dedicated API schema module. The project MUST also group handlers by user-facing functionality. A handler MAY parse transport input, invoke a domain interface, and serialize a response; it MUST NOT own inference, persistence, registry policy, or cross-service business logic.

#### API-01.03 — Use one stable error envelope

The project MUST use one stable error envelope. The project MUST also include a safe error code and correlation identifier; return actionable client guidance without leaking stack traces, filesystem paths, secrets, internal service names, or dependency errors.

#### API-01.04 — Define compatibility for every endpoint

The project MUST define compatibility for every endpoint. Additive changes preserve existing semantics. Breaking changes require an explicit API version/deprecation plan, a migration window, and consumer-facing release notes.

#### API-01.05 — Generate reference documentation from the contract when practical

The project SHOULD generate reference documentation from the contract when practical. Handwritten endpoint examples MUST be checked against the current contract and implementation.

### API-02 — API input and stream safety

*Domain:* [api](../../../torviello-enforcer/api/README.md) · *Rule:* [02-api-input-and-stream-safety.md](../../../torviello-enforcer/api/rules/02-api-input-and-stream-safety.md)

**Control objective.** These controls govern **api input and stream safety**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### API-02.01 — Treat every request field, header, URL, filename, archive entry

The project MUST treat every request field, header, URL, filename, archive entry, image, audio stream, and model input as untrusted. Parse into validated domain types before expensive work.

#### API-02.02 — Bound request bytes, multipart part count, image dimensions, audio

The project MUST bound request bytes, multipart part count, image dimensions, audio duration, decompressed size, queue wait, inference time, concurrent work, and response size. Limits MUST be configurable within safe hard bounds.

#### API-02.03 — Reject invalid content types, unsupported encodings, malformed multipart boundaries

The project MUST reject invalid content types, unsupported encodings, malformed multipart boundaries, path traversal, unexpected archive paths, and values outside schema constraints with safe client errors.

#### API-02.04 — Apply authentication and authorization to each operation

The project MUST apply authentication and authorization to each operation. Health endpoints disclose only their intended readiness state; administrative operations require explicit roles/scopes.

#### API-02.05 — Streaming routes MUST define cancellation, client disconnect handling, backpressure

Streaming routes MUST define cancellation, client disconnect handling, backpressure, timeout, partial result, and cleanup behavior. The project MUST NOT retain unbounded output in memory for a slow consumer.

#### API-02.06 — Use rate limits and concurrency controls at the API

The project MUST use rate limits and concurrency controls at the API boundary for expensive or abuse-sensitive operations. The project MUST also return a documented overload response and expose a bounded metric.

### API-03 — HTTP semantics and client behavior

*Domain:* [api](../../../torviello-enforcer/api/README.md) · *Rule:* [03-http-semantics-and-client-behavior.md](../../../torviello-enforcer/api/rules/03-http-semantics-and-client-behavior.md)

**Control objective.** This control defines the intended outcome for **http semantics and client behavior** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### API-03.01 — The API MUST use HTTP methods and status codes…

**Requirement:** The API MUST use HTTP methods and status codes according to their defined semantics; a response status MUST accurately report whether the requested operation completed, was accepted for asynchronous processing, failed validation, lacked authorization, or failed in the service.

#### API-03.02 — An operation that can be retried MUST define idempotency…

**Requirement:** An operation that can be retried MUST define idempotency behavior. For non-idempotent writes, the API MUST accept a caller-supplied idempotency key or provide another documented deduplication mechanism, scope the key to the authenticated principal and operation, retain it for a documented period, and return the original outcome for a duplicate request.

#### API-03.03 — Retries MUST be safe under the endpoint contract…

**Requirement:** Retries MUST be safe under the endpoint contract. Clients MUST NOT blindly retry non-idempotent requests; servers MUST bound retryable work and expose Retry-After only when the service can honor the stated delay.

#### API-03.04 — Pagination MUST use stable ordering and bounded page size…

**Requirement:** Pagination MUST use stable ordering and bounded page size. Cursor-based pagination SHOULD be used when concurrent inserts or deletes can make offset pagination skip or repeat records; cursors MUST be opaque, integrity-protected when they encode state, and scoped to the caller and query.

#### API-03.05 — Long-running inference and model-management operations MUST define synchronous versus…

**Requirement:** Long-running inference and model-management operations MUST define synchronous versus asynchronous behavior, request identity, status transitions, result expiry, cancellation, and duplicate-submission handling.

#### API-03.06 — HTTP caching MUST be explicit for authenticated, user-specific…

**Requirement:** HTTP caching MUST be explicit for authenticated, user-specific, model, and administrative responses. Responses containing secrets or sensitive inference data MUST use no-store or an approved stricter policy; shared caches MUST NOT reuse them across principals.

#### API-03.07 — Content negotiation and compression MUST have explicit supported media…

**Requirement:** Content negotiation and compression MUST have explicit supported media types and size limits. The service MUST reject unsupported request and response encodings safely and MUST NOT allow compressed-size limits to be bypassed by decompression expansion.

### CFG-05 — Secret configuration and operator controls

*Domain:* [configuration](../../../torviello-enforcer/configuration/README.md) · *Rule:* [05-secret-configuration-and-operator-controls.md](../../../torviello-enforcer/configuration/rules/05-secret-configuration-and-operator-controls.md)

**Control objective.** This control defines the intended outcome for **secret configuration and operator controls** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### CFG-05.01 — Secrets MUST use an approved source for the deployment…

**Requirement:** Secrets MUST use an approved source for the deployment profile: OS credential store, orchestrator secret, protected file, or explicitly configured environment input. Documentation MUST state the storage threat model and required file permissions.

#### CFG-05.02 — Production secrets MUST be validated for presence, format…

**Requirement:** Production secrets MUST be validated for presence, format, purpose, and minimum strength at startup. Missing or invalid required credentials MUST fail closed before the service accepts traffic.

#### CFG-05.03 — Secret rotation MUST support overlap or coordinated replacement where…

**Requirement:** Secret rotation MUST support overlap or coordinated replacement where clients require it, identify active key version, define rollback, and revoke compromised material without restoring the compromised value.

#### CFG-05.04 — Configuration inspection, diagnostic endpoints, support bundles…

**Requirement:** Configuration inspection, diagnostic endpoints, support bundles, crash reports, and debug logging MUST redact secret-bearing fields recursively, including nested structures and secret references.

#### CFG-05.05 — Operator controls MUST distinguish read-only inspection from mutating actions…

**Requirement:** Operator controls MUST distinguish read-only inspection from mutating actions, authenticate and authorize remote changes, audit actor/target/outcome, and prevent lost-update races with version checks or equivalent concurrency control.

#### CFG-05.06 — Configuration files and generated state MUST have explicit ownership…

**Requirement:** Configuration files and generated state MUST have explicit ownership and permissions. The service MUST detect unexpected symlinks, world-readable credentials, or writable-by-untrusted-user files where those conditions weaken the deployment threat model.

#### CFG-05.07 — Each setting with security or availability impact MUST document…

**Requirement:** Each setting with security or availability impact MUST document its default, valid range, effect, reloadability, and operational recovery path.

### ORG-01 — Functional Roles Accountability and Decision Rights

*Domain:* [organization](../../../torviello-enforcer/organization/README.md) · *Rule:* [01-functional-roles-accountability-and-decision-rights.md](../../../torviello-enforcer/organization/rules/01-functional-roles-accountability-and-decision-rights.md)

**Control objective.** People must know which outcomes they own, what authority they can exercise, who must review a decision, and who accepts residual risk. Clear authority is required for routine work, exceptions, emergencies, external commitments, and succession.

#### ORG-01.01 — The organization MUST maintain a current map of functions…

**Requirement:** The organization MUST maintain a current map of functions that perform product, engineering, security, privacy, legal/compliance coordination, finance/procurement, people operations, release, operations, support, and external communications as applicable. For each material workflow, identify one accountable owner, responsible performer(s), required consulted roles, informed parties, and delegate/escalation path; do not require a dedicated job title for every function.

#### ORG-01.02 — For architecture, security/privacy risk, release, data…

**Requirement:** For architecture, security/privacy risk, release, data use, spending, contracts, customer promises, public claims, policy exceptions, and incident disclosure, define who proposes, reviews, approves, executes, and verifies the decision. Set thresholds using impact, irreversibility, exposure, cost, and affected parties; high-impact decisions MUST receive independent review where practical.

#### ORG-01.03 — A delegation MUST state scope, limits, start/end…

**Requirement:** A delegation MUST state scope, limits, start/end, records required, subdelegation rules, and conditions for escalation. The delegator remains accountable unless the governing policy explicitly transfers accountability; informal availability or seniority MUST NOT be treated as unlimited authority.

#### ORG-01.04 — Where one person can initiate, approve, execute…

**Requirement:** Where one person can initiate, approve, execute, and attest to the same high-impact transaction, the workflow MUST use independent approval, automated safeguards, retrospective review, or another documented compensating control. Apply separation proportionate to actual fraud, error, privacy, security, and release risk.

#### ORG-01.05 — When schedule, cost, quality, security…

**Requirement:** When schedule, cost, quality, security, privacy, accessibility, and customer impact conflict, the decision record MUST state the tradeoff, evidence, affected stakeholders, residual risk, accountable approver, and rejected alternatives. The most senior person’s preference alone is not a substitute for the required decision evidence.

#### ORG-01.06 — Every material responsibility MUST have an escalation route…

**Requirement:** Every material responsibility MUST have an escalation route for blocked decisions, unavailable owners, suspected wrongdoing, unsafe instructions, or urgent user impact. The route MUST include a delegate or coverage procedure; an unresolved escalation MUST not be silently treated as approval.

#### ORG-01.07 — Role changes, departures, new products, new…

**Requirement:** Role changes, departures, new products, new jurisdictions, material incidents, and changed risk MUST trigger review of affected authority, access, approval thresholds, and succession. Remove stale owner names and privileges promptly.

### ORG-02 — Ethical Conduct Conflicts of Interest and Protected Reporting

*Domain:* [organization](../../../torviello-enforcer/organization/README.md) · *Rule:* [02-ethical-conduct-conflicts-of-interest-and-protected-reporting.md](../../../torviello-enforcer/organization/rules/02-ethical-conduct-conflicts-of-interest-and-protected-reporting.md)

**Control objective.** People must be able to act honestly, identify conflicts, raise concerns, and receive impartial handling without retaliation. The process must protect reporters and subjects while preserving fair review and applicable legal obligations.

#### ORG-02.01 — The organization MUST maintain an accessible conduct policy covering…

**Requirement:** The organization MUST maintain an accessible conduct policy covering honesty in records and claims, respectful behavior, confidentiality, responsible system/data use, gifts and inducements, conflicts, misuse of authority, and how to raise concerns. The policy MUST identify accountable owners, applicable scope, training, review date, and consequences under approved procedures.

#### ORG-02.02 — A person MUST disclose an actual, potential…

**Requirement:** A person MUST disclose an actual, potential, or reasonably perceived conflict before participating in the affected hiring, procurement, model/vendor selection, security review, incident investigation, compensation, or commercial decision. The authorized reviewer MUST decide recusal, independent review, disclosure, or other mitigation and retain a proportionate record.

#### ORG-02.03 — Rules for gifts, hospitality, referral payments…

**Requirement:** Rules for gifts, hospitality, referral payments, personal investments, outside work, and use of organizational information MUST be set by the accountable owner and reviewed against applicable law and contract. A person MUST seek review before accepting an item or commitment that could influence a decision, create a conflict, or imply organizational endorsement.

#### ORG-02.04 — People MUST be able to report suspected wrongdoing…

**Requirement:** People MUST be able to report suspected wrongdoing, unsafe practice, policy breach, retaliation, privacy/security incident, or serious product harm through at least one route independent of the person implicated. The route MUST explain confidentiality limits, urgent escalation, evidence preservation, and available external/legal avenues where applicable.

#### ORG-02.05 — A designated handler MUST acknowledge, classify urgency…

**Requirement:** A designated handler MUST acknowledge, classify urgency and risk, preserve relevant evidence, check conflicts, assign an impartial investigator or reviewer, and communicate expected next steps. Reports involving leadership, the normal handler, or a conflict MUST be routed to an independent alternative.

#### ORG-02.06 — Access to reports and investigation records MUST be limited…

**Requirement:** Access to reports and investigation records MUST be limited to need-to-know roles. The process MUST prohibit retaliation, protect against unnecessary disclosure, allow a fair opportunity to respond where appropriate, and distinguish allegation, evidence, finding, and action.

#### ORG-02.07 — The handler MUST record disposition, actions, rationale…

**Requirement:** The handler MUST record disposition, actions, rationale, and any required escalation or legal hold. The reporter SHOULD receive a status or closure update within confidentiality limits; trends and control failures MUST inform corrective action without identifying people unnecessarily.

#### PPL-02.03 — When a person is learning, working outside routine…

**Requirement:** When a person is learning, working outside routine competence, or handling an unusual high-risk task, assign a qualified reviewer/supervisor, define the allowed scope, and require checkpoints before irreversible or externally visible action.

**Requirement:** Support measures MAY include response and resolution times, backlog age, reopen rate, user impact, and satisfaction, but MUST be interpreted with case complexity, safety, fairness, and quality. Do not reward fast closure at the expense of accurate diagnosis or user outcome.
