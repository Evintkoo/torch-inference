# ENG-006 — Load models with bounded lifecycle, isolation, and capacity policy

**Requirement ID:** ENG-006  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-12](../../../torviello-engine/specifications/checks/AC-ENG-12.md)  
**Rule controls:** MOD-05, ARC-04, PERF-02

## 1. Normative requirement

Model loading MUST have an explicit lifecycle, coalesce concurrent loads, confine model paths to the configured root, prevent eviction of models with in-flight work, and enforce or explicitly disable a documented capacity policy.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

Loading is the point where files become executable state. Without an explicit lifecycle, a second request can observe a half-initialized model; without coalescing, concurrent clients multiply memory and startup cost; without reference-aware eviction, an unload can free a session that is still executing. The reference implementation has registration, scanning, loading, unloading, and a `max_loaded_models` setting that is documented as not enforced.

Torviello cannot inherit that gap. This requirement makes load state, path confinement, capacity, and in-flight protection normative so later caching and batching work rests on a sound model runtime.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to the model manager, registry loading endpoints, generic neural-network load and unload, and startup preload. It covers path resolution, descriptor validation, load state, concurrent access, capacity, and unload. It does not cover acquisition, which is ENG-005.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Expose queued, loading, ready, failed, unloading, and unloaded states with observable transitions.
- Coalesce concurrent loads for the same ID so only one initialization runs and all waiters observe the same result.
- Resolve every asset path against the configured model root, canonicalize it, and reject escapes including symlink targets.
- Track in-flight inference references and defer unload or eviction until no request holds the model.
- Apply a documented capacity policy for max_loaded_models or declare the limit disabled; never ignore a configured limit silently.
- Reject inference for a model that is unknown, failed, or not ready before dispatching to a backend.
- Release sessions, memory, and provider resources on unload and report the freed or retained result.

**Requirement:** Each model descriptor MUST declare required runtime/provider, supported data types and shapes, maximum input dimensions/sequence length, precision constraints, required assets, and estimated memory/compute needs when known.

#### MOD-05.02 — Model load MUST be a bounded lifecycle with explicit…

**Requirement:** Model load MUST be a bounded lifecycle with explicit queued, downloading, verifying, extracting, loading, ready, failed, unloading, and cancelled states where applicable. State transitions MUST be observable and invalid transitions rejected.

#### MOD-05.03 — Untrusted or third-party model parsing MUST run with least…

**Requirement:** Untrusted or third-party model parsing MUST run with least privilege and bounded CPU, memory, disk, file count, and wall-clock time. Custom operators or executable model payloads MUST be disabled unless an explicit review and isolation design approves them.

#### MOD-05.04 — Runtime adapters MUST enforce input and output shape…

**Requirement:** Runtime adapters MUST enforce input and output shape, dtype, tensor count, allocation, and execution-time limits before allocating or invoking backend operations.

#### MOD-05.05 — Cancellation and shutdown MUST release model resources within…

**Requirement:** Cancellation and shutdown MUST release model resources within a defined deadline or report the provider limitation. A stuck device operation MUST not block health, shutdown, or unrelated CPU requests indefinitely.

#### MOD-05.06 — GPU memory allocation and CPU fallback MUST be explicit…

**Requirement:** GPU memory allocation and CPU fallback MUST be explicit. Fallback MUST preserve the model contract or return a clear incompatibility/resource error; it MUST NOT silently change precision or quality behavior.

#### MOD-05.07 — Concurrent model loading and inference MUST have defined isolation…

**Requirement:** Concurrent model loading and inference MUST have defined isolation, memory admission, eviction, and fairness rules. A model MUST NOT evict or corrupt another active model without an explicit policy.

#### ARC-04.01 — Every module boundary MUST define the data it accepts…

**Requirement:** Every module boundary MUST define the data it accepts and returns, validation responsibility, error vocabulary, cancellation behavior, resource ownership, concurrency expectations, and lifecycle transitions.

#### ARC-04.02 — Dependencies MUST point toward stable abstractions. Dependency cycles…

**Requirement:** Dependencies MUST point toward stable abstractions. Dependency cycles MUST be prevented in the build graph or detected by an automated architecture check; shared modules MUST NOT import feature-specific policy or implementation details.

#### ARC-04.03 — A module MUST own or explicitly borrow every long-lived…

**Requirement:** A module MUST own or explicitly borrow every long-lived resource it creates, including threads, GPU contexts, memory pools, files, sockets, database connections, and child processes. Ownership and shutdown ordering MUST be explicit.

#### ARC-04.04 — Cross-module errors MUST preserve actionable internal context while mapping…

**Requirement:** Cross-module errors MUST preserve actionable internal context while mapping to a stable boundary error. A caller MUST be able to distinguish retryable, permanent, cancelled, unsupported, invalid-input, and resource-exhaustion outcomes where behavior differs.

#### ARC-04.05 — Failure propagation MUST be bounded. Define which failures…

**Requirement:** Failure propagation MUST be bounded. Define which failures are isolated to a request, module, model, process, or deployment; avoid cascading retries; and ensure cleanup runs on cancellation, timeout, partial initialization, and shutdown.

#### ARC-04.06 — Optional capability adapters MUST be conformant to shared lifecycle…

**Requirement:** Optional capability adapters MUST be conformant to shared lifecycle and error contracts. Capability discovery MUST not load the capability merely to determine whether it exists.

#### ARC-04.07 — Asynchronous boundaries MUST document queue ownership, backpressure…

**Requirement:** Asynchronous boundaries MUST document queue ownership, backpressure, ordering guarantees, delivery semantics, timeout budget, cancellation propagation, and behavior when the consumer disappears.

#### PERF-02.01 — Bound request concurrency, queue depth, batch size, model count

The project MUST bound request concurrency, queue depth, batch size, model count, model memory, download size, temporary disk, and request execution time. Defaults MUST be safe on the minimum supported machine.

#### PERF-02.02 — Make tradeoffs between throughput, tail latency, memory, CPU load

The project MUST make tradeoffs between throughput, tail latency, memory, CPU load, GPU utilization, energy use, and idle power explicit in profiles or configuration.

#### PERF-02.03 — Maintain a backend matrix for CPU, CUDA, Metal, Vulkan

The project MUST maintain a backend matrix for CPU, CUDA, Metal, Vulkan, and AMD paths. Each claimed combination lists provider/runtime/driver versions, hardware, build flags, support level, and known limits.

#### PERF-02.04 — Backend selection MUST be observable and deterministic

Backend selection MUST be observable and deterministic. Fallback MUST be allowed only when configured and MUST report why the requested provider was unavailable.

#### PERF-02.05 — Use load shedding and backpressure rather than allowing unbounded

The project MUST use load shedding and backpressure rather than allowing unbounded queues. Overload has a documented client response, metric, and recovery condition.

#### PERF-02.06 — Preserve a CPU-only baseline and validate inference correctness on

The project MUST preserve a CPU-only baseline and validate inference correctness on every advertised backend before performance tuning.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** ISO/IEC 25010:2023 (reliability, performance efficiency), TLA+, Loom, IETF BCP 14.

- Slot state MUST follow the declared lifecycle; initialization MUST be single-flight per model ID and every joiner MUST observe the same outcome.
- Reference acquisition and release MUST be linearizable; a slot with a non-zero reference count MUST NOT be freed, replaced, or evicted.
- Capacity policy MUST be enforced or explicitly disabled in configuration, and eviction MUST select only slots with zero references.
- Out-of-memory, provider failure, cancellation, and unload during load MUST leave the slot in a defined state with all resources released.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- A load advances through loading to ready and supports inference.
- Two simultaneous loads perform one initialization and return the same state.
- Unload waits for an active request and does not free a referenced model.
- Exceeding max_loaded_models follows the documented eviction or rejection policy.
- A path outside the root returns model.path_outside_root and is never read.
- Inference for a missing model returns model.not_found without backend dispatch.

Acceptance checks: [AC-ENG-12](../../../torviello-engine/specifications/checks/AC-ENG-12.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- A TLA+ model MUST check single-flight initialization, reference ownership, capacity, and drain; Loom MUST explore the reference primitive.
- Stress tests MUST interleave load, infer, unload, evict, cancel, and provider failure across many concurrent callers.
- Memory allocation failure MUST be injected at every initialization stage and MUST NOT produce a Ready slot.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Represent each model slot with a state machine and a reference count. Loads acquire a per-ID single-flight guard. Requests acquire a read guard for the duration of inference. Unload marks the slot draining, waits for the count to reach zero, then releases the backend session. Capacity policy runs under one lock so it cannot race with concurrent loads.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not publish a model as ready before initialization completes.
- Do not run duplicate initializations for the same ID without an explicit policy.
- Do not free a model while inference references it.
- Do not accept absolute or traversal paths from a client as model locations.
- Do not silently ignore a configured capacity limit.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Load a valid model and observe state transitions and a successful inference.
- 2. Issue two concurrent load requests and compare initialization evidence and responses.
- 3. Start a long inference, request unload, and observe deferral and completion.
- 4. Set a small capacity limit and load beyond it.
- 5. Attempt registration through an escaping path and a symlink.
- 6. Record logs, state transitions, and memory observations.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Run the lifecycle model checker and the Loom exploration and retain both reports.
- 10. Execute the interleaving stress suite with race detection and reference-leak accounting.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Load-state transitions and inference result for the valid case.
- Initialization count and responses for concurrent loads.
- Unload timing relative to the in-flight request.
- Capacity-policy output at the configured limit.
- Path-escape rejection and filesystem evidence.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The TLA+ and Loom reports with invariant coverage.
- Reference-count accounting before and after cancellation, error, unload, and eviction.
- Fault-injection results for OOM and provider failure.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- Inference observes a partially initialized model.
- Concurrent loads initialize twice or return inconsistent states.
- Unload frees a model under an active request.
- A configured capacity limit has no effect and no documented disabled status.
- A client path escapes the model root.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- Two initializations run for one model ID or joiners observe different outcomes.
- A slot is freed while a reference is held, or a reference is never released.
- A capacity limit is silently ignored.
