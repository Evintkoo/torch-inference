# ENG-017 — Map failures to one stable error contract

**Requirement ID:** ENG-017  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-23](../../torviello-engine/specifications/checks/AC-ENG-23.md)  
**Rule controls:** API-01, API-03, ARC-04

## 1. Normative requirement

Every failure MUST return one RFC 9457 `application/problem+json` error document containing a stable type, title, HTTP status, safe detail, request identifier, and stable engine code; status selection MUST distinguish validation, identity, absence, size, capacity, dependency, timeout, and internal failure.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability. At HPA-4, every error response MUST be an RFC 9457 `application/problem+json` document whose stable engine `code` extension identifies the condition and whose status mapping is exhaustive.

## 2. Why this requirement exists

Clients retry, back off, and surface errors based on status and code. The reference implementation defines an internal inference error type and an API error type with mappings from missing models to 404, invalid input to 400, timeouts to 504, GPU and model-load failures to 503, and serialization as a JSON body with error and status. Some internal detail still reaches messages and not every route uses the same shape.

Torviello requires one contract across HTTP and WebSocket transports, with codes stable across releases and messages safe for clients. The contract is also the basis for retry policy and for distinguishing client mistakes from engine health.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to all public HTTP routes, WebSocket error frames, model and registry operations, and optional upstream calls. It covers status selection, code vocabulary, message safety, correlation, and retry metadata. It does not prescribe client-side retry algorithms.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Use one RFC 9457 problem-details construction path with `type`, `title`, `status`, `detail`, `instance`, stable `code`, `category`, `retryable`, and request ID for every transport.
- Map each failure class to a documented status and never collapse distinct causes into 500.
- Keep codes stable and machine-readable; do not derive codes from prose or type names.
- Exclude stack traces, filesystem paths, secrets, dependency hostnames, and raw backend errors from client messages.
- Include Retry-After or equivalent guidance only when retry can succeed.
- Emit the same request ID in the body, response header, and log record.
- Ensure failures leave no partial success payload or side effect that contradicts the error.

#### API-01.01 — Maintain a machine-readable OpenAPI description for every public HTTP

The project MUST maintain a machine-readable OpenAPI description for every public HTTP API. The project MUST also treat it as a reviewed contract that describes paths, methods, schemas, validation constraints, authentication, authorization, status codes, error bodies, pagination, and streaming behavior.

#### API-01.02 — Keep request and response schemas in a dedicated API

The project MUST keep request and response schemas in a dedicated API schema module. The project MUST also group handlers by user-facing functionality. A handler MAY parse transport input, invoke a domain interface, and serialize a response; it MUST NOT own inference, persistence, registry policy, or cross-service business logic.

#### API-01.03 — Use one stable error envelope

The project MUST use one stable error envelope. The project MUST also include a safe error code and correlation identifier; return actionable client guidance without leaking stack traces, filesystem paths, secrets, internal service names, or dependency errors.

#### API-01.04 — Define compatibility for every endpoint

The project MUST define compatibility for every endpoint. Additive changes preserve existing semantics. Breaking changes require an explicit API version/deprecation plan, a migration window, and consumer-facing release notes.

#### API-01.05 — Generate reference documentation from the contract when practical

The project SHOULD generate reference documentation from the contract when practical. Handwritten endpoint examples MUST be checked against the current contract and implementation.

#### API-03.01 — The API MUST use HTTP methods and status codes…

**Requirement:** The API MUST use HTTP methods and status codes according to their defined semantics; a response status MUST accurately report whether the requested operation completed, was accepted for asynchronous processing, failed validation, lacked authorization, or failed in the service.

#### API-03.02 — An operation that can be retried MUST define idempotency…

**Requirement:** An operation that can be retried MUST define idempotency behavior. For non-idempotent writes, the API MUST accept a caller-supplied idempotency key or provide another documented deduplication mechanism, scope the key to the authenticated principal and operation, retain it for a documented period, and return the original outcome for a duplicate request.

#### API-03.03 — Retries MUST be safe under the endpoint contract…

**Requirement:** Retries MUST be safe under the endpoint contract. Clients MUST NOT blindly retry non-idempotent requests; servers MUST bound retryable work and expose Retry-After only when the service can honor the stated delay.

#### API-03.04 — Pagination MUST use stable ordering and bounded page size…

**Requirement:** Pagination MUST use stable ordering and bounded page size. Cursor-based pagination SHOULD be used when concurrent inserts or deletes can make offset pagination skip or repeat records; cursors MUST be opaque, integrity-protected when they encode state, and scoped to the caller and query.

#### API-03.05 — Long-running inference and model-management operations MUST define synchronous versus…

**Requirement:** Long-running inference and model-management operations MUST define synchronous versus asynchronous behavior, request identity, status transitions, result expiry, cancellation, and duplicate-submission handling.

#### API-03.06 — HTTP caching MUST be explicit for authenticated, user-specific…

**Requirement:** HTTP caching MUST be explicit for authenticated, user-specific, model, and administrative responses. Responses containing secrets or sensitive inference data MUST use no-store or an approved stricter policy; shared caches MUST NOT reuse them across principals.

#### API-03.07 — Content negotiation and compression MUST have explicit supported media…

**Requirement:** Content negotiation and compression MUST have explicit supported media types and size limits. The service MUST reject unsupported request and response encodings safely and MUST NOT allow compressed-size limits to be bypassed by decompression expansion.

#### ARC-04.01 — Every module boundary MUST define the data it accepts…

**Requirement:** Every module boundary MUST define the data it accepts and returns, validation responsibility, error vocabulary, cancellation behavior, resource ownership, concurrency expectations, and lifecycle transitions.

#### ARC-04.02 — Dependencies MUST point toward stable abstractions. Dependency cycles…

**Requirement:** Dependencies MUST point toward stable abstractions. Dependency cycles MUST be prevented in the build graph or detected by an automated architecture check; shared modules MUST NOT import feature-specific policy or implementation details.

#### ARC-04.03 — A module MUST own or explicitly borrow every long-lived…

**Requirement:** A module MUST own or explicitly borrow every long-lived resource it creates, including threads, GPU contexts, memory pools, files, sockets, database connections, and child processes. Ownership and shutdown ordering MUST be explicit.

#### ARC-04.04 — Cross-module errors MUST preserve actionable internal context while mapping…

**Requirement:** Cross-module errors MUST preserve actionable internal context while mapping to a stable boundary error. A caller MUST be able to distinguish retryable, permanent, cancelled, unsupported, invalid-input, and resource-exhaustion outcomes where behavior differs.

#### ARC-04.05 — Failure propagation MUST be bounded. Define which failures…

**Requirement:** Failure propagation MUST be bounded. Define which failures are isolated to a request, module, model, process, or deployment; avoid cascading retries; and ensure cleanup runs on cancellation, timeout, partial initialization, and shutdown.

#### ARC-04.06 — Optional capability adapters MUST be conformant to shared lifecycle…

**Requirement:** Optional capability adapters MUST be conformant to shared lifecycle and error contracts. Capability discovery MUST not load the capability merely to determine whether it exists.

#### ARC-04.07 — Asynchronous boundaries MUST document queue ownership, backpressure…

**Requirement:** Asynchronous boundaries MUST document queue ownership, backpressure, ordering guarantees, delivery semantics, timeout budget, cancellation propagation, and behavior when the consumer disappears.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** RFC 9457 problem details, RFC 9110, OpenAPI 3.2.1, OWASP ASVS 5.0.0 Level 3, IETF BCP 14.

- Every error response MUST use `application/problem+json` with RFC 9457 members (`type`, `title`, `status`, `detail`, `instance`) and engine extensions (`code`, `category`, `retryable`, `retry_after_ms`, `request_id`).
- The `type` URI MUST be stable and dereferenceable to documentation; `code` MUST be the stable machine identifier; `detail` MUST be safe for the caller.
- The status-and-code mapping MUST be exhaustive over all engine failures and MUST NOT depend on the transport or alias.
- A failure MUST never return success data, a partial result, a stack trace, a filesystem path, a secret, or a dependency host.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- Invalid input returns 400 with a stable code naming the parameter.
- Unknown resources return 404 with resource.not_found or a more specific stable code.
- Size violations return 413 with the affected limit.
- Saturation or open circuits return 429 or 503 with retry guidance where applicable.
- Dependency and inference deadlines return 504.
- Every error body is `application/problem+json`, validates against RFC 9457, contains the stable `code` and request ID, and contains no internal detail.

Acceptance checks: [AC-ENG-23](../../torviello-engine/specifications/checks/AC-ENG-23.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- Every error response MUST validate against the RFC 9457 schema and the OpenAPI contract.
- An exhaustive failure matrix MUST cover every code, status, retryability, alias, and WebSocket error frame.
- Property tests MUST prove that no failure path can produce the success envelope or omit the request ID.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Define a domain error enum with explicit variants and a single transport mapping function. Construct the envelope in one place, adding the request ID from execution context. Log the full internal cause at a safe level while returning only the mapped public fields.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not return a success-shaped body with an error field.
- Do not expose backend or dependency error text directly.
- Do not use 500 for validation, absence, size, or capacity failures.
- Do not omit the request identifier from an error.
- Do not change a code or status meaning in a compatible release.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Trigger each failure class through the public API.
- 2. Capture status, content type, type URI, engine code, safe detail, headers, and request ID.
- 3. Inspect messages for paths, secrets, stack traces, and dependency names.
- 4. Compare the error contract across HTTP and WebSocket paths.
- 5. Force an internal failure and confirm no partial success data.
- 6. Record requests, responses, and log correlation.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Execute the exhaustive failure matrix and validate every body against the schema.
- 10. Inspect bodies, headers, and logs for leakage and code/status drift across aliases.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- A response matrix covering 400, 401, 403, 404, 413, 429, 503, and 504.
- Code stability across equivalent cases.
- Redaction inspection of error messages.
- Correlation consistency between body, header, and log.
- Absence of partial success fields on failure.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The failure matrix with status, code, category, retryability, and request ID.
- Schema-validation results for every error response.
- The redaction inspection and alias-equivalence report.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- The same failure produces different codes across aliases.
- Internal detail appears in a client message.
- A client error is reported as 500.
- The request ID is missing or disagrees with logs.
- A failed request returns success data.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- An error uses a non-RFC 9457 body or a non-stable code.
- The same failure maps to different status or code across aliases.
- Internal detail or success data appears in a failure.
