# PA-031 — Documentation shall be publishable as a rendered site sourced from the repository's documentation content

**Requirement ID:** PA-031  
**Priority:** SHOULD  
**Source:** [product-and-architecture.md](../product-and-architecture.md) — User-facing surfaces  
**Status:** Active requirement; no implementation or evaluation evidence is recorded in this repository.

**Acceptance checks:** None recorded

## 1. Normative requirement

Documentation shall be publishable as a rendered site sourced from the repository's documentation content.

## 2. Why this requirement exists

This requirement is part of **User-facing surfaces** in [product-and-architecture.md](../product-and-architecture.md). It is traced to 7 rule control(s): DOC-01, DOC-02, DOC-03, DOC-05, DOC-06, MEDIA-04, MON-04. Those controls state the following purpose:

- **DOC-01 — Documentation source and publishing:** These controls govern **documentation source and publishing**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.
- **DOC-02 — Design system and accessibility:** These controls govern **design system and accessibility**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.
- **DOC-03 — Documentation architecture and content types:** This control defines the intended outcome for **documentation architecture and content types** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

### DOC-06 — Website design and delivery lifecycle

*Domain:* [documentation-and-design](../../../torviello-enforcer/documentation-and-design/README.md) · *Rule:* [06-website-design-and-delivery-lifecycle.md](../../../torviello-enforcer/documentation-and-design/rules/06-website-design-and-delivery-lifecycle.md)

**Control objective.** Guide a website from audience and content discovery to information architecture, interaction design, implementation, publication, operation, and retirement, with quality measured at user journeys and page boundaries.

#### DOC-06.01 — Establish audience, purpose, and success before choosing layout

For each site/surface, identify primary and secondary audiences, user goals, tasks, context, language, device/network assumptions, content owner, business or service outcome, and measurable success/failure signals. Validate consequential assumptions using user/operator evidence. Do not begin with a framework, visual style, or reference website as the problem statement.

#### DOC-06.02 — Define information architecture and route contracts

Create a page/route inventory and navigation model before implementation. For each route specify purpose, intended audience, content source and owner, access level, canonical URL/redirect behavior, metadata needs, and links to adjacent journeys. Group content by user mental model and task rather than internal org chart. Define search and findability needs for substantial content sets.

#### DOC-06.03 — Design complete user journeys and state transitions

For each critical journey, document entry points, prerequisites, user actions, decisions, success, validation, loading, empty, permission-denied, partial, offline/timeout, service-error, retry, and recovery states. Define confirmation for destructive or irreversible actions, preservation of user input after correctable errors, and navigation/back behavior. Every state MUST have an accessible message and a clear next action where one exists.

#### DOC-06.04 — Specify content and interaction before visual polish

Write or structure representative content and labels before final layout. Use semantic headings, links, buttons, forms, tables, and landmarks according to purpose. Make labels describe outcomes, validation errors identify how to recover, and help text available at the decision point. Separate content from presentation where localization, reuse, or editorial ownership requires it. Public claims MUST map to approved evidence and licensing.

#### DOC-06.05 — Design responsive, resilient behavior from content constraints

Define layout behavior across viewport sizes, zoom/reflow, pointer and keyboard input, orientation, reduced motion, and constrained network/device capability. Content MUST remain readable and task-completable without relying on a specific screen size or hover. Prefer progressive enhancement and platform semantics where they reduce failure modes. Specify supported browser/device profiles and fallbacks for unavailable scripts, APIs, fonts, or media according to the product support matrix.

#### DOC-06.06 — Apply accessibility and privacy requirements in design

Design to the project's WCAG 2.2 AA target and relevant legal/product requirements. Include keyboard path and visible focus, semantic structure, accessible names/descriptions, contrast, text resizing/reflow, error identification, non-color cues, captions/transcripts for meaningful media, and reduced-motion behavior. Define whether analytics, cookies, or telemetry are necessary; minimize collection, document consent/notice and retention where applicable, and do not collect sensitive fields through analytics or URL parameters.

#### DOC-06.07 — Define user-centered performance and reliability budgets

Specify measurable budgets for critical routes and tasks, including transfer and resource size, loading, interaction responsiveness, layout stability, API latency, failure states, and supported network/device conditions. Choose current field or lab measures suited to the surface and explain sampling limits. Optimize the journey bottleneck using measurements; do not trade away accessibility, security, or correctness for a synthetic score. Define behavior when the server or essential API is unavailable.

#### DOC-06.08 — Design routes and content for security and search/publication needs

For public content define indexability, canonicalization, metadata, robots/sitemap policy, redirects, and link lifecycle as appropriate; never expose private routes or secrets through indexing configuration. For authenticated surfaces, specify session/authentication transitions, authorization-denied behavior, CSRF/XSS/input risks, content security policy, safe external links, and cache behavior in coordination with security rules. Treat all user and CMS content as untrusted input and encode it for its output context.

#### DOC-06.09 — Keep site ownership and runtime boundary explicit

Each site MUST have a product-area owner, build/test/deploy path, runtime dependencies, environment/configuration contract, content/design ownership, support route, and rollback/decommission procedure. Landing, docs, marketing/media, admin, and inference-engine UIs MUST NOT acquire hidden runtime/build dependencies on one another. Reuse MAY occur through versioned design packages with owners and compatibility policy.

#### DOC-06.10 — Verify journeys on rendered pages and maintain after publication

Before release, test representative routes at supported viewports and input modes, keyboard-only and assistive technology paths, accessibility, browser console/network failures, links/forms, content correctness, performance budgets, security headers, and build/deployment rollback. Record route/profile coverage and known gaps. After publication monitor availability, errors, broken links, accessibility feedback, performance, search/indexing behavior where relevant, and content freshness; review ownership and retire stale routes safely.

#### DOC-06.11 — Integrate video as accessible, privacy-aware page content

When a page uses video, the page MUST provide a descriptive title, poster, keyboard-accessible controls, captions in the supported language(s), transcript or equivalent content path, responsive dimensions, layout-space reservation, and a clear fallback. It MUST NOT rely on video alone to communicate essential product information or autoplay with sound. Before loading third-party player code, assess cookies, tracking, external requests, consent, availability, accessibility, and provider exit; use click-to-load or an approved first-party player when needed. Coordinate export profiles and source ownership with the media production controls.

### MEDIA-04 — Production code, assets, and website integration

*Domain:* [media-production](../../../torviello-enforcer/media-production/README.md) · *Rule:* [04-production-code-and-web-integration.md](../../../torviello-enforcer/media-production/rules/04-production-code-and-web-integration.md)

**Control objective.** Treat video creation automation, large assets, and website playback as maintained product work with clear boundaries, reproducible outputs, quality gates, accessibility, privacy, and operational ownership.

#### MEDIA-04.01 — Select tools by production needs and lifecycle cost

Before choosing an editor/render framework or automation, compare the actual work: manual editing versus data-driven/programmatic scenes; number of repeated variants/locales; timeline/audio requirements; collaboration/review; preview speed; deterministic rendering; format/codec support; accessibility sidecars; platform availability; licenses; security/update posture; hardware/GPU needs; offline use; CI duration/cost; and skill/maintenance burden. Keep creative editing tools where they provide needed timing and judgment; use code-driven rendering when reusable data/templates and reproducible variants justify it. Do not adopt a framework or AI media tool solely because it is available or popular. Record decision owner, tested prototype, alternatives, limitations, and reconsideration triggers.

#### MEDIA-04.02 — Give media production a separate monorepo boundary

When production workflows are maintained in this repository, use a dedicated `media/` product area with its own `README.md` and `AGENTS.md`, toolchain/lockfiles, scripts, tests, asset policy, build instructions, and ownership. It MUST NOT be a dependency of the inference engine’s build, runtime, install, or release profiles. Define explicit interfaces to shared brand assets or website packages; avoid cross-area private imports and toolchain coupling. The `media/` owner MUST maintain a supported build/render entry point and document required licenses, hardware, and external inputs.

#### MEDIA-04.03 — Organize work products for discoverability and safe revision

Use a documented layout equivalent to: `brand/` for approved style guide/tokens; `templates/` for content-type templates and reusable scene components; `projects/<video-id>/` for brief, script, storyboard, claims, rights manifest, and edit/render config; `assets/` for approved shared source media; `automation/` for render, QC, and packaging code; and `releases/<video-id>/<version>/` or an approved artifact store for release manifests and outputs. Large binaries MUST use an approved large-file or artifact store with stable IDs/checksums and access controls rather than silently bloating ordinary source history. Keep project-specific raw footage segregated and access-limited.

#### MEDIA-04.04 — Represent automated scenes as typed, validated inputs

For programmatic video, model scenes, durations, assets, narration, captions, transitions, and output profiles in a validated schema. Give each scene a stable identifier and explicit required/optional assets, timing, locale, and accessibility text. Fail early with actionable diagnostics for missing media, unsupported dimensions, unresolved fonts, invalid time ranges, unlicensed inputs, missing captions, or contradictory project settings. Avoid arbitrary code evaluation or unchecked paths in user-editable project manifests; treat asset paths and project input as untrusted data. Keep rendering deterministic where the toolchain permits and disclose nondeterministic codecs/metadata.

#### MEDIA-04.05 — Pin and inventory production dependencies

Record editor/render-tool versions, plugins, fonts, codecs, templates, scripts, model/AI services if used, and licenses. Pin automated build dependencies and verify downloaded tools/assets; store required binaries in the approved cache/mirror for offline production when offline repeatability is a project requirement. Identify end-of-life/deprecated formats and test migration. Do not promise bit-identical output when codecs, hardware encoders, timestamps, or external services prevent it; define the reproducibility level and verify content/metadata checksums appropriately.

#### MEDIA-04.06 — Build a layered validation pipeline

A production pipeline MUST support separate fast checks and full render/QC. At minimum, validate: project manifest/schema; required sources and rights metadata; broken/missing media and font dependencies; safe paths and secrets; script/claims references; caption and transcript existence and timing; render dimensions/duration/frame rate/codec/color/audio profile; audio/video synchronization; loudness/peak limits for chosen target; black/silent/frozen frames where relevant; output integrity; and playback. Add visual snapshot or representative frame review only as supporting evidence; it cannot replace watching the complete final video. Store machine-readable QC report linked to source revision and render artifact.

#### MEDIA-04.07 — Make builds and renders resource-bounded and resumable

Specify expected render time/storage/GPU/CPU and maximum source dimensions/duration per profile. Provide progress, cancellation, safe temporary-file cleanup, disk-space checks, retry behavior, and recovery from interrupted render without corrupting approved outputs. Bound parallel encodes to available resources. A release render MUST be distinguishable from a preview and MUST NOT overwrite an approved artifact without a new version and review.

#### MEDIA-04.08 — Define explicit delivery profiles and manifests

Maintain versioned profiles for intended destinations rather than one universal export. Each profile defines container, video/audio codecs, dimensions/aspect ratio, frame rate, color space/HDR policy, bitrate or quality mode, audio layout/loudness target, captions, thumbnail, metadata, and validation commands. Record profile version, source revision, toolchain versions, output checksum, and destination requirements in a release manifest. Recheck external destination specifications at release time; keep archived master settings separate from delivery transcodes.

#### MEDIA-04.09 — Integrate video into websites as an accessible, privacy-aware component

A website video component MUST include a poster/thumbnail, descriptive title, playback controls, caption tracks, transcript or equivalent text path, accessible keyboard/focus behavior, responsive sizing, fallback/error behavior, and no autoplay with sound. Provide a local/first-party player or click-to-load consent pattern when third-party embeds would set cookies, load trackers, or contact external domains before user interaction. Lazy-load noncritical media, reserve layout space to prevent layout shift, and do not make video the sole means to understand the page or complete a task. Record supported formats, caption languages, privacy behavior, and fallback.

#### MEDIA-04.10 — Release and operate the production system safely

Deploy production tooling and website changes through their owning release controls. Restrict credentials, signing keys, publication tokens, and private raw media to least privilege; use secret stores rather than project config. Publish only approved release manifests. Monitor render failures, storage saturation, artifact integrity, player failures, accessibility reports, and broken links at a level proportionate to use. Define rollback for website/player releases, disable/revoke publication credentials on compromise, and provide a manual fallback procedure if the render or hosting pipeline is unavailable.

#### MEDIA-04.11 — Test behavior at unit, integration, and release seams

Test scene/schema parsing and timeline calculations as unit tests; test asset resolution, caption association, and render invocation as integration tests; and test representative full renders and playback as release checks. Include malformed manifests, missing assets/fonts, unsupported profile, cancellation, disk exhaustion, encoder/tool failure, caption mismatch, and privacy/embed behavior as applicable. Use tiny synthetic fixtures in CI; reserve full-quality renders for scheduled or release workflows. Document hardware and resource prerequisites; report skipped GPU or platform checks honestly.

#### MON-04.01 — Landing pages, documentation, demos, and marketing…

#### MON-04.02 — Product media MUST be stored and versioned separately from…

**Requirement:** Product media MUST be stored and versioned separately from executable runtime assets unless a documented product use requires bundling. Media build tooling MUST not enter the inference package dependency graph.

#### MON-04.03 — Content that names a release, endpoint, UI…

**Requirement:** Content that names a release, endpoint, UI behavior, or performance claim MUST identify its source artifact and release version so stale content can be detected.

#### MON-04.04 — Demo pipelines MUST use synthetic or explicitly approved data…

**Requirement:** Demo pipelines MUST use synthetic or explicitly approved data and reproducible model/runtime versions. They MUST not publish credentials, private user data, internal endpoints, or unsupported behavior.

#### MON-04.05 — Shared design tokens and components MUST be consumed through…

**Requirement:** Shared design tokens and components MUST be consumed through a defined package or source interface; independent applications MUST have a compatibility and versioning policy for those assets.

#### MON-04.06 — Published docs/media MUST retain required attribution, model notices…

**Requirement:** Published docs/media MUST retain required attribution, model notices, font/image licenses, and accessibility alternatives in both source and rendered output.

#### MON-04.07 — External hosting failure MUST not prevent a clean local…

**Requirement:** External hosting failure MUST not prevent a clean local engine build or local documentation preview when the relevant assets are already present.

- **MEDIA-04:** Pass when production tools and assets are isolated, understandable, validated, reproducible to the stated level, resource-bounded, and integrated accessibly and privately. Fail when source/tool provenance is missing, release output cannot be traced, engine builds depend on media tooling, critical failures go undetected, or website playback excludes users or violates privacy expectations. Not applicable requires that no code/tool/site integration is used and an owner documents the manual control path.
- **MON-04:** Assess each control ID as **pass**, **fail**, or **not applicable**. Pass requires every applicable MUST to be implemented and supported by current evidence. Fail applies when behavior contradicts a requirement, enforcement is bypassable, evidence is missing/stale, or a required scenario cannot be reproduced. Not applicable requires a condition stated by the requirement and reviewer rationale.

## 8. Prohibited conditions

The following conditions are explicitly prohibited by the mapped controls. Any one of them is sufficient to fail the requirement.

- [DOC-01] The project MUST NOT maintain conflicting copies of setup instructions as independent sources of truth
- [DOC-01] The project MUST NOT document an endpoint or build option that does not exist in the supported release
- [DOC-01] The project MUST NOT expose secrets in examples or leave unverified command blocks
- [DOC-02] The project MUST NOT use color or animation as the only way to communicate state
- [DOC-02] The project MUST NOT create one-off controls when a shared component is appropriate
- [DOC-02] The project MUST NOT claim WCAG conformance based only on automated tooling
- [DOC-03] Do not keep conflicting quick-start copies with different commands or configuration schemas.
- [DOC-03] Do not describe planned capabilities as available or use screenshots that conceal required warnings and choices.
- [DOC-05] Do not publish marketing claims that exceed measured support or legal approval.
- [DOC-05] Do not use real user data in design prototypes or media unless it is explicitly authorized and protected.
- [DOC-06] Designing pages solely as visual mockups without content, routes, task flows, and non-happy states.
- [DOC-06] Using inaccessible custom controls when semantic native controls meet the need.
- [DOC-06] Relying on client-side rendering for critical content without an approved crawlability, resilience, and accessibility strategy.
- [DOC-06] Treating automated audits or a single device screenshot as proof of usability or accessibility.
- [MEDIA-04] Coupling video rendering or marketing site dependencies into the inference engine’s build/runtime by convenience.
- [MEDIA-04] Publishing artifacts with no source revision, delivery profile, checksum, rights record, or QC outcome.
- [MEDIA-04] Passing an automated QC report as a substitute for human review of narrative, accuracy, accessibility, and complete playback.
- [MEDIA-04] Loading third-party players or trackers before required consent/privacy behavior is implemented.
- [MEDIA-04] Embedding secrets or publication credentials in source, project files, URLs, or logs.
- [MON-04] Do not package marketing/demo tooling into the backend-only engine.
- [MON-04] Do not treat a public media URL as proof of redistribution rights.
