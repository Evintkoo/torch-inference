# ENG-021 — Publish and evolve a validated HTTP contract

**Requirement ID:** ENG-021  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-27](../../../torviello-engine/specifications/checks/AC-ENG-27.md), [AC-ENG-06](../../../torviello-engine/specifications/checks/AC-ENG-06.md)  
**Rule controls:** API-01, API-04, GOV-08

## 1. Normative requirement

The engine MUST publish a machine-readable OpenAPI contract for its public HTTP surface, keep the router and document synchronized, make versioned aliases behaviorally identical, and follow an explicit deprecation and compatibility process for breaking changes.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability. At HPA-4, the contract MUST be valid OpenAPI 3.2.1, lint-clean, router-parity complete, and diffed for breaking changes on every revision.

## 2. Why this requirement exists

An inference engine is embedded in applications, CI pipelines, and agent runtimes. Undocumented routes and silent schema changes break those consumers without a compile error. The reference implementation publishes `/openapi.json`, exposes many routes under both unversioned and `/v1` paths, and keeps operational routes unversioned.

Torviello requires the contract to be reviewed and validated rather than hand-maintained folklore. Compatibility rules, alias behavior, deprecation signals, and an API inventory are part of the deliverable, along with a check that every public route appears in the contract.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to all public HTTP routes and their schemas, including inference, catalog, health, metrics, and optional assistant routes. It covers OpenAPI accuracy, versioned aliases, deprecation, API inventory, and contract validation. It does not require code generation for clients.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Maintain a valid OpenAPI 3.2.1 document describing paths, methods, schemas, constraints, auth, statuses, errors, and streaming media types.
- Verify in CI that every public router entry appears in the document and every documented path resolves.
- Register versioned aliases to the same handler and test behavioral equality.
- Keep operational endpoints on their documented unversioned paths and avoid advertising duplicate surfaces.
- Announce deprecation with a successor, migration window, and removal date before removing a route or field.
- Treat additive changes as compatible and record them; require a version or explicit migration for breaking changes.
- Keep the API inventory and reference documentation generated from or checked against the contract.

#### API-01.01 — Maintain a machine-readable OpenAPI description for every public HTTP

The project MUST maintain a machine-readable OpenAPI description for every public HTTP API. The project MUST also treat it as a reviewed contract that describes paths, methods, schemas, validation constraints, authentication, authorization, status codes, error bodies, pagination, and streaming behavior.

#### API-01.02 — Keep request and response schemas in a dedicated API

The project MUST keep request and response schemas in a dedicated API schema module. The project MUST also group handlers by user-facing functionality. A handler MAY parse transport input, invoke a domain interface, and serialize a response; it MUST NOT own inference, persistence, registry policy, or cross-service business logic.

#### API-01.03 — Use one stable error envelope

The project MUST use one stable error envelope. The project MUST also include a safe error code and correlation identifier; return actionable client guidance without leaking stack traces, filesystem paths, secrets, internal service names, or dependency errors.

#### API-01.04 — Define compatibility for every endpoint

The project MUST define compatibility for every endpoint. Additive changes preserve existing semantics. Breaking changes require an explicit API version/deprecation plan, a migration window, and consumer-facing release notes.

#### API-01.05 — Generate reference documentation from the contract when practical

The project SHOULD generate reference documentation from the contract when practical. Handwritten endpoint examples MUST be checked against the current contract and implementation.

#### API-04.01 — The project MUST maintain an inventory of every externally…

**Requirement:** The project MUST maintain an inventory of every externally reachable API surface, including engine HTTP routes, admin routes, health/metrics endpoints, callbacks, internal service APIs exposed through a gateway, and protocol versions. Each entry MUST identify owner, audience, exposure, auth policy, lifecycle state, and contract location.

#### API-04.02 — Production API changes MUST be classified as compatible…

**Requirement:** Production API changes MUST be classified as compatible, conditionally compatible, or breaking against the published contract and known consumers. Reviewers MUST examine field requiredness, defaults, enum expansion, response shape, status codes, ordering, pagination, streaming framing, and authorization changes.

#### API-04.03 — Breaking changes MUST use a versioning and migration policy…

**Requirement:** Breaking changes MUST use a versioning and migration policy chosen for the product (URI, media type, or another explicit scheme), with a published compatibility window, migration guidance, sunset date, and owner. Deprecation notices MUST be observable before removal.

#### API-04.04 — Every deployed version MUST be discoverable by operators…

**Requirement:** Every deployed version MUST be discoverable by operators. Remove unsupported versions from the deployment inventory only after traffic and consumer evidence show that the deprecation window has completed.

#### API-04.05 — Debug, experimental, and internal endpoints MUST be…

**Requirement:** Debug, experimental, and internal endpoints MUST be excluded from production packages or protected by an explicit access policy. Their presence and exposure MUST be checked in release qualification.

#### API-04.06 — OpenAPI contracts MUST be reviewed in the same change…

**Requirement:** OpenAPI contracts MUST be reviewed in the same change as implementation. Generated schemas MUST be reproducible; generated diffs MUST not hide semantic changes in hand-maintained descriptions or security declarations.

#### GOV-08.01 — Every interface and event between components MUST be defined…

**Requirement:** Every interface and event between components MUST be defined in a machine-readable contract covering endpoints or channels, inputs, outputs, error shapes, and event payloads. OpenAPI, JSON Schema, AsyncAPI, or an equivalent schema format MUST be used; prose alone MUST NOT be the contract.

#### GOV-08.02 — Consumers and providers MUST agree on the contract, and the…

**Requirement:** Consumers and providers MUST agree on the contract, and the repository MUST contain contract tests that verify both sides against it. A contract without a failing-then-passing contract test MUST NOT be treated as verified.

#### GOV-08.03 — Contract changes MUST be versioned and MUST state…

**Requirement:** Contract changes MUST be versioned and MUST state compatibility impact. A breaking change MUST have a migration or deprecation path, and the affected consumers MUST be identified before the change is released.

#### GOV-08.04 — Contracts MUST be linted or validated by tooling as part of…

**Requirement:** Contracts MUST be linted or validated by tooling as part of the required checks, and validation failures MUST block the change. A schema that is not parsed by any check is unverified documentation.

#### GOV-08.05 — Every contract element used by implementation or tests MUST be…

**Requirement:** Every contract element used by implementation or tests MUST be traceable to a specification and requirement identifier, and the contract MUST be referenced by the tests that exercise it. An orphan endpoint or event is a defect.

#### GOV-08.06 — An approved contract MUST NOT be altered to match an…

**Requirement:** An approved contract MUST NOT be altered to match an implementation that does not satisfy it. Contract changes REQUIRE human authority and MUST be recorded as a contract decision with consumer impact and versioning.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** OpenAPI 3.2.1, RFC 9457, Semantic Versioning 2.0.0, OWASP API Security Top 10 2023, IETF BCP 14.

- The OpenAPI 3.2.1 document MUST be the reviewed source of truth and MUST pass schema validation, linting, and reference resolution.
- Router parity MUST be bidirectional: every route is documented and every documented route resolves; aliases MUST preserve status, headers, and body shape.
- Breaking changes MUST be detected by a contract diff and MUST require a version, deprecation plan, migration window, and consumer-facing notes.
- Schemas MUST express required fields, constraints, formats, content types, and RFC 9457 error responses.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- The OpenAPI document validates and covers every public route.
- Unversioned and /v1 aliases return the same status and body shape for equivalent requests.
- Operational endpoints remain unversioned as documented.
- A deprecated route returns a deprecation signal and names its successor.
- An additive field does not change existing required fields or statuses.
- An unknown route returns 404 with the standard RFC 9457 problem document.

Acceptance checks: [AC-ENG-27](../../../torviello-engine/specifications/checks/AC-ENG-27.md), [AC-ENG-06](../../../torviello-engine/specifications/checks/AC-ENG-06.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- Spectral or an equivalent linter MUST pass with the project ruleset and zero suppressed findings.
- A router-parity test MUST enumerate the live router and compare it with the contract in both directions.
- A breaking-change diff MUST run on every change and MUST fail on an unintended removal, type change, or status change.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Generate the OpenAPI document from the same route and schema definitions used by the server where practical. Maintain a route inventory test that fails on drift. Keep aliases as explicit registrations of the same handler. Record deprecation metadata in the contract and the changelog.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not add a public route without documenting it.
- Do not let aliases drift to different handlers or schemas.
- Do not remove or rename a field without a migration path.
- Do not change status codes or error meanings in a compatible release.
- Do not treat internal Rust types as the public contract by accident.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Validate the OpenAPI document and compare its paths with the router inventory.
- 2. Send equivalent requests to unversioned and versioned aliases and compare responses.
- 3. Inspect operational route exposure.
- 4. Call a route marked deprecated and inspect the signal.
- 5. Add a harmless optional field in a fixture and verify compatibility checks.
- 6. Record commands, route inventory, and comparison results.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Validate, lint, and resolve the contract; then run router parity.
- 10. Run the breaking-change diff against the released baseline and inspect aliases.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- OpenAPI validation output and route-coverage diff.
- Alias response comparison.
- Deprecation signal sample.
- Compatibility check for an additive change.
- Unknown-route RFC 9457 problem document.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- Contract validation and lint reports.
- The bidirectional route-parity report.
- The breaking-change diff and alias-equivalence tests.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- A public route is absent from the contract.
- A documented route does not exist or has a different schema.
- Aliases behave differently.
- A breaking change ships without deprecation.
- Unknown routes return a non-standard error.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- A route exists in only one of the router and the contract.
- A schema omits required fields, constraints, or error content types.
- An alias differs in status, headers, or body shape.
