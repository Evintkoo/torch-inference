### CFG-03 — Configuration lifecycle and safe reload

*Domain:* [configuration](../../../torviello-enforcer/configuration/README.md) · *Rule:* [03-configuration-lifecycle-and-safe-reload.md](../../../torviello-enforcer/configuration/rules/03-configuration-lifecycle-and-safe-reload.md)

**Control objective.** This control defines the intended outcome for **configuration lifecycle and safe reload** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### CFG-03.01 — Configuration MUST be parsed into one typed candidate…

**Requirement:** Configuration MUST be parsed into one typed candidate and validated completely before the application binds public listeners, activates models, or mutates persistent state.

#### CFG-03.02 — Validation MUST report the setting name and a safe…

**Requirement:** Validation MUST report the setting name and a safe corrective action without echoing secret values or exposing internal paths. Multiple errors SHOULD be reported together when doing so does not expose sensitive material.

#### CFG-03.03 — Configuration reload MUST be atomic: build and validate…

**Requirement:** Configuration reload MUST be atomic: build and validate a complete candidate, verify its dependencies, then switch active state at a defined boundary. If any step fails, the running system MUST retain the last known-good configuration and report the reload failure.

#### CFG-03.04 — Each setting MUST declare whether it is startup-only…

**Requirement:** Each setting MUST declare whether it is startup-only, reloadable, or dynamically sampled. A reload MUST NOT leave components using incompatible snapshots unless the consistency model is explicitly designed and tested.

#### CFG-03.05 — Configuration watchers MUST debounce partial file writes, handle…

**Requirement:** Configuration watchers MUST debounce partial file writes, handle rename-based replacement, permission changes, deletion, and invalid intermediate files, and MUST avoid unbounded reload loops.

#### CFG-03.06 — Configuration schema evolution MUST define defaulting, deprecation…

**Requirement:** Configuration schema evolution MUST define defaulting, deprecation, migration, unknown-field, and downgrade behavior. A newer binary MUST NOT silently rewrite a file such that the prior supported version cannot start unless that migration is explicit and backed up.

#### CFG-03.07 — Operator-facing effective-configuration output MUST redact credentials, identify source…

**Requirement:** Operator-facing effective-configuration output MUST redact credentials, identify source and precedence for each value, and distinguish explicit values from defaults without exposing secret contents.

### MOD-01 — Model identity, metadata, and compatibility

*Domain:* [models](../../../torviello-enforcer/models/README.md) · *Rule:* [01-model-identity-metadata-and-compatibility.md](../../../torviello-enforcer/models/rules/01-model-identity-metadata-and-compatibility.md)

**Control objective.** These controls govern **model identity, metadata, and compatibility**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### MOD-01.01 — Give each model artifact a stable model ID

The project MUST give each model artifact a stable model ID and immutable version or digest. Registry records specify task, format, source, license, input/output schema, tokenizer/preprocessor requirements, runtime/provider constraints, memory estimates, supported platform, and verification status.

#### MOD-01.02 — Separate model metadata from model bytes

The project MUST separate model metadata from model bytes. A registry entry cannot claim available or ready until the corresponding artifact is present, digest-verified, compatible, and successfully loaded for the selected runtime.

#### MOD-01.03 — Treat model files, tokenizer data, configuration, and metadata as

The project MUST treat model files, tokenizer data, configuration, and metadata as untrusted supply-chain inputs. The project MUST also record provenance and permitted redistribution.

#### MOD-01.04 — Define compatibility checks explicitly

The project MUST define compatibility checks explicitly. The project MUST NOT infer task, architecture, or provider support from filenames or extensions alone.

#### MOD-01.05 — Preserve immutable version history

The project MUST preserve immutable version history. Updating a model means creating a new version and an explicit promotion or rollback operation.

### MOD-02 — Secure download, install, and activation

*Domain:* [models](../../../torviello-enforcer/models/README.md) · *Rule:* [02-secure-download-install-and-activation.md](../../../torviello-enforcer/models/rules/02-secure-download-install-and-activation.md)

**Control objective.** These controls govern **secure download, install, and activation**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### MOD-02.01 — Restrict downloads to configured or allowlisted sources

The project MUST restrict downloads to configured or allowlisted sources. The project MUST also enforce TLS verification, safe redirect rules, connection and total timeouts, maximum size, disk-space checks, and bounded retries.

#### MOD-02.02 — Verify a cryptographic digest or signature before extracting

The project MUST verify a cryptographic digest or signature before extracting or loading an artifact. Reject mismatches and retain evidence of the verification result.

#### MOD-02.03 — Extract archives into a staging directory after rejecting absolute

The project MUST extract archives into a staging directory after rejecting absolute paths, parent traversal, links outside the destination, duplicate collisions, and excessive expanded size.

#### MOD-02.04 — Install and activate atomically

The project MUST install and activate atomically. A failed or interrupted download, extraction, or model load leaves the prior active artifact intact.

#### MOD-02.05 — Separate download state, installed state, and active state

The project MUST separate download state, installed state, and active state. The project MUST also report each explicitly to operators and readiness checks.

#### MOD-02.06 — Provide a preloaded/offline installation path for restricted deployments

The project MUST provide a preloaded/offline installation path for restricted deployments.

### MOD-03 — Registry administration and audit

*Domain:* [models](../../../torviello-enforcer/models/README.md) · *Rule:* [03-registry-administration-and-audit.md](../../../torviello-enforcer/models/rules/03-registry-administration-and-audit.md)

**Control objective.** These controls govern **registry administration and audit**. #### MOD-03.01 — Registry mutations MUST require authenticated identity and least-privilege authorization

#### MOD-03.02 — Validate edits through one schema and policy layer whether

The project MUST validate edits through one schema and policy layer whether they arrive through an admin API or a controlled manual file change.

#### MOD-03.03 — Audit actor, time, action, target model/version, outcome, and change

The project MUST audit actor, time, action, target model/version, outcome, and change identifier. The project MUST NOT log tokens or secret configuration values.

#### MOD-03.04 — Make changes transactional: validate a candidate, persist it safely

#### MOD-03.05 — The standalone engine MUST operate with a local registry/cache

The standalone engine MUST operate with a local registry/cache and MUST NOT require a hosted control plane for local inference

#### MOD-06.01 — Model manifests MUST bind publisher identity, immutable model/version…

**Requirement:** Model manifests MUST bind publisher identity, immutable model/version identity, file list, size, cryptographic digest, license, compatibility metadata, and any signature or attestation to the exact bytes installed.

#### MOD-06.02 — Downloaded model files MUST be written to an isolated…

**Requirement:** Downloaded model files MUST be written to an isolated temporary location, size-limited during transfer, verified before activation, and atomically moved into the immutable content-addressed store only after complete validation.

#### MOD-06.03 — Archive extraction MUST reject path traversal, absolute paths…

**Requirement:** Archive extraction MUST reject path traversal, absolute paths, duplicate/conflicting paths, symlink escape, excessive file count, excessive expansion, and special device files.

#### MOD-06.04 — Update trust MUST define trusted roots, key rotation…

**Requirement:** Update trust MUST define trusted roots, key rotation, expiration, rollback/freeze/mix-and-match defenses, metadata freshness, and recovery when signing keys are suspected compromised; use TUF or an equivalent reviewed update framework for remote catalogs.

#### MOD-06.05 — Failed network, signature, digest, license…

**Requirement:** Failed network, signature, digest, license, compatibility, disk-write, or activation checks MUST preserve the last known-good model and leave a diagnosable failure record.

#### MOD-06.06 — Local/offline installation MUST have an import path that verifies…

**Requirement:** Local/offline installation MUST have an import path that verifies the same identity, integrity, license, and compatibility data as remote installation.

#### MOD-06.07 — Model deletion MUST distinguish user-owned, shared, active…

**Requirement:** Model deletion MUST distinguish user-owned, shared, active, cached, and system-provided assets; active references MUST be released safely before bytes are removed.

### OPS-01 — Service lifecycle and readiness

#### OPS-05.05 — Capacity alerts MUST warn before service objectives are breached…

#### OPS-05.06 — Operational toil MUST be measured where repeated manual repair…

**Requirement:** Operational toil MUST be measured where repeated manual repair occurs; recurring recovery actions SHOULD be automated only after failure modes and guardrails are understood.

### OPS-06 — Operational Roles Coverage Handover and Human Continuity

*Domain:* [operations](../../../torviello-enforcer/operations/README.md) · *Rule:* [06-operational-roles-coverage-handover-and-human-continuity.md](../../../torviello-enforcer/operations/rules/06-operational-roles-coverage-handover-and-human-continuity.md)

**Control objective.** Operational resilience depends on people knowing who is on duty, what they may do, how to hand work over, and how the service remains safe when a key person or supplier is unavailable. Coverage must match the service commitment without inventing unsupported staffing promises.

#### OPS-06.01 — Each production profile MUST identify service owner, incident…

**Requirement:** Each production profile MUST identify service owner, incident lead, deploy/release authority, security escalation, data/persistence owner, customer communication owner, and backup/delegate as applicable. State whether each function is staffed continuously, during defined hours, or on best-effort basis.

#### OPS-06.02 — For supported operational channels, state hours, severity…

**Requirement:** For supported operational channels, state hours, severity classes, response targets, escalation contacts, and fallback when the primary owner is unreachable. Public service promises MUST match actual staffing, monitoring, and recovery capability.

#### OPS-06.03 — An operational handover MUST include current service health…

**Requirement:** An operational handover MUST include current service health, open incidents/changes, customer impact, risks, pending actions, access used, deadlines, and next decision. The receiving owner MUST acknowledge material risk and understand their authority.

#### OPS-06.04 — Coverage MUST use named identities and pre-authorized delegates…

**Requirement:** Coverage MUST use named identities and pre-authorized delegates with time-bounded access. Never share accounts or keys to cover an absent operator; emergency access uses the security break-glass process and post-use review.

#### OPS-06.05 — For critical operations, identify single-person and supplier dependencies…

**Requirement:** For critical operations, identify single-person and supplier dependencies, recovery documentation, alternate contacts, and minimum competent coverage. Exercise absence, simultaneous incident, and unavailability of a key vendor at a frequency proportional to impact.

#### OPS-06.06 — Operational processes MUST allow responders to escalate unsafe workload…

**Requirement:** Operational processes MUST allow responders to escalate unsafe workload, conflicting incident tasks, or insufficient authority. Rotate or hand off duties as needed under approved work policies; do not use undocumented availability expectations as a service guarantee.

#### OPS-06.07 — Changes to service hours, product scope, team…

**Requirement:** Changes to service hours, product scope, team structure, vendor, incident severity, or recovery process MUST trigger review of roles, contacts, runbooks, training, and support commitments.
