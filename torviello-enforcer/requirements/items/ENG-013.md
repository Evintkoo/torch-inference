# ENG-013 — Serve realtime WebSocket sessions with bounded framing

**Requirement ID:** ENG-013  
**Priority:** SHOULD  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-19](../../../torviello-engine/specifications/checks/AC-ENG-19.md)  
**Rule controls:** API-02, API-04, ARC-04

## 1. Normative requirement

Realtime WebSocket sessions MUST negotiate capabilities explicitly, validate control and binary frames, bound per-session buffers, preserve response ordering, and release all session resources on disconnect or error.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

WebSocket transports carry continuous audio and video, where a single unbounded buffer or an unvalidated frame can consume the process. The reference implementation exposes an audio socket for TTS and STT, and vision sockets for classification and detection. It defines control frames such as ready, tts, stt_begin, stt_end, config, and response frames such as transcript and classify.

Torviello specifies the session contract rather than the exact message set: negotiation, frame types, size bounds, ordering, error frames, and cleanup. This lets clients implement against a stable protocol and prevents realtime paths from bypassing the limits enforced on HTTP.

## 3. Priority and interpretation

This requirement is **SHOULD**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to `/audio/ws`, `/ws/classify`, `/ws/detect`, and any versioned realtime aliases. It covers handshake, control frames, binary frames, inference dispatch, ordering, errors, and disconnect cleanup.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Send an explicit ready or error frame after upgrade and before accepting work.
- Require a configuration frame before binary inference frames on vision sockets.
- Validate control frame JSON, types, required fields, and ranges and return an error frame for invalid input.
- Bound binary frame size and per-session buffered audio or image data.
- Preserve response ordering for each session and never interleave results from different requests.
- Stop inference and synthesis for a session when the client disconnects or the transport errors.
- Apply the same authentication, rate-limit, and model-availability rules as the equivalent HTTP capability.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** RFC 6455, RFC 9110, OWASP ASVS 5.0.0 Level 3, OpenTelemetry 1.44.0, IETF BCP 14.

- Handshake, framing, masking, control frames, fragmentation, close codes, and UTF-8 validation MUST conform to RFC 6455 and MUST reject malformed frames with the correct close code.
- Inbound and outbound buffers MUST be bounded; backpressure MUST slow or reject the producer instead of growing memory without limit.
- Session authentication, authorization, rate limits, and limits MUST reuse the HTTP edge policy; a WebSocket upgrade MUST NOT bypass them.
- Disconnect, protocol error, and deadline MUST cancel active work and release buffers, model references, and session permits.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- An audio upgrade receives a ready frame and accepts a control frame.
- TTS control produces meta, ordered binary chunks, and a done frame.
- STT begin, PCM frames, and end produce one transcript frame.
- A binary frame before a vision config frame returns an error and runs no inference.
- A malformed control frame returns a stable error and leaves the session usable.
- Disconnect stops work and releases session buffers.

Acceptance checks: [AC-ENG-19](../../../torviello-engine/specifications/checks/AC-ENG-19.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- An RFC 6455 conformance suite MUST pass for handshake, framing, fragmentation, control frames, close behavior, and invalid UTF-8.
- Frame fuzzing MUST run for at least 24 CPU-hours and include oversized, fragmented, interleaved, and malformed frames.
- Stress tests MUST include slow consumers, abrupt disconnect, and concurrent session limits.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Implement each socket as a session state machine with negotiation state, a bounded input buffer, an outbound bounded channel, and a cancellation token. Route work through the same capability interfaces as HTTP. On close, cancel the token and await task termination before dropping session resources.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not accept inference frames before required negotiation.
- Do not grow a session buffer without a configured bound.
- Do not interleave results from concurrent requests in one session.
- Do not leave inference running after disconnect.
- Do not bypass authentication or rate limiting because the transport is WebSocket.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Connect to each socket and exercise the documented handshake.
- 2. Send valid TTS, STT, classification, and detection sessions and record frame order.
- 3. Send malformed control frames, binary frames before config, and oversized frames.
- 4. Disconnect during synthesis and inspect worker and buffer cleanup.
- 5. Attempt a connection without required credentials when authentication is enabled.
- 6. Record protocol transcripts and resource observations.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Run the protocol conformance suite and the frame-fuzz corpus.
- 10. Measure buffer bounds and resource release under slow-consumer and disconnect cases.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Frame transcripts for each successful session type.
- Error frames for malformed and out-of-order input.
- Disconnect cleanup evidence.
- Authentication and rate-limit behavior on the WebSocket path.
- Ordering evidence across concurrent requests in one session.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The RFC 6455 conformance report.
- Fuzz logs and the session resource timeline.
- Evidence that HTTP auth and rate policy applies to upgrades.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- Inference runs before negotiation.
- A session buffer grows without bound.
- Results are interleaved or out of order.
- Work continues after disconnect.
- WebSocket paths bypass HTTP security controls.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- A malformed or non-conformant frame is accepted.
- A buffer grows without bound or a session outlives disconnect.
- An upgrade bypasses authentication, authorization, or rate limits.
