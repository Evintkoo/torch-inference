# ENG-014 — Batch, cache, and coalesce work without changing results

**Requirement ID:** ENG-014  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-20](../../../torviello-engine/specifications/checks/AC-ENG-20.md)  
**Rule controls:** PERF-05, PERF-02, ARC-04

## 1. Normative requirement

Batching, caching, and request coalescing MUST be opt-in by configuration, MUST preserve the result identity and ordering of each caller, and MUST keep memory, queue depth, and wait time within configured bounds with observable statistics.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

These optimizations are the difference between an inference server and a model wrapper, but each one can silently return the wrong answer. A cache keyed only by input can cross models; a batch can reorder outputs; coalescing can attach one caller's metadata to another's result. The reference implementation contains cache, deduplication, batch processor, in-flight batching, model pool, worker pool, and statistics surfaces.

Torviello requires the invariants that make optimization safe: key completeness, per-caller result binding, bounded wait, eviction policy, and reconciliation with metrics. Performance gains are accepted only when result correctness and resource bounds are demonstrated.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to inference capabilities that use caching, batching, deduplication, in-flight batching, or worker pools. It covers cache keys and expiry, batch admission and timeout, coalescing, ordering, capacity, and statistics. It does not require every capability to use every optimization.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Disable optimizations by default unless configuration explicitly enables them, and make the active policy observable.
- Construct cache keys from every input that can change the result, including model identity, input content, and execution parameters.
- Bind each caller to its own request identity and metadata even when execution is shared.
- Preserve submission-to-result ordering for batched and coalesced requests.
- Bound batch wait time by a configured maximum and adapt within documented limits.
- Enforce cache capacity and expiry with a documented eviction policy; never serve an expired entry.
- Expose hit, miss, eviction, batch, queue, and coalescing counts that reconcile with request history and contain no payload data.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** ISO/IEC 25010:2023, TLA+, Loom, OpenTelemetry 1.44.0, IETF BCP 14.

- The cache key MUST be a canonical encoding of every input, parameter, model identity, backend-visible option, and engine version that can change the result.
- A cache hit MUST return a complete, unexpired result attributed to the same model and backend; partial, failed, or poisoned entries MUST never be served.
- Coalesced and batched work MUST preserve per-caller identity and item order; a result MUST NOT be shared across callers beyond the exact key.
- Cache, batch, and coalescing statistics MUST reconcile with observed hits, misses, joins, and executions.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- An identical request within expiry returns the cached result and increments hits.
- Requests differing only by model ID produce distinct cache entries.
- Concurrent duplicates execute once and both callers receive their own result metadata.
- A batch returns each caller's result for its own input.
- A partial batch executes after the configured maximum wait.
- Eviction follows the documented policy and expired entries are never served.

Acceptance checks: [AC-ENG-20](../../../torviello-engine/specifications/checks/AC-ENG-20.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- Property tests MUST prove key equivalence for semantically identical requests and key separation for every result-changing dimension.
- Loom or an equivalent linearizability check MUST cover concurrent lookup, insert, expiry, eviction, and coalescing.
- Stress tests MUST include identical concurrent requests, caller isolation, TTL boundaries, and cancellation of a batch leader.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Create one request identity object containing model, normalized input, and execution parameters. Use it for both cache keys and coalescing keys. Attach caller-specific response metadata outside the shared result. Run batches through a bounded queue with a timer and a maximum size. Keep statistics in atomic counters updated at the same points as state changes.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not omit model identity or execution parameters from a cache key.
- Do not return another caller's result or metadata.
- Do not grow the batch queue or cache beyond configured bounds.
- Do not serve an expired or partially written entry.
- Do not claim a performance gain without correctness evidence.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Exercise cache hit, miss, model-differing, and expiry cases.
- 2. Issue concurrent duplicates and compare results and backend execution count.
- 3. Submit a batch with distinct inputs and verify per-caller binding and order.
- 4. Fill the cache and observe eviction; force a partial batch and measure wait.
- 5. Read statistics and reconcile them with the request sequence.
- 6. Record configuration, requests, backend counts, and statistics.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Run the cache-key property suite and the collision fuzz corpus.
- 10. Reconcile statistics with an independently counted execution log.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Cache behavior transcripts for hit, miss, model difference, and expiry.
- Backend execution count for concurrent duplicates.
- Batch input-to-output mapping evidence.
- Eviction and maximum-wait measurements.
- Statistics output reconciled with the request log.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The cache-key property and collision reports.
- The linearizability or Loom report.
- Reconciled hit, miss, join, and execution counts.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- A cache hit returns a result from another model or parameter set.
- Coalesced callers receive mismatched metadata.
- Batched results are reordered.
- Queue or cache memory grows without bound.
- Statistics cannot be reconciled with observed requests.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- A result-changing input or parameter is absent from the key.
- A cached, coalesced, or batched result crosses caller identity or changes order.
- Statistics cannot be reconciled with executions.
