# ENG-004 — Maintain stable model identity and a truthful catalog

**Requirement ID:** ENG-004  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-10](../../../torviello-engine/specifications/checks/AC-ENG-10.md), [AC-ENG-03](../../../torviello-engine/specifications/checks/AC-ENG-03.md)  
**Rule controls:** MOD-01, API-01, MOD-03

## 1. Normative requirement

Every model MUST have a stable, unique ID within a profile; the catalog MUST distinguish registry, availability, download, and load state, and MUST report only capabilities and metadata that match the running engine.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

Clients route work by model ID, operators reason about storage by model ID, and evaluations compare results by model ID. Duplicate or mutable identities make caching, logging, and benchmark attribution unsound. A catalog that labels a registry entry as available when no asset exists, or as loaded when no session exists, turns the first useful operator question into a guess.

The reference implementation has a JSON model registry with display metadata, a separate downloaded-model manager, a runtime registration API, and model listings under several prefixes. Torviello specifies one identity contract and explicit state dimensions so those views can differ without contradicting each other.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to every model-like artifact the engine can list or execute: TTS engines, Whisper models, classifiers, detectors, LLM catalog entries, and generic neural networks. It covers catalog listing, lookup, availability, and the descriptors used by loading and inference.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Assign one stable ID per model within a profile and reject duplicate IDs rather than choosing one silently.
- Keep descriptive metadata separate from runtime state so availability does not mutate catalog text.
- Report at least registry presence, local availability, download state, and loaded state as distinct fields.
- Report task, format, declared backend requirements, and input constraints needed to select the model.
- Serve lookup by ID with a stable not-found error and no fallback to a similarly named entry.
- Keep catalog responses free of local absolute paths, secrets, and mutable filesystem details.
- Preserve catalog identity and ordering rules across restarts and across the unversioned and versioned API surfaces.

#### MOD-01.01 — Give each model artifact a stable model ID

The project MUST give each model artifact a stable model ID and immutable version or digest. Registry records specify task, format, source, license, input/output schema, tokenizer/preprocessor requirements, runtime/provider constraints, memory estimates, supported platform, and verification status.

#### MOD-01.02 — Separate model metadata from model bytes

The project MUST separate model metadata from model bytes. A registry entry cannot claim available or ready until the corresponding artifact is present, digest-verified, compatible, and successfully loaded for the selected runtime.

#### MOD-01.03 — Treat model files, tokenizer data, configuration, and metadata as

The project MUST treat model files, tokenizer data, configuration, and metadata as untrusted supply-chain inputs. The project MUST also record provenance and permitted redistribution.

#### MOD-01.04 — Define compatibility checks explicitly

The project MUST define compatibility checks explicitly. The project MUST NOT infer task, architecture, or provider support from filenames or extensions alone.

#### MOD-01.05 — Preserve immutable version history

The project MUST preserve immutable version history. Updating a model means creating a new version and an explicit promotion or rollback operation.

#### API-01.01 — Maintain a machine-readable OpenAPI description for every public HTTP

The project MUST maintain a machine-readable OpenAPI description for every public HTTP API. The project MUST also treat it as a reviewed contract that describes paths, methods, schemas, validation constraints, authentication, authorization, status codes, error bodies, pagination, and streaming behavior.

#### API-01.02 — Keep request and response schemas in a dedicated API

The project MUST keep request and response schemas in a dedicated API schema module. The project MUST also group handlers by user-facing functionality. A handler MAY parse transport input, invoke a domain interface, and serialize a response; it MUST NOT own inference, persistence, registry policy, or cross-service business logic.

#### API-01.03 — Use one stable error envelope

The project MUST use one stable error envelope. The project MUST also include a safe error code and correlation identifier; return actionable client guidance without leaking stack traces, filesystem paths, secrets, internal service names, or dependency errors.

#### API-01.04 — Define compatibility for every endpoint

The project MUST define compatibility for every endpoint. Additive changes preserve existing semantics. Breaking changes require an explicit API version/deprecation plan, a migration window, and consumer-facing release notes.

#### API-01.05 — Generate reference documentation from the contract when practical

The project SHOULD generate reference documentation from the contract when practical. Handwritten endpoint examples MUST be checked against the current contract and implementation.

#### MOD-03.01 — Registry mutations MUST require authenticated identity and least-privilege authorization

Registry mutations MUST require authenticated identity and least-privilege authorization. The project MUST also separate view, add, promote, rollback, and delete permissions where the product requires distinct roles.

#### MOD-03.02 — Validate edits through one schema and policy layer whether

The project MUST validate edits through one schema and policy layer whether they arrive through an admin API or a controlled manual file change.

#### MOD-03.03 — Audit actor, time, action, target model/version, outcome, and change

The project MUST audit actor, time, action, target model/version, outcome, and change identifier. The project MUST NOT log tokens or secret configuration values.

#### MOD-03.04 — Make changes transactional: validate a candidate, persist it safely

The project MUST make changes transactional: validate a candidate, persist it safely, then publish the new version. The project MUST provide a rollback to the last known-good registry state.

#### MOD-03.05 — The standalone engine MUST operate with a local registry/cache

The standalone engine MUST operate with a local registry/cache and MUST NOT require a hosted control plane for local inference

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** ISO/IEC/IEEE 29148:2018, ISO/IEC 25010:2023 (functional correctness, security), OpenAPI 3.2.1, IETF BCP 14.

- Model ID uniqueness and immutability MUST hold across registration, download, load, unload, restart, and removal.
- Catalog presence, local availability, download state, and load state MUST be separately derived; no dimension may be inferred from another.
- Every catalog response MUST validate against the published schema and MUST NOT expose absolute paths, credentials, signed URLs, or internal hostnames.
- Removal MUST be atomic: a descriptor is either fully present or fully absent, with no partially removed state visible.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- A registry entry with no local asset reports not_downloaded and loaded false.
- An initialized model reports available and loaded true with selected backend.
- Two descriptors with the same ID fail validation with model.duplicate_id.
- Unknown lookup returns 404 with model.not_found and a request ID.
- Catalog output contains no absolute host path or secret.
- The same model ID appears identically on both API prefixes.

Acceptance checks: [AC-ENG-10](../../../torviello-engine/specifications/checks/AC-ENG-10.md), [AC-ENG-03](../../../torviello-engine/specifications/checks/AC-ENG-03.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- A formal state model MUST cover descriptor and slot identity and MUST be checked for uniqueness, immutability, and independent state dimensions.
- Property tests MUST generate identifiers, state combinations, and restart sequences and compare the catalog projection with a reference model.
- The catalog response MUST be validated against the OpenAPI schema for every reachable state.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Define a model descriptor value object with immutable ID, task, format, backend requirements, input constraints, and provenance. Keep runtime state in a separate map keyed by the same ID. Build all listing responses from a projection that joins descriptor, cache, and runtime state under one serializer so aliases cannot drift.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not derive model identity from a display name or filesystem path.
- Do not report a registry entry as loaded without a live runtime object.
- Do not silently choose one of two duplicate IDs.
- Do not leak cache paths, tokens, or signed URLs in catalog output.
- Do not reorder or rename IDs between compatible releases.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Prepare a registry with one entry and an empty cache; list the catalog and inspect state fields.
- 2. Populate the asset and initialize the model; repeat the listing.
- 3. Introduce a duplicate ID and run catalog validation.
- 4. Request an unknown ID and inspect the RFC 9457 problem document.
- 5. Inspect the raw response for absolute paths or secrets.
- 6. Compare the unversioned and versioned listing responses.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Drive every combination of catalog, availability, download, and load state and validate the response schema.
- 10. Run the identity property suite and the restart reconstruction case.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Catalog responses before and after asset placement and initialization.
- Validation failure for the duplicate ID.
- Unknown-lookup RFC 9457 problem document with request ID.
- A redaction inspection of the catalog response.
- A field-by-field comparison of the two API prefixes.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The formal state model and the property-test report.
- A state-combination response matrix validated against the contract.
- Restart evidence showing identity reconstruction without in-memory display text.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- A model is listed as available without an asset.
- A model is listed as loaded without a runtime object.
- Duplicate IDs are accepted.
- Lookup falls back to a different model.
- Catalog output exposes host paths or credentials.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- One model ID resolves to two descriptors or two slots.
- A state dimension is inferred from another or silently omitted.
- A catalog response exposes a host path or credential.
