# ENG-009 — Transcribe and validate audio within explicit ingress bounds

**Requirement ID:** ENG-009  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-15](../../../torviello-engine/specifications/checks/AC-ENG-15.md)  
**Rule controls:** API-02, SEC-04, API-03

## 1. Normative requirement

The engine MUST bound audio upload size and duration before decoding, support declared audio formats, reject undecodable input with a stable error, transcribe with optional timestamp segments, and expose validation metadata without executing a model.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

Audio ingress is a direct memory-exhaustion surface: compressed formats can expand dramatically, duration controls memory, and multipart parsing can buffer unbounded bodies. The reference implementation caps multipart audio, enforces a maximum decoded duration, validates formats during load, offloads transcription, returns text, language, confidence, and optional segments, and exposes a validation endpoint.

Torviello makes those boundaries part of the contract so clients can predict failure, operators can reason about memory, and the STT path cannot be used to bypass the same limits through an alias.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to `/audio/transcribe`, `/stt/transcribe`, `/audio/validate`, `/audio/health`, their versioned aliases, and the streaming STT WebSocket path. It covers upload limits, format support, duration, decoding, transcription, timestamps, and validation metadata.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Enforce the multipart audio limit while reading the body, before allocating beyond the configured bound.
- Enforce a maximum decoded duration against both container metadata and the decode loop.
- Accept only declared formats and report the detected format in validation output.
- Return a stable invalid-format error for bytes that cannot be decoded.
- Return text, language, confidence, and optional timestamp segments in ascending order.
- Run decoding and transcription outside the request reactor and release the worker slot on failure.
- Expose audio health that reports loaded models and supported formats without requiring a transcription request.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** OWASP ASVS 5.0.0 Level 3 (file upload, input validation), OWASP AISVS 1.01 Level 3, ISO/IEC 25010:2023, IETF BCP 14.

- Audio length, compressed size, decoded size, sample rate, channels, and duration MUST be bounded before full decode or model dispatch.
- Container and codec parsers MUST reject truncated, malformed, polyglot, and decompression-bomb inputs with a stable error and no partial transcript.
- The response MUST report the effective language, duration, transcript, and timing attribution; a language hint MUST NOT be presented as a detection result.
- Temporary files, decoded buffers, and model references MUST be released on validation failure, cancellation, and timeout.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- A valid WAV transcribes with text, language, and confidence.
- Timestamps produce ordered segments whose text matches the transcript.
- Undecodable bytes return 400 audio.invalid_format and no model runs.
- An oversized upload returns 413 before full decode.
- Audio longer than the configured duration returns 400 audio.too_long.
- Validation returns format, sample rate, channels, duration, and valid true.

Acceptance checks: [AC-ENG-15](../../../torviello-engine/specifications/checks/AC-ENG-15.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- Container and codec parsers MUST survive at least 24 CPU-hours of fuzzing plus a decompression-bomb and malformed-header corpus.
- Property tests MUST verify ingress bounds are enforced before decode and that invalid input never reaches the model.
- Resource accounting MUST show no temporary-file, buffer, or reference leak across repeated failures.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Use a streaming multipart reader with an early size gate. Validate container metadata, then decode with a duration-aware processor that stops at the configured bound. Put the audio capability behind a trait so transcription runs on a blocking pool. Build timestamp segments from the same decode timeline used for text.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not buffer an unbounded multipart body before enforcing the limit.
- Do not decode an entire oversized duration before rejecting it.
- Do not return a successful transcript for undecodable input.
- Do not log audio bytes or transcript content.
- Do not run synchronous decoding on the request reactor.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Transcribe a short valid WAV with and without timestamps.
- 2. Submit random bytes, a truncated container, and an unsupported format.
- 3. Submit an upload above the multipart limit and one above the duration limit.
- 4. Call the validation endpoint with valid and invalid audio.
- 5. Inspect memory and worker behavior during the oversized cases.
- 6. Record fixtures, responses, and observed resource bounds.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Replay the malformed and bomb corpus and confirm rejection before decode and dispatch.
- 10. Measure peak memory and temporary-file cleanup for boundary inputs.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Transcript and segment output for the valid cases.
- Validation metadata for valid and invalid audio.
- 413 and 400 responses for size, duration, and format violations.
- Evidence that rejection occurred before full decode or model dispatch.
- Audio health output listing models and formats.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- Fuzz logs and the malicious audio corpus.
- Boundary results showing rejection before model execution.
- The transcript field schema and resource-cleanup report.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- An oversized body is fully buffered before rejection.
- A long file is decoded before the duration check.
- Undecodable input yields a transcript.
- Segments are unordered or do not match the transcript.
- Audio content appears in logs.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- Decode or dispatch begins before an ingress bound is enforced.
- An invalid input produces a partial transcript or an internal error.
- Temporary files, decoded buffers, or model references survive a failure.
