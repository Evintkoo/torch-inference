# CSC-001 — Every maintained directory shall have a `README.md` that describes its purpose, contents, interfaces, ownership, and relevant build or validation steps

**Requirement ID:** CSC-001  
**Priority:** MUST  
**Source:** [README.md](../README.md) — Common standards requirements  
**Status:** Active requirement; no implementation or evaluation evidence is recorded in this repository.  
**Rule controls:** COL-02, DIR-01, DIR-02, DIR-03, GOV-03  
**Acceptance checks:** None recorded  
**Open decisions:** None recorded

## 1. Normative requirement

Every maintained directory shall have a `README.md` that describes its purpose, contents, interfaces, ownership, and relevant build or validation steps.

## 2. Why this requirement exists

This requirement is part of **Common standards requirements** in [README.md](../README.md). It is traced to 5 rule control(s): COL-02, DIR-01, DIR-02, DIR-03, GOV-03. Those controls state the following purpose:

- **COL-02 — Organizational Records Knowledge and Information Lifecycle:** Information created during work must have a source of truth, owner, audience, access level, retention, and update path. The organization must preserve what future workers need while minimizing personal, confidential, and duplicate records.
- **DIR-01 — Purpose, ownership, and boundaries:** These controls govern **purpose, ownership, and boundaries**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.
- **DIR-02 — Directory documentation and adoption:** These controls govern **directory documentation and adoption**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.
- **DIR-03 — Layout, naming, and ownership contracts:** This control defines the intended outcome for **layout, naming, and ownership contracts** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.
- **GOV-03 — Coverage, risk analysis, and rule evolution:** Coverage must be assessed from system context and change scenarios, not inferred from file counts. The rule set must evolve as product boundaries, failure modes, threat conditions, dependencies, and operational evidence change.

Acceptance is not satisfied by citing these controls. The implementation must demonstrate the observable result in section 6, and the mapped rule clauses in section 5 define what must hold at the enforcement boundary.

## 3. Priority and interpretation

This requirement has **MUST** priority under the repository's requirement conventions. A MUST requirement is needed for the stated product direction or a safe release. A SHOULD requirement is expected unless a documented tradeoff justifies deferral. A COULD requirement is a candidate capability that requires product or technical validation. Acceptance describes observable evidence; it does not mandate a specific implementation unless the requirement says so.

## 4. Scope and applicability

This requirement belongs to **Common standards requirements** in [README.md](../README.md). It applies to the product area named by that source section and to every implementation, interface, release artifact, document, or operation that claims to satisfy it.

The mapped controls add the following applicability boundaries:

- **COL-02:** This control applies whenever a person, team, contractor, coding agent, automated agent, or delegated function performs an activity in scope. Responsibilities are functional roles, not mandated job titles or headcount; one person may hold multiple roles when conflicts and approval-separation risks are controlled. Apply jurisdiction-specific employment, safety, privacy, consumer, and contract rules through an accountable qualified owner.
- **DIR-01:** This control applies to every new or modified production component, interface, build or deployment artifact, operational procedure, and test within the **directory** domain. Where a clause is conditional, its stated condition defines when it applies. Legacy behavior is brought into scope when changed or when an approved migration specifically addresses it.
- **DIR-02:** This control applies to every new or modified production component, interface, build or deployment artifact, operational procedure, and test within the **directory** domain. Where a clause is conditional, its stated condition defines when it applies. Legacy behavior is brought into scope when changed or when an approved migration specifically addresses it.
- **DIR-03:** This document applies to new or materially changed directory behavior in all supported product profiles, including local/offline and hosted deployments where applicable. Requirements apply to design, implementation, configuration, packaging, operation, and tests whenever those stages affect the controlled outcome. A requirement’s stated condition limits its applicability; legacy behavior is included when changed or migrated.
- **GOV-03:** This control applies to new and changed governance decisions, artifacts, and agent-assisted work. Apply a clause where its stated condition exists. For existing behavior, use the control when that behavior is changed, relied on by a new capability, or assessed for a material risk. Product-specific choices remain governed by approved requirements and decision records.

The source requirement table remains authoritative if this view and the source disagree.

### COL-02 — Organizational Records Knowledge and Information Lifecycle

*Domain:* [collaboration-and-communication](../../../torviello-enforcer/collaboration-and-communication/README.md) · *Rule:* [02-organizational-records-knowledge-and-information-lifecycle.md](../../../torviello-enforcer/collaboration-and-communication/rules/02-organizational-records-knowledge-and-information-lifecycle.md)

**Control objective.** Information created during work must have a source of truth, owner, audience, access level, retention, and update path. The organization must preserve what future workers need while minimizing personal, confidential, and duplicate records.

#### COL-02.01 — A record owner MUST identify purpose, sensitivity…

**Requirement:** A record owner MUST identify purpose, sensitivity, authoritative status, audience, access, retention trigger, and applicable legal hold for material decisions, contracts, incidents, support cases, releases, training, and procedures. Apply approved classifications and data minimization rules.

#### COL-02.02 — For each process or decision, designate the authoritative…

**Requirement:** For each process or decision, designate the authoritative record and link secondary discussion to it. Copies and summaries MUST identify their source and date; where systems conflict, the record owner MUST resolve and announce the canonical version.

#### COL-02.03 — Operational, security, support, and recovery procedures…

**Requirement:** Operational, security, support, and recovery procedures MUST identify prerequisites, role, safe steps, expected outcome, failure/escalation, last review, and verification method. Test high-impact procedures periodically and after material change or incident.

#### COL-02.04 — When a role, owner, vendor…

**Requirement:** When a role, owner, vendor, or product area changes, transfer decision context, undocumented constraints, credentials via approved secret management, open risks, and current work to an authorized successor. Do not place secrets in documentation or handoff notes.

#### COL-02.05 — Authoritative records MUST have access appropriate to sensitivity…

**Requirement:** Authoritative records MUST have access appropriate to sensitivity, identifiable owners, version/change history proportionate to importance, and recovery from accidental deletion or corruption. Changes to policy, approvals, or audit evidence MUST preserve who changed what and when.

#### COL-02.06 — Retain records only for the approved business, legal…

**Requirement:** Retain records only for the approved business, legal, safety, security, or contractual purpose. At the retention trigger, delete or archive through the approved process; legal holds suspend ordinary deletion only for the scoped records and duration.

#### COL-02.07 — For critical capabilities and procedures, identify single-person dependency…

**Requirement:** For critical capabilities and procedures, identify single-person dependency, recovery time, and backup competence. Mitigate through cross-training, tested documentation, successor assignment, vendor transition, or explicit accepted risk.

#### COL-02.08 — Workers MUST be able to locate current procedures…

**Requirement:** Workers MUST be able to locate current procedures, decisions, ownership, escalation contacts, and approved templates without relying on private introductions. Keep material readable and accessible to intended users and provide controlled alternatives when a person cannot use the default channel.

### DIR-01 — Purpose, ownership, and boundaries

*Domain:* [directory](../../../torviello-enforcer/directory/README.md) · *Rule:* [01-purpose-ownership-and-boundaries.md](../../../torviello-enforcer/directory/rules/01-purpose-ownership-and-boundaries.md)

**Control objective.** These controls govern **purpose, ownership, and boundaries**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### DIR-01.01 — Every maintained directory MUST have one clear purpose

Every maintained directory MUST have one clear purpose and an owning subsystem. Its local documentation MUST state what belongs there, public entry points, dependency boundaries, build/run/validation steps, and generated/runtime content.

#### DIR-01.02 — Place code and assets with the component that owns

The project MUST place code and assets with the component that owns their lifecycle. Shared code belongs in an explicit shared module with documented consumers and stable interface.

#### DIR-01.03 — Create a directory only when it establishes a useful

The project MUST create a directory only when it establishes a useful responsibility, build, test, deployment, or distribution boundary. The project MUST also separate unrelated concerns instead of turning an existing directory into a catch-all.

#### DIR-01.04 — Keep production application code under source directories, automated tests

The project MUST keep production application code under source directories, automated tests under their named test categories, and benchmarks under /benchmarks. The project MUST NOT place performance harnesses or non-unit tests in production source.

#### DIR-01.05 — Keep Dockerfiles and Compose files under /containers, package/release automation

The project MUST keep Dockerfiles and Compose files under /containers, package/release automation under /packaging, and design tokens/assets under a dedicated design area.

### DIR-02 — Directory documentation and adoption

*Domain:* [directory](../../../torviello-enforcer/directory/README.md) · *Rule:* [02-directory-documentation-and-adoption.md](../../../torviello-enforcer/directory/rules/02-directory-documentation-and-adoption.md)

**Control objective.** These controls govern **directory documentation and adoption**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### DIR-02.01 — The repository root and maintained product directories MUST use

The repository root and maintained product directories MUST use README.md for purpose and usage and AGENTS.md for coding-agent instructions. These files explain different things and MUST NOT duplicate whole documents.

#### DIR-02.02 — The rules root MUST use README

The rules root MUST use README.md as its index and AGENTS.md for maintenance instructions. Each rules domain MUST contain 00-references-trails.md and numbered normative Markdown rule files, and MUST NOT use README/AGENTS files as substitutes

#### DIR-02.03 — The requirements root MUST use README

The requirements root MUST use README.md as the requirement index and AGENTS.md for requirement maintenance. Requirement sets MUST use their own named Markdown documents and local guidance only where it adds value.

#### DIR-02.04 — Update directory docs when interfaces, ownership, dependencies, operations, supported

The project MUST update directory docs when interfaces, ownership, dependencies, operations, supported build profiles, or validation steps change.

#### DIR-02.05 — Adopt documentation conventions when creating or substantially changing directories

The project MUST adopt documentation conventions when creating or substantially changing directories. The project MUST also track legacy adoption as migration work rather than adding empty placeholder files everywhere.

### DIR-03 — Layout, naming, and ownership contracts

*Domain:* [directory](../../../torviello-enforcer/directory/README.md) · *Rule:* [03-layout-naming-and-ownership-contracts.md](../../../torviello-enforcer/directory/rules/03-layout-naming-and-ownership-contracts.md)

**Control objective.** This control defines the intended outcome for **layout, naming, and ownership contracts** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### DIR-03.01 — Every maintained directory MUST have one primary responsibility…

**Requirement:** Every maintained directory MUST have one primary responsibility and an accountable owning subsystem. The owner MUST define allowed contents, public entry points, dependencies, generated content, and lifecycle.

#### DIR-03.02 — Directory and file names MUST be stable, searchable…

**Requirement:** Directory and file names MUST be stable, searchable, language-appropriate, and consistent with the repository convention. Names MUST NOT encode temporary status, personal ownership, or implementation details likely to change independently of the content.

#### DIR-03.03 — Each boundary MUST correspond to a real ownership…

**Requirement:** Each boundary MUST correspond to a real ownership, build, test, deployment, or distribution concern. Create a new module when it reduces coupling or provides independent selection; do not create levels of nesting that merely repeat product names.

#### DIR-03.04 — Public interfaces and shared assets MUST have one authoritative…

**Requirement:** Public interfaces and shared assets MUST have one authoritative location. Compatibility aliases or duplicate copies MUST identify their source of truth, synchronization mechanism, and planned removal condition.

#### DIR-03.05 — Directory-level docs MUST distinguish source, generated output…

**Requirement:** Directory-level docs MUST distinguish source, generated output, runtime data, fixtures, vendored code, and user-owned data. Build and cleanup tools MUST not delete user-owned or checked-in source data.

#### DIR-03.06 — Cross-cutting implementation MUST remain with the owning domain…

**Requirement:** Cross-cutting implementation MUST remain with the owning domain or a clearly owned shared interface; do not create a generic “optimization”, “misc”, or “common” directory without explicit scope and consumers.

### GOV-03 — Coverage, risk analysis, and rule evolution

*Domain:* [governance](../../../torviello-enforcer/governance/README.md) · *Rule:* [03-coverage-risk-analysis-and-rule-evolution.md](../../../torviello-enforcer/governance/rules/03-coverage-risk-analysis-and-rule-evolution.md)

**Control objective.** Coverage must be assessed from system context and change scenarios, not inferred from file counts. The rule set must evolve as product boundaries, failure modes, threat conditions, dependencies, and operational evidence change.

#### GOV-03.01 — A domain coverage review MUST identify relevant users…

**Requirement:** A domain coverage review MUST identify relevant users and operators, assets and data, trust boundaries, components and dependencies, deployment profiles, and intended outcomes before deciding which controls apply.

#### GOV-03.02 — A coverage review MUST consider governance, recruitment…

**Requirement:** A coverage review MUST consider governance, recruitment and role assignment, work intake, requirements, architecture, implementation, collaboration, procurement, verification, release, installation, operation, customer support, incident response, knowledge transfer, separation, migration, and retirement. Mark each area applicable, not applicable with rationale, or unresolved with owner and next review trigger.

#### GOV-03.03 — For each material boundary, consider misuse, invalid…

**Requirement:** For each material boundary, consider misuse, invalid input, resource exhaustion, concurrency, dependency failure, partial completion, restart, upgrade/downgrade, rollback, data loss, compromised credentials/artifacts, and operator error where relevant. Add controls when a credible scenario has no owner, prevention/detection behavior, recovery path, or evidence.

#### GOV-03.04 — The review MUST consider likelihood, impact, exposure…

**Requirement:** The review MUST consider likelihood, impact, exposure, reversibility, affected users, data sensitivity, blast radius, detectability, recovery time, and uncertainty. Higher-risk or irreversible outcomes MUST receive stronger prevention, independent review, and direct verification; low-risk choices MAY use proportionate checks with rationale.

#### GOV-03.05 — A change MUST be checked against adjacent domains when…

**Requirement:** A change MUST be checked against adjacent domains when it crosses their boundaries—for example API/security, model/persistence, build/release, configuration/operations, or UI/accessibility. Assign one authoritative control owner for shared obligations and cross-reference other documents instead of duplicating conflicting normative text.

#### GOV-03.06 — A gap MUST state the affected lifecycle area…

**Requirement:** A gap MUST state the affected lifecycle area, risk/scenario, impacted requirements, owner, interim mitigation, disposition, and review trigger or target. A gap MUST NOT be described as covered merely because a related document exists.

#### GOV-03.07 — After a defect, incident, security finding…

**Requirement:** After a defect, incident, security finding, near miss, production rollback, or repeated agent/user confusion, determine whether the root cause was missing, ambiguous, unenforced, or poorly assessed guidance. Update the control, tests, training/agent instructions, or ownership model as appropriate and link the corrective action.

#### GOV-03.08 — At least once per major release and when requirements…

**Requirement:** At least once per major release and when requirements or supported profiles change, reassess source versions, assumptions, controls, exceptions, owners, assessment evidence, and applicability. A new version of an external standard triggers impact analysis; it does not automatically change project policy.

#### GOV-03.09 — When a rule is obsolete, identify its replacement…

**Requirement:** When a rule is obsolete, identify its replacement or why it no longer applies, check dependent controls and open exceptions, preserve a change record, and remove stale index links. Do not leave abandoned controls appearing current.

#### GOV-03.10 — A material domain coverage review MUST dry-run its procedures…

**Requirement:** A material domain coverage review MUST dry-run its procedures against at least one ordinary case and relevant boundary/failure or lifecycle-transition cases. Record the actor, starting inputs, decision points, expected artifacts, observed ambiguities, and pass/fail outcome. A rule document’s existence or a generic “Examine/Interview/Test” section MUST NOT count as proof that a contributor can perform the work. Gaps MUST become owned rule-maintenance or training work with a review trigger.

#### GOV-03.11 — Each applicable, not-applicable, or unresolved lifecycle-area disposition…

**Requirement:** Each applicable, not-applicable, or unresolved lifecycle-area disposition in a domain trail MUST link to a dated coverage review record identifying reviewer, scope/profile, rationale, evidence, and next review trigger. Each dry-run MUST identify the procedure revision, participant, starting conditions, expected and actual outputs, result, gaps, owner, and remediation/retest evidence. An unlinked status label or an empty template MUST NOT be represented as completed coverage.

### 5.2 Assessment determination

- **COL-02:** Pass requires every applicable MUST to be followed and supported by current evidence. Fail applies when authority is unclear, an action bypasses required review, a person cannot identify the safe next step, a required record or safeguard is absent, or evidence is stale. - **DIR-03:** Assess each control ID as **pass**, **fail**, or **not applicable**. Pass requires every applicable MUST to be implemented and supported by current evidence. - **GOV-03:** Pass requires each applicable MUST to be met with current evidence and any SHOULD deviation to have a reasoned record. ### 5.3 Exceptions and nonconformance

- **COL-02:** A MUST deviation requires approval by an owner authorized for the affected risk, with independent review where practical. Record scope, rationale, impact, interim protection, remediation owner, and expiry or review trigger. Applicable law, contractual duties, safety obligations, and user rights cannot be waived by an internal exception.
- **DIR-01:** A deviation from a MUST requirement requires explicit approval from the accountable product or engineering owner before release. The exception record MUST identify affected controls, scope, risk, compensating measures, remediation owner, and expiry or review date. A SHOULD deviation MUST include a rationale and impact in the change record. Unapproved or expired deviations are nonconformances and MUST block the affected release when the requirement is release-critical.
- **DIR-02:** A deviation from a MUST requirement requires explicit approval from the accountable product or engineering owner before release. The exception record MUST identify affected controls, scope, risk, compensating measures, remediation owner, and expiry or review date. A SHOULD deviation MUST include a rationale and impact in the change record. Unapproved or expired deviations are nonconformances and MUST block the affected release when the requirement is release-critical.
- **DIR-03:** A deviation from a MUST requirement requires accountable owner approval before release. Record affected control IDs and profiles, risk, compensating measures, remediation owner, and expiry/review date. A SHOULD deviation requires rationale and impact in the change record. An expired or unapproved exception is a nonconformance and MUST block a release when the affected control is release-critical.
- **GOV-03:** A MUST deviation requires approval from the accountable engineering or product owner before release. Record affected control IDs and profiles, risk, compensating controls, remediation owner, and review/expiry date. An exception does not amend the rule; recurring exceptions require revising the rule or resolving the underlying decision.

## 8. Prohibited conditions

The following conditions are explicitly prohibited by the mapped controls. Any one of them is sufficient to fail the requirement.

- [COL-02] Do not place credentials, private keys, personal data, or customer payloads in general knowledge bases.
- [COL-02] Do not leave a material decision in a personal inbox, draft, or tool without an authoritative record.
- [COL-02] Do not preserve duplicate records indefinitely without a purpose, owner, and retention rule.
- [DIR-01] The project MUST NOT add root-level files merely because a tool defaults to the repository root
- [DIR-01] The project MUST NOT mix build outputs, downloaded models, runtime data, or user configuration into source ownership directories
- [DIR-01] The project MUST NOT introduce a directory hierarchy that only mirrors concepts without clarifying ownership
- [DIR-02] The project MUST NOT treat a README or AGENTS file as the normative rule content of a rules domain
- [DIR-02] The project MUST NOT leave stale README instructions that contradict actual config, scripts, endpoints, or directory layout
- [DIR-02] The project MUST NOT create empty guidance files solely to satisfy a count
- [DIR-03] Do not place credentials, local state, caches, or generated artifacts in source-owned directories without a defined reason and cleanup policy.
- [DIR-03] Do not create an empty placeholder directory merely to satisfy a naming template.
- [GOV-03] Do not claim “all cases” or exhaustive coverage from a finite checklist.
- [GOV-03] Do not use a risk score as a substitute for explaining the scenario, impact, and controls.
- [GOV-03] Do not let a coverage matrix mark an area complete without evidence or a named control owner.
