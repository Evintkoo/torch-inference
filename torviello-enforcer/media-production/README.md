# media-production domain

**Development stage:** SDD

This directory contains 4 normative control document(s) and the generated enforcement tests for the **media-production** domain (Media and video production). The rule documents are normative; the tests enforce them against the repository's product source.

## Layout

- [`trails/00-references-trails.md`](trails/00-references-trails.md) — authoritative sources, requirement mapping, lifecycle coverage.
- [`rules/`](rules/) — numbered, self-contained control documents.
- [`tests/`](tests/) — generated conformance tests, one per control plus a trail-integrity test. Do not hand-edit.

## Detailed controls

### MEDIA-01 — Video production lifecycle

**Objective.** Produce product demos, tutorials, and marketing videos as evidence-backed, rights-cleared, accessible, secure, and reviewable work products with clear production gates and ownership.

**Requirements traced:** PA-024, PA-032, PA-035, PDL-001–PDL-012, PDL-016

**Normative requirements:**

- **MEDIA-01.02 — Establish truth and scope for every product claim.** For each factual claim about features, performance, security, compatibility, availability, pricing, licensing, or roadmap, record an authoritative source, tested version/profile, measurement conditions where applicable, and approval owner. Demonstrations MUST show the real product state for the stated version or be clearly labeled as mockup, prototype, edited composite, or planned capability. Do not fabricate user outcomes, benchmark results, testimonials, endorsements, or availability. Remove or qualify claims that cannot be substantiated at publication time.
- **MEDIA-01.03 — Plan narrative and capture before recording.** Prepare a script, outline, or storyboard proportionate to complexity. Specify scenes, narration/on-screen text, required product state and test data, transitions, call to action, accessibility needs, expected duration, and owner for each factual segment. Rehearse demonstrations on a controlled profile using non-sensitive data. Capture a clean take and note deviations or edits that alter meaning. For tutorials, include prerequisites and recovery steps, not just the success path.
- **MEDIA-01.04 — Clear rights and permissions before using material.** Before recording or editing, inventory music, fonts, images, footage, logos, product/customer names, voices, likenesses, testimonials, code, model output, and third-party interfaces. Record creator/source, license/permission, attribution, permitted channels/territories/term, restrictions, and evidence. Obtain required releases and approvals for identifiable people, customer content, or confidential environments. Do not assume publicly viewable content is reusable. Escalate unclear ownership, commercial usage, privacy, or jurisdiction issues to authorized review before publication.
- **MEDIA-01.05 — Protect secrets, personal data, and production systems during capture.** Use a dedicated demo account/environment with least privilege, synthetic data, test credentials, and representative but non-sensitive content. Before and after capture inspect the full screen, notifications, browser history, terminal output, logs, environment variables, file paths, access tokens, customer data, and background audio for accidental disclosure. Revoke any credential exposed in raw footage, even if later cropped or blurred. Do not connect recording workflows to production systems unless explicitly approved and risk-controlled.
- **MEDIA-01.06 — Edit for accuracy, comprehension, and reproducibility.** Edits MUST preserve factual context and MUST NOT imply behavior, causality, speed, quality, or availability that the source did not demonstrate. Keep the project file and source provenance sufficient for another authorized editor to reproduce the final render. Record significant edits, compositing, speed changes, AI-generated or synthetic media, and removed limitations where those could affect viewer interpretation. Maintain a versioned review copy and a separate approved release render.
- **MEDIA-01.07 — Make published speech and meaningful sound accessible.** Provide synchronized captions for speech and meaningful audio, including speaker identification and relevant sound cues. Review captions for accuracy, timing, names, technical terms, and punctuation; automatic captions alone are not accepted without human review. Provide a transcript for long or instructional media where useful, and audio description or equivalent narration when essential visual information is not conveyed in audio. Ensure text overlays remain readable, high contrast, sufficiently long, and do not communicate meaning only through color or motion. Apply WCAG 2.2 media criteria and the target publishing surface’s accessible player requirements.
- **MEDIA-01.08 — Review the complete video as a release artifact.** Before publication, an independent reviewer MUST check the full beginning-to-end rendered video, not only the script or a partial preview. Review claim accuracy, product/version fidelity, rights and releases, captions/transcript, audio clarity, text legibility, pacing, spelling, accessible playback, privacy/security leakage, visual defects, links/call-to-action, and consistency with the approved brief. For performance or security claims, require evidence from the relevant domain owner. Record findings and resolved/dispositioned exceptions.
- **MEDIA-01.09 — Maintain reproducible technical outputs.** The production owner MUST define source project format, render settings, aspect ratio, frame rate, resolution, audio level/format, caption format, naming/version scheme, and destination-specific deliverables before final render. Preserve a high-quality archival master where retention is approved, then produce platform-specific encodes from that master. Validate the rendered file’s duration, audio/video synchronization, captions, resolution, playback, and file integrity. Platform-specific settings are confirmed against current official destination guidance at each release.
- **MEDIA-01.10 — Keep work reviewable and separate from engine runtime.** Store scripts, project files, source assets, licenses, renders, and production automation under the approved media ownership boundary. Media tooling and assets MUST NOT become build or runtime dependencies of the inference engine unless a separate requirement and architecture decision explicitly establish that dependency. Use version control for text/scripts/configuration; use approved object storage or asset management for large binaries, with stable references, access control, retention, backup, and checksums as appropriate. Do not commit secrets or restricted raw footage.

### MEDIA-02 — Video publication and asset lifecycle

**Objective.** Publish the approved video to the correct destinations with complete metadata and accessible alternatives, retain or remove production assets deliberately, and respond to corrections, rights changes, incidents, and product evolution.

**Requirements traced:** PA-024, PA-032, PA-035, PDL-013–PDL-017

**Normative requirements:**

- **MEDIA-02.02 — Keep metadata accurate and maintain accessible alternatives.** Descriptions, chapters, labels, thumbnails, captions, transcripts, and linked documentation MUST accurately represent the content and product state. Avoid misleading thumbnail/title claims. Provide an accessible transcript or equivalent content path when needed for the material’s purpose, and ensure the destination player supports keyboard and assistive technology use. Captions MUST remain available after edits or re-encoding.
- **MEDIA-02.03 — Track distribution, versions, and dependents.** Maintain an inventory of each published asset, its version, destination(s), intended audience, owner, claims-evidence links, rights terms/expiry, source project, dependent pages/docs/campaigns, review date, and support contact. Coordinate updates across destinations; do not assume replacing one copy updates embeds, downloads, or third-party reposts.
- **MEDIA-02.04 — Monitor feedback and detect content defects.** The owner MUST review viewer/user reports, broken links, caption defects, privacy disclosures, rights complaints, playback/encoding issues, and product inaccuracies. Define a response route and severity-based response expectation. Analytics MUST follow the project’s privacy and telemetry rules, collect only approved signals, restrict access, and honor retention choices. Viewer counts alone do not demonstrate that the intended learning or product outcome was achieved.
- **MEDIA-02.05 — Correct or withdraw materially inaccurate or unsafe material.** When claims become false, a secret or personal data disclosure is found, rights are disputed, a vulnerability is exposed, or the video can cause material user harm, the owner MUST assess promptly whether to unlist, restrict, replace, correct, or remove the affected content. Follow security/privacy/incident/legal escalation controls, preserve evidence as authorized, and coordinate affected embeds and stakeholders. Do not leave misleading content public solely to preserve campaign metrics.
- **MEDIA-02.06 — Revalidate content when the product or claim changes.** Set review triggers for product version, UI/API changes, compatibility claims, pricing/licensing policy, benchmark methodology, security posture, destination policy, and rights expiry. Revalidate the affected scenes and linked claims before continued promotion. Mark superseded versions clearly or retire them; do not present stale instructions as current.
- **MEDIA-02.07 — Govern source files and raw asset retention.** Classify scripts, raw recordings, project files, releases, credentials, and final renders. Store them in approved locations with role-based access and backup appropriate to business need. Define retention by purpose, rights, privacy, and legal obligations; remove unnecessary takes and sensitive data after the approved retention period. Keep enough licensed source material and project metadata to reproduce or responsibly update the final output, unless rights or privacy restrictions require deletion.
- **MEDIA-02.08 — Retire and delete media with dependency closure.** When a video is retired, identify public destinations, embeds, downloaded copies under project control, dependent documentation/campaigns, rights records, source files, and user links. Provide a replacement or redirect where needed, remove/restrict controlled copies, update links and inventories, revoke access to expired private assets, and record what cannot be recalled from third parties. Preserve only records needed for audit, legal, or provenance purposes under the applicable retention policy.

### MEDIA-03 — Media design system and content templates

**Objective.** Provide a coherent, accessible, reusable creative system for videos and related web content, while requiring each production to choose components that fit its audience, evidence, platform, and purpose.

**Requirements traced:** PA-030, PA-032, PA-035–PA-036, PDL-001–PDL-009, PDL-016

**Normative requirements:**

- **MEDIA-03.02 — Define reusable production components and their contracts.** The media system MUST define reusable components or templates with purpose, inputs, variants, duration/placement expectations, typography/color tokens, animation behavior, sound behavior, accessibility alternatives, editable source, and allowed customization. The inventory MUST consider, as applicable: opening/title card; logo bug; lower third/name and role; section/chapter marker; product UI frame/device mockup; cursor/interaction highlight; callout/annotation; comparison/before-after panel; diagram/architecture frame; metric/benchmark card; quote/testimonial card with permission; code/terminal panel; warning/limitation card; end card/call-to-action; thumbnail; captions; and audio bed/stinger. Components MUST be omitted when they add no informational value.
- **MEDIA-03.03 — Choose narrative structure by viewer task.** Select and document a structure appropriate to the content: problem → outcome → evidence for a short product overview; prerequisites → steps → verification → troubleshooting for a tutorial; context → architecture → flow → failure/recovery for a technical walkthrough; claim → method → result → limitations for a benchmark; or an explicitly reasoned alternative. Define the opening promise, information sequence, proof, transitions, ending, and call to action before production. Do not force every video into one marketing format.
- **MEDIA-03.04 — Specify shot and screen-capture grammar.** The script/storyboard MUST identify the capture type per scene (screen capture, presenter, narration over graphics, animation, live action, or mixed), composition/framing, cursor/focus behavior, text legibility, product state, scene duration target, and transition intent. For screen recordings, set a stable viewport/scale, remove distracting UI and notifications, use predictable cursor movement, zoom only to support comprehension, and use prepared synthetic data. Preserve sufficient context so viewers can understand where an action occurs. Avoid rapid cuts or motion that prevents reading or causes discomfort.
- **MEDIA-03.05 — Use visual hierarchy and motion to clarify information.** Each scene MUST have a primary message and hierarchy among headline, visual evidence, annotation, and supporting detail. Keep text within the chosen destination’s safe area and readable at expected mobile display size. Motion MUST explain sequence, focus, state, or relationship; use restrained duration/easing and provide a reduced-motion or static equivalent for essential web experiences. Do not use flashing content, color alone, tiny captions, or animation as the only carrier of meaning. Validate overlays against the actual footage and final encoded output.
- **MEDIA-03.06 — Define audio and voice treatment.** Specify narration language, pronunciation of product terms, recording environment, microphone distance, noise treatment, music/sound-effect role, voice/music priority, channel layout, loudness target, peak ceiling, and export profile. Dialogue MUST remain intelligible on common speakers/headphones and in mono fold-down where applicable. Music and effects MUST not mask speech or captions. Measure the final render against the selected delivery target; do not adopt broadcast loudness targets blindly for every online platform. Retain clean dialogue/music stems when rights and storage policy allow future remixes.
- **MEDIA-03.07 — Provide content-type templates, not one universal video.** Maintain distinct reusable briefs/storyboard templates for product overview, feature demo, step-by-step tutorial, architecture/engineering explainer, benchmark/performance report, launch announcement, and short-form cutdown when those formats are in scope. Each template MUST ask for the claims/evidence, user prerequisite, version/profile, story sequence, visual components, accessibility deliverables, length/platform constraints, and approval roles relevant to that format. A template MAY be omitted by an owner decision when that format is not in scope.
- **MEDIA-03.08 — Design for destination and aspect-ratio adaptation.** Choose a primary master aspect ratio, resolution, frame rate, color space, and audio layout from intended use and capture source. If multiple destinations/aspect ratios are needed, compose for safe reframing at storyboard time; do not rely on blind center crop for text, faces, UI, or critical information. Maintain a delivery matrix for widescreen, vertical, square, embedded/site, or archival outputs as applicable. Confirm current platform specifications at export time and keep the high-quality master separate from compressed delivery encodes.
- **MEDIA-03.09 — Keep visual/audio components accessible and localized.** Define caption font, size, placement, line length, speaker labels, timing, sound cues, and contrast so captions do not cover essential UI or graphics. Supply human-reviewed caption files and transcript; record translation ownership and terminology glossary for localized versions. Avoid embedding essential text only in the image; localize graphics or supply equivalent transcript/description. Validate each language’s fonts, line breaks, reading speed, names, and timing after export.
- **MEDIA-03.10 — Version and evolve the design system safely.** Give tokens, templates, project files, fonts, plugins, and component packages version/owner/license metadata. A change to identity, template, font, animation, or caption convention MUST assess impact on in-progress and published media, compatibility of source project files, and update cost. Keep deprecated templates readable for active projects or define a migration path. Do not silently overwrite reusable assets used by released work.

### MEDIA-04 — Production code, assets, and website integration

**Objective.** Treat video creation automation, large assets, and website playback as maintained product work with clear boundaries, reproducible outputs, quality gates, accessibility, privacy, and operational ownership.

**Requirements traced:** PA-024, PA-031–PA-036, ED-001, ED-010, ED-020–ED-024, ED-030–ED-033, PDL-006–PDL-017

**Normative requirements:**

- **MEDIA-04.02 — Give media production a separate monorepo boundary.** When production workflows are maintained in this repository, use a dedicated `media/` product area with its own `README.md` and `AGENTS.md`, toolchain/lockfiles, scripts, tests, asset policy, build instructions, and ownership. It MUST NOT be a dependency of the inference engine’s build, runtime, install, or release profiles. Define explicit interfaces to shared brand assets or website packages; avoid cross-area private imports and toolchain coupling. The `media/` owner MUST maintain a supported build/render entry point and document required licenses, hardware, and external inputs.
- **MEDIA-04.03 — Organize work products for discoverability and safe revision.** Use a documented layout equivalent to: `brand/` for approved style guide/tokens; `templates/` for content-type templates and reusable scene components; `projects/<video-id>/` for brief, script, storyboard, claims, rights manifest, and edit/render config; `assets/` for approved shared source media; `automation/` for render, QC, and packaging code; and `releases/<video-id>/<version>/` or an approved artifact store for release manifests and outputs. Large binaries MUST use an approved large-file or artifact store with stable IDs/checksums and access controls rather than silently bloating ordinary source history. Keep project-specific raw footage segregated and access-limited.
- **MEDIA-04.04 — Represent automated scenes as typed, validated inputs.** For programmatic video, model scenes, durations, assets, narration, captions, transitions, and output profiles in a validated schema. Give each scene a stable identifier and explicit required/optional assets, timing, locale, and accessibility text. Fail early with actionable diagnostics for missing media, unsupported dimensions, unresolved fonts, invalid time ranges, unlicensed inputs, missing captions, or contradictory project settings. Avoid arbitrary code evaluation or unchecked paths in user-editable project manifests; treat asset paths and project input as untrusted data. Keep rendering deterministic where the toolchain permits and disclose nondeterministic codecs/metadata.
- **MEDIA-04.05 — Pin and inventory production dependencies.** Record editor/render-tool versions, plugins, fonts, codecs, templates, scripts, model/AI services if used, and licenses. Pin automated build dependencies and verify downloaded tools/assets; store required binaries in the approved cache/mirror for offline production when offline repeatability is a project requirement. Identify end-of-life/deprecated formats and test migration. Do not promise bit-identical output when codecs, hardware encoders, timestamps, or external services prevent it; define the reproducibility level and verify content/metadata checksums appropriately.
- **MEDIA-04.06 — Build a layered validation pipeline.** A production pipeline MUST support separate fast checks and full render/QC. At minimum, validate: project manifest/schema; required sources and rights metadata; broken/missing media and font dependencies; safe paths and secrets; script/claims references; caption and transcript existence and timing; render dimensions/duration/frame rate/codec/color/audio profile; audio/video synchronization; loudness/peak limits for chosen target; black/silent/frozen frames where relevant; output integrity; and playback. Add visual snapshot or representative frame review only as supporting evidence; it cannot replace watching the complete final video. Store machine-readable QC report linked to source revision and render artifact.
- **MEDIA-04.07 — Make builds and renders resource-bounded and resumable.** Specify expected render time/storage/GPU/CPU and maximum source dimensions/duration per profile. Provide progress, cancellation, safe temporary-file cleanup, disk-space checks, retry behavior, and recovery from interrupted render without corrupting approved outputs. Bound parallel encodes to available resources. A release render MUST be distinguishable from a preview and MUST NOT overwrite an approved artifact without a new version and review.
- **MEDIA-04.08 — Define explicit delivery profiles and manifests.** Maintain versioned profiles for intended destinations rather than one universal export. Each profile defines container, video/audio codecs, dimensions/aspect ratio, frame rate, color space/HDR policy, bitrate or quality mode, audio layout/loudness target, captions, thumbnail, metadata, and validation commands. Record profile version, source revision, toolchain versions, output checksum, and destination requirements in a release manifest. Recheck external destination specifications at release time; keep archived master settings separate from delivery transcodes.
- **MEDIA-04.09 — Integrate video into websites as an accessible, privacy-aware component.** A website video component MUST include a poster/thumbnail, descriptive title, playback controls, caption tracks, transcript or equivalent text path, accessible keyboard/focus behavior, responsive sizing, fallback/error behavior, and no autoplay with sound. Provide a local/first-party player or click-to-load consent pattern when third-party embeds would set cookies, load trackers, or contact external domains before user interaction. Lazy-load noncritical media, reserve layout space to prevent layout shift, and do not make video the sole means to understand the page or complete a task. Record supported formats, caption languages, privacy behavior, and fallback.
- **MEDIA-04.10 — Release and operate the production system safely.** Deploy production tooling and website changes through their owning release controls. Restrict credentials, signing keys, publication tokens, and private raw media to least privilege; use secret stores rather than project config. Publish only approved release manifests. Monitor render failures, storage saturation, artifact integrity, player failures, accessibility reports, and broken links at a level proportionate to use. Define rollback for website/player releases, disable/revoke publication credentials on compromise, and provide a manual fallback procedure if the render or hosting pipeline is unavailable.
- **MEDIA-04.11 — Test behavior at unit, integration, and release seams.** Test scene/schema parsing and timeline calculations as unit tests; test asset resolution, caption association, and render invocation as integration tests; and test representative full renders and playback as release checks. Include malformed manifests, missing assets/fonts, unsupported profile, cancellation, disk exhaustion, encoder/tool failure, caption mismatch, and privacy/embed behavior as applicable. Use tiny synthetic fixtures in CI; reserve full-quality renders for scheduled or release workflows. Document hardware and resource prerequisites; report skipped GPU or platform checks honestly.

## Verification

From the repository root:

```sh
uv run --locked pytest torviello-enforcer/media-production
uv run --locked python torviello-enforcer/tools/generate_rule_tests.py
```

Regenerate tests after changing a rule document. A control passes only when every applicable MUST requirement is implemented and supported by current evidence; missing product behavior fails the generated test with an explicit no-evidence message. Record exceptions in [`governance/assurance-register.md`](../governance/assurance-register.md).
