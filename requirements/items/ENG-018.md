# ENG-018 — Expose health, readiness, liveness, and bounded metrics

**Requirement ID:** ENG-018  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-24](../../torviello-engine/specifications/checks/AC-ENG-24.md)  
**Rule controls:** OBS-02, OPS-01, SEC-10

## 1. Normative requirement

The engine MUST expose distinct liveness, readiness, and subsystem health, a Prometheus-compatible metrics endpoint with bounded cardinality, and a live dashboard stream, and it MUST keep probes available when inference traffic is saturated or rate limited.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability. At HPA-4, telemetry MUST follow OpenTelemetry Semantic Conventions 1.44.0 and Prometheus/OpenMetrics exposition, with bounded labels and probe independence from inference admission.

## 2. Why this requirement exists

Operators need three different answers: is the process alive, can it serve the configured workload, and which subsystem is degraded. Collapsing them into one endpoint causes restart loops or silent outages. The reference implementation provides `/health`, `/health/live`, `/health/ready`, `/metrics`, and `/dashboard/stream`, with subsystem checks for error rate, performance, monitor, and capacity.

Torviello specifies semantics and operational properties: what each probe means, which components gate readiness, how labels stay bounded, and why probes must bypass inference rate limiting. Metrics also need a retention and cardinality policy so a scrape endpoint cannot become a memory leak.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to health, liveness, readiness, metrics, dashboard streaming, and any aliases used by orchestrators. It covers response semantics, subsystem aggregation, metric naming and labels, scrape behavior, and probe exemptions. It does not define alert thresholds.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Keep liveness dependent only on the process and runtime being able to accept work.
- Gate readiness on required configuration, providers, and models and report pending or failed components.
- Report subsystem health with status, message, and observed values without secrets.
- Emit Prometheus text format with documented metric names, types, units, and bounded label dimensions.
- Keep scrape cost bounded and cache expensive system sampling within a documented interval.
- Exempt health and metrics from inference rate limiting and circuit breaking.
- Stream dashboard updates on a documented interval and close cleanly when the client disconnects.

#### OBS-02.01 — Expose bounded metrics for request volume, failures, latency distributions

The project MUST expose bounded metrics for request volume, failures, latency distributions, saturation, active work, queue depth, model load/readiness, resource use, and upstream failures.

#### OBS-02.02 — Give each metric one meaning and unit

The project MUST give each metric one meaning and unit. The project MUST also use standard base units and type suffixes where appropriate. The project MUST also use labels for bounded dimensions only; review multiplicative cardinality before adding labels.

#### OBS-02.03 — Distinguish process liveness from readiness to serve the selected

The project MUST distinguish process liveness from readiness to serve the selected product profile. A live process with required models unavailable is not ready.

#### OBS-02.04 — Restrict metrics endpoints to trusted monitoring networks or protect

The project MUST restrict metrics endpoints to trusted monitoring networks or protect them using deployment-supported authentication and TLS. The project MUST NOT expose Prometheus admin/lifecycle endpoints publicly.

#### OBS-02.05 — Monitoring profiles MUST document scrape intervals/timeouts, target discovery, authentication/TLS

Monitoring profiles MUST document scrape intervals/timeouts, target discovery, authentication/TLS, storage retention, dashboards, alert thresholds, ownership, and runbooks. Scrape timeout MUST NOT exceed scrape interval.

#### OBS-02.06 — Validate Prometheus configuration and alert/recording rules with official tooling

The project MUST validate Prometheus configuration and alert/recording rules with official tooling before deployment. Configuration changes are reviewed and rolled back on failed validation.

#### OBS-02.07 — Alerts MUST focus on user-visible symptoms, saturation, and recovery

Alerts MUST focus on user-visible symptoms, saturation, and recovery failure. Each production alert MUST have severity, owner, action, and a test path.

#### OPS-01.01 — Document and support installation, start, stop, restart, readiness, liveness

The project MUST document and support installation, start, stop, restart, readiness, liveness, logs, configuration, upgrade, rollback, and uninstall for each declared deployment profile.

#### OPS-01.02 — Startup MUST validate configuration and required runtime prerequisites before

Startup MUST validate configuration and required runtime prerequisites before readiness becomes true. Readiness MUST reflect whether configured capabilities can serve; liveness MUST reflect whether the process can continue operating.

#### OPS-01.03 — Shutdown MUST stop accepting work, drain or cancel requests

Shutdown MUST stop accepting work, drain or cancel requests within a defined deadline, flush required state, and release model/runtime resources. Repeated signals and abrupt termination MUST have bounded behavior.

#### OPS-01.04 — Configure process supervision or container restart behavior with bounded

The project MUST configure process supervision or container restart behavior with bounded retry/backoff and visible failure state. Endless restart loops MUST NOT hide invalid configuration or unavailable required models.

#### OPS-01.05 — Keep the local engine usable without a hosted account

The project MUST keep the local engine usable without a hosted account, hosted registry, or telemetry endpoint unless the selected profile explicitly requires that service.

#### SEC-10.01 — Every security-relevant setting MUST have a safe default…

**Requirement:** Every security-relevant setting MUST have a safe default for its deployment profile and a validation rule preventing known-dangerous combinations.

#### SEC-10.02 — Authentication MUST be required for remote administrative and persistent…

**Requirement:** Authentication MUST be required for remote administrative and persistent user-data operations. Local account-free operation MUST be restricted to a clearly defined local exposure boundary.

#### SEC-10.03 — Authentication and authorization failures MUST not disclose credential validity…

**Requirement:** Authentication and authorization failures MUST not disclose credential validity, protected object existence, tenant membership, or internal policy details beyond what the caller needs to remediate.

#### SEC-10.04 — Expensive operations MUST enforce per-actor and global resource budgets…

**Requirement:** Expensive operations MUST enforce per-actor and global resource budgets, deadline, queue admission, cancellation, and retry ceilings; budgets MUST apply to preprocessing, model download, inference, and response serialization.

#### SEC-10.05 — Resource exhaustion MUST degrade predictably: reject new work…

**Requirement:** Resource exhaustion MUST degrade predictably: reject new work, protect existing work according to policy, preserve essential health/administrative recovery, and avoid process-wide failure from one request.

**Requirement:** Abuse detection MUST correlate repeated authentication failures, model-download abuse, sensitive business flow automation, and unusual resource consumption with bounded signals and privacy-safe retention.

**Requirement:** Security controls MUST fail closed when their required key, policy, validator, or authorization dependency is unavailable; availability exceptions require a named decision and a bounded degraded mode.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** OpenTelemetry Semantic Conventions 1.44.0, W3C Trace Context, Prometheus/OpenMetrics, Google SRE monitoring practice, IETF BCP 14.

- Telemetry MUST use OpenTelemetry 1.44.0 semantic conventions for HTTP, service, resource, exception, and trace fields.
- Liveness, readiness, and health MUST answer distinct questions; probes MUST NOT be blocked by inference admission, rate limits, or circuit state.
- Metric names, units, and histogram buckets MUST be documented; label sets MUST be bounded and MUST NOT contain request IDs, paths, prompts, or user-controlled values.
- Every scrape and probe MUST be attributable to the engine version and profile without disclosing secrets.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- Liveness returns 200 for a running process even when no model is loaded.
- Readiness returns 503 and names pending components before initialization, then 200 when ready.
- Health reports per-subsystem checks and does not report overall healthy when a required subsystem failed.
- Metrics parse as Prometheus text and use only documented labels.
- Health and metrics remain available after the client exceeds its inference request budget.
- Dashboard events arrive on the documented interval and stop after disconnect.

Acceptance checks: [AC-ENG-24](../../torviello-engine/specifications/checks/AC-ENG-24.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- Metrics MUST validate against the Prometheus/OpenMetrics exposition and be checked for naming, units, histogram, and cardinality.
- Cardinality analysis MUST show the series budget under mixed traffic and MUST fail on unbounded labels.
- Probe tests MUST run while queues are full, circuits are open, and a long inference is active.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Compute readiness from a startup state registry. Aggregate health from named subsystem checks with explicit required and optional flags. Use a metrics facade with predeclared label enums. Cache system sampling and keep scrape handlers independent of inference permits.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not make liveness depend on model availability.
- Do not return ready while required components are pending.
- Do not add unbounded request IDs, prompts, or paths as metric labels.
- Do not block probes behind inference concurrency limits.
- Do not expose secrets or raw payloads in health or metrics.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Probe liveness and readiness before, during, and after initialization.
- 2. Introduce a failed required component and inspect health aggregation.
- 3. Scrape metrics under load and validate format and label sets.
- 4. Exhaust the rate-limit budget and repeat probe and metrics calls.
- 5. Subscribe to the dashboard stream and disconnect.
- 6. Record responses, timings, and metric cardinality.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Scrape metrics under mixed load and run cardinality and naming checks.
- 10. Execute probes under saturation and record status, latency, and response body.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Probe responses for each lifecycle stage.
- Health aggregation output for a failed component.
- Prometheus scrape validation and label inventory.
- Probe exemption evidence after rate-limit exhaustion.
- Dashboard event timing and disconnect behavior.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The scrape output, naming/units report, and cardinality analysis.
- Probe latency and status under saturation.
- The metric-to-requirement and dashboard mapping.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- Readiness is true before required components are ready.
- Liveness fails because a model is absent.
- Metric labels grow without bound.
- Probes are rate limited or blocked by saturated workers.
- Health reports healthy while a required subsystem is down.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- A metric label is unbounded or contains user-controlled data.
- A probe is blocked by inference saturation or rate limiting.
- Health, readiness, and liveness are substituted for one another.
