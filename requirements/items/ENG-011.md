# ENG-011 — Detect objects with validated model selection and thresholds

**Requirement ID:** ENG-011  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-17](../../torviello-engine/specifications/checks/AC-ENG-17.md)  
**Rule controls:** API-02, API-03, MOD-01

## 1. Normative requirement

The engine MUST validate detection model version and size, resolve thresholds from request or configuration, bound upload size and image dimensions, reject missing models and invalid images before inference, and return boxes with stable class labels and applied thresholds.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

Detection has more selection dimensions than classification: model family, size, confidence threshold, and IoU threshold. The reference implementation validates version and size, applies per-request or configured thresholds, caps multipart image size, validates decoded dimensions, caches the ONNX detector, and returns class names, confidence, and boxes.

Torviello requires those choices to be explicit and reproducible. A request that silently substitutes another model version or threshold cannot be compared with prior results, and an image with zero dimensions can crash or produce meaningless boxes.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to `/yolo/detect`, `/yolo/info`, `/yolo/models`, `/yolo/download`, their versioned aliases, and the detection WebSocket path. It covers model selection, threshold resolution, upload and dimension bounds, inference, class labeling, and response metadata.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Accept only declared model versions and sizes and list supported values on rejection.
- Resolve confidence and IoU thresholds from the request when present, otherwise from configuration, and report the applied values.
- Enforce the multipart image limit while reading and validate decoded width and height before inference.
- Reject a missing or unusable model with a stable not-found or unavailable error and never substitute another model.
- Return detections with class name, confidence, and box coordinates in image space.
- Cache an initialized detector only when doing so preserves model configuration and thread safety.
- Report model identity, latency, and postprocessing state in the response envelope.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** OWASP AISVS 1.01 Level 3 (model provenance and behavior), ISO/IEC 25010:2023, OpenTelemetry 1.44.0, IETF BCP 14.

- Model family, version, and size MUST be validated against an explicit allowlist before load; an unsupported combination MUST fail rather than substitute a model.
- Confidence and IoU thresholds MUST be validated and applied as declared; results MUST be monotonic in confidence for a fixed image and model.
- Boxes and scores MUST be finite, normalized according to the contract, and carry a stable class identifier and label.
- Detection output MUST be compared with the declared model behavior within a stated numeric tolerance, not merely checked for shape.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- A valid image returns detections with count, class names, confidences, and boxes.
- Per-request thresholds override defaults and all returned confidences meet the threshold.
- An unsupported version returns 400 detect.invalid_model with supported values.
- A missing model returns 404 detect.model_not_found without substitution.
- An oversized upload returns 413 before full decode.
- A zero-dimension image returns 400 detect.invalid_image without model invocation.

Acceptance checks: [AC-ENG-17](../../torviello-engine/specifications/checks/AC-ENG-17.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- Property tests MUST verify threshold monotonicity, finite outputs, and stable identifiers over randomized inputs and parameters.
- A differential suite MUST compare outputs with the reference model within a recorded tolerance for a fixed corpus.
- Image decoders and model-selection parsers MUST be fuzzed, and every supported model family and size MUST be exercised.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Resolve a model descriptor from validated version and size before touching the image. Resolve thresholds once and pass them explicitly to the detector. Validate dimensions from the encoded header before full decode where possible. Keep the detector cache keyed by model identity plus any initialization-bound settings.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not silently change model version, size, or thresholds.
- Do not run detection on an image that failed dimension validation.
- Do not return boxes outside the declared coordinate system.
- Do not load a model from a path derived from an unvalidated request.
- Do not reuse a cached detector configured for different thresholds if the backend binds thresholds at initialization.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Run detection with defaults and with explicit thresholds.
- 2. Request an unsupported version and size.
- 3. Remove the model file and request detection.
- 4. Submit an oversized upload and a zero-dimension image.
- 5. Inspect response metadata and class labels.
- 6. Record fixtures, commands, and observed results.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Run the threshold and numeric property suite across every supported model family.
- 10. Compare the detection corpus with the reference model and record tolerance and deviations.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Detection response with boxes, labels, confidences, and count.
- Threshold override effect on returned confidences and metadata.
- Validation and missing-model error responses.
- Upload and dimension rejection evidence.
- Response envelope with model ID and latency.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The model-family and size validation matrix.
- The differential report with corpus digest and tolerance.
- Property-test and fuzz reports for image and parameter parsers.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- An unsupported version executes another model.
- Returned confidences violate the requested threshold.
- A missing model returns an empty success.
- An invalid image reaches the detector.
- Box coordinates or labels are unstable across equivalent requests.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- An unsupported model is substituted silently.
- A threshold is ignored or produces non-monotonic results.
- A non-finite or out-of-range box or score is returned.
