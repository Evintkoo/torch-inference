# ENG-005 — Acquire, verify, and remove model assets safely

**Requirement ID:** ENG-005  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-11](../../torviello-engine/specifications/checks/AC-ENG-11.md)  
**Rule controls:** MOD-02, MOD-06, SEC-06, SEC-04

## 1. Normative requirement

Model acquisition MUST run as bounded, observable jobs; validate source schemes, names, and destinations; verify provenance and integrity before activation; and delete only managed assets inside the configured cache root.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

Model downloads combine untrusted network content, filesystem writes, large transfers, and executable inference artifacts. The reference implementation already creates download tasks, supports Hugging Face repositories and HTTP URLs, rejects path separators in names, streams progress, and reports cache usage. Those are necessary controls, not a complete supply-chain contract.

Torviello requires a job state machine, digest or signature verification before activation, atomic placement, and confined deletion. The requirement also keeps offline operation possible by making downloads an explicit action rather than a hidden startup dependency.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to the download manager, registry download endpoints, cache maintenance, and any startup bootstrap that fetches assets. It covers remote acquisition, local import, verification, activation, listing, and deletion. It does not prescribe a specific model hub.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Represent acquisition as a job with queued, downloading, verifying, extracting, ready, failed, and cancelled states that are observable and monotonic.
- Validate model names and destination paths so no request can write outside the configured cache root, including through traversal or symlinks.
- Allow only declared source schemes and require the needed repository or URL fields for each source type.
- Verify the downloaded artifact against a declared digest or signature before it becomes available for loading.
- Place verified assets atomically and never expose a partially written file as ready.
- Bound transfer size, time, and concurrency; record bytes transferred and the terminal reason.
- Delete only assets owned by the manager and refuse paths outside the cache root.

#### MOD-02.01 — Restrict downloads to configured or allowlisted sources

The project MUST restrict downloads to configured or allowlisted sources. The project MUST also enforce TLS verification, safe redirect rules, connection and total timeouts, maximum size, disk-space checks, and bounded retries.

#### MOD-02.02 — Verify a cryptographic digest or signature before extracting

The project MUST verify a cryptographic digest or signature before extracting or loading an artifact. Reject mismatches and retain evidence of the verification result.

#### MOD-02.03 — Extract archives into a staging directory after rejecting absolute

The project MUST extract archives into a staging directory after rejecting absolute paths, parent traversal, links outside the destination, duplicate collisions, and excessive expanded size.

#### MOD-02.04 — Install and activate atomically

The project MUST install and activate atomically. A failed or interrupted download, extraction, or model load leaves the prior active artifact intact.

#### MOD-02.05 — Separate download state, installed state, and active state

The project MUST separate download state, installed state, and active state. The project MUST also report each explicitly to operators and readiness checks.

#### MOD-02.06 — Provide a preloaded/offline installation path for restricted deployments

The project MUST provide a preloaded/offline installation path for restricted deployments.

#### MOD-06.01 — Model manifests MUST bind publisher identity, immutable model/version…

**Requirement:** Model manifests MUST bind publisher identity, immutable model/version identity, file list, size, cryptographic digest, license, compatibility metadata, and any signature or attestation to the exact bytes installed.

#### MOD-06.02 — Downloaded model files MUST be written to an isolated…

**Requirement:** Downloaded model files MUST be written to an isolated temporary location, size-limited during transfer, verified before activation, and atomically moved into the immutable content-addressed store only after complete validation.

#### MOD-06.03 — Archive extraction MUST reject path traversal, absolute paths…

**Requirement:** Archive extraction MUST reject path traversal, absolute paths, duplicate/conflicting paths, symlink escape, excessive file count, excessive expansion, and special device files.

#### MOD-06.04 — Update trust MUST define trusted roots, key rotation…

**Requirement:** Update trust MUST define trusted roots, key rotation, expiration, rollback/freeze/mix-and-match defenses, metadata freshness, and recovery when signing keys are suspected compromised; use TUF or an equivalent reviewed update framework for remote catalogs.

#### MOD-06.05 — Failed network, signature, digest, license…

**Requirement:** Failed network, signature, digest, license, compatibility, disk-write, or activation checks MUST preserve the last known-good model and leave a diagnosable failure record.

#### MOD-06.06 — Local/offline installation MUST have an import path that verifies…

**Requirement:** Local/offline installation MUST have an import path that verifies the same identity, integrity, license, and compatibility data as remote installation.

#### MOD-06.07 — Model deletion MUST distinguish user-owned, shared, active…

**Requirement:** Model deletion MUST distinguish user-owned, shared, active, cached, and system-provided assets; active references MUST be released safely before bytes are removed.

#### SEC-06.01 — Pin and review build dependencies and release inputs

The project MUST pin and review build dependencies and release inputs. The project MUST also generate an SBOM and preserve provenance for every release.

#### SEC-06.02 — Scan dependencies, source, secrets, containers, and model artifacts

The project MUST scan dependencies, source, secrets, containers, and model artifacts. Triage findings using exploitability and deployment context; block unsafe releases under the documented severity gate.

#### SEC-06.03 — Download models only from configured trusted sources

The project MUST download models only from configured trusted sources. The project MUST also verify digest/signature and license/source metadata before installation or activation.

#### SEC-06.04 — Preserve model and software version identity

The project MUST preserve model and software version identity. Updates are atomic and have a rollback path; failed verification never replaces a known-good artifact.

#### SEC-06.05 — Review build workflows and credentials as production security boundaries

The project MUST review build workflows and credentials as production security boundaries. The project MUST also use least privilege and short-lived credentials for release automation.

#### SEC-04.01 — Validate type, size, structure, dimensions, duration, encoding, path

The project MUST validate type, size, structure, dimensions, duration, encoding, path, and resource cost before parsing or inference. The project MUST also apply independent limits at network, parser, queue, and model boundaries.

#### SEC-04.02 — Protect against path traversal, symlink escape, archive bombs, decompression

The project MUST protect against path traversal, symlink escape, archive bombs, decompression bombs, parser crashes, SSRF, command injection, and unsafe deserialization.

#### SEC-04.03 — Use allowlisted sources for remote fetches

The project MUST use allowlisted sources for remote fetches. The project MUST also restrict schemes, redirects, resolved addresses, ports, response sizes, and timeouts; block loopback/private/link-local destinations unless specifically required.

#### SEC-04.04 — Run model/file parsing with least privilege and bounded memory/CPU/time

The project MUST run model/file parsing with least privilege and bounded memory/CPU/time. The project MUST NOT execute model-provided code or custom operators without an explicit security review and isolation design.

#### SEC-04.05 — Use safe output encoding and content security policy

The project MUST use safe output encoding and content security policy for web views. The project MUST also treat model outputs as untrusted when rendered or used to construct downstream operations.

#### SEC-04.06 — Apply bounded concurrency, request size, queue depth, and timeouts

The project MUST apply bounded concurrency, request size, queue depth, and timeouts to prevent denial of service.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** OWASP ASVS 5.0.0 Level 3 (file handling, input validation), OWASP AISVS 1.01 Level 3 (model supply), SLSA v1.2 Build Level 3, NIST SSDF SP 800-218 v1.1, IETF BCP 14.

- Path confinement MUST use canonicalization plus no-follow and directory-relative operations; absolute paths, traversal, symlinks, hardlinks, device files, and special files MUST be rejected.
- Archive extraction MUST enforce entry count, total uncompressed size, per-entry size, path depth, and compression-ratio quotas before writing.
- Integrity verification MUST use an approved digest or signature over the exact activated bytes; verification MUST precede atomic activation.
- Concurrent verification, replacement, deletion, and cleanup MUST be free of time-of-check/time-of-use races and MUST never expose a partial asset.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- A valid source creates a task ID and advances through documented states.
- Progress events carry task ID, state, and bytes, and close after the terminal state.
- model_name ../escape returns 400 and writes no file outside the cache.
- A file:// source is rejected without reading the file.
- A digest mismatch ends the task failed and does not activate the asset.
- Deletion removes only the targeted managed model and leaves unrelated assets intact.

Acceptance checks: [AC-ENG-11](../../torviello-engine/specifications/checks/AC-ENG-11.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- Archive and path parsers MUST survive at least 24 CPU-hours of fuzzing plus a curated corpus of traversal, symlink, hardlink, zip-bomb, and malformed-header cases.
- Property tests MUST prove that no client-derived path resolves outside the configured root under any separator, encoding, or normalization.
- Supply-chain verification MUST validate the signed provenance and SBOM for every downloaded model artifact that declares them.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Use a job manager with a persisted or in-memory state machine, bounded worker pool, and per-task cancellation. Destination paths should be constructed from canonical cache root plus validated ID segments. Verify into a temporary sibling, then rename atomically. Track ownership in a manifest so deletion and cleanup cannot target arbitrary paths.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not activate an unverified artifact or expose a partial download as ready.
- Do not accept arbitrary local paths or file URLs from a remote client.
- Do not follow a model name or link outside the configured cache root.
- Do not leave a failed download in the available set.
- Do not delete unmanaged files during cache cleanup.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Start a download from a prepared test source and poll status and event streams.
- 2. Attempt traversal names, a file:// source, and a destination symlink that escapes the cache.
- 3. Serve a deliberately corrupt artifact and observe verification and activation behavior.
- 4. Delete a managed model and compare cache contents before and after.
- 5. Inspect state transitions and terminal reasons for each case.
- 6. Record source fixtures, commands, and observed filesystem changes.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Replay the malicious archive and path corpus and confirm rejection before any write.
- 10. Interrupt transfer, verification, extraction, activation, and cleanup at every boundary and inspect the visible state.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Task state transcripts and event streams for a successful and failed download.
- Rejection responses for unsafe names, schemes, and paths.
- Digest verification output and the post-failure availability listing.
- Before-and-after cache inventories for deletion.
- Evidence that no file was created outside the cache root.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- Fuzz logs, the malicious corpus, and zero-finding reports.
- Digest and signature verification records tied to the activated bytes.
- Crash-consistency evidence showing no partial asset becomes available.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- A partial or unverified file is loadable.
- A traversal name or file URL writes or reads an arbitrary host path.
- A failed job remains marked available.
- Progress never reaches a terminal state.
- Deletion removes unrelated assets.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- Any path can escape the model root or follow a link outside it.
- An asset is activated before integrity verification succeeds.
- A partial or failed asset is listed as available or loadable.
