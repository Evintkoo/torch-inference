# ENG-024 — Preserve local offline operation and optional service boundaries

**Requirement ID:** ENG-024  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-30](../../torviello-engine/specifications/checks/AC-ENG-30.md), [AC-ENG-04](../../torviello-engine/specifications/checks/AC-ENG-04.md)  
**Rule controls:** ARC-02, SEC-08, OPS-03

## 1. Normative requirement

The core engine MUST start and serve supported local inference with no account, control plane, or outbound network once required assets exist; optional upstream services MUST be explicit, disabled by default, and isolated so their failure cannot degrade local inference.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

Torviello's product promise depends on local execution that does not phone home. The reference implementation can start without the optional LLM service, serves local speech, vision, and classification paths, and auto-downloads models on first start. Auto-download is convenient, but a hidden network dependency contradicts an offline claim.

Torviello distinguishes preparation from execution: assets may be acquired by an explicit command or configured bootstrap, but the serving path must not require network access. Optional services are adapters with their own configuration, timeouts, and failure domains. This requirement protects both user trust and reproducibility.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to local engine startup, inference paths, asset preparation, optional LLM or STT services, telemetry, and deployment profiles. It covers offline serving, explicit acquisition, service configuration, failure isolation, and data egress. It does not define a hosted control plane.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Serve all configured local capabilities without an account or control-plane call once assets are present.
- Make network acquisition explicit and observable; do not perform a hidden download in a request path.
- Allow downloads or bootstrap to be disabled, and report actionable local placement guidance when assets are absent.
- Configure optional upstream services explicitly and leave their routes unavailable when unconfigured.
- Isolate upstream failures so local capabilities remain ready and measurable.
- Disable telemetry and external analytics by default and document every outbound endpoint.
- Record outbound destinations in the runtime profile so an operator can audit egress.

**Requirement:** Loopback-only local mode MUST bind to loopback and MUST reject or clearly warn when configuration exposes it to a non-loopback interface without an explicit network-exposure policy.

**Requirement:** Production network traffic carrying credentials, user data, model metadata with access impact, or administrative changes MUST use authenticated TLS with validated peer identity and supported protocol/cipher policy.

**Requirement:** Proxy-derived identity and forwarding headers MUST be trusted only from configured proxy hops. The service MUST ignore spoofed forwarded headers from direct clients.

**Requirement:** CORS MUST use explicit origins, methods, headers, and credential policy. Wildcard origins MUST NOT be combined with credentials; browser security headers and cache policy MUST match the UI/API threat model.

**Requirement:** Outbound connections MUST use destination allowlists where feasible, validate DNS results and redirects, block prohibited address ranges, and revalidate after redirect or DNS change to resist SSRF and rebinding.

**Requirement:** DNS, proxy, TLS, certificate-expiry, and upstream timeout failures MUST be observable and fail safely without falling back to plaintext or an untrusted endpoint.

#### OPS-03.02 — Install and upgrade procedures MUST be repeatable from…

**Requirement:** Install and upgrade procedures MUST be repeatable from a clean machine and MUST distinguish administrator actions from service-user actions. The service MUST run with least privilege and writable paths limited to documented state/cache locations.

#### OPS-03.03 — Service definitions MUST set restart policy, startup ordering…

**Requirement:** Service definitions MUST set restart policy, startup ordering, graceful stop timeout, environment/config source, resource limits, and log routing appropriate to the target service manager.

#### OPS-03.04 — Container images MUST pin base image identity, use…

**Requirement:** Container images MUST pin base image identity, use non-root execution where feasible, include only runtime artifacts, define health checks, and avoid embedding secrets or mutable model downloads in image layers.

#### OPS-03.05 — Network listeners MUST bind to the intended interface by…

**Requirement:** Network listeners MUST bind to the intended interface by default. Remote exposure MUST require an explicit deployment choice and documented authentication, TLS termination, firewall, and proxy trust policy.

#### OPS-03.06 — First startup MUST distinguish missing prerequisites from corrupt state…

**Requirement:** First startup MUST distinguish missing prerequisites from corrupt state and transient dependency failures; automated restart MUST use backoff and MUST not create a restart loop that hides permanent configuration errors.

#### OPS-03.07 — Installation MUST preserve user data and configuration on upgrade…

**Requirement:** Installation MUST preserve user data and configuration on upgrade; uninstall MUST explain which state is retained or removed and require explicit confirmation before destructive deletion.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** ISO/IEC 25010:2023, NIST SSDF SP 800-218 v1.1, SLSA v1.2, OWASP ASVS 5.0.0 Level 3, IETF BCP 14.

- After declared assets are prepared, local inference MUST operate with no account, control plane, license check, telemetry call, or DNS lookup.
- Every outbound destination MUST be declared and disabled by default; optional upstreams MUST be isolated from local readiness.
- Dependency and build manifests MUST be inspectable, and no hidden download may occur at request time.
- A blocked-egress run MUST exercise the complete local capability matrix and MUST fail only for an explicitly configured remote feature.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- With assets present and egress blocked, local inference endpoints serve successfully.
- With assets absent and downloads disabled, the response names the missing asset and local path without a network attempt.
- With no assistant upstream configured, assistant routes return not_configured and local inference works.
- An unreachable upstream leaves local capabilities ready and healthy.
- Telemetry is off by default and no analytics endpoint is contacted.
- The runtime profile lists every configured outbound destination.

Acceptance checks: [AC-ENG-30](../../torviello-engine/specifications/checks/AC-ENG-30.md), [AC-ENG-04](../../torviello-engine/specifications/checks/AC-ENG-04.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- An egress-blocked network namespace MUST run the complete local matrix with captured traffic showing zero external connections.
- A dependency and build audit MUST identify every outbound endpoint and its configuration gate.
- Optional upstream failure MUST leave local readiness and local capabilities unchanged.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Split preparation from serving. The serving process reads only local assets. Optional services live behind adapters with explicit base URLs and disabled defaults. Maintain an egress inventory in configuration and expose it in runtime introspection. Keep telemetry opt-in and route it through one documented client.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not require an account, control plane, or network call for local inference.
- Do not perform an unadvertised download from a serving request.
- Do not let an optional upstream gate engine readiness.
- Do not send prompts, audio, images, or results to an external endpoint by default.
- Do not hide an outbound dependency in a helper library.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Prepare assets, block egress, and run each local capability.
- 2. Remove one asset, disable downloads, and request that capability.
- 3. Run with no assistant upstream configured and with an unreachable one.
- 4. Inspect runtime and network observations for outbound calls.
- 5. Check telemetry defaults and configuration.
- 6. Record hosts, network policy, requests, and observations.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Run the local matrix with egress blocked and capture all network activity.
- 10. Inspect build and runtime dependencies for undeclared endpoints.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- Offline inference success with egress blocked.
- Missing-asset guidance without network activity.
- Unconfigured and failed upstream behavior with local health.
- Outbound destination inventory and telemetry defaults.
- Network trace showing no external call in the local path.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- The egress capture and blocked-network results.
- The endpoint inventory mapped to configuration gates.
- The local readiness timeline during upstream failure.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- Local inference requires a network call or account.
- A request triggers a hidden download.
- An optional upstream failure makes the engine unready.
- User content leaves the host by default.
- Outbound dependencies are undocumented.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- A hidden outbound call, telemetry ping, or license check occurs.
- Local mode requires an account or control-plane credential.
- Optional upstream failure changes local readiness.
