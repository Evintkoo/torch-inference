# SO-024 — Telemetry export shall be optional and configurable for offline or privacy-sensitive installations

**Requirement ID:** SO-024  
**Priority:** SHOULD  
**Source:** [security-and-operations.md](../security-and-operations.md) — Logging and observability

## 1. Normative requirement

Telemetry export shall be optional and configurable for offline or privacy-sensitive installations.

### OBS-01 — Secure structured logging and traces

*Domain:* [observability](../../torviello-enforcer/observability/README.md) · *Rule:* [01-secure-structured-logging-and-traces.md](../../torviello-enforcer/observability/rules/01-secure-structured-logging-and-traces.md)

**Control objective.** These controls govern **secure structured logging and traces**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### OBS-01.01 — Emit structured runtime logs through the shared logging system

The project MUST emit structured runtime logs through the shared logging system. The project MUST also include timestamp, severity, service identity, event name, and correlation/trace context where available.

#### OBS-01.02 — Record operational and security events consistently: startup/shutdown, authentication

The project MUST record operational and security events consistently: startup/shutdown, authentication and authorization outcomes, configuration changes, model installation/promotion, dependency failures, and request outcomes.

#### OBS-01.03 — Log passwords, tokens, API keys, private keys, database credentials

The project MUST NOT log passwords, tokens, API keys, private keys, database credentials, full prompts, raw uploads, or unnecessary personal data. It MUST redact secrets at boundaries and sanitize untrusted values against log injection.

#### OBS-01.04 — Bound log volume and retention

The project MUST bound log volume and retention. The project MUST also use rotation or external collection without allowing disk exhaustion to interfere with application state.

#### OBS-01.05 — Use OpenTelemetry semantic conventions for HTTP, service identity, exceptions

The project MUST use OpenTelemetry semantic conventions for HTTP, service identity, exceptions, and resources. Propagate trace context across trusted service boundaries; never treat correlation identifiers as identity or authorization.

#### OBS-01.06 — Make telemetry export explicitly configurable and off by default

The project SHOULD make telemetry export explicitly configurable and off by default in local/offline profiles. The project MUST also document all exported fields and endpoints.

### OBS-02 — Metrics, health, and Prometheus operations

*Domain:* [observability](../../torviello-enforcer/observability/README.md) · *Rule:* [02-metrics-health-and-prometheus-operations.md](../../torviello-enforcer/observability/rules/02-metrics-health-and-prometheus-operations.md)

**Control objective.** These controls govern **metrics, health, and prometheus operations**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### OBS-02.01 — Expose bounded metrics for request volume, failures, latency distributions

The project MUST expose bounded metrics for request volume, failures, latency distributions, saturation, active work, queue depth, model load/readiness, resource use, and upstream failures.

#### OBS-02.02 — Give each metric one meaning and unit

The project MUST give each metric one meaning and unit. The project MUST also use standard base units and type suffixes where appropriate. The project MUST also use labels for bounded dimensions only; review multiplicative cardinality before adding labels.

#### OBS-02.03 — Distinguish process liveness from readiness to serve the selected

The project MUST distinguish process liveness from readiness to serve the selected product profile. A live process with required models unavailable is not ready.

#### OBS-02.04 — Restrict metrics endpoints to trusted monitoring networks or protect

The project MUST restrict metrics endpoints to trusted monitoring networks or protect them using deployment-supported authentication and TLS. The project MUST NOT expose Prometheus admin/lifecycle endpoints publicly.

#### OBS-02.05 — Monitoring profiles MUST document scrape intervals/timeouts, target discovery, authentication/TLS

Monitoring profiles MUST document scrape intervals/timeouts, target discovery, authentication/TLS, storage retention, dashboards, alert thresholds, ownership, and runbooks. Scrape timeout MUST NOT exceed scrape interval.

#### OBS-02.06 — Validate Prometheus configuration and alert/recording rules with official tooling

The project MUST validate Prometheus configuration and alert/recording rules with official tooling before deployment. Configuration changes are reviewed and rolled back on failed validation.

#### OBS-02.07 — Alerts MUST focus on user-visible symptoms, saturation, and recovery

Alerts MUST focus on user-visible symptoms, saturation, and recovery failure. Each production alert MUST have severity, owner, action, and a test path.

### OBS-03 — Traces, context propagation, and telemetry cost

*Domain:* [observability](../../torviello-enforcer/observability/README.md) · *Rule:* [03-traces-context-propagation-and-telemetry-cost.md](../../torviello-enforcer/observability/rules/03-traces-context-propagation-and-telemetry-cost.md)

**Control objective.** This control defines the intended outcome for **traces, context propagation, and telemetry cost** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### OBS-03.01 — Trace context MUST propagate across API handling, queues…

**Requirement:** Trace context MUST propagate across API handling, queues, model loading, inference, persistence, and external calls where causal relationships exist, using supported W3C trace context or an explicitly documented equivalent.

#### OBS-03.02 — Incoming trace context MUST be validated and treated as…

**Requirement:** Incoming trace context MUST be validated and treated as untrusted. It MUST NOT authorize access, select an arbitrary exporter, or cause unbounded trace state or baggage growth.

#### OBS-03.03 — Spans MUST represent operations with meaningful duration or cross-boundary…

**Requirement:** Spans MUST represent operations with meaningful duration or cross-boundary causality. Attributes MUST use stable semantic names, bounded values, documented units, and approved redaction rules.

#### OBS-03.04 — Telemetry sampling MUST define head/tail behavior, error…

**Requirement:** Telemetry sampling MUST define head/tail behavior, error and latency retention, per-profile defaults, and operator controls. Sampling MUST NOT create an unbounded memory buffer or delay request completion.

#### OBS-03.05 — Export MUST be optional for local/offline deployments. Exporter…

**Requirement:** Export MUST be optional for local/offline deployments. Exporter destination, TLS/authentication, data categories, sampling, retry buffer, and shutdown flush timeout MUST be configurable.

#### OBS-03.06 — Telemetry failures MUST not fail inference or block readiness…

**Requirement:** Telemetry failures MUST not fail inference or block readiness unless telemetry is explicitly a required product dependency. Export queues MUST have bounded size and drop behavior with a metric.

#### OBS-03.07 — Changes to semantic conventions MUST document migration and compatibility…

**Requirement:** Changes to semantic conventions MUST document migration and compatibility because dashboards and alert rules can consume the emitted names.

### OBS-04 — Alerts, SLOs, dashboards, and operator actions

*Domain:* [observability](../../torviello-enforcer/observability/README.md) · *Rule:* [04-alerts-slos-dashboards-and-operator-actions.md](../../torviello-enforcer/observability/rules/04-alerts-slos-dashboards-and-operator-actions.md)

**Control objective.** This control defines the intended outcome for **alerts, slos, dashboards, and operator actions** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### OBS-04.01 — Each production service profile MUST define service indicators…

**Requirement:** Each production service profile MUST define service indicators and objectives for user-visible availability, latency, and correctness or error rate where measurable; state measurement population, window, exclusions, and objective owner.

#### OBS-04.02 — Alert thresholds MUST be derived from user impact…

**Requirement:** Alert thresholds MUST be derived from user impact, saturation, error-budget consumption, or recovery failure. Each actionable alert MUST include severity, owner, runbook, expected response, and a test or simulation path.

#### OBS-04.03 — Alerts MUST distinguish symptoms requiring immediate intervention from diagnostic…

**Requirement:** Alerts MUST distinguish symptoms requiring immediate intervention from diagnostic conditions suitable for dashboards or tickets. Avoid paging on a single noisy host or raw dependency metric when service behavior remains healthy.

#### OBS-04.04 — Dashboards MUST show request traffic, successful and failed…

**Requirement:** Dashboards MUST show request traffic, successful and failed latency distributions, error rate, saturation, queueing, model/backend state, resource utilization, and dependency health for the selected service profile.

#### OBS-04.05 — Alert and dashboard queries MUST use bounded labels…

**Requirement:** Alert and dashboard queries MUST use bounded labels and preserve distinctions between failed and successful request latency. Missing telemetry MUST be visible rather than rendered as healthy zero.

#### OBS-04.06 — Prometheus scrape and alert configuration MUST be syntax-validated…

**Requirement:** Prometheus scrape and alert configuration MUST be syntax-validated and rule-tested before deployment; scrape timeout MUST not exceed interval and scrape/authentication settings MUST match the exposed target.

#### OBS-04.07 — Runbooks MUST explain detection, impact, first safe…

**Requirement:** Runbooks MUST explain detection, impact, first safe action, escalation, rollback/recovery, verification of recovery, and evidence to retain.

### OBS-05 — Retention, privacy, and diagnostic access

*Domain:* [observability](../../torviello-enforcer/observability/README.md) · *Rule:* [05-retention-privacy-and-diagnostic-access.md](../../torviello-enforcer/observability/rules/05-retention-privacy-and-diagnostic-access.md)

**Control objective.** This control defines the intended outcome for **retention, privacy, and diagnostic access** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### OBS-05.01 — Logs, traces, metrics, crash reports…

**Requirement:** Logs, traces, metrics, crash reports, and support bundles MUST each have a stated purpose, data classification, retention period, storage location, access policy, and deletion mechanism.

#### OBS-05.02 — Inference prompts, completions, uploaded files, model…

**Requirement:** Inference prompts, completions, uploaded files, model outputs, credentials, and direct identifiers MUST not be collected by default for diagnostics. Any opt-in collection MUST disclose fields, purpose, destination, retention, and how to disable/delete it.

#### OBS-05.03 — Structured fields MUST use an allowlist or explicit classification…

**Requirement:** Structured fields MUST use an allowlist or explicit classification policy. Redaction MUST occur before persistence or export, and tests MUST cover nested fields, exception strings, URLs, query parameters, and malformed input.

#### OBS-05.04 — Diagnostic access MUST be least-privilege and audited when it…

**Requirement:** Diagnostic access MUST be least-privilege and audited when it permits viewing security events, user identifiers, or sensitive inference content.

#### OBS-05.05 — Log rotation and storage limits MUST prevent disk exhaustion…

**Requirement:** Log rotation and storage limits MUST prevent disk exhaustion; behavior when storage is full MUST preserve service safety and surface a bounded alert.

#### OBS-05.06 — Telemetry pseudonyms and correlation identifiers MUST have bounded lifetime…

**Requirement:** Telemetry pseudonyms and correlation identifiers MUST have bounded lifetime and MUST NOT be reused as authentication credentials or stable cross-service user profiles.

#### OBS-05.07 — Support bundles MUST be previewable or field-selectable before export…

**Requirement:** Support bundles MUST be previewable or field-selectable before export and MUST exclude secrets and user payloads unless explicitly selected under an approved support workflow.

### OPS-01 — Service lifecycle and readiness

*Domain:* [operations](../../torviello-enforcer/operations/README.md) · *Rule:* [01-service-lifecycle-and-readiness.md](../../torviello-enforcer/operations/rules/01-service-lifecycle-and-readiness.md)

**Control objective.** These controls govern **service lifecycle and readiness**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### OPS-01.01 — Document and support installation, start, stop, restart, readiness, liveness

The project MUST document and support installation, start, stop, restart, readiness, liveness, logs, configuration, upgrade, rollback, and uninstall for each declared deployment profile.

#### OPS-01.02 — Startup MUST validate configuration and required runtime prerequisites before

Startup MUST validate configuration and required runtime prerequisites before readiness becomes true. Readiness MUST reflect whether configured capabilities can serve; liveness MUST reflect whether the process can continue operating.

#### OPS-01.03 — Shutdown MUST stop accepting work, drain or cancel requests

Shutdown MUST stop accepting work, drain or cancel requests within a defined deadline, flush required state, and release model/runtime resources. Repeated signals and abrupt termination MUST have bounded behavior.

#### OPS-01.04 — Configure process supervision or container restart behavior with bounded

The project MUST configure process supervision or container restart behavior with bounded retry/backoff and visible failure state. Endless restart loops MUST NOT hide invalid configuration or unavailable required models.

#### OPS-01.05 — Keep the local engine usable without a hosted account

The project MUST keep the local engine usable without a hosted account, hosted registry, or telemetry endpoint unless the selected profile explicitly requires that service.

### OPS-02 — Reliability objectives and recovery

*Domain:* [operations](../../torviello-enforcer/operations/README.md) · *Rule:* [02-reliability-slos-and-recovery.md](../../torviello-enforcer/operations/rules/02-reliability-slos-and-recovery.md)

**Control objective.** These controls govern **reliability objectives and recovery**. The intended outcome is that every applicable requirement is implemented at the correct system boundary, produces the specified behavior under normal and adverse conditions, and can be verified from current repository or runtime evidence.

#### OPS-02.01 — Define service-level objectives for availability, latency, and error rate

The project MUST define service-level objectives for availability, latency, and error rate for each production deployment profile. State measurement windows, exclusions, and alert thresholds.

#### OPS-02.02 — Bound request concurrency, queues, model downloads, memory, disk

The project MUST bound request concurrency, queues, model downloads, memory, disk, and timeouts. The project MUST also define backpressure and overload responses before exposure to production traffic.

#### OPS-02.03 — Changes to configuration, models, and registry state MUST validate

Changes to configuration, models, and registry state MUST validate a candidate before activation and retain a known-good rollback point.

#### OPS-02.04 — The project MUST define backup scope, frequency, retention, encryption

For persistent deployments, the project MUST define backup scope, frequency, retention, encryption, access, recovery point objective, and recovery time objective.

#### OPS-02.05 — Provide runbooks for the highest-impact failure modes, including model

The project MUST provide runbooks for the highest-impact failure modes, including model unavailable/corrupt, disk full, GPU lost, database unavailable, credentials expired, and upstream outage.

#### OPS-02.06 — Verify backup restore and release rollback periodically

The project MUST verify backup restore and release rollback periodically; a backup that has never been restored is unverified.

### SEC-09 — Privacy, data minimization, and inference boundaries

*Domain:* [security](../../torviello-enforcer/security/README.md) · *Rule:* [09-privacy-data-minimization-and-inference-boundaries.md](../../torviello-enforcer/security/rules/09-privacy-data-minimization-and-inference-boundaries.md)

**Control objective.** This control defines the intended outcome for **privacy, data minimization, and inference boundaries** and the evidence needed to assess it across normal operation, boundary conditions, failures, and change.

#### SEC-09.01 — Each product profile MUST identify personal, sensitive…

**Requirement:** Each product profile MUST identify personal, sensitive, confidential, and security-relevant data processed at collection, inference, persistence, telemetry, support, and deletion boundaries.

#### SEC-09.02 — Inference inputs and outputs MUST be processed in memory…

**Requirement:** Inference inputs and outputs MUST be processed in memory only by default. Persistence, remote export, training reuse, analytics, or support access MUST require explicit product behavior, disclosure, and retention controls.

#### SEC-09.03 — Data collection MUST be limited to fields necessary…

**Requirement:** Data collection MUST be limited to fields necessary for a stated feature or operational purpose. Optional telemetry MUST be opt-in for local/offline profiles and MUST expose a clear disable path.

#### SEC-09.04 — Access to stored prompts, outputs, credentials…

**Requirement:** Access to stored prompts, outputs, credentials, identity records, and audit data MUST be separated by role and purpose; support access MUST be time-bounded, approved, and audited.

#### SEC-09.05 — Privacy-sensitive operations MUST define deletion scope, backup expiry…

**Requirement:** Privacy-sensitive operations MUST define deletion scope, backup expiry, export, retention exceptions, and legal hold behavior before implementation.

#### SEC-09.06 — Privacy risk review MUST consider inference re-identification, model…

**Requirement:** Privacy risk review MUST consider inference re-identification, model memorization claims, prompt injection into logs, third-party provider handling, and accidental output exposure through caches or shared traces.

#### SEC-09.07 — Incident response MUST include a process to determine whether…

**Requirement:** Incident response MUST include a process to determine whether personal or sensitive data was exposed, preserve minimal forensic evidence, contain access, and notify affected parties according to approved legal/product policy.

## 8. Prohibited conditions

The following conditions are explicitly prohibited by the mapped controls. Any one of them is sufficient to fail the requirement.

- [OBS-01] The project MUST NOT use direct print calls for runtime service diagnostics
- [OBS-01] The project MUST NOT attach prompts, model inputs, user IDs, email addresses, credentials, or request IDs as metric labels
- [OBS-01] The project MUST NOT assume logs are harmless just because they are local files
- [OBS-02] The project MUST NOT generate metric names procedurally
- [OBS-02] The project MUST NOT use unbounded labels or high-cardinality per-user/per-request dimensions
- [OBS-02] The project MUST NOT expose host details, model paths, secrets, or sensitive configuration in health responses
- [OBS-03] Do not place prompts, uploads, credentials, raw model output, or high-cardinality identifiers in trace attributes by default.
- [OBS-03] Do not let an exporter retry queue grow without a hard bound.
- [OBS-04] Do not page on a condition with no owner or safe next action.
- [OBS-04] Do not interpret absence of samples as zero errors or full availability.
- [OBS-05] Do not treat local log files as inherently private or safe.
- [OBS-05] Do not retain sensitive telemetry indefinitely because storage is inexpensive.
- [OPS-01] The project MUST NOT report ready before required models and listeners are usable
- [OPS-01] The project MUST NOT require an operator to manually repair transient failures that the service can recover from safely
- [OPS-01] The project MUST NOT make a hosted control plane a hidden startup dependency for local inference
- [OPS-02] The project MUST NOT define success only as process uptime while users cannot complete inference
- [OPS-02] The project MUST NOT retry non-idempotent operations indefinitely
- [OPS-02] The project MUST NOT claim self-maintaining service behavior without recovery evidence and alerting for unrecoverable failures
- [SEC-09] Do not promise that model outputs are anonymous or private without evaluation and a defined system boundary.
- [SEC-09] Do not reuse customer prompts or outputs for model training or product analytics by implication.
