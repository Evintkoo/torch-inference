# ENG-001 — Resolve, validate, and report one effective configuration

**Requirement ID:** ENG-001  
**Priority:** MUST  
**Source:** [engine-runtime.md](../engine-runtime.md)  
**Acceptance checks:** [AC-ENG-07](../../torviello-engine/specifications/checks/AC-ENG-07.md), [AC-ENG-01](../../torviello-engine/specifications/checks/AC-ENG-01.md), [AC-ENG-02](../../torviello-engine/specifications/checks/AC-ENG-02.md)  
**Rule controls:** CFG-01, CFG-03, CFG-04, SEC-05

## 1. Normative requirement

The engine MUST load one typed TOML configuration, apply the documented precedence of built-in defaults, file values, environment overrides, and command-line overrides, validate the complete candidate before binding a listener, and report the effective values with their sources while redacting secrets.

The capitalized keywords MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative in the sense of BCP 14. Where a clause below is conditional, the stated condition determines applicability.

## 2. Why this requirement exists

Configuration is the first executable statement of the engine's security and resource policy. A host, port, device, concurrency limit, body cap, or authentication secret that is parsed differently from the way it is documented turns every later control into an unreliable claim.

The reference implementation already keeps a typed `Config` structure with defaults, a TOML file, validation for authentication secrets, ports, worker bounds, and detection thresholds, and an effective-configuration endpoint. It does not yet provide one complete precedence model or redacted source attribution. Torviello therefore specifies the stronger behavior and treats the existing structure as the starting point rather than as evidence of conformance.

## 3. Priority and interpretation

This requirement is **MUST**. A MUST requirement is necessary for the stated engine behavior and for a safe release; an unmet MUST blocks release unless an approved exception with compensating measures, an owner, and an expiry exists. A SHOULD requirement is expected unless a documented tradeoff justifies deferral; the tradeoff must still name the affected checks and the residual risk.

Priority applies to the behavior observed through the shipping engine, not to the presence of code, a design document, or a test double. Passing evidence must exercise the same boundary that carries the risk.

## 4. Scope and applicability

Applies to every executable profile that reads configuration, including the local engine, packaged service, container image, and test harness that starts the shipping binary. It covers startup configuration, runtime-visible settings, and operator inspection. It does not define wire-protocol JSON or generated model metadata.

The requirement applies to new and materially changed behavior in the declared profiles. A legacy path becomes subject to it when changed, when it participates in a claimed capability, or when a migration explicitly brings it into scope. Behavior outside the declared platform matrix may be excluded only when the exclusion is published and the unsupported path fails clearly.

## 5. Detailed obligations

The following obligations refine the normative statement for design, implementation, and review.

- Keep one typed schema with documented type, unit, default, valid range, and restart requirement for every setting; reject unknown keys instead of accepting them silently.
- Apply precedence in exactly one order and expose the winning source for each effective value; do not allow an undocumented environment alias to bypass validation.
- Validate cross-field constraints such as minimum and maximum worker counts, authentication secret strength, port range, and threshold bounds before any socket bind or model load.
- Resolve path-valued settings against a stated base, canonicalize them, and reject paths that escape a configured root where confinement is required.
- Redact secret-bearing values in logs, diagnostics, error text, and effective-configuration output; never serialize a resolved secret.
- Treat reload as a separate, explicit capability; if reload is unsupported, say so and require a restart rather than mutating part of the active configuration.
- Make invalid configuration fail with setting-specific, actionable diagnostics and a non-zero process status.

#### CFG-01.01 — TOML MUST be the single canonical human-edited application configuration

TOML MUST be the single canonical human-edited application configuration format. JSON MAY be used for wire protocols and generated machine data, but MUST NOT be a second user configuration format.

#### CFG-01.02 — Keep one typed configuration schema with documented defaults, valid

The project MUST keep one typed configuration schema with documented defaults, valid ranges, units, examples, and compatibility rules. Configuration docs and packaged examples MUST be generated from or checked against the same schema.

#### CFG-01.03 — Define precedence in one order and apply it consistently

The project MUST define precedence in one order and apply it consistently: built-in defaults, selected configuration file, environment overrides, then command-line overrides. The project MUST also document any intentional exception.

#### CFG-01.04 — Parse and validate the complete candidate configuration before binding

The project MUST parse and validate the complete candidate configuration before binding network ports, loading models, or replacing active state. Unknown keys, invalid enum values, unsupported paths, and contradictory settings fail with a setting-specific message.

#### CFG-01.05 — Include an explicit schema version or a compatibility mechanism

The project MUST include an explicit schema version or a compatibility mechanism. The project MUST provide a migration/deprecation path for changed fields and reject unsupported versions clearly.

#### CFG-03.01 — Configuration MUST be parsed into one typed candidate…

**Requirement:** Configuration MUST be parsed into one typed candidate and validated completely before the application binds public listeners, activates models, or mutates persistent state.

#### CFG-03.02 — Validation MUST report the setting name and a safe…

**Requirement:** Validation MUST report the setting name and a safe corrective action without echoing secret values or exposing internal paths. Multiple errors SHOULD be reported together when doing so does not expose sensitive material.

#### CFG-03.03 — Configuration reload MUST be atomic: build and validate…

**Requirement:** Configuration reload MUST be atomic: build and validate a complete candidate, verify its dependencies, then switch active state at a defined boundary. If any step fails, the running system MUST retain the last known-good configuration and report the reload failure.

#### CFG-03.04 — Each setting MUST declare whether it is startup-only…

**Requirement:** Each setting MUST declare whether it is startup-only, reloadable, or dynamically sampled. A reload MUST NOT leave components using incompatible snapshots unless the consistency model is explicitly designed and tested.

#### CFG-03.05 — Configuration watchers MUST debounce partial file writes, handle…

**Requirement:** Configuration watchers MUST debounce partial file writes, handle rename-based replacement, permission changes, deletion, and invalid intermediate files, and MUST avoid unbounded reload loops.

#### CFG-03.06 — Configuration schema evolution MUST define defaulting, deprecation…

**Requirement:** Configuration schema evolution MUST define defaulting, deprecation, migration, unknown-field, and downgrade behavior. A newer binary MUST NOT silently rewrite a file such that the prior supported version cannot start unless that migration is explicit and backed up.

#### CFG-03.07 — Operator-facing effective-configuration output MUST redact credentials, identify source…

**Requirement:** Operator-facing effective-configuration output MUST redact credentials, identify source and precedence for each value, and distinguish explicit values from defaults without exposing secret contents.

#### CFG-04.01 — The documented precedence MUST be deterministic across every executable…

**Requirement:** The documented precedence MUST be deterministic across every executable and deployment profile. The current product requirement is built-in defaults, TOML file, environment overrides, then command-line overrides; any change MUST be approved and reflected in examples and tests.

#### CFG-04.02 — Environment variable names MUST be namespaced, documented…

**Requirement:** Environment variable names MUST be namespaced, documented, and parsed by the same typed validation rules as file values. Ambiguous aliases, silent coercion, and undocumented environment discovery MUST be rejected.

#### CFG-04.03 — Command-line overrides MUST be visible in help output…

**Requirement:** Command-line overrides MUST be visible in help output, validated identically to file settings, and excluded from process listings or logs when values are sensitive.

#### CFG-04.04 — Path-valued settings MUST define resolution base, canonicalization…

**Requirement:** Path-valued settings MUST define resolution base, canonicalization, symlink behavior, permissions, and behavior when parent directories do not exist. User-supplied output paths MUST NOT escape an explicitly confined workspace when confinement is required.

#### CFG-04.05 — Default configuration MUST be safe for local use…

**Requirement:** Default configuration MUST be safe for local use and MUST NOT expose network listeners, enable telemetry, grant administrative access, or select a non-local provider without explicit operator action.

#### CFG-04.06 — Configuration examples MUST be syntactically valid TOML, use…

**Requirement:** Configuration examples MUST be syntactically valid TOML, use non-secret placeholders, and remain checked against the schema and shipped defaults.

#### CFG-04.07 — Deployment-specific configuration MUST separate product policy from secrets…

**Requirement:** Deployment-specific configuration MUST separate product policy from secrets and generated state; package upgrades MUST preserve operator-owned settings unless a versioned migration explicitly changes them.

#### SEC-05.01 — Use maintained cryptographic libraries and standard algorithms

The project MUST use maintained cryptographic libraries and standard algorithms. The project MUST NOT implement cryptographic primitives or protocols directly.

#### SEC-05.02 — Store secrets in an appropriate OS/orchestrator secret store

Each supported deployment profile MUST name an approved secret store and enforce least-privilege read access. Prefer an OS or orchestrator secret manager; when one is unavailable, use a protected file readable only by the owning service identity on encrypted storage. The profile MUST define rotation and revocation steps and MUST fail closed if required secret material cannot be loaded or its access protections cannot be verified.

#### SEC-05.03 — Protect sensitive data in transit and at rest according

The project MUST protect sensitive data in transit and at rest according to classification and deployment threat model. Minimize retention and define deletion behavior.

#### SEC-05.04 — Keep secrets out of source control, logs, telemetry, crash

The project MUST keep secrets out of source control, logs, telemetry, crash reports, screenshots, URLs, and support bundles. Redact at system boundaries and test redaction.

#### SEC-05.05 — Use constant-time comparison for secret-derived authenticators where relevant

Every comparison of a secret-derived authenticator, including a password verifier, MAC, or token, MUST use a constant-time comparison. The project MUST generate secrets with cryptographically secure randomness and MUST fail closed if required entropy or key material is unavailable.

### 5.2 Highest-standard assurance

This requirement is assessed at **HPA-4**, the Highest Practical Assurance level defined in [assurance-standard.md](../assurance-standard.md). The following obligations are additional to section 5 and equally normative.

**Applicable standards:** ISO/IEC/IEEE 29148:2018, ISO/IEC 25010:2023 (security, reliability), OWASP ASVS 5.0.0 Level 3 (configuration and secret management), NIST SSDF SP 800-218 v1.1, IETF BCP 14.

- Precedence MUST be a total, deterministic function over defaults, file, environment, and command line; the same inputs MUST produce the same effective snapshot on every run and platform.
- Unknown keys, wrong types, invalid enums, contradictory settings, and weak authentication secrets MUST be rejected before any listener bind, model load, or file write.
- Validation failures MUST expose a stable machine-readable setting identifier and a safe corrective action, never the rejected secret value or an absolute host path.
- Effective-configuration output MUST report the winning source for every value, distinguish explicit values from defaults, and pass a seeded secret-redaction corpus.

A claim of conformance to an external standard is prohibited unless the complete control-by-control evidence exists; citing the standard is not evidence.

## 6. Acceptance criteria

### 6.0 HPA-4 acceptance rule

Acceptance is binary and evidence-gated by [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md). The check-specific threshold in section 3 of that document is normative; the outcomes below are necessary but not sufficient. One occurrence of any failure criterion in section 4 of that document fails acceptance, and no partial or conditional pass is permitted.


The requirement is satisfied when all of the following observable outcomes hold on a stated revision and environment.

- Starting with no file yields documented defaults and does not create or rewrite a file.
- A file value overrides a default and the effective output identifies the file as its source.
- An unknown key, an out-of-range port, and contradictory worker bounds each fail before the listener binds.
- A malformed environment override fails naming the variable and expected type.
- An enabled authentication mode with a placeholder or short secret fails without echoing the secret.
- Effective-configuration output redacts secrets and distinguishes explicit values from defaults.

Acceptance checks: [AC-ENG-07](../../torviello-engine/specifications/checks/AC-ENG-07.md), [AC-ENG-01](../../torviello-engine/specifications/checks/AC-ENG-01.md), [AC-ENG-02](../../torviello-engine/specifications/checks/AC-ENG-02.md).

### 6.1 Highest-standard gates

These gates are additional to the outcomes in section 6. A gate that cannot be executed is a blocked check, not a pass.

- Property tests MUST compare the precedence implementation with a reference total-order model over randomized source combinations, including absent, empty, duplicate, and malformed values.
- Every configuration parser and overlay path MUST survive at least 24 CPU-hours of coverage-guided fuzzing with no panic, hang, unbounded allocation, or secret disclosure.
- Mutation testing MUST kill at least 90% of mutants in the precedence, validation, and redaction functions.

All gates MUST run against the shipping artifact and configuration, with retained, reproducible evidence.

## 7. Implementation guidance and assessment determination

Keep one configuration module that owns deserialization, defaults, environment mapping, validation, and redaction. Handlers receive an immutable resolved snapshot; they do not read environment variables or files directly. Generate the effective-configuration view from the same snapshot and use an allowlist for fields that may be serialized.

A determination of **pass** requires that every applicable MUST clause is implemented at the authoritative boundary, that each acceptance check has current reproducible evidence, and that no prohibited condition occurs. A determination of **fail** applies when implementation is absent, behavior contradicts the requirement, evidence is missing or stale, or the result cannot be reproduced. **Not applicable** requires a stated deployment or platform condition and reviewer rationale; it cannot be used to excuse an unimplemented capability that the profile claims to support.

Assessment combines examination, interview where an operational procedure is involved, and test. Examination confirms that the design and source address the boundary. Test confirms observable behavior, including at least one negative or boundary case per limit, failure mode, or security decision. Documentation alone does not establish effectiveness.

## 8. Prohibited conditions

- Any failure criterion in [`acceptance-criteria.md`](../../torviello-engine/specifications/acceptance-criteria.md) section 4 is also prohibited and fatal.


- Do not maintain YAML and TOML descriptions of the same application settings.
- Do not accept unknown keys or silently coerce invalid values.
- Do not echo a secret, token, or credential in a validation error or configuration dump.
- Do not bind a public interface with authentication disabled by default.
- Do not apply a partially validated candidate or leave components on incompatible snapshots.

Additional control prohibitions apply where the mapped clauses state them. A prohibited condition is a failure even if a happy-path scenario passes.

## 9. Verification procedure

- 1. Prepare fixtures for defaults-only, valid file, unknown key, invalid range, malformed environment override, and invalid authentication secret.
- 2. Run the shipping binary with each fixture and capture the exit status, stderr, and whether a listener was created.
- 3. Read the effective-configuration endpoint or the documented startup report and compare each value with the expected source and resolved value.
- 4. Attempt to read a known secret through the effective-configuration endpoint and through logs.
- 5. Repeat with an environment override to confirm precedence and validation parity with file values.
- 6. Record the revision, fixture, command, observed status, and any setting that could not be exercised.

The procedure must be executed through the shipping path. A unit-only substitute does not establish that the public boundary enforces the requirement. Record skipped steps and their reason; a skipped check is not passing evidence.

### 9.1 Highest-standard procedure

In addition to the steps above:

- 9. Generate a precedence truth table for every setting class and compare it with the documented order.
- 10. Run the fuzz corpus and the seeded redaction corpus, then attach both reports and the replay commands.

Each step MUST retain its command, input digests, environment, and observed result. A skipped step is recorded as skipped and does not count toward a pass.

## 10. Required evidence

- The configuration fixtures and the exact startup commands.
- Exit status and setting-specific diagnostics for each invalid case.
- Effective-configuration output showing values and sources with secrets redacted.
- A listener check proving invalid configuration never bound a port.
- The redaction inspection result for logs and error bodies.

Evidence must identify the revision, environment, configuration, fixture, command or inspection, observed result, and any limitation. Evidence that predates a relevant change is stale.

### 10.1 Highest-standard evidence

Retain the following with the evidence bundle described in [assurance-standard.md](../assurance-standard.md):

- A precedence truth table and the reference-model property report.
- The fuzz corpus, 24-hour run log, and the redaction report with zero findings.
- The rejected-configuration matrix showing setting IDs and exit status.

Evidence MUST record the source revision, build inputs, toolchain, hardware, configuration, model digests, command, observed result, threshold, and limitations. A summary without retained measurements is not evidence.

## 11. Failure conditions

- Unknown keys are accepted or ignored.
- An invalid value reaches runtime and fails later during inference.
- Precedence differs between the documented order and observed behavior.
- A secret appears in output, logs, or an error message.
- The effective configuration reports a default as if it were explicitly configured.

A failure also exists when an approved exception is expired, lacks compensating measures, or is not linked from the affected check.

### 11.1 Highest-standard failure conditions

- HPA-4 assurance evidence is missing, stale, unsigned where required, or below the recorded threshold.

- Precedence depends on iteration order, locale, environment enumeration order, or an undocumented alias.
- A secret, credential, or absolute path appears in diagnostics or effective-configuration output.
